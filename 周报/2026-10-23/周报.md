1. **（官方）生产级自改进闭环首次公开架构**：OpenAI《[How we built ChatGPT's novel ad stack for user trust and relevance](https://openai.com/index/building-chatgpt-ad-stack)》，后训练 LLM 当编排器在 agent 循环里调用召回、过滤、打分、拍卖工具；最强、推理最深的模型"观察并评判"整条链路，再用这些反馈训练负责编排和召回的小模型，文中原话是"powerful self-improvement loop"。系统一年前还不存在，现在年化收入超过 10 亿美元。详见下文 OpenAI 小节。
2. **（官方）带治理关卡的自演进 agent 参考架构**：Google《[Architecting Governed, Self-Evolving AI Agents on Google Cloud](https://developers.googleblog.com/architecting-governed-self-evolving-ai-agents-on-gemini-agent-platform/)》（Project Chrysalis），把自我修补、动作归因、规则沉淀、子 agent 拓扑重写分成不同风险等级，各自过沙箱 / 策略 / 签名 / 两人批准。注意是模拟演示数据。详见下文 Google 小节。

### Anthropic

- ⭐ **[Building agents: When to fold subagents into your main agent loop](https://claude.com/resources/articles/building-agents-when-to-fold-subagents-into-your-main-agent-loop)** · claude.com（Applied AI 团队，Claude Platform）· 2026-10-22

**这篇解决什么问题**：大企业做 agent 时常见的走法是每个团队建一个子 agent，平台团队在上面加一个编排器，结果 agent 架构成了组织架构图的翻版（文章直接点名康威定律）。作者团队在多家企业部署中比较过几种设计，这篇讲什么时候该把子 agent 折回主循环、怎么迁、什么时候不该折。

**核心论点与数据**：①多 agent 拆分在大组织里带来五个问题：agent 之间传上下文丢细节、子 agent 泛滥、各团队往系统提示里各加一句形成"拼凑 prompt"、各自优化局部评测、额外延迟；一个客户把多 agent harness 和单循环对比，后者运行快约 2 倍。②"单 agent + skills"在质量上常常胜过"一个大 prompt"和"子 agent"两种设计，成本和延迟更低。③单循环的具体设计：一个模型一个上下文窗口，harness 管轮次、成本预算和写操作关卡；流程性知识放 skill，硬性限制和权限检查放工具；工具按用户意图分组而不是一个 API 一个工具，**超过 30–50 个工具定义后工具选择准确率会下降**，要用 tool search 延迟加载。④迁移方法：先建端到端评测（10 条黄金样例就能起步），按"共享上下文最多"的顺序一次折叠一个子 agent，对比哪些任务结果翻转，每个任务至少跑两次。⑤仍该保留子 agent 的三种情况：可测量的上下文膨胀、需要并行的一次性上下文、工具选择出现冲突；保留时让主 agent 把子 agent 当工具调用。配套开源迁移工具包 [single-agent-loop-kit](https://github.com/anthropics/single-agent-loop-kit)。文中还提到"僵硬的多 agent 结构常常是新模型做不了更多事的原因"。

**对 AI 应用工程师的启示**：面试被问多 agent 设计，先讲"什么时候不拆"，再讲拆的三个条件，最后讲"用评测决定"——这比直接画编排图更像有实战经验。和 OpenAI FDE 一文合读：两家都把"多 agent + 定制工具"迁成"一个强 agent + skill + MCP"，理由都是新模型来了以后结构越简单越容易升级。

- **[LLMs are making formal software verification feasible at a much larger scale](https://www.anthropic.com/research/formal-verification)** · Anthropic Research（Frontier Red Team，与 Theorem 合作）· 2026-10-22

**这篇解决什么问题**：形式化验证能证明某类 bug 不存在，但写规格和证明的成本太高，一直只用于极少数关键系统。这篇演示用 LLM 把它铺到大量开源库上。

**核心做法与数据**：用开发者现成的测试当规格。把 OSS-Fuzz 的 fuzz 入口编译成 RISC-V 二进制，结合 Theorem 的 RISC-V 指令和 Linux 进程形式语义，自动生成"任何 64 MB 以内的输入都不会崩溃（包括 ASan 报错）"这一规格，由 Claude 写证明、Rocq 内核检查。几周内 Claude 先修掉自己发现的 bug，再为 **123 个库的 239 个入口**完成证明，总量约 1.8 亿行 Rocq。证明过程中发现并修复了数百个 fuzzer 很难触发的 bug（例如需要 64 MB 输入加 2 GB 内存才出现的越界读），还重新发现了 libexpat 的一个 CVE。成本：Opus 5.5 在一组小任务上比 Opus 5 少用约 40% token；允许多个 agent 共享证明工作区再省 17%，有的 agent 单独失败、共享后成功。局限写得很清楚：只覆盖单线程、静态链接的 RISC-V/musl 环境，ASan 也不覆盖所有内存安全问题；需要信任的是机器语义模型、定理陈述和证明检查器。

**对 AI 应用工程师的启示**：结构是"已有测试 → 自动变规格 → LLM 生成 → 确定性检查器验收"，这和"用 LLM 生成、用编译器/测试/类型检查兜底"是同一个模式，任何有可靠判定器的 agent 任务都能套。"多个 agent 共享中间产物"能直接省 token，是多 agent 协作少见的有数据的收益。

- **[How Claude designed protein binders against scorpion neurotoxins](https://www.anthropic.com/research/claude-scorpion-toxin-binder-design)** · Anthropic Research（Science）· 2026-10-20

**这篇解决什么问题**：Anthropic 与 Citrini Research 合作，看一群非专家借助 Claude 能不能推进一个真实的健康问题，选定为蝎毒神经毒素设计小型结合蛋白（minibinder）。

**核心数据**：内部研究模型在 Claude Science 环境里基本自主工作 64 小时，人工只追加了 4 次指令；生成 318,484 个设计、挑出 180 个，团队另加 31 个，由 Adaptyv Bio 和 Twist Bioscience 实测全部 211 个，其中 17 个达到结合标准，覆盖 4 种对人危险的毒素。数据分析、出图和报告初稿也由 Claude 完成。文章明确说明尚未验证中和效果、不能称为抗蛇毒血清，211 个设计和数据全部公开。

**对 AI 应用工程师的启示**：长时自主任务的组织方式可以是"一个初始 prompt + 少量人工追加指令 + 外部实测验收"；对外报告时把"验证到哪一步、不主张什么"写清楚，是这类结果可信的前提。

### OpenAI

- ⭐ **[How we built ChatGPT's novel ad stack for user trust and relevance](https://openai.com/index/building-chatgpt-ad-stack)** · OpenAI（Engineering）· 2026-10-21

**这篇解决什么问题**：传统广告系统由"一次搜索 / 一次打开页面"触发一次请求；ChatGPT 的对话没有这样的时刻，用户意图在多轮甚至多次对话里逐步变清楚。OpenAI 从零搭了一套广告栈。

**核心设计**：①**有状态的广告会话**：跨轮次、跨对话记住并更新意图，避免第一句话就误判、过早出广告、每改一次请求就重跑。②**后训练 LLM 当编排器**：在 agent 循环里反复调用工具——把对话改写成一个或多个检索 query（一次旅行规划可以拆成交通、住宿、活动几个意图）、多个 ANN 索引召回、资格过滤（预算、定向、政策、节奏）、相关性 / 参与度 / 历史表现打分；编排器只提名候选，定价和最终选择交给拍卖工具。③**和回答链路完全隔离**：不同服务、不同模型、不共享代码；广告慢了或挂了不影响回答，没赶上当前这一轮就不出，"不出广告是正常的成功结果"。④**漏斗分段日志**：不符合条件 / 会话开始但未检索 / 召回为空 / 未通过资格 / 已投放并有交互，分别记录，各段单独优化。⑤**自改进闭环**：最强的模型观察并评判整条链路的结果，再训练负责编排和召回的小模型；人的反馈（点击、隐藏、调研、广告主反馈）决定方向，"模型能理解意图，但品味由人来定"。一年前还没有这套系统，现在年化收入超过 10 亿美元；文中称 Codex 是从零搭建的倍增器。

**对 AI 应用工程师的启示**：非核心的 agent 功能按"旁路服务 + 超时即放弃 + 空结果也算成功"设计，就不会拖累主链路；LLM 负责理解和提名，确定性组件负责定价和最终决策；用大模型当评判和老师、线上跑小模型，是目前最可落地的自改进结构。面试讲"agent 怎么进延迟敏感的生产系统"，这篇可以整篇当案例。

- **[What FDE means at OpenAI](https://openai.com/index/forward-deployed-engineering-means)** · OpenAI（AI Adoption）· 2026-10-22

**这篇解决什么问题**：OpenAI FDE（Forward Deployed Engineering）团队负责人讲这个岗位做什么、怎么做。团队 2025 年初成立，目标是缩小"部署鸿沟"：模型看起来能做到的事，和人们能可靠拿来工作的东西之间的距离。

**核心论点与数据**：①**先拿结果，再做规模化**：2025 年中约 15 名 FDE 在一家半导体客户做 10 多个验证场景，嵌进客户团队、和工程师一起建评测、为每个场景写定制 harness，3–6 个月全部上线：定向测试生成省时约 48%，内核优化中位性能提升 22%，数周的调试压到数小时。②**把成功变成可复制的**：Codex 变强后，团队把定制应用迁到以 Codex 为核心的公共 harness，定制应用变成 skill 和插件，**删掉每个项目约 90% 的定制代码**；扩到新团队只需换连接器 / MCP、建新评测（建评测也有 skill），一个 2026 年 8 月的案例首次部署两个月、扩到第二个团队一天。架构图从"多个专职 agent + 定制工具"变成"Codex + skills + MCP + 代码仓库"。③**模型做不到时把缺口交给 Research**：一家电信客户的语音客服，关键评测开始只有约 60%，FDE 定义需求、Research 用连续的模型快照改进，六个月到 90% 以上。Thrive Holdings 的 Tax AI 试点处理 7,000 份报税表、吞吐提升约 50%，租赁房产一项花六周才到 90% 精确率和召回率。

**对 AI 应用工程师的启示**：这是官方对"AI 应用工程师 / FDE 到底干什么"最完整的一次描述：嵌入客户、先建评测、为场景写 harness、上线后随模型升级主动删代码。面试可以直接用"先做出结果、再把它变成 skill/插件、最后把模型缺口反馈给研究"这三步讲自己的项目。和 Anthropic 单循环指南一起看，多 agent 定制结构被公共 harness 取代是两家共同的一线经验。

- **[Using thousands of AI agents to uncover new leads in biological data](https://openai.com/index/scaling-ai-research-for-complex-biological-data)** · OpenAI（Publication）· 2026-10-21

**这篇解决什么问题**：OpenAI 与 PerturbAI、Scripps Research 合作，看大规模并行 agent 能不能替代"人工逐个分析 + 文献综述"这种要几个月到一年的工作。

**核心做法与数据**：数千个 GPT-Rosalind agent 分析全脑 CRISPR 图谱，用时 32 分钟。做法叫"分布式生物推理"：每个 agent 只负责一个基因扰动，分析细胞响应、检索文献、提出解释，最后汇总成可公开查询的推理图谱。agent 复现了人工分析的结论，对新颖性的判断与盲评专家一致，还找到 Tsc1/Tsc2 在小脑中的差异等新线索。对照实验固定模型和资源：工作量最大时单 agent 只引用 11 篇文献，分布式 agent 引用 700 多篇，专家也更认可后者。

**对 AI 应用工程师的启示**：大批量分析任务按"最小独立单元"拆给并行 agent 再结构化汇总，比让一个 agent 读完全部数据更可靠；要证明拆分有效，必须做"同模型同资源的单 agent 对照"。注意这和"折叠子 agent"不矛盾：这里的并行单元之间不需要共享上下文，正是 Anthropic 说的"需要并行的一次性上下文"那一类。

- **[Recoverability and Verifier Strength: Two Measured Preconditions for Unattended Agent Self-Improvement](https://arxiv.org/abs/2610.27465)** · De Wang、Peng Qi（Uniphore）· 提交 2026-10-19 · AgenticOS workshop

**问题**：agent 平台开始自己改自己的 agent：读部署 agent 的执行轨迹、推导出一个修改、让自动验证器（常常是 LLM 评审）批准、无人署名就上线。这个循环里哪些步骤可以不要人？

**做法**：定义两个平台可以测的量。**验证器强度 σ**：现有验证器和一个可信参考验证器的一致程度，它决定一步修改最多能带来多少改进。**可恢复性**：一个坏修改能多便宜地撤销——撤销是否需要新的验证器批准，回滚能恢复多少旧行为。规则：两者都达标的步骤才能无人值守。在他们的平台上，这条规则允许 prompt、工具和 skill 的编辑无人值守，权重更新保留人工签字。

**关键数据**：在平台自己的审批关和 τ²-bench 受控实验上验证。①平台的 LLM 评审在 37 个设置中有 9 个**无论看到什么都给同样的分数，而且不报错**——验证器可以看起来很健康却什么都批准，所以强度必须实测，两个简单测试就能抓到这种失效。②**恢复保存的旧副本能回到原行为，而"重新生成一个撤销"做不到**；所以只有保留了旧版本的修改才能不经人工撤销。③一个修改在部署期间改变了 17% 任务的结果（超出正常的运行间波动），这部分损失任何撤销都补不回来。

**对 AI 应用工程师的启示**：
- 这是本期最可直接落地的一篇。做 skill / prompt 自动优化时，**每次修改都要存旧版本（不是"让模型再生成一个回滚"）**，并定期用一组"已知该拒绝的修改"测评审是否还在工作。

### 精读 C · 上下文与 KV cache 的自改进

- **[Cache Engineering for Agents](https://arxiv.org/abs/2610.28577)** · Tianyu Fu 等 9 人（HF 组织 Tsinghua-NICS-EFC）· 提交 2026-10-20 · HF ↑112

**问题**：长轨迹 agent 用裁剪或摘要压上下文，会让后续 KV cache 失效、必须重新 prefill，成本和延迟都上去。

**做法**：让 agent 直接操作 KV cache：drop（让选中的 cache 不再参与注意力）和 repos（调整保留 key 的位置编码），配套 AKV 服务引擎，对外保持无状态接口。再对 cache 策略本身做递归自改进。

**关键数据**：工具返回结果滚动 drop 的策略比阈值触发摘要平均高 1.7 分、成本低 27.7%，吞吐最高 1.2 倍；对 cache 策略做递归自改进，又比专家设计省 7.1%。

**对 AI 应用工程师的启示**：长轨迹 agent 优先丢弃旧的工具返回结果，而不是改写前缀，才能保住 prefix cache 命中率——这和 Anthropic"prompt caching is everything"一致。同期 Microsoft M365 生产轨迹研究（见简版）显示 cache 驻留在机群规模上是真实瓶颈，两篇可以一起讲"上下文工程的成本面"。

## 趋势观察

**1. 架构层的"删脚手架"：子 agent 正在被 skill 取代。** 本期最重要的信号是两家一线工程团队在同一天给出同一个结论。Anthropic 的单循环指南（单 agent + skills 常胜过子 agent，一个客户快 2 倍，30–50 个工具后选择准确率下降）和 OpenAI FDE 的半导体案例（多 agent 定制应用迁到 Codex + skills + MCP，删掉约 90% 代码，扩展从两个月到一天）互为印证；同周 Agent Skills 标准捐给 Linux 基金会下的 AAIF，Agent4Sci 用三个轻量 skill 把科学爬坡幅度翻倍，MS-Eval 测出子 agent 委派普遍加成本。九月"删 prompt"、十月"删 git"（Scion）之后，现在轮到"删编排层"。面试里讲多 agent，先讲为什么不拆，再讲拆的三个条件。

**2. 自演进的"验收危机"：增益要打折，验收要外置，修改要可回滚。** 本期一周内有六七篇独立工作指向同一处：HDA（54% 是过拟合）、ARC-AGI-3 受控研究（两轮自改进留出集置信区间跨 0）、RSI 证据审计（只有 22% 重跑过完整循环）、Elicitation or Expansion（pass@1 优势在大采样下反转）、SSR（任务越多越差）、Continual Learners（可塑性换稳定性）、Repair-Generalization Gap。对应的解法也一致：Uniphore 的"保留旧版本 + 实测验证器强度"、VisualEvolve 的"快照 + 独立验证集选版本"、Compile Once 的"继承旧版本修补胜过重写"（8/8）、OpenAI 广告栈的"最强模型当评判、人定方向"、Google Chrysalis 的分级审批。上期是"涨的分保不保得住"，本期答案已经具体到工程规则。

**3. 自演进的安全面：改进者本身是攻击面。** Scale AI 的 RSI Control（模型训练继任者时可做监控抓不到的隐蔽破坏）、RedDarwin（攻击 skill 自进化把成功率从 18.8% 推到 47.3%）、Model-as-a-Trojan（后门写进权重）、Compaction Laundering（压缩上下文时来源被洗掉）、Privilege Escalation（auto-approve 规则 81% 被滥用）放在一起看：自动化程度越高，"谁有权改什么"越需要在代码层而不是 prompt 层保证。这和 Anthropic 10-12 自复制报告、NVIDIA Sentry"监控放在 agent 够不着的地方"是同一条线。

**4. 记忆研究集体回调：简单检索往往更好。** Naive RAG、MemoryTax、MemDerive、MemDev-Bench、Why Bother Me Again 五篇独立得出"复杂记忆系统常常输给原始历史 / BM25 / 强模型自己搜"。另一侧是记忆安全与治理（凭据串户 84.7%、删除后三分之二可恢复、跨会话隐私推断）。实际工程建议：先上原始历史 + 检索的基线，记忆系统必须证明在你的任务上赢过它；记忆条目要带所有者和来源。

**5. 官方长文的"生产 agent 运行手册"继续加厚。** OpenAI 广告栈（旁路服务 + 超时放弃 + 漏斗分段日志）、xAI IncidentSweep（批准后范围冻结、失败即停）、Google 非阻塞语音工具（首句 14.4 秒 → 1.2 秒）、NVIDIA Sentry（带外策略执行）、Anthropic 形式化验证（测试即规格）。它们共享一条原则：LLM 负责理解和提名，确定性组件负责最终执行和验收。
