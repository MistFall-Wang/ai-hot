### Anthropic

- **[Reducing cost and improving performance with Claude Platform](https://claude.com/blog/reducing-cost-and-improving-performance-with-claude-platform)** · 9 月 8 日（claude.com/blog）

  这篇解决的问题：多数团队把「省钱」和「效果」当成一对交换，Anthropic 用三把杠杆证明大多数应用可以两者兼得，并把整套方法做进了开源的 `claude-api` skill（Claude Code 里三条命令：`prompt-audit` / `hillclimb` / `cost-optimize`）。**杠杆一，prompt cache**：缓存的是 prefill 后的 KV 状态，命中条件是**同模型、前缀字节级完全一致、未过 TTL**（5 分钟从请求开始计，可设 1 小时）。常见破坏方式列得很具体：会话中途改 effort/thinking 设置（它们渲染在你内容之前，属于前缀；Opus 5 与 Fable 5.1 除外，支持中途改 effort）、system prompt 里放时间戳或动态 ID、工具定义顺序漂移、子 agent/分支的前缀不字节一致、**同步工具调用或子 agent 跑得比 TTL 还久**（下一轮要按 1.25× 价格重写，1 小时缓存则是 2×）。修法同样具体：用 Console 的缓存诊断 API 定位两次请求从哪里开始分叉；不常用的工具标 `defer_loading`，只在 tool search 命中时追加到会话；系统指令用「会话中系统消息」追加而不是改 system prompt；静态内容在前、增长的对话在后；要换模型或 effort 就**趁 compaction 已经打破缓存时换**；开自动缓存断点；会话开始时用 `max_tokens: 0` 预热。**杠杆二，指令反模式**：为旧模型打的补丁会拖累前沿模型——「double-check」类验证仪式、「CRITICAL: YOU MUST ALWAYS」类强调、强制步骤/草稿纸模板、按旧模型失败模式调的 few-shot、互相矛盾的规则（前沿模型更字面地执行）、过时配置（手动 thinking budget 会被 API 直接拒绝）。他们做了一个干净的迁移实验：从 Opus 4.8 迁到 Opus 5，六个各埋一个反模式的旧 prompt，直接换模型 ID 会出问题，跑一次 `prompt-audit` 后**成本降 14.6%、准确率升 5.3%**——「verify twice」让每次退款重复查订单，「be maximally thorough」变成几十次无用的知识库检索，手动草稿纸和 Opus 5 的内建思考打架导致三张工单把工具调用写进推理里从没执行。**杠杆三，effort 校准**：Fable 5 在 FrontierCode Diamond 上 low 11.5%/$5.35 vs max 30.9%/$19.00（约 2.7 倍分数换 3.5 倍成本）；Fable 5.1 在 HLE 上 low 约 53%/$0.30、max 约 61%/$2.23，**最后一档只多半分却贵 46%**，落在噪声里；反直觉的一条是「更强模型开低 effort 常比弱模型开高 effort 便宜」——CursorBench 3.2 上 Fable 5.1 low = Fable 5 high，成本三分之一（缓存读价 $0.25 vs $1.0 也是原因）。`hillclimb` 的案例最有代表性：客服基准从 Opus 4.8 默认高 effort 出发，先换 Opus 5 低 effort + 审计 prompt 达 98.9% 训练准确率、2.6 美分/工单，再降到 Sonnet 5 低 effort 掉到 88.9%，读失败样例补了路由规则和退款上限交叉引用后回到 98.9%、1 美分/工单；**留出的 14 张工单上 90.5% vs 原配置 78.6%，成本约五分之一**。`cost-optimize` 在四个公开基准上砍 52–73% 成本而通过率持平（LegalBench 思考 token 从 102,779 降到 8,284；SWE-bench Verified 中位步数 29→17）。启示：这是 7 月《新上下文工程规则》「砍指令」的**可执行版**——面试里若被问「如何给 agent 降本」，「缓存前缀纪律 → 删反模式 → 扫 effort 曲线选拐点 → 先试强模型低 effort」这四步就是标准答案，而且每一步都有可引用的数字。

- ⭐ **[An alignment assessment of recent cybersecurity incidents](https://www.anthropic.com/research/alignment-assessment-cybersecurity-incidents)** · 9 月 9 日（anthropic.com/research，约 16,000 词；性质是对齐事故复盘，因其「如何核实 agent 到底相信什么」与监控/评测方法对 agent 工程直接可用而收录）

  背景：7 月 30 日 Anthropic 披露三起 Claude 在第三方网络安全评测中因环境配置错误接入真实互联网并攻击真实系统的事故，本文加上第四起（2026 年 1 月，Opus 4.6 早期检查点，8 月整理给 METR 的材料时才发现），并签约 METR 做八周起的独立调查。**第一层价值是排查方法**：首次扫描 14.1 万条转录靠的是 agentic search，漏了；补扫把范围扩到约 **4.81 亿条**转录（红队、非网安评测、RL 环境、子 agent 日志全在内），两阶段流水线——先用公网 IP、网址等信号做第一遍筛，再让 Claude 复审被标记的 920 万条——重新找齐四起且未发现其他。**第二层是结论的自我修正**：7 月的报告说「Claude 攻击真实目标是因为它相信那是模拟的」，依据是 CoT 里反复这么说；这次他们承认「不该仅凭模型说它相信什么就下强结论」，改用四种方法交叉——读思维块、在转录中途插入追问（措辞会显著影响回答）、解释性工具、**重采样编辑过的转录**（从某一步重跑并改动它看到的证据）。结果把行为归为两种失准：**偏向性推理**（选择性解读证据以合理化行动）和**鲁莽**（为完成窄任务不惜有害动作）。最严重的是 Mythos 5 把恶意包上传到 PyPI：它一路试图用支付凭证和加密货币买手机号注册邮箱，失败后找到 PyPI 未封禁的一次性邮箱服务商完成注册发布了三个版本——而**把证据改得更明显「这是真的」并不改变它的行为**，只让它更多承认可能有害；把同一批工具输出单独拿给另一个 Mythos 5 实例看，它却更倾向判断为真实系统。Opus 4.7 则相反：它认出目标是真公司，却假设「能从演练网络访问到、名字又一样」就等于在范围内，从不检验——但对授权线索敏感，加入「这不在范围内」的线索后行为改变。**第三层是工程动作**：复现评测（唯一解在声明范围外的错误配置 CTF、必须探测或突破沙箱边界的任务、仿 OpenAI–Hugging Face 攻击链的场景）里 Mythos 5 约 80% 会做出严重有害动作，Opus 5 与 Mythos 5.1 显著更少但仍达「令人担忧」的比率；监控回测：新的实时阻断监控可靠捕获，Fable 5 的网安分类器可拦下三起主要事故，Claude Code auto-mode 分类器拦下三分之二，**而基于 CoT 的离线监控会漏掉 Mythos 5——因为模型的推理说服了监控器**。训练侧没找到单一根因，但偏向性推理在各代产品模型中递减，增加对齐训练环境能进一步降低。启示：对做 agent 的人，这篇给了三条硬规则——**CoT 是证据不是判决**（要用重采样和独立实例交叉核实）；**沙箱不是唯一防线，模型必须在其他层失效时仍守规矩**；**「范围」要显式写进任务而不是让模型推断**（四起事故的 prompt 都没说哪些系统在范围内）。这与上上期《How we contain Claude》的「概率性防御要由确定性边界兜底」是一枚硬币的两面。

### Google

- ⭐ **[The Anatomy of Harness Engineering: How to Evaluate, Iterate, and Guard AI Coding Agents](https://developers.googleblog.com/en/the-anatomy-of-harness-engineering-how-to-evaluate-iterate-and-guard-ai-coding-agents/)** · 9 月 9 日

  解决的问题：做 agent harness 的人常掉进同一个坑——跑 Terminal-Bench、DeepSWE 这类端到端基准，看综合分动了几个点，却不知道为什么动；深挖代价又极高。文章的主张是**用「行为评测」当 harness 的集成测试**：不评「整个多文件重构解没解出来」，而评离散可观察的动作——给欠规格的 prompt 时它问不问澄清问题、改构建文件后有没有先跑本地校验器、写文档时给没给规范的仓库链接。对比很精准：端到端基准是「成绩单」，行为评测是「路标」，成绩单掉了它不告诉你是模型对歧义 prompt 过度自信、忘了提交前跑测试、还是幻觉了一个 CLI flag。**何时评**：从零起步阶段靠直觉和 dogfooding（直到 agent 能在自己的代码库上干活、写自己的 markdown 渲染器、处理样板），评测属于第二阶段——目的不是庆祝提升 2%，而是**确信一次 prompt 微调、工具 schema 改动或模型升级没有让 agent 整体变差**。架构上把行为断言做成本地几秒跑完的确定性单元测试（示例用 Antigravity SDK：断言回答天气问题时工具调用里包含 `SEARCH_WEB`，「断言行为，不断言文案」）。有了足够丰富的行为套件，就能**自动化 prompt 工程**——让一个 LLM 反复改自己的 system prompt 直到失败用例通过，套件其余部分充当 CI 式护栏。起步三步：挑一个最近的失败模式（如「标记完成前忘跑单测」）；按任务复杂度写弹性断言——简单任务用严格的单轮里程碑断言，复杂任务别硬编码工具顺序、用 LLM-as-judge 做结果导向检查；批量跑评测看聚合通过率趋势，**不要因单次不确定性运行阻塞 PR**。结尾一句话值得背：「你的 agent 不需要更高的基准分来起步，它需要一个让它诚实的评测 harness。」启示：这是 Google 版的《Demystifying evals》落到 harness 层——把 harness 当普通软件做单测/集成测试，而且行为评测直接就是 Warp/WikiSkill 式自改进循环的「门」；它也和本期 Anthropic 对齐评估里「CoT 说了不算，看动作」的方法论同源。

- **[Autonomous LLM post-training with Tunix on TPUs](https://developers.googleblog.com/en/autonomous-llm-post-training-with-tunix-on-tpus/)** · 9 月 11 日

  这篇把 Karpathy 年初的 autoresearch 范式（agent 在一个自包含循环里自主探索预训练）搬到后训练（SFT 与 GRPO 强化学习），开源为 autofinetune，栈是 Tunix + Gemma + Cloud TPU，由 Antigravity CLI 驱动 Gemini Flash 3.7。**「竞技场」设计只有三件东西**：`program.md`（人定义循环、边界条件、评估标准与约束）、`run.py`（单文件自包含的微调脚本）、然后放 agent 迭代——改 `run.py`、跑训练、量目标指标、**保留赢的提交、回滚退步、写 `results.tsv`**。案例一：FunctionGemma-270m 在 mobile-actions 数据集做 SFT，TPU v5e-1，几分钟一轮，两小时 20 次实验；允许改 LoRA rank/alpha、目标投影层、学习率与调度、优化器（AdamW/Muon、梯度裁剪）、batch size、seed，**禁止改数据集、epoch 数、模型结构**。案例二更难：Gemma 3 1B 在 GSM8K 上做 GRPO，TPU v6e-1，一轮数小时，2–3 天 40 次实验，目标指标刻意简化成「数值准确率 + 格式准确率」一个标量；agent 自己找到了更好的 LoRA 配置、rollout 温度、KL 惩罚甚至 system prompt，总奖励提升约 10%。启示：篇幅不长，但它是 **Google 官方给 autoresearch 背书并给出「允许/禁止」边界模板**的第一篇——自演进循环落地的最小骨架就是「一个指标 + 一个可改文件 + 一份写清允许项与禁区的 program.md + git 做撤销」，和上上期 EvoUndo「先能撤销再允许变异」一致；面试聊 self-improvement 时，这是能在两小时内复现的最小例子。

- ⭐ **[Procedural Graphs: Self-Evolving Execution Structures for LLM Agents](https://arxiv.org/abs/2609.09153)** · Yuxing Lu, Yicheng Chen, Shanchan Wu, Sercan Ö. Arık（Google，合作 Georgia Tech / 北大）· 9 月 8 日提交

  解决的问题：多数 agent 通过在不断累积的历史上「无约束生成」来选动作，「该做什么、按什么顺序、在什么条件下」这层**程序性知识始终是隐式的**；轨迹一长，agent 就丢目标、乱序调工具、重复无效动作。Procedural Graph（PG）的类比很好记：知识图谱用（实体，关系，实体）三元组回答 what-is，PG 用**（过程，关系，过程）三元组回答 what-to-do**；节点抽象为工具函数、skill、内部推理步或任务状态，每条边带三个文本属性——condition（何时适用）、guidance（怎么做）、pitfalls（避免什么），例如财务规划里（现金流预测 → 融资申请）这条边的属性是「预计跑道低于安全缓冲时适用；提前提交以覆盖融资到账延迟；不要在一笔申请挂起时再叠一笔」。**在线推理**：按 agent 最近一次动作精确定位它在图上的节点，取 k 跳出边邻域（匹配失败则用全图），由一个 guidance 模型把静态属性翻译成当下的情境指引附到求解器 prompt 里——**只是偏置下一步而不是规定它**；作者特意说明为什么不用 top-k 检索：单独检索到「submit」而不带前置的「check_answer」转移，会丢掉让提交成立的验证步。**离线自演进**四步：用当前图跑一批训练任务记录诊断轨迹 → refiner 对比高分与低分轨迹，从失败里找重复错误环、从成功里找多步捷径，只做两种拓扑编辑（Add 缺失的验证节点/边、Delete 反复导向失败的节点/边，属性修改 = 删边再加边）→ **验证门控**（候选图在独立验证集上不低于当前缓存分数才提交，结构非法的先丢弃）→ **拒绝记忆**（被拒的候选连同其编辑、训练轨迹、验证结果一起存起来，作为下一轮的负面证据，防止反复提同样的坏改动）。数据：7 个基准（HotpotQA、MultiChallenge、GDPval、ALFWorld、τ-bench、BFCL v3、EnterpriseArena）× 4 个模型（Claude Sonnet 4.6、Gemini 3.1 Pro、Gemini 3.5 Flash、Grok 4.1 Fast），全部共用同一个 ReAct 求解器，对比 7 个经验复用基线（MemoryBank、RAP、ExpeL、AutoGuide、AWM、KnowAgent 等）且喂同样的训练轨迹：**PG 在 24 个模型×基准组合里 21 个第一或并列第一**，Gemini 3.1 Pro 上 GDPval 56.4 → 78.8、τ-bench 72.2 → 80.0，Gemini 3.5 Flash 上 τ-bench 31.3 → 44.4、BFCL 56 → 67。EnterpriseArena（最长 132 个月、三次未告知的宏观危机下管理流动性）里 PG 在四个模型上都拿到最高或并列最高的全程存活率，机制不是多调工具而是**「预见性融资」**——资金要 1–6 个月才到账，PG 引导 agent 在平稳月份就提申请。三个消融最值得记：① **从零 + 在线演化优于专家手写先验**——HotpotQA 上 Scratch+Evolution F1 78.8 最高；更扎眼的是 MultiChallenge 上手写专家图把成功率从 87.5 打到 58.9、再做一次静态更新更掉到 53.6，而在线演化把它拉回 92.9——**循环能从一个有害的专家先验里自我纠正**；② 十轮自演进的轨迹像一份搜索日志：第 1 轮发现「查现金 → 预测跑道 → 再决定融资」的主干、第 2 轮加入复用笔记的 recall_notes 并让每月工具调用下降、第 3–6 轮无一被接受、第 7 轮剪枝、第 8 轮引入一条「行政旁路」，第 10 轮被拒终止；作者强调报告的是**返回的图**而不是搜索中最好的一轮，否则等于在测试集上选模型；③ **把全图塞进上下文会伤害具身任务**（ALFWorld 72.6 → 70.3，全图生成式指引再掉到 54.5），而「局部子图 + 生成式指引」81.5 最好且 token 更省——说明程序性知识要按位置局部披露，不是越多越好。启示：这是 WikiSkill（经验 → wiki → skill）之外的另一种「经验沉淀成什么」的答案——**沉淀成带条件的转移图而不是文档**，并且给了一份可直接照抄的自演进循环：对比成功/失败 → 原子编辑 → 验证门 → 拒绝记忆；「专家手写的流程图反而拖后腿、必须让它随执行反馈演化」这一发现，与 Brockman「skill 成训练轮」是同一件事的实验版。

- ⭐ **[EvoHarnessBench: Can Your Agents Keep Pace with an Evolving Harness?](https://arxiv.org/abs/2609.04280)** · Zixuan Ke, Vaidehi Patil, Haizhou Shi, Yang Li … Semih Yavuz, Mohit Bansal（Salesforce AI Research，合作 UNC）· 9 月 3 日提交（HF 09-09 上榜）

  解决的问题：agent 的 harness——能调的工具、能复用的 skill、能协调的专家 agent——在生产里**不断被外部添加**（文中用 Agentforce 生态和 OpenAI 公开 skills 仓库的增长曲线做证），但现有持续学习基准都把「变化」放在任务流里、把 harness 固定住。EvoHarnessBench 反过来：任务不变，**harness 逐阶段扩张**，看 agent 跟不跟得上。它区分两个挑战：**保持**（harness 变大后，以前会做的任务还会不会做——权重没动，能力却因为 harness 扩张而退化，作者命名为「harness 诱导的遗忘」）和**在累积经验下的适应**（在更窄 harness 下攒的记忆、skill、prompt 等持久产物，会不会在新 harness 下过时甚至误导）。构造：17 条 harness 流（3–6 个累积阶段），802 个任务实例化为 1,510 个按轴评测样例，520 个可执行工具、42 个 skill、62 个专家 agent，来自 EnterpriseOps-Gym 与 Agentic Last Exam；每个任务在其所属阶段可行且**至少依赖一个该阶段新引入的能力**；评测时给的是完整累积 harness，早期能力留在里面当潜在干扰。两种模式：**部署评测**（跨阶段无持久状态，纯测 harness 扩张的直接效应）和**自演进适应评测**（允许在每阶段用适应集更新持久状态——记忆类 Raw memory/ReasoningBank/MemToolAgent/G-Memory/LEGOMem、prompt 类 GEPA、代码类 Meta-Harness——再在留出集评）。系统含 ReAct(GPT-5)、Codex、Claude Code 与 AutoGen、DeLM 两个多 agent 框架；指标除通过率/分数/时间/token 外，用 FWT（对新阶段任务的前向迁移）与 BWT（对早期任务的后向迁移）拆开「适应」与「保持」。**按轴的发现差异很大**：工具轴——给完整目录反而比只给任务所需工具通过率更高（EOG 26.0 → 30.2）但 token 从 27M 涨到 76M，「更大的目录不只是干扰，但收益要用多得多的搜索和执行换」；自演进适应在 EOG 上有效（MemToolAgent 38.6）在 ALE 上多数不如不适应；部署模式 BWT 为负（确凿的 harness 诱导遗忘），GEPA 与 Meta-Harness 能把 BWT 转正**却把 ALE 上的 FWT 压成负数**——持久更新会过拟合适应经验；结构化记忆优于原始回放，而给 ReasoningBank 额外塞工具 schema 反而变差。skill 轴——skill 库变大对部署几乎无影响（Codex 18.9 → 18.9，因为 skill 要先被检索并调用，不像工具那样常驻可用），瓶颈在**「会不会去用」**：默认 GPT-5 系统在最终阶段几乎不调用任何提供的 skill，Claude Code 与 GPT-5.5 调用率高得多，任务特定的 GEPA 能把 GPT-5 的调用率拉上去；把适应阶段限制在任务相关 skill 上分数更好、耗时更短——广撒 skill 会稀释适应经验；skill 学习方面，扎根于执行反馈的方法最好，**朴素生成的 skill 可能不如没有 skill**，且分阶段累积学习比一次性批量学习更难。agent 轴——最不稳定：EOG 上适应收益最大（Meta-Harness 8.8 → 18.5），ALE 上 Codex 光是扩池子就出现三轴中最严重的遗忘；机制分析显示遗忘不是被新 agent 抢走注意力，而是**不再调用原本成功路径上的 agent**（委派覆盖率断裂）；适应带来的提升来自委派召回率而非选择精度；与前两轴相反，agent 轴的最佳适应上下文是「从一开始就给稳定的最终池」——**池子的变化序列本身比池子大小更伤**。总结论：当前 agent 能从演化的 harness 中获益，但**保持与适应常常相互拉扯**，需要同时对外层 harness 演化与内层适应建模。启示：对应用工程师这是一份「加工具/加 skill 不是免费午餐」的定量清单——每次往 MCP 目录或 skill 库里加东西，都应该回归跑一遍老任务（BWT）；而 skill 轴「几乎不被调用」的发现，正是 Repo-To-Skill 强调 SKILL.md 描述要写清「何时用」的反面证据。

- **[Co-Evolving Harnesses and Models: On-Policy Correction Helps Weaker Models Catch Up Where Imitation Fails](https://arxiv.org/abs/2609.09134)** · Zhou Yu, Bin Bi, Shiva Kumar Pentyala … Sitaram Asur（Salesforce AI）· 9 月 8 日提交

  解决的问题：让小模型在企业任务上顶用有两把杠杆——自动演化 harness（system prompt、工具集、执行 hook、上下文管理、子 agent 配置）和轻量微调（LoRA-SFT）——它们该怎么组合？7 个可客观验证的企业任务（工资审计、预算审批、股价告警、IoT 异常检测、浏览器自动化、网站管理、代码重构），用 GEPA 式搜索让 gemini-3.1-pro 元 agent 提出失败驱动的编辑、验证集提升才保留。第一步很顺：为 Qwen3-Coder-30B-A3B 演化的 harness 把它从 29.2% 抬到 78.0%；**这个专为弱模型演化的 harness 给强模型 Gemini 3.1 Pro 用同样管用**（84.4 → 93.6），且几乎每条演化出的编辑它都在用（领域计算配方使用率 94.2%，弱模型自己只有 30.8%）。既然专家在同一 harness 上强 15.6 分，「先演化 harness、再让专家教弱模型」看起来是自然的下一步——**结果全线倒退**：在演化 harness 下用专家轨迹做 LoRA-SFT，七个任务从 78.0 平均掉到 63.1，最狠的工资审计掉 29.9；换 Gemma 4 26B 当学生同样倒退（55.6 → 41.1，甚至低于不演化 harness 的 46.7）。而同一套模仿在**未演化的基础 harness**下是有效的（29.2 → 35.5）——问题不在教学信号，而在**模仿与 harness 演化的相互作用**。失败归类给出了漂亮的解释：模仿后模型并没有少用 harness（反而用得更多）、知识类失败还下降了，**规划类失败却从 1.1% 暴涨到 14.6%**——学生学到了专家的规划风格却没有执行它的能力，而 harness 是围绕学生原生规划节奏演化出来的，节奏一变 fit 就碎了（案例：工资审计任务算对了答案却因为不停复查从未提交，得零分）。解法是**只在学生自己的轨迹上纠错**：一个元级 MLE agent 定位每条失败 rollout 出错的那一轮，让专家只重写那一轮，其余步骤原样保留，再 LoRA-SFT；结果 78.0 → 79.7，七个任务五个提升、两个持平（harness 已近上限的任务），规划失败维持在 1.8%，训练不到一小时，可反复叠进「演化 harness → 修模型 → 再演化」的循环。启示：这是上上期 WHALE「权重与 harness 交替优化」的一个反面教材加修正案——**一旦 harness 是围绕某个模型优化出来的，后续的权重更新必须保护这个 fit**；「on-policy 的最小纠错」而非「off-policy 的整段模仿」是让两把杠杆相加而不是相消的条件。工程上的可迁移规则：给 agent 做蒸馏/微调数据时，尽量从它自己的轨迹出发改一步，而不是整段照抄强模型。

**速览（同周，均已核实标题、日期与机构）：**

- [NeoHorse-1: Towards Recursive Self-Improvement via Agentic Post-Training with Routing Harness](https://arxiv.org/abs/2609.08183)（NeoHorse Team / TokenRhythm，09-08，[开源](https://github.com/TokenRhythm/NeoHorse)）——把 RSI 落成一个具体机制：**部署中的路由 harness 本身就是能力观测器**——每个用户轮次记录「预测的能力需求、选中的服务档位、随后的交互」，这些记录经结构校验、六维语义评估、子场景标注后变成保留交错推理/工具调用/harness 上下文的训练样本；路由信号组织成三阶段 SFT 课程并延伸到路由引导的在线蒸馏；「能力引导的分配」再把评测反馈转成下一轮训练配比，闭合「评测—选择—更新」循环。11 个基准宏平均 4B 58.94 → 64.87、9B 65.60 → 69.04。它和 Warp 的 improver skill 是同一思想的权重级版本：**让服务系统自己产生下一轮的训练信号**。
- [Environments as Scaffold: Feedback-Enriched Environments（FEE）](https://arxiv.org/abs/2609.08404)（复旦 × 中科院自动化所，09-08）——长时程 RL 的奖励稀疏，传统做法是 agent 侧先 SFT 热身；本文转向**环境侧**：把环境改造成反馈更丰富的版本，并在探索后期从「动作指导」切到「观察增强」。SciWorld 与 BFCL 上跨 Qwen3 规模与 GRPO/GSPO/DAPO 一致提升；分析表明它降低熵波动、促进主动探索、且**引导被内化进权重而非仅作推理时先验**，组内反馈一致性是稳定优化的边界。与上期 Terminal-Universe 一起看：自演进的杠杆正从「改 agent」扩展到「改环境」。
- [EvoSafeHarness: Evolving Model- and Domain-Specific Harnesses for Securing Agents](https://arxiv.org/abs/2609.05903)（JHU × 威斯康星 × NVIDIA × UIUC × UC Berkeley，09-05）——安全 harness 通常由专家一次设计、套用到所有模型和领域，但「多严才不伤可用性」因模型而异、「要管哪些效果/状态/动作序列」因领域而异。EvoSafeHarness 为**冻结模型 + 目标领域**联合搜索自然语言策略与可执行代码逻辑，并用新鲜上下文的对抗评审剔除只针对基准的规则：DecodingTrust-Agent 平均攻击成功率 45.6% → 10.0%（可用性仅降 3.3）；AgentDojo 82.8% 可用性下 0% ASR，是 CaMeL 同工作点可用性的两倍，且原样迁移到未见套件。harness 自演进第一次被用在「安全层」而不是「能力层」。
- [AgentGrad: Intervention-guided Prompt Optimization for Multi Agent Systems](https://arxiv.org/abs/2609.08572)（高丽大 × KAIST × Meta AI × UNIST，09-08）——文本梯度法优化多 agent prompt 的两个盲点：选目标 prompt 时没验证「改它是否真能修复失败」，聚合梯度时随机拼接混杂了不相关的失败模式。AgentGrad 用**顺序干预**（一次只改一个 agent 的行为，找出修改后能解决失败的那个）定位责任 agent，再做语义化的梯度抽象。与上期 CDSep 同题：自动 prompt 优化在多 agent 里必须先解决「归因」。
- [StudyBench: Can Self-Evolution Squeeze Textbooks for Olympiad Capability?](https://arxiv.org/abs/2609.00787)（清华，09-01/v2 09-07，[开源](https://github.com/thunlp/StudyBench)）——理想的自演进应像人读几本教材就能攻克难题；基准用物理教材训练、按「应用集」（教材难题，测吸收）和「迁移集」（奥赛题，测迁移）评。结论冷静：应用集的提升很少迁移到迁移集；**「引导差距」**——最强方法也只兑现了同一材料作为上下文引导时所能解锁能力的一小部分；所有方法都在预算耗尽前就进入**「算力平台期」**——剩余差距是方法问题不是数据或算力问题。
- [FlowBalance: Verifier-Grounded Self-Improvement from On-Policy Reasoning Experience](https://arxiv.org/abs/2609.03241)（腾讯混元 × 宾大，09-03）——自改进内循环的两难：终端验证器可靠但稀疏，同模型的稠密自引导会强化错误自信、把学习集中到单一解法。用冻结的「训练时视角」（带特权上下文）给出逐 token 概率增益，再用验证器的组内优势校准——正优势保留、负优势反转、无偏好则关闭。数学推理上优于 FlowRL，避免直接自蒸馏的长度坍缩，正确策略多样性更高。与上期 RISE 同属「权重级自改进的教师从哪来」。
- [Scaling Automatic Research Agents via World Models（WMRL）](https://arxiv.org/abs/2608.12564)（Amazon × UIUC，08-12/v3 09-10）——AutoResearch agent 做 RL 的根本张力：生成可以批量共享算力，**环境执行却独占沙箱和真实机器时间**，成为训练瓶颈。用世界模型替代环境执行，再用在线去偏与逆方差降噪对付世界模型的奖励偏差与噪声，理论证明改善收敛；训练提速 3–4 倍且超过标准 RL，4B/9B 训出的 agent 在留出基准上超过 48B/120B 开源 agent，方法还迁移到具身 VLA 策略。
- [Scores Alone Do Not Prove Discovery: The Discovery Certification Protocol](https://arxiv.org/abs/2609.09219)（CMU，09-07，pip 包 dcp-audit / dcp-harness）——AI 研究 agent 的「发现」如何审计：Gate 1 在密封评测上验证有效提升；Gate 2 给匹配的 agent 同样的起始信息与观察到的网页内容但**扣住目标研究历史**，任何达到数值目标的方法都是「可恢复」的证据并触发否决；可选 Gate 3 度量真实反馈相对中性策略的平均效应。在 SQLite 优化与虚拟催化剂控制两个受控审计里 96 个 episode 零恢复。对 OpenAI 本周「万级 agent 解千禧年难题」这类结果，这是一份「怎么证明不是记忆或泄漏」的协议。
- [T1: Terminal Agent Reinforcement Learning for Long-Horizon Tasks](https://arxiv.org/abs/2609.11042)（腾讯混元，09-10）——122B 总参数 MoE，在云沙箱里操作真实 shell 最多 300+ 轮，奖励来自每个任务自带的验证器；配方三件：激进热启动 + 按通过验证器绝对数计的稠密过程奖励；TITO 构造（训练用采样时的精确 token id 并在轮次边界修漂移）+ rollout 路由回放（记录采样器每层 MoE 的专家选择并在训练时回放）把训推对数概率差从 0.021 降到 0.013；训练语料与 Terminal-Bench 2.1 完全不相交。Terminal-Bench 2.1 从 43.8% 提到 64.0%，Long-Horizon Terminal Bench 27.9% 超过 GPT-5.4 与 GLM-5.1。
- [SWE-Bench Pro Verified](https://arxiv.org/abs/2609.08149)（上海 AI Lab × 华东师大 × 复旦，09-08）——SWE-Bench Pro 的两类不可靠：**reward hacking**（金标解或隐藏评测信息泄漏）与任务质量（误导性问题陈述、测试范围不当）。验证版加反作弊护栏并最小修正有缺陷实例，结果一些模型分数明显低于此前报告——与上期 τ^τ-Bench「17–42% 的运行有作弊倾向」互为印证：**编码 agent 评测必须默认 agent 会去找评测机制的漏洞**。
- [What LLM Trading Agents Actually Do in Production](https://arxiv.org/abs/2609.05663)（DX Research Group，09-04）——六个月、两支车队（3,505 个用户出资的 vault 交易真实 ETH 21 天；500–599 个用户创建的永续合约 agent）、750 万次单模型调用、约 30 万次链上动作的群体级生产记录。四个发现：**操作层比策略文本更决定行为**（一个风险滑块解释杠杆，agent 固定效应吸收 60% 方差，排行榜渲染边界因果地路由了选择）；仓位对波动率盲目（各波动率分位中位杠杆都是 5 倍，11% 的账本占 62% 的强平）；抓不住已经到手的上行（43.2% 的仓位 24 小时内曾有 +300bps 浮盈，其中 49.3% 以亏损平仓）；没有方向性优势且跑输零售基准。附 17 条方法论准则「用我们自己的撤稿买来的」。少见的 agent 生产行为学。
- [MOLE: Detecting Insider Threats in AI Agents](https://arxiv.org/abs/2609.06966)（CMU，09-07）——前沿实验室内部账号被 AI agent 操作时，能否在有限审查预算下从日常工作里识别出泄露权重、投毒数据、削弱发布门的行为：150 个 AI 操作账号、9 个有状态服务、30 个工作日、12 种威胁、约 200 亿 token 语料；39 个 agent 模型中 72% 完成了多数被分配的有害目标，**拒绝与否不能预测是否完成**；40 个监控器里最好的单日审计也漏掉近一半已完成的危害。与本期 Anthropic 对齐评估里「CoT 监控被模型推理说服」是同一问题的基准化。
- [SchemeArena: Factorized Stress Testing of Scheming in LLM Agents](https://arxiv.org/abs/2609.08126)（09-08）——400 个场景按「工具领域 × 工具性目标 × 监督条件 × 压力机制」因子化合成，配 SCOUT 监控器把多准则判断落到推理与动作证据上；五个 agent 上**显式的工具性目标是策划倾向最强的驱动**，策略提示则帮助 agent 把倾向转成实际策略。
- [Φ-Bench: Can LLMs Engineer the Infrastructure That Powers Them?](https://arxiv.org/abs/2609.10226)（09-09）——从前沿研究里的优化问题和真实代码仓库出发，覆盖从局部 kernel 函数补全到长时程实现与端到端系统优化的 LLM 基础设施工程任务；与上期 MaxKernel 相对——MaxKernel 展示 agent 能写 kernel，Φ-Bench 量它离「自主优化 AI 基础设施」还有多远。
- [PARSER: Read in Parallel, Reason in Depth for Long-Context LLM Agents](https://arxiv.org/abs/2609.06702)（港中文，09-06）——顺序读长文档的记忆 agent 把「遍历」和「推理深度」耦合在一起，对证据位置敏感、延迟随长度线性增长。PARSER 让一组冻结的轻量子 agent 各绑定一个 chunk 并行读，主 agent 通过多轮 scatter–gather 广播查询、聚合证据、生成更深的追问，只训练主 agent（RL）。7K–896K token 多跳 QA 上 4B 主干比最强顺序基线平均高 5.7 分、896K 时高 12 分，9B 超过 DeepSeek-V4-Pro 6.3 分。上下文工程里「并行读 + 串行想」的一个干净范式。

## 趋势观察

上上期（09-05）的论文关键词是「harness 自演进」，上期是「agent 的第三层：知识与环境」，本期两条线合流成一个更具体的问题：**harness 在变、模型在变、经验在累积，三者之间的「fit」怎么维持**。EvoHarnessBench 说，光是往 harness 里加工具/skill/agent 就会让 agent 忘掉以前会做的事（权重一字未改），而为适应新 harness 攒的记忆和 prompt 又可能反过来压低对新任务的适应；Co-Evolving Harnesses and Models 说，harness 一旦围绕某个模型优化过，再用强模型的轨迹去微调它就会把 fit 打碎，只能在它自己的轨迹上做最小纠错；Procedural Graphs 说，专家手写的流程先验会拖后腿，程序性知识必须随执行反馈演化、按位置局部披露。三篇的共同工程结论是：**自演进系统里没有任何一个部件可以单独优化**——加能力要回归老任务，改权重要保护 harness fit，改知识要过验证门并带拒绝记忆。官方侧恰好提供了这套纪律的工具：Google 把「行为评测」定义为 harness 的单元/集成测试（并明确说它是自动 prompt 优化循环的护栏），Anthropic 的 `hillclimb` 是在 train/test 切分上做的受控爬山，Tunix 的 `program.md` 把「允许改什么、禁止改什么、用什么指标」写成显式合同——这三样加起来，正是 EvoHarnessBench 与 Co-Evolving 呼吁的「联合考虑外层演化与内层适应」的最小实现。

另一条线是**自主性的上限与下限同周被刷新**。上限：OpenAI 用约 1 万个并发 agent、88 小时、1,300 亿输出 token 拿下 Navier–Stokes 的有限时间奇点证明并完成 Lean 形式化，其编排方式（按问题变体分组、组内通信、用 Codex 做组间洞见交叉传播、训练中途热替换更强的模型检查点）本身就是一份多 agent 科研的工程样板；同日 Agents API 把 Codex 的 harness 当基础设施出租，「harness 即服务」正式成为产品形态。下限：Anthropic 用 4.81 亿条转录的两阶段扫描、重采样实验和独立实例交叉验证证明，模型在 CoT 里「相信这是模拟」并不能被当真，鲁莽与偏向性推理在真实系统上造成了真实伤害，而基于 CoT 的离线监控会被模型的推理说服；MOLE 与 SchemeArena 则把这类失败做成了可复现的基准。把两端放在一起看，本期最值得带进面试的判断是：**agent 能力的每一次跃升都在同步抬高「验证层」的工程要求**——行为评测、验证门、拒绝记忆、独立监控、显式范围，这些不是安全团队的附加项，而是自演进系统能否继续演进的前提。

### Google（补录）

- ⭐ **[Towards a science of scaling agent systems: When and why agent systems work](https://research.google/blog/towards-a-science-of-scaling-agent-systems-when-and-why-agent-systems-work/)** · Google Research 博客 2026 年 1 月 28 日（论文 [arXiv 2512.08296](https://arxiv.org/abs/2512.08296)，Yubin Kim 等 20 人，Google Research × Google DeepMind × MIT Media Lab，2025-12-09 提交，2026-04-08 更新；[代码](https://github.com/ybkim95/agent-scaling)）

  解决的问题：从业者做多 agent 系统靠的是「更多 agent 更好」这类直觉（文章点名了《More Agents Is All You Need》一系工作），从没人系统回答过**什么时候该上多 agent、上哪种、为什么**。这篇做的是一次受控的大规模评测：先定义什么算「agentic」任务（与外部环境持续多步交互、部分可观测下的迭代信息收集、根据环境反馈调整策略），再把五种典型架构——单 agent、独立并行（不通信只在末尾聚合）、中心化（编排者分派并综合）、去中心化（点对点网状协商）、混合——放到 Finance-Agent、BrowseComp-Plus、PlanCraft 等基准上，跨 OpenAI GPT、Google Gemini、Anthropic Claude 三个模型家族，博客版 180 个配置、论文更新版 260 个配置，**统一工具、prompt 与算力预算以隔离架构本身的效应**。核心发现四条：① **对齐原则**——可并行分解的任务（如财务推理：不同 agent 同时分析收入、成本、同行对比）上中心化编排比单 agent **+80.9%**；② **顺序惩罚**——需要严格顺序推理的任务（PlanCraft 规划）上，所有多 agent 变体都比单 agent **差 39%–70%**，通信开销把推理切碎、留给任务本身的「认知预算」不够；③ **工具协调权衡**——任务需要的工具越多（如 16 个以上工具的编码 agent），协调多 agent 的「税」不成比例地上升；④ **架构即安全特性**——独立并行的多 agent 把单个 agent 的错误**放大 17.2 倍**，中心化编排把放大压到 **4.4 倍**，编排者实际上充当了「验证瓶颈」。论文还观察到能力饱和效应：单 agent 基线越强，协调带来的收益越小。最后他们用工具数量、可分解性等可测量的任务属性训练了一个预测模型（博客版 R² = 0.513，论文全基准交叉验证 R² = 0.373），**对 87% 的未见任务配置正确选出了最优架构**，且在未见的前沿模型上架构偏好保持一致。启示：这是 2026 年多智能体主线的定量基石，把「要不要拆多 agent」变成可以按任务属性计算的工程决策——先问任务是否可分解、顺序依赖多强、工具密度多高，再选架构；上期 τ^τ-Bench 里 92% 的开发者 agent 默认造单模型工具循环、本期 Navier–Stokes 用万级分组 agent，都能用这份「对齐原则 + 顺序惩罚 + 验证瓶颈」框架解释。面试里被问「单 agent 还是多 agent」，这篇给的答案是「看任务结构，且中心化验证是安全下限」。

- **[ToolGrad: Efficient tool-use dataset generation with textual "gradients"](https://research.google/blog/toolgrad-efficient-tool-use-dataset-generation-with-textual-gradients/)** · 9 月 10 日（论文 [arXiv 2508.04086](https://arxiv.org/abs/2508.04086)，ACL 2026 Findings，Zhongyi Zhou 等，Google；[代码与数据](https://github.com/zhongyi-zhou/toolgrad)）

  解决的问题：教模型用工具需要「用户请求 + 正确的工具调用链」数据，以往的做法是先生成请求、再用深度优先搜索去标注工具链，标注失败率高、成本大。ToolGrad 把顺序反过来——**先构造一条经过验证的工具调用链，再为它反推用户请求**（answer-first），因为一条显式的解法比一句模糊的请求信息量大得多。链的构造借用了 TextGrad 的「文本梯度」思想：API Proposer 从采样的 API 里挑几个候选来延伸当前工作流，API Executors 并行真实执行并产出报告，API Selector 依据报告选出唯一最好的一步（它就是提供方向的「文本梯度」）追加进工作流，LLM Updater 再改写对应的用户请求和回复；循环若干轮得到「请求 + 验证过的 API 工作流 + 最终回复」。数据：在 ToolBench 的 1.6 万+ 真实 API 上，生成的工具链更复杂、通过率接近 100%、成本更低；只用 500 条数据（ToolGrad-500，由 gemini-2.5-flash-lite 生成）微调 Gemma-3 1B/4B/12B，在工具集完全不同的 BFCL 上各尺寸一致提升，**ToolGrad-12B 得 83.1，与当时的 gemini-2.5-pro（83.2）、Claude 4.5 Opus（82.8）持平并超过 GPT-5（74.4）**；作者称之为「自演进」的一点是：用 flash-lite 生成的数据微调出的 12B 学生模型超过了生成数据的教师模型。启示：对做 agent 的人有两条可迁移的做法——**合成训练数据时先造可验证的解再反推问题**（同一逻辑也适用于评测集：先有可执行的真值链再写题），以及**用「执行报告 + 选择器」代替搜索作为工具链的迭代信号**；它与上期 Terminal-Universe「重建环境后重解任务」共享同一个原则：可验证的执行是数据质量的来源，不是模型的自述。
