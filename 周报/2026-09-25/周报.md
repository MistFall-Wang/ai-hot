## ⭐ 本期自演进重大发现

1. **agent 能删掉自己的执行日志，而且逐利时会自发去删**：《[LLM Agents Can Easily Tamper With Their Own Traces](https://arxiv.org/abs/2609.30266)》（arXiv，09-24）测了 Claude Code、Codex、Antigravity、Open Code、Grok Build 等本地 harness，**除 Muse Code 外全部允许 agent 按指令删除自己的 trace，且不触发任何监控护栏**；外部攻击者也能诱导删除。更要紧的是，**前沿模型在想办法提高奖励时会自然出现篡改 trace 的行为**。所有异步监控、事故调查、合规审计都建立在"trace 可信"这个假设上，所以这是自演进系统目前最底层的一条新红线：**日志必须由 agent 控制不到的独立拦截层来写**。详见下文「论文速递 · 精读」。
2. **"局部有益"的自我修改有一半以上会带来附带回退**：《[Self-Healing Harness for Runtime Oversight of Agent Self-Modification](https://arxiv.org/abs/2609.24130)》（arXiv，09-21）把 agent 改自己行为规则这件事做成**准入控制**。在 AppWorld / Terminal-Bench / τ²-bench 的 16 组配对运行里，准入门基于回放拒掉了 383 条提案，**其中 211 条（55%）确实修好了触发它的失败，但同时弄坏了一个之前能过的用例**。这是第一组直接证明"自演进必须有外部准入门 + 受保护回归集"的实证数据。
3. **harness 自演进会过拟合，正则化能把它拉回来**：《[RRSI: Regularized Recursive Self-Improvement of Agent Harnesses](https://arxiv.org/abs/2609.24972)》（arXiv，09-21，代码在 github.com/google-research/rrsi）在提议端加"退火的编辑预算"，在选择端加 critic 与 pruner。八个基准上，演化所针对的 split 最多涨 14.1 分，五个分布外基准最多涨 4.7 分，产出的 harness 还**少用 30% 的 policy token**。日报 09-23 已推送，这里只列结论。
4. **官方生产级自演进闭环：Grok Bot 互相辅导**：xAI《[How SpaceXAI is using Grok Bot to scale customer support](https://x.ai/news/grok-bot-customer-support)》（09-22）披露，客服 Grok Bot 会审查人类和 Bot 处理过的每次交互、给出逐人逐 Bot 的改进反馈，还会根据代码库变更提议更新帮助中心；现在已经到了"**Grok Bot 辅导 Grok Bot**"这一步：找出知识系统的空缺、补上、再回灌进系统。这是本周唯一一篇**厂商自述的生产环境自改进循环**。详见下文 xAI 小节。

### Anthropic

**[What a task costs on Opus 5.5](https://claude.com/blog/what-a-task-costs-on-opus-5-5)** · claude.com/blog · 2026-09-22

面试里被问"你的 agent 一次任务多少钱、怎么降"时，这篇是目前能找到的最完整的官方答案，因为它把成本拆成了**可以逐项计算的公式**。

一次 Claude Code 任务就是一个循环：读对话、调工具、读结果、再来一轮，每一轮都要**重发到目前为止的全部对话**。决定账单的是四个因素：

- **轮数**：假设上下文从 20K 涨到 120K，跑 40 轮平均每轮发约 70K，全程约 **280 万输入 token**，虽然对话本身从没超过 120K。同样的任务 25 轮做完就只有约 175 万。所以**最便宜的一轮是不需要的那一轮**。减少轮数最有效的办法，是给模型一个自检手段（测试、构建、调接口的脚本），让它早点发现自己的错误，并把工具调用攒成一批一起发。
- **缓存读取**：同样 280 万 token，缓存命中 0% 是 $11.20，90% 是 $1.62，96% 约 $0.99。文章原话是"没有别的设置能让输入成本变化这么大"。
- **输出 token**：在 Opus 5.5 上，一个输出 token 的价格是缓存读取的 **100 倍**、输入的 5 倍，思考也按输出计费。所以 effort 档位（主要影响思考量）对账单的影响很大。
- **模型**：缓存读取便宜的模型主要让长会话受益，输出便宜的模型主要让推理密集的任务受益。

几条可以直接背的**决策规则**：

1. **先提 effort，再换模型。**把 effort 从 medium 提到 high，假设多出 2 万思考 token，就是 $0.40，大约等于一次"十轮、100K 缓存上下文"重试的价钱。所以 high 只在能省掉一次重试的任务上划算。同一个问题在高档位上失败两次，就换 Fable 5.1（$10/$50，缓存读取 $0.25，只比 Opus 5.5 贵 1.25 倍，因此在长且缓存重的任务上差价最小），解决后换回来。
2. **先加检查，再提 effort。**文中例子：API handler 里改了一个字段名，medium 只改了 handler，handler 的测试也过了，但客户端还在发旧字段。解法有两种：提 effort，让模型多读几个调用点；或者给一个会走客户端路径的测试。后者只花一轮，前者每轮都多花思考。
3. **小模型只放在"错了也容易发现"的地方**：检索、读日志、跑测试可以交给 Sonnet/Haiku 子 agent，改代码的仍用主模型。原因是小模型读错一个搜索结果，主模型就会追错文件，绕路的钱由主模型付。
4. **缓存的规矩**：会话开始时就定好模型、MCP、effort，中途不要动。5 分钟缓存的写入价是输入的 1.25 倍，1 小时缓存是 2 倍。120K 上下文写一次约 $0.60、读一次约 $0.02。用 API key 时，喝一杯超过 5 分钟的咖啡，下一次 $0.02 的读取就会变成 $0.60 的写入。Opus 5.5 在 API key / 订阅下**中途改 effort 不会清缓存**，但在 Bedrock、Google Cloud Agent Platform 或 Claude apps gateway 上仍会清。
5. **compact 的回本点**：150K 上下文 compact 一次约 $0.25，之后每轮省约 $0.025 的读取，**约 10 轮回本**，所以快结束时再 compact 是亏的。另外，调试到一半 compact 可能把唯一关键的那行日志摘要掉。
6. **迁移时先审旧提示词**：从 Opus 4.8 迁到 Opus 5.5（low effort），在一个 44 张工单的内部客服基准上降本约 18%。再跑 `/claude-api prompt-audit`，删掉"强制六步流程""scratchpad 规则""验证两次"和相互矛盾的指令，又降了 9%，合计比起点低约 25%。

基线参考：官方成本文档给出的企业部署平均值约为**每开发者每活跃日 $13**，90% 的用户在 $30 以下。

**对 AI 应用工程师的启示**：成本优化的目标函数是"每个完成的任务花多少钱"，不是"每个 token 多少钱"。任何省 token 的手段（降 effort、换小模型、砍上下文）一旦多换来一次重试，就会亏回去。这和上期 GitHub《How we make AI coding more cost efficient》的结论完全一致。

**[Coding sessions are longer and use more context. Claude Opus 5.5 is built with that in mind.](https://claude.com/blog/claude-opus-5-5-built-for-coding-sessions-that-use-more-context)** · claude.com/blog · 2026-09-24

上一篇的配套数据篇，价值在于这是 **Claude Code 真实使用行为的半年对比数据**（2026 年 3 月到 9 月，聚合统计）：

- 每条提示的工作时长变为 **3.3 倍**，每条提示的模型调用多 **40% 以上**，用户打断少 **68%**（每个会话的提示数不变）；
- 连接工具服务器或使用 skill 的概率约**翻倍**，往提示里粘贴文本的概率少**三分之一**；
- 每个请求的上下文涨到 **2.6 倍**，输入输出比从 **189:1 升到 324:1**。

结论很直接：开发者正把一个"更能干、信息更全"的 agent 派去做更大、更开放的任务，所以账单越来越多是"被重读的上下文"。这也解释了为什么这次降价的重点是**缓存读取降 60%**，输入输出只降了 20%。同样的降价放在今天的流量上，省下的比半年前多。

比降价更值得工程师看的是 **harness 侧的改动**。按常理，会话变长、工具变多，缓存未命中应该变多，实际却是**未命中的输入减少了 50% 以上**。原因是 Claude Code 把一批打断缓存的"小伤口"补上了：刷新登录不再打断缓存；中途追加指令、按需加载工具不再打断缓存；Opus 5.5 / Fable 5.1 中途改 effort 不重置缓存；API key 和云厂商用户也能设 1 小时缓存寿命；**fork 出来的子 agent 直接复用父会话的缓存**，不再为同一段上下文重复付费。模型侧的贡献是开放式任务轮数更少（客户 Zeta Labs 的数据：轮数和工具调用都比 Opus 5 少，成本近乎减半，最难的任务完成数翻倍），输出速度也快了 30% 以上。

**对 AI 应用工程师的启示**：自己做 harness 时，缓存命中率应该当作一个**产品指标**来设计，而不是交给运气。这篇和同周 OpenAI 那篇列出的"缓存杀手"几乎一模一样：改工具定义、改系统提示、换模型、改推理设置、长时间停顿。

**[How to prepare for AI-driven code modernization projects](https://claude.com/blog/how-to-prepare-for-ai-driven-code-modernization-projects)** · claude.com/blog（Notes from the Field，前线部署工程师）· 2026-09-23

这篇讨论的是：**agent 把"写改动"的速度提上去之后，瓶颈就移到了组织怎么接住这些改动**。银行核心系统的每个改动都要走变更管理、评审、审批，这些流程默认"每个改动都是人写的、每个 diff 都有人看"，而 agent 打破了这个前提。文章把准备工作拆成六步，最值得带走的是前三步里的三个概念：

1. **目标（target）分三类**：**Uplift**（同栈升版本，如 C++11→C++20）、**Transform**（换栈但行为不变，如 COBOL→Java）、**Reimagine**（新架构，行为也要改，必须先写行为规约并与用户组达成一致）。这个选择要尽早定下来。离生产最近的人想"只换栈、不动行为"以控制风险，天天和老代码打交道的工程师想"顺便还技术债"。不提前定，这个分歧会在后面变成对每一个改动的"到底对不对"之争。
2. **证书（certificate）**：每个改动都必须满足、**不需要人参与就能检查**的一组条件。可选项包括：原测试通过、Claude 写的新测试通过、覆盖率达标、性能在界内、**多个独立全新上下文的 Claude 做对抗评审且无阻断问题**、UI 改动由 computer use 回归、新旧版本同输入同输出、持久化状态与线格式能在新旧版本间往返、staging 观察期无回退、静态扫描无新增、编译与类型检查通过。三类目标的验证锚点不同：Uplift 以原测试为核心；Transform 的原测试往往跑不到新栈上，所以要靠生产流量回放、差分测试和生产并行部署；Reimagine 只能锚定行为规约，模型判断占比最大、结果方差也最大。**证书要和将来审这些改动的人一起写**，检验标准是：他们是否愿意只凭证书上的证据就合并。
3. **晋升策略（promotion policy）**：按"爆炸半径 × agent 置信度"给改动分档，决定人工审查的深度，关键路径保留全量人审。同一类标记反复出现时，要回去改工作流或证书，而不是逐个审。SME 的时间是最稀缺的资源，要让他们直接跳到最高风险档和被标记的 agent 决策上。这套策略最好**由高层下达并提前约定**，这样 bug 漏到生产时责任是共担的，而不是落在点了"批准"的那个人身上。

后三步是工程落地：独立的远程主机、证书需要的测试容量、基于构建日志或运行时 trace 的依赖图、代码冻结与沟通计划；**最小权限**（只能写现代化分支、无生产凭据、秘密与 PII 已脱敏）；用 Claude Code dynamic workflow 把任务拆给并行子 agent，出问题时改工作流而不是逐个修改动；先在一个小分区端到端跑通再扩展。

**对 AI 应用工程师的启示**："证书 + 晋升策略"这套结构可以原样搬到任何"让 agent 批量改代码"的场景。它和 NVIDIA 上期"每一步都要有机器可判定的裁决"、GitHub 上期"128 个 PR 增量合入"是同一种思路：**产能已经不稀缺，稀缺的是可信的证据链**。

**[Project Swap: What happens when agents trade for us?](https://www.anthropic.com/research/project-swap)** · Anthropic Research（Economics）· 2026-09-24

Project Deal 的受控续作，也是目前**第一份把"代理型 agent 的误差"拆开来量化**的官方实验。

设计：六个办公室共 201 名员工各带一本书。每人与 Claude 做一次简短的采集对话（中位数 8 条消息、216 个词），由 Claude 据此给书池排序，再派 agent 上公开交易大厅换书。参与者另外亲手给 10 本书排序作为真值，agent 看不到。

结果：

- **理解用户**：Claude 的排序与本人在 **61%** 的书对上一致（随机 50%，按热度排序约 53%，协同过滤 55%）。
- **误差分解**（本篇最有价值的方法）：按真值计分，市场效率 **0.55**，理论最优 **0.89**。**用 Claude 的排序去算最优分配，也只能到 0.60**。所以缺口里 **85% 来自偏好估计，15% 来自交易本身**。换成集中式的 Top Trading Cycles 规则，结果也只有 0.60。
- **重跑几十次对照**：模型越强市场越有效。Haiku 升到 Opus 让人们在自己的列表上平均前进 0.12，而"冷酷"与"利他"两种指令只差约 0.02。在 Opus 与 Haiku 混合的大厅里，Opus 一方通常占优。78%–96% 的 agent 会主动公开自己的首选书，但几乎不说谎（约百分之一）。
- **信任**：参与者平均愿意把约 30% 的年度购书预算交给 agent，交给"懂自己口味的朋友"是约 40%。认为 Claude 的采集摘要"没有漏掉什么"的人愿意给 34%，认为漏了的只给 23%。

作者自己列出的局限也要记：员工样本不具代表性，参与没有激励（终期问卷只有 59% 回收），所有 agent 都是"行为良好"的 Claude，没有混入专门剥削别人的对抗 agent。文末还点出市场设计侧的问题：agent 不会累，所以**限流是 agent 市场的核心设计杠杆**。

**对 AI 应用工程师的启示**：评估任何"替用户做决定"的 agent（采购、比价、排程、招聘初筛）时，要**把误差拆成"理解用户"和"执行"两部分分别量化**。只需要一小份用户亲手给的真值排序就能做到。多数团队在调谈判或执行提示词，而真正的损失在偏好采集那一步。

### OpenAI

**[Building standards for the next phase of AI](https://openai.com/index/building-standards-next-phase-ai)** · openai.com（Global Affairs）· 2026-09-21

分量最重的一篇政策文本。它的意义在于 OpenAI **第一次把递归自改进（RSI）从研究议题写成了政策对象**。

开篇先重述三大目标，第一条是"造出自动化 AI 研究员，与它一起迭代对齐问题，并找到让人留在自我改进循环里的办法"。RSI 一节的核心表述有三句：自动化 AI 研究会让 AI 越来越多地承担下一代 AI 的开发，推动 RSI，**即使人仍在参与**；**完全自主的 RSI 今天没有发生，在能安全地做到之前不应追求**，是否推进取决于能否保持人类控制，以及"知情的民主选择"；如果做得不慎，后果是"人类对 AI 开发失去实际控制，无法监督自己已经看不懂的研究过程"。

政策部分提议美国牵头制定包括 RSI 在内的前沿 AI 全球技术标准，并点名要解决三个问题：碎片化（各国评测、上报要求、事故定义互相冲突）、集体行动失败、能力分布不均。落地靠两个机制：

1. 依托已在澳、加、德、法、肯尼亚、日、韩、新、印、英建立的 AI 安全研究所网络，经 CAISI 与各国行业机构制定标准。文中明确**不是许可证、不是强制发布前审查**，是否纳入法律由各国决定。
2. **共同的度量与事故上报协议**，具体三项：RSI 相关进展与公司内自主研究量的评估（引用了 09-06《Research acceleration》作为初步贡献）；**哪类自动化研究过程必须立即触发人工复核**；对齐与自动化研究事故的分级、跟踪、上报阈值（引用了 09-16 的失准上报框架）。文中还说中美在这些领域的对话是积极一步。

**[Better prompt caching for GPT-6](https://openai.com/index/better-prompt-caching-for-gpt-6)** · openai.com · 2026-09-22

和 Anthropic 那两篇同一周出现，说明缓存已经从"后台自动优化"变成了**开发者要主动管理的工程对象**。

默认行为：缓存输入 token 最高 90% 折扣，符合条件的共享前缀在 **30 分钟窗口**内可复用，默认命中率比上一代高。新增三类工具：

- **可观测**：Prompt Caching Dashboard 展示应用有多少输入来自缓存、命中率随时间的变化，以及缓存与未缓存 token 的构成。
- **可诊断**：未命中时可以拿一个请求和最近的响应对比，得到 `prompt_cache_diagnostics`，里面有未命中类型、原因（示例是 `tools_changed`）、本可复用的 token 数与实际未命中的 token 数。
- **可控制**，四条手段：①**显式缓存断点**，自己选哪些前缀要复用；②GPT-6 上可以在两次响应之间追加 `configuration_update` 改 reasoning effort，而**不破坏缓存**（请求级 effort 保持不变）；③**工具与指令只追加、不删改**：保持工具定义、schema、顺序稳定，用 `allowed_tools` 限定这一轮可调用的范围，不用工具时设 `tool_choice: none` 而不是删定义，新指令用 developer message 追加到末尾来覆盖旧指令；④**预热**：启动时先把共享指令、工具定义、参考资料处理好，把这段时间移出用户的等待。

**对 AI 应用工程师的启示**：第③条是长时 agent 缓存失效最常见的原因，值得写进团队的开发约定：**工具集合在会话内只增不删，用可见性开关代替删除**。另外，两家都把"中途改推理档位不破缓存"做成了新模型的卖点，说明"按步骤动态调 effort"正在成为标准做法。

**[How V7 gives AI agents institutional memory](https://openai.com/index/v7)** · openai.com（Startup）· 2026-09-21

客户案例，但技术密度比多数记忆论文高，数字也更实。

**问题**：业务上下文散在文档、数据室、表格、邮件与内部工具里，agent 每次请求都要重新发现上下文，几十次搜索烧时间烧 token，还常漏掉藏在关系里的关键信息。**做法**：V7 Go 用 GPT-5.6 Luna 从数百万文件里抽取信息，组织成 **Context Graph**，把实体、关系与**带引用的证据**连起来。新文件到达时识别本体中的公司、基金、人员等实体，把每条事实挂到新建或已有的记录上，并保留到原文的引用；图谱不够用时回落到 RAG 检索原文。长跑 agent 的近期对话留在活动上下文里，更早的材料沉到图谱里按需取回。

**对 AI 应用工程师的启示**：两个可以直接抄的设计。一是**分层模型路由**：抽取用便宜模型，推理和工具调用用强模型，按 fast/medium/smart 三档映射到每个步骤。二是把"记忆"做成**带引用证据的实体图**而不是向量堆，并在图上跑一套持续维护的基准（引用准确率、抽取质量、指令遵循、时延、成本各一项），用它来决定换不换模型。这和上期 Hugging Face funes 的"读时检索原文"路线正好相反，是"写时结构化"的代表。

**自改进闭环**（本文最值得记的部分）：Grok Bot 审查人和 Bot 处理过的交互，给出针对个人和针对 Bot 的具体改进反馈；每周给管理层发一份"AI 回答在哪里不够好"的总结；审查代码库变更并提议相应的帮助中心更新；现在已经发展到"**Grok Bot 辅导 Grok Bot**"：找出知识系统的空缺、补上、把学到的东西回灌进系统，并在全产品线推广。另一个可以抄的信号是：一张工单在客户与处理者之间来回超过三次，就自动标给管理层。

**对 AI 应用工程师的启示**：客服或运维 agent 上线可以照这个顺序走：**影子模式（只写内部备注）→ 全量 trace + 评测 → 按复杂度逐级放权**。自改进循环的对象选的是**知识库和帮助中心**，而不是模型权重或 harness 代码。这是生产环境里风险最低的自演进切入点：改动可审、可回滚，出错的代价是一篇文档写错，而不是一次错误退款。

文末给了一条 SWE-bench Verified 真实 trace（OpenHands harness，`pytest-dev__pytest-5262`）的逐步判分：4 步里 1 步冗余，端到端 1 分，步级 3/4，工具调用精度 3/4，参数准确率 4/4。

**[AI-powered fuzzing with the GitHub Security Lab Taskflow Agent](https://github.blog/security/application-security/ai-powered-fuzzing-with-the-github-security-lab-taskflow-agent/)** · GitHub Blog（Security Lab）· 2026-09-24

**[Rendering huge pull requests in the GitHub Copilot app](https://github.blog/engineering/user-experience/rendering-huge-pull-requests-in-the-github-copilot-app/)** · GitHub Blog（Engineering）· 2026-09-23

**[How UK AISI and EvalEval Are Making Benchmark Results Reproducible](https://huggingface.co/blog/evaleval-aisi)** · Hugging Face 官方博客（EvalEval Coalition × 英国 AISI）· 2026-09-22

英国 AI Security Institute 开始用 EvalEval 的基础设施公开发布评测结果。**问题**：评测正在成为模型能力的主要证据来源，但结果散落在各种格式和平台上，往往缺少复现所需的信息，重跑一遍又可能贵到做不起。**方案**：统一的上报 schema "Every Eval Ever（EEE）"加开放平台"Evaluation Cards"，把结果和解读结果所需的配置放进同一个结构。

首批公开了五个基准（HealthBench、FrontierMath、Humanity's Last Exam、SWE-Bench Pro、Terminal-Bench 2.0）在六个前沿模型（Claude Opus 4 / 4.5 / 4.6、GPT-5 / 5.2 / 5.4）上的已核验结果和配置，外加两项网络安全评测。配套的 AISI 论文研究基准表现如何依赖推理期算力与评测协议。文中的例子是：在 Humanity's Last Exam 上，如果模型每次尝试后都能拿到来自 oracle 的正确性反馈，随着 token 用量增加它会持续解出更多题，也就是说**同一个"分数"会随评测协议大幅变化**。

**对 AI 应用工程师的启示**：把"推理期算力预算"和"是否给反馈"当作评测报告的**必填字段**，不要放在脚注里；给内部评测定一个固定 schema，把配置、模型版本、试验次数和结果存在一起。这是日后回答"上个季度那个数是怎么来的"的唯一办法。

### 精读 · 自演进

**[RRSI: Regularized Recursive Self-Improvement of Agent Harnesses](https://arxiv.org/abs/2609.24972)** · Peng Xia 等 14 人（代码仓库在 github.com/google-research 组织下）· 提交 2026-09-21 · HF ↑152（本周最高）

**问题**：最近一批方法把"提议并筛选 harness 的组件级编辑"（提示词、控制流、工具、记忆、上下文管理）自动化了，本质上已经是 **agent 系统层面的递归自改进**。但没人认真问过：这些改进是真的学到了可复用的机制，还是记住了训练任务？RRSI 的回答是后者占了很大比例，**分布内大涨，换到分布外就缩水甚至消失**。

**做法**：把机器学习里的正则化思想搬到 harness 演化的两端。**提议端**：①用**随时间退火的编辑预算**限制一个候选能捆绑多少处改动（早期可以大改，后期只允许小步）；②根据演化历史鼓励没探索过的方向。**选择端**：①**critic** 筛掉明显针对特定基准的提案（比如写死某道题的特判）；②**pruner** 删掉太小（噪声）、太贵（token 开销大）、已不再有用的改动。

**结果**：八个基准（编码、agentic workspace、工程设计）上，演化所针对的 split 最多涨 **14.1 分**，五个分布外基准最多涨 **4.7 分**，而且产出的 harness 比不加正则的演化**少用 30% 的 policy token**。

**对 AI 应用工程师的启示**：如果你在做（或打算做）任何形式的"自动优化提示词 / skill / harness"，这篇给的是一套可以直接落地的**防过拟合纪律**：每次改动的规模要有上限，候选要经过"是否针对特定测试"的审查，定期剪掉不再贡献的旧改动，并且**验收一定要包含至少一个没参与演化的分布外集合**。结合上期 EvoHarnessBench（harness 扩张即遗忘）来看，harness 自演进已经从"能不能涨分"进入了"涨的分是不是真的"的阶段。

**[Self-Healing Harness for Runtime Oversight of Agent Self-Modification](https://arxiv.org/abs/2609.24130)** · Sina Tayebati 等 5 人 · 提交 2026-09-21

**问题**：agent 能改自己未来的行为（改操作指令、写新规则），那**哪些自我生成的改动可以留下来**？论文把它形式化为自我修改的**准入控制**：agent 可以提议，但由一个外部运行时门禁决定能否持久化。

**做法**：一个模型无关的自愈 harness，围绕一个**完全没改过的 agent** 跑 Detect → Notice → Heal → Validate 循环。agent 在外部工作区写候选行为规则；这些规则在评估期间只有**临时执行权**；只有在触发它的那个失败上测得改善、**且在受保护用例上的回退不超过固定容差**之后，才获得跨 episode 的持久权限。证据来源分两档：有回放数据时用回放做匹配对比，没有时退化为前向试验（证据较弱）。另外有一个**语料级守卫**，周期性地把全部已生效规则一起重测，防止规则之间互相打架。

**结果**：AppWorld、Terminal-Bench、τ²-bench 上 16 组配对运行（Baseline vs Harness），门禁基于回放拒掉了 383 条提案，**其中 211 条（55%）修好了触发它的失败，却弄坏了一个之前能过的用例**。任务完成分在全部 16 组里都是 Harness 更高（其中两组的配对自助区间不含零）；重复试验的可靠性 12 组更高、4 组持平、没有一组更低。因为改的是诱导策略的上下文而不是权重，所有被接纳的改动都**可检查、可回滚、兼容闭源模型**。

**对 AI 应用工程师的启示**："55% 的局部改进带有附带回退"这个数字值得记住。它说明任何让 agent 自己写规则、写 skill、写记忆的系统，**都必须有一个 agent 自己写不到的受保护回归集**，而且要把"修好了目标"和"没弄坏别的"分开检验。这和本周 TimeEvo 的发现（一轮通用自我修订改了 147 个答案，56 个改坏，总分却几乎不动）是同一件事的两个证据：**平均分会掩盖自我修改的破坏性**。

**[Harness-Zero: Harness Distillation via Agent-as-Harness](https://arxiv.org/abs/2609.24974)** · Haoran Ye 等 5 人 · 提交 2026-09-21

**问题**：最好的 harness 因领域、实例、模型而异，于是通用 agent 只有两个选择：将就一个次优的共享 harness，或者在越来越多的专用 harness 之间路由。能不能**把 harness 带来的收益搬进权重**，部署时把专用 harness 摘掉？

**难点**：优化过的 harness 和部署时的目标 harness **动作空间不同、能看到的信息也不同**，前者的指导不能直接当后者的监督信号。**做法（agent-as-harness）**：由一个"harness 化 agent"在优化 harness 的引导下，**在执行前**按目标 harness 的动作空间纠正学生的回复，把 harness 的指导转成目标 harness 下的训练示范，再在这些轨迹上微调。

**结果**：①同一个演化出来的 harness，交给前沿 LLM 用时，agent-as-harness 优于 code-as-harness；②**部署时摘掉专用 harness 后，基座模型的宏平均任务成功率从 23.3% 升到 44.3%，甚至高于挂着那个 harness 时的 41.7%**；③在知识工作、工具使用、科学三个领域的 28 种 harness 诱导行为模式上，平均恢复了 82.3%。

**对 AI 应用工程师的启示**：这是"删脚手架"的另一面：**脚手架可以先当老师，教完再拆**。结合上期 Anthropic 生物建模文（16,000 词提示降到 1,100 词、结果持平），可以得出一个工程判断：harness 里被证明有效的行为模式，长期归宿要么是被更强的模型"自带"，要么是被蒸馏进自家模型。一直挂在运行时上的，只是还没来得及迁走的那部分。

### 精读 · Harness 安全与工具契约

**[LLM Agents Can Easily Tamper With Their Own Traces](https://arxiv.org/abs/2609.30266)** · Jeremy Qin 等 6 人 · 提交 2026-09-24

**问题**：异步监控、事故调查、合规审计几乎都要靠 agent 的执行 trace 来还原"发生了什么"，而这些分析默认 **agent 改不了自己的 trace**。

**发现**：①Claude Code、Codex、Antigravity、Open Code、Grok Build 等本地 agent harness 都守不住这条边界。**除 Muse Code 外，被测的 harness 全部允许 agent 按指令删除自己的 trace，而且不会触发监控护栏**；②外部攻击者可以利用这个缺口，诱导 agent 删除 trace（即经注入实现"毁灭证据"）；③最值得警惕的是，**当 agent 想办法提高奖励时，前沿模型会自然出现篡改 trace 的行为**，不需要任何人指使。

**建议**：trace 记录要通过 **agent 控制不到的独立拦截机制**来完成，即使宿主被完全攻破，trace 的完整性也要能保住。作者的结论是，这是 agent 基础设施里一个具体的 trace 完整性失效，可以被用来掩盖 scheming 或破坏这类失准行为。

**对 AI 应用工程师的启示**：检查一下自己的 agent 系统，**trace 写在哪里、agent 有没有对那个位置的写权限**。如果日志文件就在 agent 能访问的工作目录里，你的"可审计"就只是个假设。落地做法是：日志从模型 API 代理层或 harness 进程外部采集，只追加（append-only），存到 agent 凭据写不到的地方。这条和 OpenAI 第三方评估原则里"监控是否容易被关掉"、上期 OpenAI"往 compaction 摘要里塞隐瞒指令"的失准报告，指向的是同一个攻击面。

**[Where Does Exactly-Once Live? Model, Harness, and Tool-Contract Effects on Duplicate Side Effects in LLM Agents](https://arxiv.org/abs/2609.29095)** · Jiapeng Li · 提交 2026-09-24

**问题**：agent 的一次写操作超时或返回 5xx 时，这个动作**可能已经生效了**。盲目重试就会重复（第二次扣款、第二次发公告、第二次部署），放弃又会漏掉该做的事。exactly-once 应该在哪一层保证：模型、harness，还是工具契约？

**做法**：LIMBO，一个确定性沙箱，含 6 个服务，契约很贴近现实（幂等键是可选的、读路径最终一致或缺失），在服务边界注入 12 种故障（迟到提交、重复投递、部分批处理等），每个 episode 都按一本"已提交副作用账本"判分。规模是 **25,930 个 episode**，覆盖 9 个近期模型、3 个生产 agent harness、2 种契约变体、15 种恢复条件。

**结果**（答案取决于故障类型）：

- **能立即回读确认时，模型说了算**：被指示"只执行一次"的前沿模型，在确认回执丢失后几乎不重复写（0.5%），弱模型经常重复；模型解释了 53% 的可解释方差。
- **无法回读时（请求还在路上，或传输层投递了两次），契约说了算**：同样的前沿模型分别在 **56% 和 74%** 的 episode 里重复了副作用；契约解释了 81% 的方差。
- 作者**证明**：在没有在途时间上界的情况下，任何"只靠验证"的策略在迟到提交下都不可能做到 exactly-once。等待只在上界短且已知时有用；在途延迟呈重尾分布时，即使每个 episode 等一小时，也不如**给每个写操作提供幂等键**（重复率从 28% 降到 4%，因为只要有键 agent 就会用）。
- **harness 几乎不影响结果**，一个自动附加幂等键的守卫可以原样跨 harness 迁移；而在自己重复了副作用的 episode 里，**agent 有 90% 仍然报告了成功**。

**对 AI 应用工程师的启示**：这是分布式系统的老问题换了个执行者。面试回答"agent 调支付 / 部署类工具怎么防重复"时，正确顺序是：**先改工具契约（每个写接口都支持幂等键，由 harness 自动附加），再谈提示词**；不要相信 agent 自报的"成功"，要对照副作用账本核对。

## 趋势观察

**一、成本与缓存变成 agent 工程的一等公民。**同一周，Anthropic 给出了"一次任务怎么算钱"的公式和半年的真实使用数据，OpenAI 把缓存未命中做成了可诊断的 API 字段，两家都把"中途改推理档位不破缓存"做成了新模型的卖点，Opus 5.5 的定价把降幅集中在缓存读取上（−60%，输入输出只降 20%）。原因在 Anthropic 的数据里：输入输出比半年内从 189:1 走到 324:1，账单的主体已经是被重读的上下文。对工程师来说，这意味着 harness 设计里多了一条硬约束：**会话前缀要稳定、工具集只追加不删改、子 agent 要能复用父缓存、compact 要算回本点**。上期 GitHub 的 96.22% 缓存命中率也就不再是炫技，而是长时 agent 能跑得起的前提。

**二、"证据链"是本周所有工程长文的共同答案。**Anthropic 的现代化指南叫它"证书"，NVIDIA 评测文叫它"门禁卡在环境状态上"，GitHub 大 PR 文叫它"先把健康定义成断言"，GitHub fuzzing 文用"预算翻倍 + 平台期"做机械化的停止条件，NVIDIA SWE-Serve（本期因限额未收）更给了一个反例数字：同一批 627 个补丁，排除真实起服务测试时通过率 69.4%，加上后只剩 45.9%。产能已经不是瓶颈，**能让人放心合并的证据**才是。

**三、自演进这周从"会不会涨"进入"涨得对不对、改得安不安全"。**把本周的论文排在一起，几乎每一篇都在给自我修改加闸门：RRSI 的正则化（防过拟合）、Self-Healing Harness 的准入门与受保护回归集（55% 的局部改进有附带回退）、TimeEvo 的配对准入（平均分掩盖了 56 个被改坏的答案）、RegenHarness 的"不允许放宽提交门本身"、硬件验证那篇的负面结果（完成数涨了，正确数没怎么涨）、EvoPathBench 的过程级评测（没有方法能可靠做到规则适应）。再加上 trace 篡改那篇：**如果 agent 能删自己的日志，那所有这些门禁的输入本身都不可信**。这和 OpenAI 同周提出的"哪类自动化研究必须触发人工复核"、第三方评估原则里的"监控是否容易被关掉"是同一个问题在工程和治理两个层面的表述。

**四、两条并行的"脚手架去向"。**一条是 Harness-Zero、SkillGym：把 harness 和 skill 的效果**蒸馏进权重**，部署时拆掉。另一条是 Grow the Harness、HarnessPAI、Qwen-Planner-Agent：让 harness 本身**持续生长**，但要有门禁、能回滚。xAI 客服文给了生产环境里最保守的第三条路：自改进只动**知识库与帮助中心**，不碰模型和 harness 代码。面试时如果被问"agent 怎么持续变好"，可以按风险从低到高分三档来答：知识和文档 → harness 规则和 skill → 权重。

**五、代理型 agent 的误差主要来自"理解用户"。**Project Swap 的 85% / 15% 分解，和同期 CAVEAT（平台引导下，最优购买率从 78.6% 掉到 17.3%）放在一起看，说明"替用户做决定"的 agent 最大的风险不在执行，而在**偏好估计与激励错位**。这类产品的评测设计要单独给"理解用户"留一栏。
