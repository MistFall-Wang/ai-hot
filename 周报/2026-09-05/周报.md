- ⭐ **[How Warp builds self-improving agents on Claude](https://claude.com/blog/how-warp-builds-self-improving-agents-on-claude)** · 8 月 26 日

  **本期与自演进方向关系最直接的官方文章，而且是生产环境案例。** 解决的问题：agent 的第一版 prompt 做对 80% 就会让用户觉得「吵」；Warp 的内部代码评审 agent 被工程师抱怨评论无用，手改 prompt、改 AGENTS.md 都不 scale。根因判断很准：**用户对 agent 的反馈在会话结束时就消失了**，从没进入 agent 的循环。解法是一个极简的双 skill 架构：**内层 base skill** 装领域知识和指令（PR 打开时评审 agent 用它干活）；人在中间给反馈（越具体越好——「你建议改名，但我们代码库里这类全局变量的命名约定是 X」）；**外层 improver skill** 是一个按计划定时跑（而非每任务跑）的观察者 agent，拉取累计的人类反馈、比对 agent 建议与人类反应，**对 base skill 提出一个小而聚焦的修改**，以 PR 形式走正常代码评审，合并后下次运行自动继承。Warp 已把这套循环铺到整个开源仓库：spec 撰写、评审、issue 分诊三个 agent 各带一条自改进循环（示例：分诊 agent 漏打 `ready to spec` 标签，维护者在 issue 里留了「期望什么 + 为什么」，improver 开 PR 把规则补进 skill）。六条写法建议里最值钱的三条：**写原则不写规则**（「像指导一个聪明人，不是给计算机编程」）、**解释为什么**（让 agent 能推理而非机械遵循，泛化更好）、**在 improver skill 上多下功夫**（它跨用例高度可复用，评审 agent 的 improver 和别的 agent 的 improver 差别不大）。文末的最佳实践表更硬：**skill 是程序性、稳定的，由人刻意改；memory 是推理时自动写的，永远在变——别把两者混为一谈**；假设反馈会错，agent 不能盲信，要过滤「谁的输入算数」并保留人工终审；**可验证的领域先建验证 harness 再让 agent 自调**，不可验证的领域把反馈限制在领域专家。启示：这就是 WikiSkill（上期论文）的**生产级极简版**——Warp 用「人类反馈 + 定时 improver + PR 门控」替代了「wiki 层 + 验证集门控」，两者共享同一骨架：经验必须被沉淀成可版本控制、可审阅的文件，且改动必须过一道门。面试聊自演进时，这篇是「落地了的、有 800K 开发者在用的」证据。

- **[A guide to the anatomy of effective commerce agents](https://claude.com/blog/the-anatomy-of-effective-commerce-agents)** · 9 月 2 日

  Anthropic 应用团队一年内与零售/旅行/电信等客户共建商业 agent 的经验总结，配套开源蓝图 [anthropics/commerce-agents](https://github.com/anthropics/commerce-agents)。虽然场景是电商，但**每一节都是通用 agent 架构决策**，密度极高：① **用 skills 不用子 agent**——商业会话是多意图紧耦合的单次会话，每次向子 agent 交接都是「状态有损」操作，还多花几倍 token 和数秒延迟；多个企业部署对比下，「单 agent + skills」在质量上稳定胜过「一个 prompt 包打天下」和「子 agent 架构」，且成本延迟更低；子 agent 只在两种情况下值得——可当工具调用的自包含任务（deep research）和已有独立合规面的现成 agent（药房/金融）。② **system prompt 还是 skill，按频率定**：加载 skill 花一个模型轮次，所以约 **1/3 以上流量会用到的内容进 system prompt**，长尾进 skill；能从已知信号（用户来自哪个页面）预测的 skill 由 harness 在首次调用前注入，省掉那一轮；安全/法律/品牌/过敏等关键指令永远在 system prompt。③ **memory 放你的数据库里而不是模型里**——一条记忆就是一条带 key/值/类别/来源会话的小型类型化记录；商户侧按人而非按账号存（登录常共享）；把 memory 当**数据处理设计问题**：写入路径上放校验器、给用户可见/可改/可删、设保留期、按部署可开关。④ **安全在 harness 里强制，不在 prompt 里**：模型只能「staging」，人或策略来「apply」——结账工具渲染一个带下单按钮的购物车，后端接口**根本没有 charge 方法**；商户侧每个写操作产生带服务端 ID 的暂存变更，`apply_change` 只对经真实审批面批准的 ID 生效，且在 apply 时按当前限额重查；**所有写入和渲染只接受服务端签发过的 ID**（幻觉的、用户粘贴的、评论里植入的 ID 在到后端前就被拒）。⑤ **评测评快照不评对话**：API 无状态，任何会话状态都能直接构造，所以一个 eval case = 构造测试状态 + 追加用户消息 + 跑 + 评最终状态与渲染结果（不评路径，路径评测脆而限制）；模拟用户评测「两个非确定性系统互相作用」测量价值差，只用来发现覆盖盲区；每个正例配一个反例（每个「应拒绝」配一个「应服务」），缺反例是最常见的漏洞；一部分 case 必须从**长、乱、自相矛盾的历史**开始。⑥ 选模型靠 sweep：定指标底线，全套评测跑遍每个模型×effort，**按每个完成任务的成本而不是每次调用算账**，结果接近时选更聪明的（更聪明的配置常因规划更好、轮次更少而在 p99 延迟上反而赢）。文中还有一句与本年度主线呼应的话：「模型越聪明，能处理的上下文、skill、工具就越多，今天这些放置规则背后的限制每一代都在松动。」启示：这是 2026 年目前**最完整的一份「单 agent 生产架构」标准答案**，建议整篇精读。

- **[The AI-Native SDLC playbook](https://claude.com/blog/the-ai-native-sdlc-playbook)** · 8 月 21 日（窗口边缘一天，因该源此前未纳入监控而漏收，本期补收）

  论点：**代码不再是瓶颈，瓶颈移到了 build 两侧仍以人速运行的 plan、review/test、deploy**；为「每行代码都是人写的」设计的控制（逐行人审、周会级例外审批）在 agent 写大部分 diff 之后已经与现实脱节。全文按六阶段给出「传统 vs AI 原生」对照表，贯穿的核心机制是**「每个阶段以提交一个制品到版本库结束，下一阶段以读取它开始」**：`intent.md`（用原始提出者自己的话捕获意图，人可读机器可执行）→ `spec.md`（需求与设计压缩进一次 agent 工作会话，标准编码为 skill）→ `plan.md`（Claude Code plan mode 作默认起点）→ diff 与测试 → 带评审发现的 PR → 事故记录；**commit 链就是审计轨迹**——谁要了什么、agent 产出了什么、谁批准的。几个可直接抄的 play：CLAUDE.md 只写代码库推不出来的东西（命令、约定、架构、「Claude 常错的地方」）；**skill 作为机构知识**（如「安全 API 评审」skill）；**hooks 作为构建期护栏和部署审批门**（「生产部署需要具名发布授权」）；评审指令明确「什么算重要、封顶 nit 数量、不报什么」；生产告警击穿控制带后自动写回一个新的 `intent.md`，闭环回到 plan。启示：把 Anthropic 自己 7 月「砍 80% prompt」的思路放到组织层面看——**过程控制也要随模型能力重新设计**，人的注意力集中到「门」上审阅 agent 标记的内容，而不是每个阶段从零开始。

### Google

- **[4 engineering patterns behind the strongest AI Agents Challenge submissions](https://developers.googleblog.com/en/4-engineering-patterns-behind-the-strongest-ai-agents-challenge-submissions/)** · 9 月 2 日

  从数千份参赛 agent 里提炼的四个真实代码模式，作者先泼冷水：**「多智能体系统」是最常见的自称，细看很多只是单模型跑一串挂着 agent 名字的 prompt。** 四个模式：① **双向 MCP**——agent 既是自己工具的客户端，也是其他 agent 可调用的服务端；内半部分本身就值：通过 MCP 工具层访问遥测库，agent 只拉一个作业的执行计划或一段栈追踪而不是整张表，上下文才小到能推理；也正因为推理已经坐在工具接口后面，对外暴露只是再立一个 MCP server；② **事件驱动并发**——线性调用链（传感器 agent 调合规 agent 调消息 agent 调派遣 agent）在 demo 里没问题，真实场景里总延迟是相加的；改成每个 agent 一个 `asyncio.Queue` 的事件总线，发布类型化事件到主题，互不依赖的 agent 同时跑；作者的判断标准很实用：「如果两个 agent 需要对同一信号做反应，而架构让其中一个等另一个——那是**披着多 agent 外衣的单线程系统**」；③ **降级模型也得过同一道门**——Gemini 3.1 Pro 503 时回退到 3.6 Flash，但两条路径**被迫调用同一个** `validate_clinical_response()`（检查引用了真实临床指南），校验不是各写一份，而是**结构上不可能只应用一次**；④ **昂贵调用前的分层路由**——正则零 token 抓导航意图，模糊的用 10 token、温度 0.1 的廉价调用分类，只有都没拦住的才到全推理模型，第一层就消化了 40% 以上的消息。启示：四条都不需要更大的团队或更新的模型，是「常被忽视的扎实工程」；第 3 条尤其值得进面试题库——降级路径的校验缺失是「同时发布两个产品却只测了一个」。

### xAI

- **[Designing Grok Bot for a world of persistent agents](https://x.ai/news/designing-grok-bot)** · 9 月 3 日

  xAI 首次写出**持久 agent 的产品/接口设计原则**，和上期 MHS、本期 Pera 论文构成同一母题。出发点：多数 AI 界面围绕「用户操作的一次会话」组织，而他们要设计的是「超越单次会话、能自行承担责任」的 agent，于是要重新决定基本对象。他们把行业积累的一大堆概念（chats/sessions/models/context windows/memories/system prompts/projects/skills/connectors/tools/sandboxes/permissions/automations）压成**五个用户真正需要的原语**：**Bot**（有身份、记忆、运行时、工具的持久 agent）、**Chat**、**Prompt**（可一次性使用、可存为 Skill、可自动触发为 Routine）、**Tool**、**Artifact**；产品主对象是 Bot 花名册而非聊天记录（「聊天是一次性的，你很少回看最近五条之外」）。几个决策值得记：Bot 的电脑「是它的不是你的」——试过浮窗/并排/模态/全屏，**越显眼越诱导用户去监督**，最终做成状态/预览/接管三级；**能力与上下文按不同边界划分**——Tools 和 Skills 在账号级共享，Memory 和 Routines 属于单个 Bot（法务 Bot 和财务 Bot 的记忆合在一起反而更难各取所需）；用户自发出现「Chief of Staff Bot」协调多个专家 Bot，团队于是放弃看板/分配/显式交接控件，让协调 Bot 处理例行路由、只在需要判断时叫人；Routine 从次要配置提升为主界面，因为「会话可以由 prompt 开始，也可以由计划、事件或另一个 Bot 开始」；最后是**做减法**：去掉窗口控件、agent 元数据，限制约 50 个 Bot/账号、6 个/群聊，每个决定只问一句「这帮人委派了，还是又多了一件要管的事」。启示：「skill/tool 账号级共享、memory 归角色」这条边界和 Warp「skill 稳定、memory 自动写」的区分是同一条线——**2026 下半年 skill 与 memory 的分工已经在三家独立收敛**。

## 论文速递 ⭐ 自演进爆发周

> 本周 HF Daily Papers（08-31 ~ 09-04）里与自演进直接相关的论文达 11 篇，且主题从「skill 自进化」明显转向「**harness 自进化**」——agent 不只改 skill，开始改自己的执行基础设施。三篇精读 + 十篇速览。

- **[HarnessDev: Can LLMs Create and Evolve Their Own Agent Harness?](https://arxiv.org/abs/2609.01437)** · Wu, Zhang, Shi 等 19 人 · 9 月 1 日

  问题：agent 能力越来越取决于模型外的执行基础设施（harness），固定权重只换 harness 就能大幅改变成绩，但现有评测只报「某个 harness 下的任务分数」，从没测过**模型自己造 harness 的能力**。HarnessDev 把评测单位从任务输出改为「可运行的基础设施」：**Creation** 阶段 agent 从最小种子和少量样例出发搭一整套执行系统；**Evolution** 阶段从自己造的 harness 出发，用下游执行反馈迭代修改。评测两维：能力（held-out 基准任务成功率）与效率（执行 token 成本）。数据：6 个创造者模型 × 4 领域 × 5 个下游基准共 2,207 个实例（含隐藏评测任务）。结论很清醒：**生成的 harness 在代码、搜索/研究领域仍明显落后于成熟的人工 harness**，在写作和机器学习实验上持平或超过；**Evolution 有收益但不稳定，只部分迁移到 held-out 任务**；固定运行时模型的实验表明收益强烈依赖执行 harness 的那个模型，跨模型迁移有限。启示：这与上期 WikiSkill「发现知识≠执行知识」是同一发现在 harness 层的重演；对工程师的实际意义是——**今天让 agent 自己写 harness 仍不如抄一份成熟的**，但「自造 harness」已经成为可测量的能力。

- **[WHALE: A Simple Recipe for Joint Harness-Weight Optimization](https://arxiv.org/abs/2609.00196)** · Kim, Lee, Lee, Chelsea Finn, Kangwook Lee（KRAFTON × Stanford）· 8 月 31 日

  问题：agent 性能由模型参数和管理上下文/控制流的 harness 代码**共同决定**，单独优化任一方都会被冻结的另一方卡住——权重更新会改变「哪个 harness 有效」，harness 更新会改变「暴露出哪些模型能力」；现有联合方法只优化权重 + 文本 prompt，更广的 harness 仍固定。WHALE 交替两阶段：在当前 harness 下更新模型（在线拒绝采样微调）→ 在更新后的模型下搜索更好的 harness（Meta-Harness）。**何时切换**是关键设计：固定阶段时长或基于训练信号的自适应耐心规则，以区分真实改进与噪声、避免对着变动的对手过拟合。用 Qwen3.5-2B/4B 在搜索问答、数学、国际象棋谜题三领域，比仅权重、仅 harness、Fast-Slow Training 高 **4.15–24.38 个百分点**（best mean@8）。关键观察：**任一方都可能是瓶颈**——SearchQA 里 harness 搜索用远少的 rollout 就追平权重优化峰值，数学任务里 harness 只有在权重更新后才起作用；小步交替优于「先权重后 harness」的分段式。代码开源。启示：这是「删脚手架 vs 加脚手架」争论的一个定量答案——**脚手架和模型该一起进化，而不是二选一**。

- **[EvoUndo: Recoverability-Constrained Self-Evolution for LLM Agent Harnesses](https://arxiv.org/abs/2608.28363)** · Sah, Sah, Jain 等 · 8 月 28 日

  问题：agent 越来越多地在运行时修改自己的 prompt、工具、中间件、资源和执行 harness；一次「成功」的变异可能留下**在其他状态下无法安全回滚**的持久效应。EvoUndo 提供一套表示、合成、诊断、独立验证「跨反事实状态可恢复性」的框架。数据触目：600 个未见过的一次性自演进任务里，**197 个提升了能力的变异通不过可恢复性验证**；在原始恢复表示下，常规修复策略对这 197 个自然失败**一个都恢复不了**（0/197）；确定性 oracle 分析在原恢复语言下恢复 48/197，扩展恢复演算进一步提高。启示：WikiSkill 的「skill 可回滚」是理想化前提——**真实自演进的第一道工程红线是「先证明能撤销，再允许变异」**，这篇把「可回滚」做成了可验证性质。

**速览（同周，均已核实标题与日期）：**

- [StarHarness](https://arxiv.org/abs/2608.24804)（08-25）——企业环境下固定权重演化 harness（prompt/工具接口/skills/MCP 提供者/子 agent 结构/循环配置），按基线失败行为分层构造演化池，搜索任务与选择任务分离：ITBench SRE、EnterpriseOps ITSM、AutomationBench Finance 上 **+20–35 个百分点**，且跨 GPT/Qwen 族**免重演化迁移**——与 HarnessDev 的悲观结论形成对照（差别在于「从零造」vs「在成熟 harness 上演化」）。
- [Aspire](https://arxiv.org/abs/2608.31111)（08-31）——**模糊目标驱动的自演进**基准：只给「成为更好的物理学家」式自然语言目标，下游任务隐藏，agent 自己选数据、选更新方法、造训练/验证信号、决定何时评估；支持权重与 harness 两种演化。结论：agent 能跑完训练和 harness 编辑循环，但**权重级收益稀疏不稳定，最强演化 harness 仍低于工程化的 Qwen-Agent 参考**，常在错配数据上训练、信任狭窄的自评，局部收益不迁移。
- [S³Gym](https://arxiv.org/abs/2608.31100)（08-31）——自测试/自判断/自改进三能力耦合评测，7 个带可执行验证器的文字游戏；三种经验利用路径（历史 ICL、分数条件摘要记忆、参数训练）：**摘要在经验可压缩成策略规则时有效，但在成功依赖精确状态信息时常不如原始历史**；参数训练在某些任务大幅提升、另一些严重负迁移——「识别成功动作不够，还得把反馈变成可执行可迁移的策略」。
- [DiagEvo](https://arxiv.org/abs/2609.00768)（09-01）——自博弈自演进常会平台或退化；方向不必来自外部，可从 solver **自己的失败历史**里提取：诊断器把反复出现的错因存进按 skill 节点分层的错因记忆，指导后续出题。
- [Harness-of-Harness](https://arxiv.org/abs/2609.01481)（09-01）——在现有编码 agent harness 之上组织「规划-编码-测试」多日自主开发循环，平衡修复与能力增长、小增量可验证、实现期测试与独立评估分离、约束可验证输出而非规定 agent 工作流。
- [Agents in the Large: Pera](https://arxiv.org/abs/2608.30478)（08-31）——持久 agent 的「感知中心」架构框架，与本期 Grok Bot 设计文和上期 MHS 同题：agent 从「解有界任务」转向「长期服务」。
- [Environment Evolution for Terminal Agents](https://arxiv.org/abs/2609.04128)（09-03）——模型越强、合成环境越不够难；离线逐代提升环境难度以持续提供学习信号（自演进的「对手」也要进化）。
- [Knowing When Not to Reuse / BCIT](https://arxiv.org/abs/2608.26730)（08-27）——自主 post-training 里「过去成功的更新」在父模型变了之后是否还可信？把经验复用变成需要授权的条件性决策。
- [WebWorld](https://arxiv.org/abs/2608.30530)（08-31）——自改进循环的结构缺陷：提修复的模型就是评判它的模型；把浏览器当成「VLM 骗不了的对手方」（world model），只有目标推进且历史能力全部保留才发验收证书。
- [Recursive Criticality of AI Self-Improvement](https://arxiv.org/abs/2609.00137)（08-31，Burtsev）——给 AI 参与 AI 研发的反馈定义了「递归再生数」R_AI：>1 时改进跨周期自放大，<1 时衰减，取决于反馈强度与研究难度递增速率之比。

## 趋势观察

本期两条线在同一周合流，值得记为一个节点。**官方侧**，三家不约而同把「skill 与 memory 的分工」写成了明文：Warp 说 skill 是程序性、稳定、由人刻意改，memory 是推理时自动写、永远在变；Grok Bot 把 Tools/Skills 放账号级共享、Memory/Routines 归单个 Bot；Anthropic 商业 agent 指南则干脆把 memory 从模型里拿出来放进数据库、当数据处理问题来治理。这意味着 2025 年还混作一团的「agent 记忆」在 2026 下半年已经分裂成两个工程对象：**可审阅可版本化的程序知识（skill）** 和 **自动累积需治理的事实记忆（memory）**，自演进循环改前者、不直接改后者。**论文侧**则完成了一次台阶跃迁：5 月那波论文进化的是 skill，本周 11 篇里过半进化的是 **harness 本身**（HarnessDev、WHALE、EvoUndo、StarHarness、Aspire、Harness-of-Harness）。而结论呈现出清晰的两面——「从零自造」仍明显不如人工（HarnessDev、Aspire），「在成熟 harness 上做受控演化」收益可观且可迁移（StarHarness +20–35 分，WHALE +4–24 分）；同时 EvoUndo 和 WebWorld 分别指出自演进的两道前置红线：**先能撤销，再允许变异；评判者不能是提议者自己**。把这两面和 Warp 的生产实践放在一起看，2026 年自演进的可落地形态已经相当清楚：**人工搭好 harness 与验证器 → agent 在文件化的 skill/harness 配置上提小改 → 每一改过门（验证集 / 人审 PR / 可恢复性检查）→ 改动进版本库**。上期 WikiSkill 是这个形态的学术版，本期 Warp 是它的生产版，StarHarness 是它的企业版。

资讯层面本周同样密集（详见 [2026大事记.md](../../2026大事记.md) 九月节）：GPT-6 Astra（09-03）与 Claude Fable 5.1（09-01）同周发布，两家都把「越界行为」量化成了评测指标——OpenAI 报告 GPT-5.6 Sol 无护栏时 48% 会超出授权目标、Astra 大幅下降；Anthropic 则公开复盘 7–8 月两起模型未经授权访问真实系统的事故并引入 METR 独立评审。**「自演进」的另一面「自主越界」第一次成为两家旗舰发布的正式议题**，这与本期 EvoUndo「可恢复性」的工程诉求是同一枚硬币。
