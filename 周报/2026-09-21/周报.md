## 本周新文章

### Anthropic

**[How Claude is uplifting biomolecular modeling](https://www.anthropic.com/research/claude-uplifts-biomolecular-modeling)** · 2026-09-17

这篇表面是生物学成果，内核是**两条 agent 工程结论**，而且都带对照数字。

第一条是"AI 做 kernel 工程"。结构预测模型（AlphaFold3、OpenFold3、Boltz-2）的运行时间与显存绝大部分耗在 triangle attention 与 triangle multiplication 上，这两个算子在时间和空间上都是**立方复杂度**（系统规模翻倍 → 8× 开销，翻三倍 → 27×）。Anthropic 让一个内部通用研究模型去啃这块，产出 FlashPairformer：相对行业标准 NVIDIA cuEquivariance，三角注意力快 **2.7–2.9×**、三角乘法快 **1.7–3.2×**。再叠加逐模型的具体优化（缓存重复计算、把死分支折叠成常量），**30+ 个开源模型在不到四周内平均提速约 4×**（精度损失极小），若要求输出逐位一致则约 1.6×。文章特意点明：监督这件事的是**两位懂生物建模但完全没做过推理优化和 kernel 工程的员工**——换句话说，这类工作的门槛从"有一支资深 kernel 团队、每个模型花几周且经验不可迁移"降到了"有基准、有判据、有人看着"。此外 Claude 还做了个低显存的 "Big" 模式，让 >10,000 token 的分子机器（线粒体复合体 I、TRiC、蛋白酶体、细菌核糖体）能在**单个 GPU 节点**上跑出与实验结构吻合的预测。

第二条才是真正该记的：**脚手架的对照实验**。上一轮蛋白结合体设计的配置是约 16,000 词提示词、鼓励使用子 agent、每个靶点最多花 10,000 美元 Modal 算力（≈2,500 H100 小时）、24 小时；这一轮把脚手架几乎全部拆掉——**单个模型、一张 H200、24 小时、约 1,100 词提示 + 一份预装工具的速查表、没有子 agent、没有人工挑选设计**。三个模型（Mythos 5.1 / Mythos 5 / Opus 5）在 16 个靶点上跑下来，中位数与最高分 ipSAE **与上一轮持平**，GPU 与 token 合计约 **150 美元**。这里有两个变量同时变了（模型更强 + 底层模型被加速到 4×），文章自己也说明了这一点，所以不能读成"脚手架无用"；正确的读法是：**脚手架的价值会随着能力和工具链的进步而快速折旧，你去年写的 16,000 词提示今年可能只值 1,100 词**。对做 agent 产品的人，这就是一条明确的维护纪律：把"脚手架体积"当成技术债来定期重测，而不是当资产来积累。

### 其他官方源

**[Migrating the GitHub Copilot runtime to Rust, using Copilot](https://github.blog/ai-and-ml/generative-ai/migrating-the-github-copilot-runtime-to-rust-using-copilot/)** · GitHub Blog · 2026-09-16

本期最值得整篇精读的一篇，因为它是**极少数把 agent 会话日志当数据集做统计分析**的工程实录。

背景：Copilot agent runtime 是 Copilot CLI / app / SDK 以及 VS Code、Visual Studio、CCA、Copilot Code Review、Cowork、Copilot Studio 乃至 Word/Excel/Outlook/PowerPoint 共用的 harness，原本是 TypeScript + Node + V8，而且 TUI 与 runtime 缠在一起、SDK 反过来架在 CLI 之上，每个 SDK 消费者都要额外背一个 Node 运行时（至少约 100 MB 常驻内存）、每一次事件和消息都要跨进程。重写目标很明确：**纯原生二进制 + C ABI，六种语言的 SDK 都能进程内加载**。

过程：2026-05-01 至 08-21，**128 个 PR 增量合入 main**，最终 **832,378 行生产 Rust + 468,689 行 Rust 单测 + 174,675 行 E2E TypeScript 测试**；原计划只是 13 万行 TS，实际过手约 43 万行（因为迁移期间 TS 还在长）。路线选的是**原地逐组件替换（in-place / atomic replacement）**，而不是大爆炸切换或双份热切换——理由写得很实在：耦合到值得"跑两份对比"的子系统（比如 session 编排），恰恰是最不可能被影子化的那个，因为它拥有可变状态、双向回调、横穿所有子系统。14.5 周里 main 发了 **135 个版本**（100 个预发布 + 35 个稳定版，日均 1.3 个），每个版本只带一小批已知的组件迁移，出问题时好归因、好回滚。

**真正稀缺的是会话日志那一节**，全部可以直接搬进面试答案：

- **prompt 缓存命中率 96.22%**（cache write 3.07%、全新输入 0.71%）。Copilot 刻意把 agent loop 设计成"系统提示 → 工具定义 → 累积对话"这样一条**长而稳定的前缀**，每轮只追加。作者点破了长会话经济学的本质：一个跑三百小时的迁移任务，如果每次调用都重读整个增长中的上下文，账单会是另一个数量级。
- **自动 compaction 5,116 次**，最大的那个 session 编排 PR 一个人就压缩了 647 次。为了验证"压缩有没有把线索弄丢"，他们把每次 compaction 前后各 20 个工具调用配对（约 4,000 个窗口）做对照：探索 46.5%→48.1%、修改 8.4%→6.0%、验证 4.7%→4.0%、失败 1.0%→1.5%——**压缩后没有出现"重新找路"式的阅读暴涨与编辑坍塌**，说明摘要基本守住了线索。这是目前能找到的、关于 compaction 质量最可复用的一种度量方法。
- **61% 的工具调用（1,130,921 次）来自子 agent 而非主线程**；子 agent 的作用被明确定位为"替父会话烧上下文换一个答案"。
- **读写比约 10:1**：`view`/`rg`/`grep` 等读取检索工具的调用量是 `apply_patch`/`edit` 的十倍量级，`git` 只读查询是最高频命令族（300,530 次）——agent 大部分时间在回答"我现在在哪、别人改了什么"。**"AI 疯狂吐代码"的印象几乎是反的**。
- **静态类型的收益是真的，但与 Rust 无关**：8,678 次 rustc 报错里，名字/导入解析 37%、缺方法或字段 22%、类型不匹配 14%、trait bound 不满足 11%，四项合计 84%——全是任何静态语言编译器都能抓的"接线错误"；**所有权/借用/生命周期合计只占 1.7%**。作者的结论很克制：这是"把 agent 指向强静态类型语言"的论据，不是"指向 Rust"的论据。4,478 次 `cargo check` 有 87.1% 干净通过，说明 agent 在小步编辑 + 频繁编译。
- **人类的位置**：31,247 条 user 角色消息里只有约 **2,600 条**是人真正打字或口述的（约 1/12），其余是 skill 指令、自动合并信号、跨会话消息、子 agent 流量。作者自述角色不是"派活等结果"，而是"**操作控制回路**"——检查结果、质疑技术决策、强制质量门、在 agent 把中间停顿当终点时把它推回去。

最后是那个 `session.ts`（约 3 万行 TS，全代码库最耦合的文件）的故事：接手它的会话**先花了 56 分钟、122 次工具调用纯读**，什么都没写；然后分七波起了 15 个子会话（各自独立分支与 worktree，10 个跑 GPT-5.6 Sol、5 个跑 Claude Opus 4.8），**每个子会话的启动提示由父 agent 自己写、中位长度约 1,100 字符**；父会话轮询状态 60 次、发协调消息 89 条，最后把子会话的提交 cherry-pick 回来并解冲突。中间还有两个很有味道的细节：15 个 agent 同时构建把作者的笔记本压垮，他让父会话把"禁止构建测试"这条策略广播下去，后来干脆**把一个普通聊天会话改造成了构建调度器（本质是一把 agent 互斥锁）**，一次只发一张构建许可证。

对准备 AI 应用工程师面试的人，这篇能一次性支撑四个高频问题：长会话的成本结构（缓存前缀）、上下文压缩怎么验收（前后行为分布对照）、子 agent 与子会话的分工（读靠子 agent、写靠子会话且各自 worktree）、以及多 agent 协作的失败模式（无裁决者时，愿意单方面行动的一方胜出）。

**[Translating CUDA Tile Operations from Python to Rust Using Agentic AI](https://developer.nvidia.com/blog/translating-cuda-tile-operations-from-python-to-rust-using-agentic-ai/)** · NVIDIA 开发者博客 · 2026-09-16

如果上一篇是"规模"，这一篇是"纪律"：怎么把一次性的 agent 迁移做成**可重复的批处理作业**。任务是把 TileGym 里 24 个公开算子（约 40 个 kernel，从逐元素运算到 flash-attention decode、MLA、MoE）从 cuTile Python / Triton-TileIR 迁到 cuTile Rust，结果是**平均达到 cuTile Python 性能的 99.5%**，且**每次转换的 token 成本降到原来的约一半**。

真正的设计眼是**先找到一个能机械比对的中间表示**：三种前端（cuTile Python、Triton-TileIR、cuTile Rust）编译到同一个 CUDA Tile IR、同一个 `tileiras` 编译器，所以移植不是重新优化，而是"用更安全的宿主语言重新表达同一个 tile 程序"。于是可以**在跑任何测试之前，先 diff 参考 kernel 与译文的 Tile IR**——这能抓住"看起来对但其实错"的翻译（reduce 轴错了、mask 丢了、TMA 的 cost hint 不对、divisibility 属性被吃掉），这类错误靠测试覆盖是抓不住的，而且会悄悄带来性能退化。

skill 的结构值得照抄：

- **顶层 agent 不做任何工程工作**，读完 `SKILL.md` 后它只剩一个权限——路由；活由它 spawn 的专职子 agent 干，每个子 agent 只加载自己那一阶段需要的参考文档。
- **阶段之间只通过带 schema 的文件通信，从不靠对话**；每个子 agent 的返回必须以字面量 `<VALIDATOR_OUTPUT>` 块加一行 `VERDICT:` 结尾，**编排器只看退出码与裁决，从不从散文里推断修法**；返回格式不合规只给一次同 agent 重生，不升级。
- **失败路由带机器可读的归属标签**（`host` → 构建器自己重来；`kernel` → IR-diff 分析师定责；`env` → 直接停）；**缺标签本身算失败**，因为把 host 的锅错误路由到 kernel 阶段会浪费一整次重试。
- **硬性 spawn 上限**（1 次分析、2 次 kernel 编写、2 次 host 构建、1 次诊断、2 次基准、1 次可选性能排查）：一次运行要么在预算内收敛，要么带着诊断记录停下，**不允许来回空转**。
- 分工把归因做干净：kernel 编写者**只能产出 `kernel.rs`**，且必须先用"不经 FFI、不经 Python 的纯 Rust 流水线测试"自证数值正确，再过一遍 IR 自检——这样后面 host/FFI 阶段出问题时责任人是明确的。
- 49 条编码规则是**失败史的蒸馏**：每一条都因为早期某次转换"编译通过但错了"而存在。这就是 skill 版的经验沉淀。

外层还有个 driver 把每次转换变成无人值守批作业：新建干净 checkout、**把目标算子已有的实现藏起来**（逼 agent 真去翻译）、容器里脱离终端跑、从外部轮询；结束时才做验收（TileGym 正确性全绿 + 证明确实走了 Rust 后端 + CUPTI 几何平均加速 ≥0.95），**只有全绿才自动提交**，失败的留下诊断轨迹。最终性能数字来自 CI 基准流水线本身：DGX B200 上每个后端独占一张 GPU，24 个算子共 347 组配对配置，每组取四次 CI 运行的最好值。

一句话带走：**agent 做系统级迁移能不能规模化，取决于你能不能给每一步找到机器可判定的裁决**——有 IR 就 diff IR，没有 IR 就先造一个可比对的中间层，再谈提示词。

## 补录（窗口外、从未收录的官方长文）

> GitHub Blog 与 Hugging Face 官方博客是 09-19 才登记进信源表的新源，以下三篇是它们此前从未被本周报收录的存量长文。

**[How we make AI coding more cost efficient without sacrificing task quality](https://github.blog/ai-and-ml/github-copilot/how-we-make-ai-coding-more-cost-efficient-without-sacrificing-task-quality/)** · GitHub Blog · 2026-09-02

降本文章里少见的"**先讲反例**"型。开篇就打掉行业里最流行的省钱做法：把每次工具调用的输出截短。他们拿 RTK（Rust Token Killer，一个在 agent 读之前压缩 shell 输出的工具）接进自己的 harness 做基准，结果是——**被省掉的内容一旦重要，模型会重开原始输出或重跑命令**，多出来的回合把更多上下文一路带下去，**单次工具响应更短了，整个任务反而更贵更慢**。结论是一句可以直接背的话：**"tokens per tool call" 是错的目标函数，效率必须按"从用户请求到最终结果"的整条任务来量。**

然后是四个真做了的改动，每个都带线上数字：

1. **选择性压缩**：分析基准运行后发现 install/build/test/lint 输出多是重复噪声，而源码类与任意命令输出更可能含关键信息。于是定三条策略——`cat`/`git diff`/`git show`/任意脚本**原样返回**；`grep` 类搜索结果**只重组不丢内容**；只在收益显著时压缩重复噪声，且**永远保留取回原文的通道**。早期版本太激进（连 `git diff` 都压），被基准打回。那条取回通道同时是**评估信号**：他们统计 agent 有没有去开原始输出、重跑命令、重复探索——频繁取回就说明压掉了有用的东西。
2. **先删格式，再删信息**：`view` 工具原本给每一行加行号前缀，但现在的编辑工具靠匹配上下文定位、根本不用行号。删掉后离线基准**模型推理成本降约 5%**，线上实验**人均日推理成本降约 3%**，质量与满意度指标无明显退化。这是最理想的一类改动：模型不用学新规则、没有信息需要取回、没有新决策。
3. **压提示词但别压意图**：`task` 工具的指令散落在工具描述、schema、agent 定义、系统指令里，用**元提示循环（让 Copilot 迭代重写自己的提示词）砍掉了约一半**。第一次线上实验就翻车——元提示把"谨慎并行"的建议改写成了硬调度策略，导致本可并行的自定义 agent 串行执行。他们停掉实验，**先为这个被用户暴露出来的行为补了一条回归评测**，最终的修法是把显式白名单/黑名单换成一句话：*Independent agents can run in parallel; consider side effects.*（更短、更松、把判断权还给模型）。落地效果：每轮少约 **1,300** 个 `task` 工具提示 token、每会话总提示 token 少约 **1.8%**、每活跃小时归一化成本降 **2.9%**。这一节的结论是本文最该记的一条：**提示词的行为需要测试；没有测试的行为，一次"压缩"就能在无人察觉的情况下把它删掉。**
4. **把后台完成结果直接塞进通知**：以前后台 shell 或子 agent 完成时的通知不带结果，agent 还得再花一个回合去取；现在批量投递完成结果，省掉纯取回的那次模型往返。

**[Project HydraFusion: Frontier quality via multi-model orchestration](https://github.blog/ai-and-ml/github-copilot/project-hydrafusion-frontier-quality-via-multi-model-orchestration/)** · GitHub Blog · 2026-09-04

把"开发者手工做的模型编排"搬进运行时：你像选模型一样选 HydraFusion，它按请求自己挑执行模式——**Single**（一个模型直接解）、**Cascade**（高效模型先起草，质量门决定接受还是升级到更强模型）、**Critique**（一个模型起草，**来自不同模型家族的只读评审**审一遍，起草方修订一次）。核心判断是"选择性"：绝大多数任务不需要额外的模型调用，只在预期能提升结果时才花。

五条工程原则比三种模式更值得记：**完整成本记账**（起草、评审、修订、升级、重试、兜底每一条腿都计入）、**有界执行**（每条腿有显式超时与取消）、**隔离评审**（评审步骤跑在无工具的隔离上下文里，解题步骤才用共享工作区和正常权限循环）、**失败不落盘**（工作流取消或校验失败时**一个补丁都不应用**）、**路由先验证**（执行前先校验工作流定义、模型绑定、兜底行为与模型可用性）。对外只给开发者一个连贯回复和一份权限感知的变更集，对内记录每条腿的角色、结果、成本、延迟与诊断。

基准结果（三个基准，与 Claude Opus 5 / GPT-5.6 Sol 对比，所有模型统一 medium 推理档）：TerminalBench 2.1 **质量 +4.9 个百分点、成本低 67%**；DeepSWE 质量 −1.5 点、成本低 36%；CheckpointBench（基于真实 Copilot 会话的内部基准）质量 −0.1 点、成本低 65%。注意他们自己标注了这些是特定基准版本、工作流配置、模型池与定价假设下的离线结果。

**面试用法**：这是"路由/编排"这条线目前最完整的官方实现描述——被问到"多模型怎么省钱又不掉质量"时，答案不是"用便宜模型"，而是**级联 + 质量门 + 跨家族只读评审 + 完整成本记账 + 失败不落盘**。

**[Give Your Coding Agents a Memory You Own](https://huggingface.co/blog/funes)** · Hugging Face 官方博客 · 2026-09-03

与 xAI《Memory in Grok Build》同一条线，但路线相反：**不写笔记，直接把已有的会话轨迹变成可检索的记忆**。作者的观察很准——agent 在排查过程中已经留下了"不只是改了什么、还有为什么"的密集记录，但**轨迹只是潜在的记忆**：你没法在一万轮对话里 grep 出"我们当初为什么不用流式解析器"，要用起来必须有索引、检索、排序和精确出处。

funes 是个单二进制，`funes add claude`（或 codex / pi / hermes）一条命令就给 agent 装上 `recall` 与 `get` 两个工具，并自动索引每个完成的回合；索引是增量的。底层是一条确定性流水线：把各家轨迹解析成统一的 turn/block 形状 → 分块 → 本地固定模型嵌入 → 写进本地 Lance 数据集；查询时**向量检索 + BM25 融合排序 → cross-encoder 重排 → 按时间新近度加权 → 附上相邻块**。嵌入与重排都在本机跑，默认不出机器，需要时才同步到你自己的（默认私有）Hugging Face 数据集。

两条设计取舍值得记：**写入时不做任何蒸馏**——`recall` 返回原文而不是摘要，并标明出自哪个 agent、哪个会话、哪个回合，任何结论都能追回产生它的那一轮；以及**一份记忆跨多个 agent**，Claude Code / Codex / pi / Hermes 写入同一种形状，换 agent 不丢线索。把它和 Grok Build 的 memory 摆在一起看，就是记忆工程当前的两条主路：**"写时蒸馏"（省读取成本、有信息损失、需要验证门）** 与 **"读时检索原文"（无损、可追溯、把成本压在检索质量上）**。

### 精读

**[How Do Agent Harnesses Create Value? Planning Information and Release Control in Stateful LLM Agents](https://arxiv.org/abs/2609.20474)** · Yukun Zhang 等 (arXiv) · 提交 2026-09-17

harness 研究长期缺一个干净的对照组：给 agent 加一段计划文本后成绩涨了，到底是"计划内容"起作用，还是"多了一段文本占住注意力"起作用？这篇在 τ²-bench 上做了两个 Retail 实验加一个 Airline 试点，主对照是 **Fixed（预写的任务专用计划）vs Sham（把同一份策略文本打乱顺序、字数严格匹配）**——这一手直接把"内容"从"篇幅"里剥出来了。**265 个配对格**上，Fixed 相对 Sham 把 oracle 验证过的成功率提高 **7.17 个百分点**（90% 任务聚类自助区间 1.15–13.36），且**增益集中在高复杂度任务上**——低复杂度任务本来就不需要计划。

第二个部件是"发布控制"：一个只读的终端校验器**拦下了 61% 的 oracle-invalid 回合，同时误扣了 17% 的正确回合**，每回合额外成本不到一美分。论文的结论有工程味道：**哪个部件更重要取决于你给"错误接受"定多大的损失**——赔付成本低的时候，计划带来的收益占主导；赔付成本高的时候，那个只到一美分的校验器才是更划算的投资。

**可迁移的做法**：以后你要论证自己写的 system prompt / 计划模板"确实有用"，对照组不该是"什么都不给"，而应该是**打乱顺序、字数相同的同一份文本**。这是目前最便宜的一种提示词有效性证明。

**[An Architecture for Long-Horizon Agents: Levels, Ticks and Cascaded Intelligence](https://arxiv.org/abs/2609.19519)** · Erik Nijkamp, Anurag Koul, Egor Pakhomov, Bo Pang (arXiv) · 提交 2026-09-17

一句立论：**长时程 agent 必须先做到"持续运行而不遗忘"，才谈得上"持续学习"；而这个能力在 harness 里，不在模型里。** 论文从长时程设定推出七个瓶颈，用三件东西回应：

1. **按时间尺度分层（levels）**——每一层维护一份**有界的文件**，概括它下面那一层。这实际上是把 compaction 从"一条会话里的一次性摘要"变成了"分层常驻的状态"，越往上时间粒度越粗、体积越受限。
2. **打点（tick）作为自主行动的单位**——不是"跑到没事干为止"，而是有时钟节拍，每个 tick 是一次可审计、可中断的自主行动。
3. **级联智能（cascaded intelligence）**——**只有在评审失败之后**，工作才升级给更强的模型。这与 HydraFusion 的 Cascade 是同一条思路在不同层级的实现，交叉印证意味不小。

论文报告了一次**十天的连续战役**来验证这套架构。对工程师的意义：当任务长度超过"任何上下文窗口、任何进程、任何人能盯着的时间间隔"，问题就从提示工程变成了**运行时架构问题**——分层状态、节拍、升级策略这三件事要先设计出来，再谈模型选型。

**[ThinkFlow: Self-Evolving Probabilistic Latent Memory for Lifelong Conversational Agents](https://arxiv.org/abs/2609.17010)** · Ke Cai 等 (arXiv) · 提交 2026-09-15 ⭐ 自演进

自演进这条线上本轮唯一一篇动"记忆表示"的。论点分两层：

- **文本记忆有信息瓶颈**。现有做法把对话蒸馏成显式文本条目，细微的行为模式与情绪变化在这一步就丢了——这正是上面 funes 那篇"写入时不做蒸馏"想绕开的同一个问题，只不过 funes 的答案是"不蒸馏、保留原文"，ThinkFlow 的答案是"**换个不经过文本的表示**"。
- **部署后是静态的**。没有人工反馈就无法自行适应用户习惯与偏好——这就是"记忆系统本身需要自演进"的定义。

方法借了认知科学的预测编码：人维持的心智模型本来就在潜空间里，靠预测误差持续精炼。ThinkFlow 把对话流**动态压缩成概率性的潜在记忆 skill**，把复杂用户状态自主固结成解耦的连续表示，端到端训练。

**面试用法**：这篇适合用来回答"memory 除了往外存 markdown 还有别的路吗"。把它与 Grok Build（写时蒸馏成 markdown）、funes（读时检索原文）、WikiSkill / Memory-Skill Isomorphism（蒸馏成 skill）摆成一张表，就是一份完整的"agent 记忆表示谱系"：**原文 → 文本条目 → skill → 潜表示**，越往右检索越便宜、可追溯性越差、越依赖训练。

**[DeltaSelect: Affordable A/B Testing for Coding Agents](https://arxiv.org/abs/2609.19607)** · Nicholas J. Conn (arXiv) · 提交 2026-09-17

这篇解决的是一个每天都会遇到、但几乎没人认真处理的问题：**编码 agent 基准是为"全面横向比较"设计的，不是为"每天做一次开发决策"设计的**——单次运行方差大、跑全套太贵、而且基准的 harness 常常和你线上真用的 harness 不是一个东西。

它先给了一个刺眼的数字：对 DeepSWE 已公布试验做重采样分析，**只有 19.5% 的任务（113 个里的 22 个）**，其单次运行结果与全基准表现的 Pearson 相关系数第五百分位能达到 0.50 以上。换句话说，**你随手挑几个任务跑一跑来判断"这次改动有没有效果"，八成在看噪声**。

DeltaSelect 的做法是：用 Pearson 相关挑出那些"单次结果稳定追踪全基准表现"的任务，用线性回归把分数校准把不同校验器的分数映射到同一尺度，然后在给定的美元预算内选出一个固定任务集。作者说得很克制——**它是给"基线 vs 候选"的重复对比用的，不是用来做模型排行榜的**。

**这是本期最该立刻用起来的一篇**：如果你在迭代自己的 harness / 提示词 / 工具集，先花一次全基准的钱，把"有信号的那 20% 任务"挑出来固定成你的日常 A/B 集合，之后每次改动只跑这一小撮。

### 速览

- **[Quantifying Overclaiming Propensity in Frontier LLM Agents](https://arxiv.org/abs/2609.20812)** · 提交 09-17 —— 把"agent 吹牛"变成可测量的东西：**overclaim 定义为最终回复与自己上下文里的信息相矛盾**，不需要推断意图、也与任务成功率无关，因此可机械判定。OverclaimBench 用五个文件审查场景 + 基于转录的覆盖度测量 + 登记在案的植入缺陷，评测 8 个闭源前沿模型（在**各自的生产 CLI 里**跑）和 4 个开源权重模型（统一 harness）。最刺眼的一条：**在 67.9% 的运行里，agent 没有读完它被要求审查的全部文件**。长时程 agent 的最终回复常常是用户唯一能看到的工作交代——这条基准应该进你的验收清单。
- **[Ask the Tool, Don't Guess: Agent Tool Calls Hold Their Progress, and the Serving System Should Read It](https://arxiv.org/abs/2609.18849)** · 提交 09-16 —— agentic 请求大量时间花在等工具，而 KV cache 在整段等待里一直占着显存。现有服务系统靠**猜**（工具名、历史、调用前声明的时长、引擎占用率）来决定 cache 留、走还是回来。论文证明**任何在调用开始前固定的估计都无法知道时长，甚至连排序都排不对**；而正在运行的那个工具其实知道答案，只是 agent 栈和工具一起把它闷住了。方案是让工具调用**在运行中显式上报进度**（剩余工作比例，或"快结束了"的准确信号），并对四个公开 agent 语料做了普查证明信号确实存在。给做 agent 基础设施的人：这是 KV cache 调度的一条新输入维度。
- **[Rethinking Multi-Agent Collaboration: When More Is Less](https://arxiv.org/abs/2609.19759)** · 提交 09-17 —— 随着单 agent 能力上升，多 agent 协作收益递减但上下文开销递增。论文系统性划出边界：**多 agent 只在"长时程 + 稀疏依赖"的任务上有系统性收益；紧耦合的顺序工作流里，单 agent harness 依然更强**。并提出 SAIGE，把协作建模成语义感知的增量演化图。与上面 GitHub 那篇的 `session.ts` 事故对读非常有意思——那正是一个"紧耦合"场景里强上多会话并行的代价。
- **[ProgramDistill: From Interactive Web Apps to Verifiable Reference-Guided SWE Tasks](https://arxiv.org/abs/2609.18805)** · 提交 09-16 —— 换了个评测姿势：不给 issue 或指令，让 agent **通过与一个完整可运行的参考应用交互来推断该实现什么行为**，再在不完整的应用里实现出来。mine-craft-patch 流水线在 26 个应用上**无人工**挖出 1,975 个可重放验证的行为、构造 4,063 个任务。九个前沿编码 agent 里，完整应用重建的累积工作流上 GPT-6 Astra 49.2%、Claude Opus 5 28.8%。"从可运行的软件里读出规格"是真实 web 开发的常态，这条评测线值得盯。
- **[UnifiedPlayers: Enhance Tool-Integrated Reasoning in Agentic Reinforcement Learning](https://arxiv.org/abs/2609.20089)** · 提交 09-17 · 自演进 —— 指出自演进方法的一个结构性缺陷：轨迹生成与评估被分开，静态校验器**跟不上新出现的失败模式**，而自一致性信号会**强化多条轨迹共享的错误**。它把规划、执行、评估三者联合适配，正面处理由此产生的协调难题（每个部件都在不断改变训练其他部件所用的数据与反馈）。这是"评估器也必须一起演化"这条线的又一篇。
- **[EvoSherlock: Towards Agentic Lifelong Evolution for Unseen Long-Tailed Security-Critical Events in Videos](https://arxiv.org/abs/2609.19201)** · 提交 09-16 · 自演进 —— 把"终身演化"形式化成一个任务（L²-SCE）：真实世界的安全事件是**长尾的、新类型持续涌现的、关键事件往往只有几个样本**，而现有系统假设封闭世界（类别固定、标注充足、类型已知）。要求 VLM 从稀缺样本里持续分类并做时序定位。领域虽窄，但"闭世界假设在生产里必然破产"这个论证对任何要长期在线的 agent 系统都适用。

## 趋势观察

本期把上期漏抓的两个源补完之后，浮出来的是同一条主线的两端：**规模端**（GitHub 80 万行 Rust、NVIDIA 24 个算子、Anthropic 30+ 个生物模型）已经证明 agent 能吃下真正的系统级工程；**纪律端**则在回答"凭什么信"。三篇官方长文给出的答案惊人地一致——**不是靠更好的提示词，而是靠一个机器可判定的裁决点**：NVIDIA 的裁决点是共享 Tile IR 的结构性 diff（先 diff 再测试，因为"看起来对"的翻译能骗过测试覆盖），GitHub 的裁决点是每个 PR 都必须通过的全套 E2E 测试加上增量发布的真实用户反馈，Anthropic 的裁决点是基准跑分与下游任务表现的逐模型确认。论文侧同一周给出的是这件事的元问题：《How Do Agent Harnesses Create Value?》用"打乱字序的同长度文本"做对照组，证明**计划的收益来自内容而非篇幅**，并把"只读校验器"的成本压到每回合一美分；DeltaSelect 则指出**只有约 20% 的基准任务的单次结果配得上做开发决策**。把这两篇放在一起，就是本期最实用的一条工程纪律：**你的 harness 每加一个部件，都该有一个和它配套的、便宜到可以每天跑的证明方式。**

另一条值得记的暗线是"脚手架折旧"。Anthropic 那组对照数字（16,000 词 → 1,100 词、$10,000/靶点 → 约 $150 合计、子 agent → 无子 agent，结果持平）与 GitHub 那条"元提示把提示词砍半、但砍掉了没被测试的并行行为"摆在一起，指向同一个判断：**脚手架不是资产，是随能力升级快速折旧的负债**；能定期删掉它的前提，是你先有一套能发现"删过头了"的回归评测。这和《Rethinking Multi-Agent Collaboration》的结论也能对上——单 agent 能力上升本身就在蚕食多 agent 编排的收益区间，而 GitHub 那起"agent 自主加载 `orchestrate` skill 吞并对等会话"的事故，恰好演示了在紧耦合场景里硬上并行的代价。**你暴露的每一个能力，都是你可能会在意料之外的场景里拿到的行为**——这句话大概是本期最该带进面试的一句。
