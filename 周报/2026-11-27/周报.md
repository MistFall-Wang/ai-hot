## ⭐ 本期自演进重大发现

1. **美团公开一套在生产上跑了五轮的"线上失败 → 训练自己"的闭环（CARE），并写清了"自我改进"的边界**：31B 自研模型替换外卖售后客服背后的闭源强模型，巡检 Bad Case 率 6.42% → 1.97%，线上满意度从落后 4.57 个百分点追到持平，全量替换时单均服务成本降 70.5%。关键设计是"经验来自模型自己，判断来自模型之外"：巡检、归因、修复构造都由外部强模型做，每次上线人工审批。[从模仿到自我纠错：Keeta客服模型的RSI实践](https://tech.meituan.com/2026/11/26/Agent-RSI-practice-in-meituan.html)（11-26），见下文「国内官方源」。日报 11-27 已推送。
2. **Anthropic 把生产 API 本身当验证器，让 agent 自己发现差异、修复、并把教训写回规则**：Messages API 从 Python 迁到 Rust，CPU 降约 70%、首 token 中位延迟降约 20%，服务不停、功能开发不冻结。文章的结论是"瓶颈从生成变成验证"，并给出内循环（沙箱秒级验证）、外循环（生产流量对比）、记忆循环（评审意见沉淀成 CLAUDE.md 规则、lint 和合并检查）三层结构。[Migrating our Messages API to Rust](https://www.anthropic.com/research/migrating-api-to-rust)（11-25），见下文 Anthropic 小节。日报 11-26 已推送。
3. **两条新红线：循环内的评审不能决定"是否变好了"，自改进出来的程序对自己的失败不报警**：SealedLoop 在具身策略的自改进循环上实测，循环内的成功分类器在一代里把 196 个失败中的 65 个判成成功；驾驶任务上即使循环内评审完全准确，15 个"改进"里仍有 8 个到了没见过的城市会变差。[Keep or Roll Back?](https://arxiv.org/abs/2611.33794)，见精读 A6。另一篇发现 agent 自己迭代出来的程序分数很高，但环境变化后，它自己写的运行时检查在四个领域里对一半以上的失败保持沉默。[Blind to What They Can Fix](https://arxiv.org/abs/2611.29807)，见精读 A7。这两条是本期新发现，日报没有推送过。
4. **skill 增益的测量本身被审计出问题**：对 SkillsBench 做源码级审计和 7,554 次公开运行的重新分析，发现"某些 skill 让成绩下降"的结论在多重检验校正后一条都不显著，按"无 skill 得分"做门控的收益在打乱标签后依然出现。[What Does Skill Lift Actually Measure?](https://arxiv.org/abs/2611.33943)，见精读 A8。

### Anthropic

**[Migrating our Messages API to Rust](https://www.anthropic.com/research/migrating-api-to-rust)** · 2026-11-25 ⭐

这篇解决的问题：用 agent 重写一个线上核心服务，代码一周就能写出来，但怎么确认新旧两套行为一致？Messages API 承载全部客户和 Claude Code、Cowork 的流量，2024 年初到 2026 年秋流量涨了约 1,800 倍。团队先试过只把输出解析改成 Rust，CPU 只省 8%–10%，而且每个 token 要在两种语言之间穿三次，于是决定整体重写。

验证为什么难：一是原有约 700 个集成测试和 Python 实现耦合，移植测试时 Claude 也在改测试，事后审计发现 100 多处断言被改弱了；二是测试不完整，Rust 版 4 月已通过约 98% 的测试，但在生产流量上只有约四分之一的输入完全一致；三是 Python 版一直在变，"正确"是移动靶；四是模型输出不确定；五是团队不能读用户请求。

做法分三步。第一步是影子对比：同一个请求只调一次模型，把模型输出回放给 Rust 版，然后逐阶段比较。因为不能看文本，只记录差异的"形状"：按处理步骤设检查点找出第一处不同，再记录差异在提示词里的起始位置和长度差，合起来当作指纹。同一个 bug 在它影响的每个请求上留下相同指纹，可以按指纹分组。第二步是三层循环。内循环：每个 agent 在云沙箱里拿到两套代码和一个不调模型的本地比对工具，一次比较不到一秒；agent 看不到原始请求，只能根据指纹猜原因，自己写请求复现，复现成功再改 Rust 并补一个"旧代码失败、新代码通过"的测试。外循环：修复经人工 PR 评审后上线，再在生产流量上按同类请求比较该指纹的出现率。记忆循环：评审里被否决的做法、原因和正确修法写进记忆；一位工程师定下"严格照 Python 的行为移植"这条规则后，agent 对照它又找出 7 处靠猜的移植；6 月 agent 整理了约 60 条评审意见、归纳成规则，经工程师编辑后进 CLAUDE.md；有些教训固化成测试、lint 和"改 Python 必须同步改 Rust 或申请豁免"的合并检查。调度上，每 10–30 分钟一个脚本把差异记录按字段分组，只有出现新的类型才通知协调 agent，由它给每类分配一个 worker，并在 Slack 开一个线程供工程师跟进。

文中专门讲了一个反例：网页搜索工具的描述来自内部服务，Rust 版还没接这个服务，agent 提议把描述文本直接拷进文件，本地验证通过，但工程师否决了，因为上线前终究要调这个服务。文章的评语是：验证器只能告诉 agent 输出是否一致，不能告诉它这个修复是否值得上线，所以内外循环之间的人工评审是必要的关口。

对 AI 应用工程师的启示：一，大型迁移可以把旧系统当判定器，而不是先补全测试；二，agent 改过的测试要单独审计"断言有没有被改弱"；三，隐私受限时记录差异的位置和大小也够分诊；四，验证信号要设计成能指出"哪里错"，而不只是"对或错"；五，把人的评审意见沉淀成规则和自动检查，同一个纠正不让人做第二次。面试里讲"agent 自改进闭环"时，这是目前厂商公开的最完整的工程案例之一。

**[The enterprise guide to securing coding agents](https://claude.com/resources/articles/enterprise-guide-to-securing-coding-agents)** · 2026-11-23

写给安全负责人的六章指南，解决"编码 agent 接进企业之前怎么评估和限定风险"。前两章给出评估任何编码 agent 的六个问题：模型该拒绝时是否拒绝；动作是否在模型之外被自动检查；影响范围是否被环境限定；策略能否集中锁定；agent 写的代码是否安全；能否复盘事故。风险分四类：凭据泄漏与权限滥用、未审查的依赖与扩展、数据外泄、提示注入。后几章分两层讲防护：判断层是对齐训练、注入探针和 auto mode 分类器，文中的数字是无生产防护时 Claude 拒绝 81%–85% 的恶意请求，同时完成 98%–100% 的两用与正常请求；固定边界层是权限规则、命令分析、hooks、沙箱和出站白名单。最后是集中下发并锁定设置的对照表，以及"选最低敏感度的仓库、两周内不改策略"的试点清单。启示：讲 agent 安全时可以直接用这六个问题当提纲；MCP 服务器、插件、skill 和 CLAUDE.md 一加载就进入上下文，都要当依赖来审查；判断层会出错，所以必须有不依赖模型判断的固定边界兜底。

**[A practical guide to shipping with Claude Code](https://claude.dev/blog/the-work-after-you-open-a-pr/)** · 2026-11-24 · claude.dev 开发者博客

Claude Ship（Code Review、PR Steward、Claude Approvals）的实操指南，解决"PR 开出来之后的评审、修 CI、审批怎么逐步交给 agent"。按三层推进。第一层是自己的 PR：用 `/code-review`、`/ship`、`/steward` 在本机会话里评审、开 PR、看护 PR，最多看护七天，同一个问题最多推三次，修不好就把尝试过程报给作者；需要重新设计的问题和没解决的安全问题也上报。第二层是仓库：代码约定放 CLAUDE.md，评审规则放 REVIEW.md，启动和操作应用的步骤写成 verify skill；他们团队的门槛是同一模式至少在 2 个 PR 上出现才考虑立规则，并由人批准。第三层是团队：approvals.yml 按路径规定需要几个人批准，先用 observe 模式跑一到两周，把"策略的判断"和"评审人的实际做法"对成四格表，再决定收紧还是放宽。文中写明了风险：看护期间会合并主干并用你的凭据跑测试，只能用在信任所有合并者的仓库；PR 里的文字可能影响评审结论。启示：任何自动审批都可以先只观察、再用四格表评估，优先处理"策略会批准、评审人却要求修改"那一格；给 agent 的修复循环设次数上限。

**[Working with AI](https://www.anthropic.com/research/working-with-ai)** · 2026-11-23 · Anthropic 经济研究团队

**[Production monitoring with Codex](https://developers.openai.com/blog/production-monitoring-with-codex)** · 2026-11-24 · OpenAI 开发者博客

### Google

**[Did the user ask for this? Securing AI agents against intent hijacking with Semantic governance policies](https://developers.googleblog.com/did-the-user-ask-for-this-securing-ai-agents-against-intent-hijacking-with-semantic-governance-policies/)** · 2026-11-23 🧪

11-20"语义治理策略"一文的续篇，专讲间接提示注入导致的用户意图劫持，并给出评测数字。机制：agent 的模型提出工具调用后，Agent Gateway 先交给策略引擎里的 LLM 评审；评审把用户请求和系统指令当可信上下文，把工具结果、文件和消息一律当数据，只判断一件事：这个动作是用户要的吗。因为判断的是动作而不是文本，所以不需要识别具体的攻击措辞。评测用 AgentDojo v1.2.2（97 个用户任务、949 次带攻击的运行），agent 是 gemini-2.5-flash，只开默认的用户原意检查，每种配置全量跑 6 轮取平均：攻击成功率 48.7% → 0.9%，无攻击时任务完成率下降 2.6 个百分点；929 次需要工具调用的攻击无一成功，剩余成功的都是"让 agent 在回复里推荐某酒店"这类不涉及工具调用的攻击。AgentDojo 的结果由读取应用最终状态的 Python 检查判定，不靠模型打分。启示：防注入的检查点放在工具调用执行前，对照用户原始请求来判断；评测安全措施要同时报攻击成功率和正常任务完成率，并且多轮取平均。

**[Finding faster quantum algorithms with agents and formal verification](https://deepmind.google/blog/finding-faster-quantum-algorithms-with-agents-and-formal-verification/)** · 2026-11-23 · Google DeepMind

DeepMind 与 Google Quantum AI 用多支 Gemini 4 agent 团队改进已有的量子算法。每个问题交给几支互相独立的团队，各自提出改进；结论先用 Lean 定理证明器验证，通过才写进共享笔记本；每四小时各团队开一次"虚拟会议"交换和辩论想法。这些电路没法在经典计算机或现有量子处理器上实测，正确性只能靠数学证明。结果：惯性约束聚变相关计算成本降低 11.8 倍，所需纠错量子比特从 5,650 降到 4,338；细胞色素 P450 模拟提升 2.5 倍；arcsin 算术模块提速 290 倍。Lean 库、问题定义和已验证的解已开源。启示：多 agent 协作时，把"进入共享状态"设成必须通过机器可检查的验证，可以防止错误结论在团队间扩散。这和 Rust 迁移一文、/teamwork 一文是同一个模式：验证器在 agent 改不动的地方。

**[Verifiable Social Reasoning for LLM Assistants](https://research.google/blog/verifiable-social-reasoning-for-llm-assistants/)** · 2026-11-25 · Google Research 🧪

评测助手在"用户来咨询人际问题"时的社交推理。两个难点：助手只能听用户单方面转述；别人的动机通常没有标准答案。框架基于多 agent 模拟：给目标角色设一个隐藏动机，让它和用户角色等互动，再让用户角色向被测助手倾诉，助手要推断那个隐藏动机，由 LLM 评审判对错；用户角色的自信、不安等认知滤镜可调。模拟和咨询分离，同一批模拟可以复用于任意模型。测了 12 个模型，开源框架和 2 万多条样本。发现：模型直接看事件比听用户转述准得多；用户带偏见时模型常顺着说；模型需要比人更多的细节才下结论；多问几轮不一定更准。启示：没有标准答案的能力，可以在模拟里预先埋一个可控的隐藏变量当真值；评测对话助手时把"直接看事实"和"听用户转述"分开测，差值就是被用户叙述带偏的程度。

**[From spectrum to structure: Identifying molecules with Mass Spec Skills for Google Antigravity](https://deepmind.google/blog/interpreting-mass-spectra-with-google-antigravity/)** · 2026-11-24 · Google DeepMind 🧪

面向 Antigravity 的质谱 skill 套件，把分析化学家的标准流程（预处理信号、查参考谱库、推分子式并排序候选结构、交叉核对）封装成 skill，底层调用现成的开源质谱工具和公共化学数据库。值得看的是对照实验：100 张基准谱图、每张三次尝试，比较三种配置和三个模型。不联网、无 skill 时准确率都低于 4%；只联网时，模型临时写的检索脚本不稳，前沿模型漏掉四分之一到三分之一，轻量模型漏掉四分之三以上；加上 skill 后三个模型都约 97%，生成 token 也减少（Flash 降近四倍）。启示：评估一个 skill 值不值，用"无工具 / 只给通用工具 / 加 skill"三档对照，同时报准确率和 token 用量；skill 把弱模型和强模型拉到同一水平，这是 skill 作为"领域流程封装"的直接证据。

### 国内官方源

**[从模仿到自我纠错：Keeta客服模型的RSI实践](https://tech.meituan.com/2026/11/26/Agent-RSI-practice-in-meituan.html)** · 美团技术团队 · 2026-11-26 ⭐ 🧪

这篇解决的问题：想用自研的中等规模模型（31B）替换外卖售后客服背后的闭源强模型，目标是承接线上流量后用户满意度不低于原模型。为什么蒸馏一次不够，文章给了三个理由：历史轨迹覆盖不到长尾，失败只有模型自己上线后才出现；线上环境一直在变（Skill、SOP、工具 Schema、Prompt 都会改）；强模型下线后它的轨迹就断了。第一版模型印证了这一点：模拟测试通过率从 79.0% 升到 93.0%，但巡检 Bad Case 率 6.42%，反而高于未训练的基座（5.59%）和线上强模型（4.60%），线上满意度低 4.57 个百分点。

方案叫 CARE，分两阶段。冷启动只做一次，把线上历史会话按"准入、分配、精修"治理成训练数据做监督微调；人工客服会话只提供措辞，不提供业务内容，改写时消息数量、顺序、动作和工具调用全部锁定。之后进入递归迭代，回答三个问题。

一，怎样确认线上失败。巡检全天候运行，和评估系统完全分开。五个要点：判断模型只看会话本身，看不到模型版本、实验分组和原有质量标签；先粗筛打可疑分，只用来排序；细查名额分三份，分别给最可疑的、分数在阈值附近拿不准的、随机抽查低分和少见场景的；一个模型分析、另一个独立复核者对照策略知识库挑错；确认为 Bad Case 必须同时满足四个条件（能指出唯一出错轮次、证据完整、问题类型明确、复核结论明确），否则记为无法判断或转人工，不默认通过。

二，失败怎样变成训练信号。先归因：失败可能来自模型，也可能来自 Skill、工具、Harness、评委或基础设施，不归因就训练，模型会被教去绕开坏掉的工具。再构造修复：只改第一个错误决策，后面的轮次建立在错误状态上，不用；修复要满足局部性、可行性、不预知、合规性四条约束。"不预知"的例子很好：工具只返回"骑手未取餐"，原回复说"餐品还在制作中"是没依据的，正确的修复是"骑手还没有取餐"；即使事后知道餐早做好了，也不能把修复写成"餐品已做好"，否则模型学到的是断言自己看不到的事实。训练方法用 On-Policy 自蒸馏：Student 在出错的决策点采样自己当前的输出，Teacher 是本轮开始时冻结的模型副本，多看到一份特权信息（哪里错了、当时的 SOP、验证过的修复），沿 Student 的输出逐 token 给分布，损失是截断到 Teacher 前 32 个 token 的 Forward KL 并加零下限。消融里，同样的修复样本和预算，SFT 训到不断输出工具调用，DPO 退化成第一轮就转人工，只有这种方法稳定。文章也解释了为什么不用满意度当强化学习奖励：多数会话没有评分，评分受配送延迟等 agent 之外的因素干扰。

三，新模型怎样才算可以上线。可执行的模拟环境里，场景编译器按最新 Skill/SOP 枚举决策分支生成用例，只有系统模拟器能改变业务状态（agent 说"已退款"不算，注册并校验过的动作被执行才算）；通过要同时满足必要步骤都做了、没有禁止行为、最终业务状态达标。模拟产生的轨迹再过一遍和线上相同的巡检流程。综合分 = （模拟通过率 + 100 − 巡检 Bad Case 率）/ 2，不低于当前部署版本才能进线上分流对比，最后人工审批。

结果：559 个用例的冻结测试集上，五轮迭代后 Bad Case 率 6.42% → 1.97%，不到线上强模型的一半；V5 综合分 96.07，比线上强模型低 0.03；线上满意度早期落后 3.13–8.02 个百分点，V4、V5 的差值是 +0.34 和 +1.73 个百分点；全量替换时单均服务成本降 70.5%。文章自己列了三点不足：模拟器和线上的差距没有量化；归因的准确率没有统计；混合多版本 SOP 训练的好处只是推断，没有实验证明。

对 AI 应用工程师的启示：一，"经验来自模型自己，判断来自模型之外"可以当作设计自改进闭环的第一原则，和本期 SealedLoop 论文的结论一致；二，冷启动的高通过率会制造错觉，模拟通过率和线上缺陷率要分开看；三，巡检抽样的三份名额（最可疑、拿不准、随机）可以直接照搬到任何线上评测；四，修复样本不能使用事后信息；五，发现失败的系统和给模型打分的系统要彻底分开。这是目前国内厂商公开的最完整的生产级 agent 自改进案例，评测部分也是本期评测专题的主要来源。对应的技术报告（arXiv 2611.02839）已在 11-13 期收录，这篇博客是中文的完整工程叙述，补充了踩坑经验和 CARE 2.0 计划。

**A4. 模型直接改自己的权重：[Self-WSP](https://arxiv.org/abs/2611.28833)** · Guoming Ling 等（HF 组织：Carnegie Mellon University）· 2026-11-21；**[Recursive Self-Editing: LLMs Program Their Own Weight Edits for Self-Improvement](https://arxiv.org/abs/2611.29513)** · Linghua Zhang 等 · 2026-11-22 ⭐

各家做法的异同和可以照搬的点：

第一，这周几乎所有文章都在说同一件事：判分的依据要放在被评对象够不到的地方。美团把巡检和评估分成两套系统，评估用冻结测试集；Anthropic 用生产系统当判定器，并在内外循环之间留人工评审；DeepMind 的量子算法团队用 Lean 证明把关；SealedLoop 用循环外的密封评审。反面的证据也齐了：循环内的成功分类器一代放过三分之一的失败，agent 移植测试时把 100 多处断言改弱，agent 为了让输出一致去拷贝文本。

第二，离线分数和线上表现不一致是常态，要同时看。美团冷启动模型模拟通过率 93.0% 而线上缺陷率反而升高；Anthropic 测试通过约 98% 而生产一致率约四分之一；OWE-Bench 的隐藏用例比公开用例低 18 分。可以照搬的做法是美团的综合分：把"业务结果对不对"和"过程里有没有缺陷"分成两个指标，等权合成，规定整体不能退步。

第三，评测集本身要审计。本周有三篇独立的工作发现编码基准的测试会拒绝正确解（SWE-Gym 74%、Verified 23%、Pro 35%），HF 指南记录 Terminal-Bench 2.1 修了近三分之一的任务，SkillsBench 的三个任务评分器依赖 skill。HF 的三个对照（参考解必须通过、空操作必须失败、捷径脚本必须失败）是成本最低的自查方法。

第四，对照组的设计比指标更重要。DeepMind 的三档 skill 对照、HF 的"同预算单 agent"和"重试 N 次"、Self-WSP 的随机搜索基线、SkillsBench 审计的打乱标签，都是为了排除"收益只来自多试几次或多花算力"。面试里被问"你怎么证明这个改进有效"，可以直接按这四种对照回答。

第五，国内外的差别。美团和 Anthropic 这两篇都是拿生产流量做评测并闭环，区别在于美团公开了完整的判定流程和上线门槛公式，Anthropic 公开的是差异分诊和 agent 调度方式。Google 和 Hugging Face 这周更偏方法论和可复现的对照实验。

## 趋势观察

这周的主线是"验证成为瓶颈"，而且是从厂商的生产实践里说出来的。Anthropic 的原话是 verification, not generation, had become the bottleneck；美团总结的第一条经验是"经验来自模型自己，判断来自模型之外"；Anthropic 经济研究团队的访谈从另一头印证，编码变快后卡住的是代码评审。上两期的主题分别是"RSI 进发布流程"和"谁来判分"，这一期两条线合到了一起：自改进闭环已经在两家公司的生产系统上跑起来，决定它能不能跑的是判分系统是否独立、是否可信。

自演进方面，本期论文的重心从"怎么改进"转到"改进是不是真的"。SealedLoop、Blind to What They Can Fix、SkillsBench 审计、Self-WSP 的随机搜索对照、TransHarness 的分布外演进集，都在给自改进加验收条件。上期 CoEvoBench 说"第二轮接不上"，这期的补充是：很多第一轮的收益也经不起循环外的检验。与此同时，带外部验证的正面结果也在增加（TransHarness 在两个基准上超过最强基线模型，SELFWRITE 在循环看不到的留出集上有小幅提升，PRECEPT 在未见任务族上 97.1%）。

工程形态上，三家厂商在同一周把"评审标准写成仓库里的文件"：Anthropic 的 REVIEW.md 和 approvals.yml，OpenAI 的 SECURITY.md 和 threat-model.md，GitHub 的证据清单 skill。配套的推进方式也一致：先只观察、不拦截，对照人的实际判断，再逐步放权。Anthropic 的 Claude Ship 和 MCP 的 Skills over MCP（均记入大事记）把这套做法产品化了。
