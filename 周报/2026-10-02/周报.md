### Anthropic

**[Automating eval design and hillclimbing with Claude](https://claude.dev/blog/automating-eval-design-and-hillclimbing/)** · Anthropic（claude.dev 开发者博客）· 2026-09-28 ⭐

**这篇解决什么问题**：有了 eval 才能知道应用或 skill 好不好，但 eval 很容易设计错；照着 eval 改系统，又很容易把分数改上去而生产没变好。这篇先讲原则，再讲 claude-api skill 新增的两条命令怎么把原则落成流程，最后给两组实跑数据。

**好 eval 的四个特征**：

1. **任务镜像生产**。不要因为好生成、好打分就选某类题。
2. **更强的模型、更高的 effort 应该得分更高**。如果不是，通常是题目有歧义或 grader 没校准。
3. **前沿留有"可通过的"余量**。最强模型开最高 effort 应明显低于 100%，否则看不出改动的影响；但这个差距不能来自不可能或有歧义的题。判断方法：一道题无论重复多少次都失败，多半是题有问题。
4. **重复运行方差低**。方差的来源有三个：题目歧义、grader 对同一输出给出不同结论、配置（effort 没有一致生效；上一轮留下的文件或 git 历史把答案递给了 agent）。

**一个容易踩的坑：对抗式取样**。模型能力是锯齿状的。如果专挑"当前模型做不对"的题，测到的是这个模型的失败指纹，而不是任务本身的难度。正确做法是因为**人判断它难**才选，并且能说出难在哪。只从用户流量取样也不行：用户倾向于只试他们觉得能成的事，分布会偏易。

**`build-eval` 的流程**：

- **取样顺序**：生产记录（先问数据留存与敏感性）→ bug 报告与工单 → 手写 5–10 条 → 从代码库合成。生成一个页面让人逐条确认输入。
- **选最便宜的 grader**：输出空间受限就用代码校验（精确匹配、固定标签、JSON schema、测试通过）；开放式输出才用 LLM judge，rubric 写成**可逐条核对的陈述**而不是 1–5 分；有基线时让 judge 盲比两份输出、顺序随机；**judge 不能是被测模型**。
- **先验证 grader**：评几条，问人"哪条你会打不一样的分"。文中直说，评分错误是 eval 配置出错最常见的原因之一。
- **基线运行时的三项诊断**：同一输出让 grader 跑两次看结论变不变；检查超时、API 错误、截断，避免把基础设施噪声当成模型方差；基线已到约 95% 就提醒"余量不够，去优化成本或延迟"。

**`hillclimb` 的流程**：

- **选什么来爬**：改起来便宜（prompt、skill 这类文本）、分数变化能归因到被改的面（例如 skill 触发率对 skill 描述）、目标收得窄。**成本是一个通用的好目标**：eval 饱和了也可以要求"性能持平、成本更低"。
- **防过拟合三条**：把用例拆成 hillclimber 能读的 train 和永远不看的 test；**不把失败内容贴进 prompt**；答案在结构上放在模型够不着的地方。文中的例子：eval 里某题受益于 OCR，hillclimb 就给 harness 加了个 OCR 工具，基准涨了，生产毫无变化。
- **每轮只提一个改动**：读上一轮 train 轨迹，修根因（重写导致问题的那一节、补一条缺的规则），不做措辞微调。train 涨、test 不涨 → 判为过拟合并回滚；有回归 → 回滚；都涨才保留。
- **开爬前先量噪声**：如果分数靠运气就能波动的幅度大于你愿意采纳的最小提升，先加重复次数或用例。
- **停滞两三轮时不改东西，只分桶**：把剩余失败按原因归类。这一步能抓出有歧义的题、harness 错误和纯粹的运行方差。
- **收尾**：代码停在 test 上最好的版本，报告带置信区间；收益在噪声内就明说并建议不合并。

**两组实跑数据**：

| 案例 | 起点 | 过程 | 终点 |
|---|---|---|---|
| 内部客服基准（44 张工单，30 张搜索 / 14 张留出） | Opus 4.8 high，74.4%，4.6 美分/张 | 审计 prompt（删掉强制工具调用仪式、scratchpad 步骤、互相矛盾的规则）→ Opus 5.5 low：87.8%，1.9 美分 → Sonnet 5 low：88.9%，1 美分 → 加路由规则和退款上限交叉引用：98.9% | **留出集 90.5%（原配置 78.6%），成本约五分之一** |
| claude-api skill 自身 | 66.1% | 补 8 个缺失特性 → 74%；修 C# / Java 类型表 → 77%；停滞后分桶 → 80%；修掉题目和 grader 自身的错 → 约 88% | **87.9%** |

第二个案例里"分桶"那一步值得细看。Claude 发现 skill 里内容是有的，但模型**凭训练先验写出旧的 API 形态**（例如固定 token 预算的 extended thinking，新 Opus 模型已拒绝）。修法是在 skill 顶部加一张"你记得的旧写法 → 现在的写法"对照表。另外有两道题是 eval 自己错了：一道题要求捕获一种错误，grader 却要三种；另一个 grader 的要求与文档矛盾，实测 API 证明文档是对的。

**对 AI 应用工程师的启示**：这篇可以当面试里"你怎么做 eval / 怎么防止 prompt 调优过拟合"的标准答案骨架：①取样从生产来，难题由人判断；②grader 先验证再信；③先量噪声；④train / test 拆分，一轮一改，test 不涨就回滚；⑤停滞时先怀疑 eval 本身。它也和本期论文侧的结论互相印证：下文《Do Self-Evolving Skills Generalize?》说"单次编辑有没有用只能靠跑"，这里的做法正是每个 patch 都跑留出集。

**[How we made claude.ai 3x faster in two weeks](https://claude.dev/blog/how-we-made-claude-ai-faster/)** · Anthropic（claude.dev 开发者博客）· 2026-09-23

**这篇解决什么问题**：用户抱怨 claude.ai 慢。团队 8 月做了两周冲刺，所有工作在一个 Slack 频道里进行，每个 thread 里都有 Claude（Claude Tag beta，内部研究模型，大致相当于 Opus 5.5）。这是目前最完整的一份"**让 agent 在生产代码库上持续 hillclimb**"的官方复盘。

**结果**（真实用户监控 p75，08-13 对 08-27）：claude.ai 首次加载到可输入 3.1 秒 → 0.55 秒；新建 Claude Code 会话 0.8 → 0.3 秒；加载 Cowork 云会话 2.6 → 0.73 秒。**合入三千多个改动，没有一次面向客户的事故或回滚。**

**怎么起步**：频道里放一条常驻指令，把 Claude 的职责写清楚（盯部署回归、评估遥测是否准确完整、维护仪表盘、主动修、提项目、和人沟通）。Claude 通过 Datadog MCP 分析使用数据，定出占 95% 用户活动的四条旅程、13 个测量点。人挑了约 20 个项目，Claude 估每个项目能省多少毫秒，汇总成目标。**第三天就达成 13 个目标里的 12 个。**

**核心方法："能数的东西都能爬"**。墙钟时间是用户感受到的，但噪声大，毫秒级波动没法当 CI 闸门。于是他们找**确定性的替代指标**：

- 纯 JS 热路径：用 Valgrind + `node --predictable` 数 CPU 指令数，一次运行就够，不需要统计；
- 浏览器路径：每次交互的 React commit 数、V8 函数调用数、样式重算次数、DOM 变更数。

每个新基准要干两件事：在实验室里让 Claude 有个数可降；进 CI 当**只能往下走的棘轮**。而且必须先证明它和墙钟时间相关，证明不了就下掉，免得 Claude 爬错山。例子：两条热路径指令数降 48% 和 31%，墙钟降了 78% 和 44%，于是这两个棘轮进了 CI，之后任何抬高指令数的 PR 直接失败。

文中把这条总结为冲刺的中心教训：**有了 Claude，测量本身让问题变得可解**。以前加指标是第零步，要等数据回来才能开始理解问题；现在它是爬坡的第一步，所以杠杆最高的事是"找更多能测的东西"。

**每个 thread 的循环**：有人开 thread 指出某段慢 → Claude 追踪流程，找到或造一个能复现问题的基准 → 实验室里有结果后提 PR（按风险拆小，用户可见的改动放在 flag 后面）→ 上线后 Claude 盯部署、读线上数据 → 变好就把棘轮拧紧，没变好就关 flag 再来 → 继续找同一旅程的下一个慢点。同时在跑的 thread 超过 150 个，单个 thread 会提 50 到 100 个 PR，最忙的日子一天合入 200 多个改动，约三分之一的 PR 带新的遥测或护栏。

**Claude 找到的几个问题**（都是人不容易想到去量的）：输入框的打字路径上有 6,900 个 hook 和 900 个 store 订阅，每敲一个键都重渲染；一个 `:root:has()` 选择器让每次 DOM 变更多花 24 毫秒；一处遗留的 `location.reload()` 每天造成五十万次用户看不见的重载；回复里只要有一个破折号或弯引号，V8 就把整个字符串存成 UTF-16，语法高亮的正则全走慢路径，修复只有 20 行。

**护栏**（提前建好的）：每个 PR 过自动审查 + 至少一个人批准；先有单测再优化；可能影响用户的改动都放在短命 feature flag 后面（两周新增近 200 个 flag，过半在结束前已清理）；高风险改动按员工 → 1% 用户 → 全量灰度。

**人做什么**：定方向和做取舍。每个 thread 故意收得很窄（一个基准或一条旅程）。一个 900 行的 PR 得到的回复只有一句："每次发送省 2 毫秒，不值得为它维护这个构建插件。"

**对 AI 应用工程师的启示**：①想让 agent 长时间自主优化，**先给它一个确定性的、能在本地跑的数**，再证明这个数和真实目标相关；②**每个被证明的收益都变成 CI 棘轮**，否则在快速迭代的代码库里会退化；③并行靠"多开窄 thread"，不靠一个大任务；④自主程度高的前提是 flag、灰度、人工批准这些护栏先到位。这和上面 hillclimb 一文是同一方法论在工程规模上的版本。

**[Using Claude Code: Spending your effort](https://claude.dev/blog/spending-your-effort/)** · Anthropic（claude.dev 开发者博客）· 2026-09-25

**这篇解决什么问题**：effort 参数到底调的是什么、什么时候用哪一档。作者读了评测结果并亲手对比了多种任务。

**结论一句话**：effort 调的是模型**做多少验证和边界测试、自己拿多少主意**。把它想成给人的时限：同一件事给 12 小时和给 1 小时，交回来的东西和期待的迭代方式都不同。

**日常开发的三个小实验（Opus 5.5）**：

- **需求模糊的构建任务**（"做个健身记录应用"）：low 只有日志和一张简单图表；effort 越高功能越全，同时 Claude **替你做的决定也越多**。
- **轻度指定的设计任务**（重做 `/config` 菜单）：low 用 1 分钟给出能说明想法的交互草图；max 用 28 分钟给出很像 Claude Code 的成品稿和多条流程走查。想快速反馈就用 low。
- **高度指定的任务**（先让 Claude 访谈出完整 spec）：各档产出很接近。

作者据此推荐的循环：**让 Claude 访谈你补全 spec → low 实现 → 人看方向对不对、low 迭代 → high 做验证和测试。**

**难任务上 effort 帮在哪**（Terminal-Bench 3.0）：**隐藏边界情况多的任务受益最大**。`html-js-filter`（写一个 HTML 净化器）上 Fable 5.1 从 low 的 1/5 升到 xhigh 的 5/5：low 约 2 分钟，一遍写完、用一个手写页面测；high 约 33 分钟，对抗式审查初稿、读解析器源码、跑标准 XSS 测试集、最后写了个随机文档 fuzzer。

按领域看 Fable 5.1 从低档到最高档的通过率：安全 64% → 87%，硬件 34% → 75%，ML 54% → 73%，科学 41% → 61%，软件 43% → 56%，媒体 18% → 30%，运维 12% → 22%。

**effort 修不了什么**：失败归因图显示，Fable 5.1 从 low 到 max，通过数 140 → 214（共 370 次），"测试没覆盖到的 bug"从 40 降到 14；但"**选错了对需求的理解**"从 25 升到 47。也就是说，effort 减少的是漏掉边界情况的失败，方向选错它不管。

**对 AI 应用工程师的启示**：把 effort 当成"验证预算"来分配。需求没说清时加 effort 只会让模型替你做更多假设，先把 spec 补齐更有效；安全、硬件、性能、代码审查这类边界多的任务值得高档。另外文首提到一个工程细节：在 Claude Code 里调 effort **不会打破 prompt 缓存**。

**计价与规格**：每百万 token 输入 $2、输出 $10、缓存读 $0.20、5 分钟缓存写 $2.50、1 小时缓存写 $4，与 Sonnet 5 完全相同；因为完成同样的工作用的 token 更少，多数工作成本最多低 30%，速度快 30%。1M 上下文原生支持，最大输出 128k。**最小可缓存 prompt 从 1,024 降到 512 token**，更短的系统提示和工具定义也能缓存。API 默认 effort 是 high，Claude Code 里是 medium；文中提醒，如果想开 xhigh 或 max，可能已经丢掉 Sonnet 的性价比，该考虑 Opus 5.5。

**迁移时的破坏性变更**（文中列了五项，另有一项响应形态变化）：

1. **思考默认开启，且不能关**：`thinking: {"type": "disabled"}` 返回 400。改用新的 `between_tools`（只在工具调用之间思考）。它只支持 low / medium / high，不能带其他字段，对话中途不能改 effort。
2. **强制 `tool_choice` 被移除**：`any` 和 `tool` 返回 400。改成 `auto` + 把工具标 `strict: true` + 在 prompt 里说明何时用它。
3. 对话保持只追加（append-only）。
4. computer use 改到 toolset 里。
5. 检查 advisor 配对。
6. 工具调用之间的文字从 `thinking` 块里读。因为响应可能以 `thinking` 块开头，**读 `content[0].text` 的代码会坏**，要按块类型遍历。

**调优建议**：重跑 effort 扫描；删掉为 Sonnet 5 写的变通提示；low effort 下明确要求"真的跑检查"；要进度就读 `thinking.display: "summarized"`，**不要让模型在回复里写出推理过程**（会触发 `reasoning_extraction` 类拒绝）；请求之间改顶层 effort 会让缓存失效，单轮换档用 per-message effort（beta）。

**拒绝的形态**：被拒的请求返回 HTTP 200，`stop_reason: "refusal"`，`stop_details` 给出五类之一：`cyber`、`bio`、`frontier_llm`、`reasoning_extraction`、`general_harms`。服务端回退（beta）只对 `cyber` 和 `frontier_llm` 两类重试到 Sonnet 5。

**对 AI 应用工程师的启示**：两处接口变化值得记住，因为它们代表方向：**强制工具调用退场**（靠 strict schema + 提示），**关思考退场**（最多只能关"开头那一段"）。写客户端时别再假设第一个内容块是文本，别把拒绝当异常处理（它是 200）。`reasoning_extraction` 这个拒绝类别和本期 OpenAI 披露的蒸馏行动是同一件事的两端。

**[Getting the most out of Opus 5.5 in Claude and Claude Code](https://claude.dev/blog/getting-the-most-out-of-opus-5-5/)** · Anthropic（claude.dev 开发者博客）· 2026-09-22

**这篇解决什么问题**：Opus 5.5 有三点和前代不同：能独立工作更久、会直白地汇报做了什么、每次回复前都思考。这篇是面向使用者的操作指南，每条都按"做什么 / 为什么 / 怎么做"写。

**提问**：

- **一条消息交代完整任务，写明"完成"长什么样、什么时候停下来问**。例："迁移支付端点到新客户端。完成 = 每个端点都用新客户端、旧客户端已删除、测试通过。只有测试失败且你解释不了原因时才停下来问我。"
- **删掉"仔细思考""一步步想"**。模型每次都会思考并自己决定想多少；测试里删掉这类句子，回复开始得更快，质量没有明显下降。
- **设计类请求要列出不想要的具体样式**。"避免千篇一律"只会换一种默认风格；列"不要米白背景、不要标题里的斜体强调词、不要 01/02/03 编号、不要等宽标签、不要药丸按钮"才有效。

**驾驭长任务（Claude Code）**：

- 在 CLAUDE.md 里写清**哪些停顿你要、哪些不要**：不需要我输入就继续，状态说明和下一步动作放在同一条消息里；只有无法继续或要做破坏性操作（删数据、force-push、改仓库外的东西）时才停。
- 大型审计或迁移，让它**拆给子 agent 并核对每个子 agent 的证据**，最后汇成一张表。
- 让它把**任务清单写在文件里**并随时更新。长任务会触发上下文压缩，文件里的清单不受影响。

**检查结果**：先看"它需要你做什么"，再看其余总结；让它审 diff 时要求"只列你会拦住合并的问题，给出文件行号、为什么错、怎么证明它会失败"；研究类任务加一句"标出你没能确认的内容，并说明查过哪里"。

**对 AI 应用工程师的启示**：这份指南反映的是模型代际变化对 prompt 的要求变了：**过程性指令（怎么想）在减少，边界性指令（做到什么算完、何时停、哪些不能碰）在增加**。给自己的 agent 写系统提示时可以直接套这个结构。

**[Getting started with Claude Code mods](https://claude.dev/blog/getting-started-with-claude-code-mods/)** · Anthropic（claude.dev 开发者博客，Addy Osmani）· 2026-10-01

**这篇解决什么问题**：10-01 Claude Code 开放了 mods。设置、权限规则、slash 命令、skill、状态栏都只能"配置"Claude Code；mod 可以**改写或替换它的行为，还能画自定义界面**。这篇从空文件夹写一个约 80 行的 mod（Token Weather，在输入框上方显示上下文窗口占用）。

**mod 是什么**：一个普通插件，行为写在一个 JS / TS 模块里。模块导出 `register(on, options)`，用 `on(event, matcher?, hook)` 挂钩子，每个钩子的签名是 `($, e, next)`：`$` 是 mods API（ui、session、state、store、fs、process、http、tool、command、model 等），`e` 是事件输入，`next` 把事件交给链上的下一个插件，最底层是 Claude Code 自己的行为。

**钩子是一条中间件链，能做三种事**：

| 动作 | 写法 | 例子 |
|---|---|---|
| 观察 | `const r = await next(e); return r` | 记录每次文件编辑、每轮结束后取一次读数 |
| 改写 | `return next({ ...e, command: safer })` | 改变链上后续看到的内容 |
| 应答 | 不调 `next`，直接 `return { deny: "…" }` | 拒绝一次工具调用，或自己实现一个命令 / 工具 |

事件覆盖工具调用、提交的 prompt、轮次开始与结束、会话开始与结束、slash 命令，以及 `ui.render`（界面每一块被绘制时）。

**和 settings hook 的区别**：settings hook 是每个事件起一个 shell 命令，经 stdin / stdout 传 JSON；mod 加载一次、常驻会话，能**保存状态、随事件更新界面、反过来调用 Claude Code**（开面板、跑进程、注册 slash 命令、注册一个模型可调用的工具）。

**两个值得知道的事实**：Claude Code 自己的一些功能就是用 mod 写的（AGENTS.md 支持、`/diff` 面板），源码和测试在公开仓库 anthropics/claude-code 的 `mods/` 下；教程说模块跑在没有 DOM、没有 Node 的独立运行环境里，对外一切经 `$`，但同日的产品公告也说明 mod 的权限等同 Claude Code 本身，团队版和受管设备上有一个最先加载的内置 `sec-default`，阻止用户 mod 覆盖权限拒绝规则。

**对 AI 应用工程师的启示**：这是"**harness 可编程化**"的一个具体形态：把 agent 循环的每个事件开放成中间件链。自己设计 agent 平台的扩展点时，"观察 / 改写 / 应答"三分法和"安全类钩子最先加载、最后看到结果"的顺序约定都可以借用。同时它也带来新的攻击面：本期论文《Approval Laundering》研究的正是"人批准的动作"和"实际执行的动作"在 harness 里被改写后不一致的问题。

**[Claude-shaped science](https://www.anthropic.com/research/claude-shaped-science)** · Anthropic Research（Science，特邀作者 Matthew Schwartz）· 2026-10-01

**这篇解决什么问题**：物理学家 Matthew Schwartz 的第二篇特邀文。去年 12 月他把 Claude Opus 4.5 当研究生带，结论是"相当于 20 倍速的优秀研究生，但每句话都要改"。这次他换了思路：**不再把 Claude 当成他希望的那种合作者，而是按它实际的样子找问题**。他称之为"Claude 形状的问题"：依赖跨学科知识、需要大量编码、结果可检验。

**做法**：让 Claude 先搭一套数学物理工具，再不断用旧工具、造新工具，积累成一个开源 harness，叫 BootLoops。Claude 反复指出同一种模式：很多领域有一个问题，只要有人知道另一个领域的某个技术就能直接解决。比如群体遗传学里的贝叶斯证据积分，和 BootLoops 原本要算的费曼积分是同一类计算。

**规模**：三个月，约 400 个候选问题里推进了 **18 个领域的 36 篇稿件，19 位合作者**。一个例子是生态学的中性理论：2005 年提出的一个方程 20 年没人能大规模求解，Claude 认出它是 BootLoops 形状的并解了出来。

**一个关键教训**：离开自己的专业后，他发现自己会相信 Claude 说的"这个结果很棒"。请来领域专家后发现，**Claude 几乎总是技术上正确，但结果本身没多大意思，直到专家帮忙把方向拧过来**。

**技术细节一节是全文对工程师最有用的部分**：

- **会话组织**：每个项目一个 Claude Code 会话，另有一个主会话负责协调、分配算力、验证结果；还有单独的会话负责写作、建仓库和工具手册、写和验证工具代码，以及一个专门当"对抗式审稿人"反复核对结果。
- **子 agent 的一个实际好处**：他经常撞上 Fable 5 的分类器。撞上时只会关掉一个子 agent，不会毁掉整个会话。
- **压缩丢上下文**：让 Claude 定期整理和合并文件，保证随时能读到最新版计划。
- **Claude 没有时间感**：工作了三天，它说"两年的战役"；问 ETA，要么长得离谱要么短得离谱。作者最后靠自己的感觉判断进度。
- **Claude 默认"硬磨"**：宁可跑一个多天的计算，也不去造一个让同样的计算只要几分钟的工具。要反复提醒"想得更巧，别更使劲"。

**他列的失败模式清单**：爱宣布胜利（"完成了，只剩一个未证的引理"，而那个引理就是整个证明）；自动检查不可信，要自己看图；计算对、结论可能错；品味要人给（Claude 偏爱高引用但被遗忘的旧争论）；会无限磨下去。

**对 AI 应用工程师的启示**：这是一份来自重度用户的**长时程多会话 agent 失败模式清单**，和上期 Amazon AutoResearch 的五种失败模式（记忆衰减、方向停滞、指标执念）可以对着读。能直接照做的三条：①给"完成"定硬标准，不接受"完成，但有一点保留"；②设一个独立的对抗式验证会话；③计划写在文件里并定期合并，别指望上下文。

**[GLM-5.3 and the spread of advanced cyber capabilities](https://www.anthropic.com/research/glm-5-3-and-the-spread-of-advanced-cyber-capabilities)** · Anthropic Research（Frontier Red Team）· 2026-09-29

**这篇解决什么问题**：五个月前 Anthropic 以 Project Glasswing 限量发布了第一个能自主构造端到端漏洞利用的模型 Claude Mythos Preview，当时的判断是这种能力迟早会扩散。这篇是对智谱开源权重模型 GLM-5.3 的评估，结论是**这种能力已经出现在任何人都能下载的模型里，而且它的安全措施很容易去掉**。

**能力评估**（模型都跑在隔离沙箱里，只攻击离线靶标）：

- **ExploitBench**（V8 引擎已知漏洞的端到端利用）：GLM-5.3 在 410 次尝试中成功 50 次，Claude Mythos Preview 是 56 次。
- **内部 Binary Exploitation 基准**（100 个 OSS-Fuzz 项目任务，完整控制流劫持才算满分）：GLM-5.3 4%，Mythos Preview 6%；Claude Opus 4.6 和 GLM-5.2 都是 0。
- **人在回路测试**：一位研究员用一天时间、很少的注意力，让 GLM-5.3 在一个流行浏览器的 JavaScript 引擎里找到多个此前未知的漏洞，并串成一个可用的利用（访问网页即可读取本地任意文件）。另一位研究员用更小的 GLM-5.3-Flash 把一个已公开的 Chrome CVE 做成可靠的利用链：**20 分钟人工注意力 + 模型 8 小时，按智谱 API 价格是 20.40 美元**。

NIST 的 CAISI 在 09-17 发布的独立评估与此大体一致，称它是"迄今网络能力最强的开源权重模型"，落后美国前沿约四个月。

**安全措施评估**：在一个模拟环境里直接提出明显恶意的攻击请求，GLM-5.3 开箱全部拒绝。但三种简单手段可以绕过：

| 手段 | GLM-5.3 配合率 | 对 Claude |
|---|---|---|
| 欺骗性提示（告诉它"你是红队演习里的自主 agent"） | 64% | 被安全措施拦住 |
| 预填思考 token（让它看起来已经考虑过并决定执行） | 92% | API 不提供预填思考的途径 |
| abliteration（改权重去掉拒绝方向） | 100% | 权重不公开，无法操作 |

**对 AI 应用工程师的启示**：有三点和应用工程直接相关。①**预填（prefill）思考内容是一个真实的越狱面**。自己托管开源模型并暴露完整 chat template 时要意识到这一点；闭源 API 不开放这个口子不是偶然。②安全措施如果只存在于权重里的拒绝倾向，对拿得到权重的人等于没有。**部署侧的独立层（分类器、沙箱、出网控制）才是能留下来的那部分**，这和本期 dots、上期 OpenShell 的分层思路一致。③做安全评测时要报"绕过后"的数字，开箱拒绝率说明不了什么。

**这篇解决什么问题**：OpenAI 主张，**继续任何前沿强化学习训练之前都应该有结构化的安全文档**，长期目标是达到航空、核电那种"safety case"（成体系、有证据的风险论证）的水平。这篇公布了他们正在内部实施的初版指南。注意范围：只管前沿 RL 训练，不管部署。据 CNBC 报道，OpenAI 在同一天宣布放弃发布 GPT-6.1 Astra，理由是没达到自己的安全标准（见大事记），两件事要放在一起读。

**三部分内容**：

**一、技术防线，分三层**：

- **对齐（第一道）**：防止训练本身强化了作弊。用 agent 自动审查 RL 环境，找出能靠漏洞拿高分的环境并修掉；人工抽查数据集；调 grader 去惩罚钻环境空子的行为；对以往实验的轨迹跑分类器，确认 grader 按预期工作。测量侧：训练中跑离线对齐评测；在过去的事故上回测评测能否检出；**监控"模型是否意识到自己在被测"并设阻断阈值**；做最坏情况压力测试。还有一条很具体：**RL 里的自动 grader 不许看思维链**，防止模型演化出躲避思维链监控的能力。
- **围堵（第二道）**：沙箱和承载沙箱的研究基础设施都加固；用训练中的检查点红队攻击自己的围堵；跨样本的高带宽通信只走批准的通道；**所有 RL 训练、评测和内部部署的轨迹写入不可变存储**。
- **监控（第三道）**：用评测保证模型仍然可监控；监控器在留出的历史事故上要有高召回；为新风险补评测样本，免得召回率数字过期；告警有 SLA，白天呼叫值班和负责人，**夜间无人确认就自动暂停训练**。

**二、运营规则**：safety case 写好后由**另一个团队的人写一份异议**（相当于事前验尸）；高层逐一审阅，每人都有否决权；负责训练的高层对 safety case 和事故响应负责并计入绩效；发现使 safety case 失效的问题时有暂停所有相关训练的手册和技术手段；**技术控制要 fail-closed**：不开监控就起不了训练，也不能从 RL 训练、评测或内部部署内部关掉监控；能方便地找出一个失准模型的所有下游用途（数据生成、打分）以便回滚；显式列出没被缓解措施覆盖的残余风险。

**三、事故调查**：调查期间定期内部通报；做消融或重采样实验找出失准是怎么被训练出来的；做运营和文化层面的复盘；开发能发现同类倾向的测试方法，但**不能直接在事故信息上 hillclimb**，事故派生的评测只当回归测试；调查结束后公开结果。

**对 AI 应用工程师的启示**：这份清单虽然针对前沿训练，但几乎每一条都能缩小成 agent 系统的工程规则，而且和近三期论文的结论逐条对得上：**评分器不看被评对象能操纵的信号**（对应 grader 不看思维链）；**轨迹不可变存储**（对应上上期的 trace 篡改论文）；**监控 fail-closed、不能从被监控的环境内部关掉**（对应 OpenShell 的带外执法）；**事故派生的用例只当回归测试，不拿来调优**（对应本期 hillclimb 一文的"不把失败贴进 prompt"）。面试里被问"怎么给一个会自我改进的系统做安全设计"，可以按"对齐 → 围堵 → 监控 + 异议与否决 + 可回滚"这个骨架答。

**[How we build safety, security, and privacy into dots](https://openai.com/index/how-we-build-safety-security-and-privacy-into-dots/)** · OpenAI · 2026-09-29

**这篇解决什么问题**：DevDay 发布的 dots 是常驻 agent：每个 dot 有自己的云电脑，跨你连接的应用持续工作，你不在时也推进。这篇讲它的安全架构，是目前 OpenAI 对"always-on agent 的控制面"最具体的公开描述。

**分层结构**：

- **模型层**：GPT-6 Astra，训练成会停在请求范围内、在答案会改变做法时提问。
- **工作区**：每个 dot 一台云电脑，沙箱限制代码和工具能碰什么，用户之间的云环境互相隔离。关键的一句：**dot 运行代码的环境，和协调它工作、执行关键安全措施的系统是分开的**；它在工作区里能建文件、跑工具，但没法用这些权限去改安全系统或关掉必需的检查。
- **凭据**：安全登录时**模型被暂停**，用户在安全表单里输入，凭据直接送到浏览器环境提交，不进模型上下文；保存的密码走独立的加密凭据服务。文中也写明了边界：你另外贴在消息或文档里的密钥，模型还是看得见。
- **行动规则，按后果分三档**：能自己做的（读有权限的信息、分析、起草）；**每次都要你确认的**（永久删除数据、安装或运行来源不明的软件、授予新的安全敏感访问）；**必须交还给你做的**（改密码、在金融账户间转账）。购买可以用商户网站上已存的卡，但要你批准。
- **按数据敏感度定收件人授权粒度**：健康数据必须指明具名收件人；邮箱、电话这类较不敏感的个人数据默认要指定收件人类别（"任何航空公司"）。授权绑定在这次任务的指令上，**之后继续或委派给别的 agent 都不会扩大它**。
- **Auto-review：行动前的独立检查**。发邮件、改文件之前，一个独立的安全系统拿计划的步骤去对照你的指令、Custom Rules 和安全要求。放行就执行；**拦下时会把原因告诉 dot**，它可以要更多信息、请你批准、换一条允许的路，或者停。执行 Auto-review 的控制放在 dot 能改动的环境之外。
- **主动研究（proactive research）**：dot 会在后台找别的能帮上忙的事。这类任务**只有只读工具**，结果存成 dot 的私有笔记；不能发消息、不能改连接应用里的内容、不能操控浏览器或桌面，这些限制是**在代码里强制的**。任何后续动作仍走通常的规则和检查。
- **Custom Rules**：用户可以加自己的规则（"永远不要发邮件"）。dot 可以帮你写规则，但改规则要你批准；规则不能去掉强制确认和核心安全要求。

**对 AI 应用工程师的启示**：把它和 Anthropic × NVIDIA 的方案（Managed Agents 的循环与沙箱分离、凭据放独立保险库、OpenShell 带外执行策略）并排看，**两家的控制面已经同构**：模型内安全 → 沙箱 → 凭据不进上下文 → agent 够不到的独立审查 → 按后果分级的确认。设计自己的 agent 产品时，这五层可以当检查表。两个细节尤其值得抄：**后台自主任务只给只读工具**；**拦截时把原因返回给 agent**，让它能换路而不是卡死或硬闯。

**[Disrupting a coordinated model-distillation campaign](https://openai.com/index/disrupting-a-coordinated-model-distillation-campaign)** · OpenAI（Security）· 2026-09-30

**这篇解决什么问题**：OpenAI 披露并处置了一起有组织地**提取模型受保护推理**的行动，用途与对抗性蒸馏一致（用一个模型的输出或推理去训练另一个模型）。篇幅不长，但对"推理内容怎么保护"有工程价值。

**手法**：攻击者没有攻破加密、没有入侵数据库，而是操纵模型交互，让隐藏的推理以请求者看得见的形式被复现。文中点名的一种做法：**把一个会话里的加密推理复制出来，在另一个会话里让模型解密并转写**。独立安全研究者还通过负责任披露报告了相关的跨模型和会话压缩（compaction）漏洞，OpenAI 确认属实。

**规模与时间线**：07-01 起低量出现；07-24 和 07-25 出现高峰，16,000 次请求、4,000 多个用户；进一步调查关联出 15,000 多个用户的集群，07-28 全部处置。

**归因**：不确定是否全部出自同一行动者，但 OpenAI 把**核心集群归因于与 Moonshot AI（Kimi 开发方）有关联的人员**。

**修复**：封禁账号、加强注册与基础设施控制；加强隐藏推理在用户、工作区、组织、模型家族之间的隔离；**堵住"已持有他人加密推理的人可以重放并恢复其内容"的路径**；对可能暴露推理的流式输出加检测和拦截。文中还提醒：**支持可携带或可重放推理产物的系统都可能有同类风险**，合作方托管的部署需要同样的保护，工具输出类攻击需要检查的不只是可见文本。信息已通过 Frontier Model Forum 分享。

**对 AI 应用工程师的启示**：如果你的系统会在轮次之间回传"加密的推理块"（很多 agent API 现在都这样做以保持思考连续性），要知道**这些块是有归属的**：不要跨用户、跨会话混用；自己做上下文压缩或会话迁移时，别把别处来的推理块原样塞进新会话。Sonnet 5.5 新增的 `reasoning_extraction` 拒绝类别是同一威胁的防守侧。

### 其他官方源

**[Tracing Agent Harness Behavior with NVIDIA NeMo Relay](https://developer.nvidia.com/blog/tracing-agent-harness-behavior-with-nvidia-nemo-relay/)** · NVIDIA 开发者博客 · 2026-09-30

**这篇解决什么问题**：agent 做对了任务，路径仍可能很浪费：一次搜索失败触发又一次搜索，一次被截断的文件读取引出一条重新取同样内容的命令。只看最终是否成功，解释不了它为什么从工具错误里恢复过来、为什么多调了几次模型。这篇教程用 Hermes Agent 内置的 NeMo Relay 记录轨迹，并演示**怎么用轨迹证据验收一次 harness 改动**。

**三种轨迹格式，各有用途**：

| 格式 | 内容 | 用在哪 |
|---|---|---|
| ATOF | JSONL 事件流：scope 开始、结束、时间点标记，带 ID 和时间戳 | 调试或审计单个事件、时序、父子关系 |
| ATIF | 按步骤的 JSON：交互、工具调用、观察 | 逐步回看或评估 agent 的路径 |
| OpenTelemetry + OpenInference | 父子 span，标注 agent / LLM / 工具 | 放进 Phoenix 等 OTEL 工具看调用、耗时、token、错误 |

一个容易忽略的点：**ATIF 里的工具请求只说明模型"要求"跑什么，不能证明结果**。要确认发生了什么，得去 ATOF 里找对应的开始和结束事件以及记录的错误。

**评估 harness 改动的六步**：①选一个有**精确、自动化成功判定**的固定任务；②定基线和**一个**聚焦的改动；③其余全部不变（模型快照、provider、输入、执行预算、超时）；④基线和候选跑**相同次数**；⑤**先比经过验证的任务结果**，再用轨迹看模型调用、工具调用、重试、错误、耗时、token；⑥推广结论前，在改动要支持的模型和负载上都重复一遍。只有任务完成率可重复地上升，或完成率不变而你想改的那个指标变好，才能叫改进。"某一次跑得更快"不算。

**案例：Hermes ToolPerf（108 次 A/B）**。Nous Research 从生产会话里挖出九类失败模式做成确定性用例，再评估一批工具层修复。9 个任务 × 每臂 3 次 × 2 个模型：

| 模型 | 臂 | 任务成功 | 平均 LLM 调用 | 平均工具调用 | 平均工具结果数据 | 平均耗时 |
|---|---|---|---|---|---|---|
| Claude Sonnet 4.5 | 基线 | 24/27 | 2.9 | 2.2 | 17 KB | 16 秒 |
| Claude Sonnet 4.5 | 修复后 | 23/27 | 2.8 | 2.1 | 17 KB | 22 秒 |
| Qwen3 Coder 30B | 基线 | 19/27 | 3.8 | 2.8 | 16 KB | 27 秒 |
| Qwen3 Coder 30B | 修复后 | 22/27 | 4.9 | 3.9 | 33 KB | 42 秒 |

读法：**强模型没有实质变化**（差一次运行）；弱模型多做成 3 个任务，但更慢、更啰嗦。轨迹解释了原因：在"命令被拦"任务上，基线的 Qwen 撞上解析器拦截就放弃（33%），修复后加的恢复指引让它做到 100%，**多出来的轮次是恢复，不是乱撞**。同时有一个任务变差了：大小写不敏感搜索返回零匹配的探测输出，让 Qwen 在三次里有两次多做了探索性搜索，从 3.3 轮涨到 9.3 轮。

**对 AI 应用工程师的启示**：这篇把"harness 改动要怎么验收"写成了可照做的流程，而且示范了一个反直觉但常见的结果：**同一批修复对强模型无效、对弱模型有效但有代价**。两条可以直接用：①别把"调用次数变少"当成改进的证据，先看验证过的完成率；②为多个模型维护 harness 时，每个改动要分模型看，一个模型的收益可能是另一个模型的无操作甚至回归。

## 补录

> 以下四篇来自本期新登记的 claude.dev 开发者博客（RSS 存量），发布于 4–6 月，此前从未收录。作者是 Claude Code 团队的 Thariq Shihipar（dynamic workflows 一篇与 Sid Bidasaria 合写），讲的是 Claude Code 这个 harness 自己的设计决策，属于面试里可以直接引用的一手材料。

**[Lessons from building Claude Code: Prompt caching is everything](https://claude.dev/blog/lessons-from-building-claude-code-prompt-caching-is-everything/)** · Anthropic（claude.dev 开发者博客）· 2026-04-30

**这篇解决什么问题**：长时程 agent 在成本和延迟上之所以可行，靠的是 prompt 缓存。Claude Code **整个 harness 是围绕缓存设计的**：团队对缓存命中率设了告警，过低就按事故（SEV）处理。这篇讲他们踩出来的几条不直观的规则。

**根本约束：缓存是前缀匹配**。API 缓存从请求开头到每个 `cache_control` 断点的内容，前缀里任何一处变了，后面全部失效。所以顺序决定一切：

1. 静态系统提示和工具（全局缓存）
2. CLAUDE.md（项目内缓存）
3. 会话上下文（会话内缓存）
4. 对话消息

这个顺序很脆。他们自己弄坏过：在静态系统提示里放了精确时间戳；工具定义的顺序不确定；改了某个工具的参数（比如 Agent 工具能调用哪些 agent）。

**四条规则**：

- **要更新信息，用消息，不改 prompt**。时间变了、用户改了文件，都放进下一条用户消息或工具结果里的 `<system-reminder>` 标签，不动系统提示。
- **会话中途不换模型**。缓存按模型区分。和 Opus 聊了 10 万 token 后想问个简单问题，切到 Haiku 反而更贵，因为要给 Haiku 重建缓存。真要换，用子 agent：让 Opus 写一条交接消息给另一个模型（Explore 子 agent 用 Haiku 就是这么做的）。
- **会话中途不增删工具**。工具在缓存前缀里，增删一个就让整段对话的缓存失效。
  - **Plan Mode 的设计**：直觉做法是进入计划模式就把工具集换成只读的，但那会破坏缓存。实际做法是**所有工具始终都在**，EnterPlanMode 和 ExitPlanMode 本身是工具；进入计划模式时用一条系统消息告诉模型规则。附带的好处是模型遇到难题可以自己进入计划模式。
  - **工具搜索**：几十个 MCP 工具全量放进每个请求太贵，中途移除又破坏缓存。解法是 `defer_loading`：只发轻量存根（只有工具名），模型需要时通过工具搜索"发现"完整 schema。存根始终以同样的顺序存在，前缀稳定。
- **压缩（compaction）也要对缓存安全**。最简单的做法是另起一个 API 调用，用"总结一下"的系统提示、不带工具。这正是成本陷阱：前缀从第一个 token 就不同，整段对话都按未缓存价格计费，而对话越长越需要压缩。Claude Code 的做法是**"缓存安全的分叉"**：压缩请求使用和父对话**完全相同**的系统提示、用户上下文和工具定义，把父对话消息放在前面，最后追加一条压缩指令。API 看到的请求和父对话的上一个请求几乎一样，前缀命中缓存，新增的只有压缩指令本身。代价是要预留一段"压缩缓冲区"放压缩指令和摘要输出。

**对 AI 应用工程师的启示**：这是讲"缓存如何反过来决定 harness 架构"最清楚的一篇，结论可以背下来：**状态变化用工具和消息来表达，不用改系统提示或工具集来表达**；任何旁路计算（压缩、摘要、skill 执行）都要共享父请求的前缀；缓存命中率要像可用性一样监控。上期的《What a task costs on Opus 5.5》给了缓存命中率对账单的影响（0% 时 $11.20，90% 时 $1.62），这篇给的是怎么把命中率做上去。

**[Seeing like an agent: how we design tools in Claude Code](https://claude.dev/blog/seeing-like-an-agent/)** · Anthropic（claude.dev 开发者博客）· 2026-04-10

**这篇解决什么问题**：给 agent 设计工具，是给一个通用工具（bash），还是给五十个专用工具？作者的框架是：工具要**贴合模型自身的能力**，而能力是什么只能靠读它的输出、做实验来了解。全文用 Claude Code 里三个工具的演变来说明，包括做错的版本。

**案例一：AskUserQuestion（让模型更好地提问）**

- 第一版：给 ExitPlanTool 加一个"问题数组"参数。失败，因为同时要计划和关于计划的问题，模型困惑：答案和计划冲突怎么办？
- 第二版：改输出格式，让模型按一种特殊 markdown 输出问题和选项，再解析成界面。失败，模型通常能做到但不可靠，会多写句子、漏选项、放弃格式。
- 第三版：做成一个随时可调用的独立工具，触发时弹出模态框并阻塞 agent 循环直到用户回答。成功。文中的判断标准很实在：**模型"喜欢"调用它，调用出来的结果也好**。设计得再好的工具，模型不会调就没用。

**案例二：TodoWrite → Task（工具要随模型能力更新）**

早期模型需要 todo 列表防止跑偏，后来还每 5 轮插一次系统提醒。模型变强后，todo 反而成了束缚：提醒让它以为必须照着列表做，不敢改计划。再加上子 agent 能力上来后需要协调，于是 TodoWrite 被 Task 工具取代：**todo 是为了让模型不跑偏，task 是为了让多个 agent 互相沟通**（带依赖、能跨子 agent 共享更新、可改可删）。结论：模型曾经需要的工具，后来可能在限制它，要不断回头审视；这也是只支持少数几个能力相近的模型的理由。

**案例三：搜索接口（从给上下文到让模型自己找）**

最早内部版本用 RAG：向量库预索引代码库，harness 检索片段塞给模型。问题是要建索引、跨环境脆弱，更重要的是上下文是**被给的**而不是模型自己找的。换成 Grep 工具后模型自己搜、自己建上下文。之后 Agent Skills 把"渐进式披露"正式化：模型读 skill 文件，文件再指向别的文件，递归下去。一年里模型从基本不会自己建上下文，变成能跨多层文件做嵌套搜索。

**渐进式披露的另一种用法：不加工具就加能力**。Claude Code 大约有 20 个工具，**加新工具的门槛很高，因为每多一个都是模型要多考虑的一个选项**。例子：模型不了解 Claude Code 自己（怎么加 MCP、某个 slash 命令做什么）。把这些全写进系统提示会造成上下文腐烂；给一个文档链接让它自己查，它会把大段文档拉进上下文。最后的解法是 **Claude Code Guide 子 agent**：在自己的上下文里查文档，只把答案交回来。

**对 AI 应用工程师的启示**：面试里"工具该怎么设计"这道题的一手答案。四个要点：①结构化输出需求优先做成工具，别靠输出格式约定；②一个工具只做一件事，别在已有工具上叠参数；③工具集要随模型代际做减法；④想加能力先考虑渐进式披露或子 agent，最后才是加工具。这篇和上面的缓存一文是配套的：ExitPlanTool 为什么存在，答案在缓存那篇。

**[A harness for every task: dynamic workflows in Claude Code](https://claude.dev/blog/a-harness-for-every-task-dynamic-workflows-in-claude-code/)** · Anthropic（claude.dev 开发者博客）· 2026-06-02

**这篇解决什么问题**：默认的 Claude Code harness 要在**同一个上下文窗口里既规划又执行**。对多数编码任务够用，但对长时间、大规模并行、高度结构化或需要对抗的任务会失效。dynamic workflows 让 Claude **为眼前的任务现写一个 harness**：一个 JavaScript 脚本，用 `agent()` 起一个子 agent，用 `parallel()` 和 `pipeline()` 组合多个，还能决定每个子 agent 用哪个模型、是否放进独立 worktree。

**单上下文长任务的三种失败模式**（这是全文最值得记的定义）：

- **agent 式偷懒（agentic laziness）**：复杂多部分任务没做完就宣布完成，比如安全审查 50 项只处理了 35 项。
- **自我偏好（self-preferential bias）**：让它按 rubric 验证或评判时，偏向自己的结果。
- **目标漂移（goal drift）**：多轮之后对原始目标的保真度逐渐下降，尤其在压缩之后；每次摘要都有损，边界要求和"不要做 X"这类约束容易丢。

workflow 的对策是让多个子 agent 各有独立上下文和聚焦的目标。

**为什么是"动态"**：以前用 Agent SDK 或 `claude -p` 写的静态 workflow 要覆盖所有边界情况，所以通常很通用。现在模型足够聪明，可以为具体任务量身写一个。

**六种可组合的模式**：

| 模式 | 做法 |
|---|---|
| 分类后行动 | 用分类 agent 判断任务类型再路由 |
| 扇出后综合 | 拆成许多小步，每步一个 agent，各自干净的上下文；综合步骤等全部完成后合并结构化输出 |
| 对抗式验证 | 每个 agent 的产出由另一个 agent 按 rubric 对抗核查 |
| 生成后过滤 | 生成一批想法，再按 rubric 或验证过滤、去重 |
| 锦标赛 | 多个 agent 用不同方法做同一件事，由评判 agent 两两比较 |
| 循环直到完成 | 工作量未知时循环起 agent，直到满足停止条件（没有新发现、日志里没有错误） |

**几个用例里的工程细节**：

- **排序**：一千多行的定性排序放进一个 prompt 会掉质量也放不下。改用锦标赛或成对比较，文中给的理由是**比较式判断比绝对打分更可靠**；每次比较是一个新 agent，确定性的循环拿着对阵表。
- **规则遵守**：某些规则写进 CLAUDE.md 模型还是会漏，就为每条规则起一个验证 agent，再加一个"怀疑者"过滤误报。反方向也成立：从最近的会话和代码审查评论里挖出反复做的纠正，聚类、对抗验证（这条规则真能防止一次真实的错误吗），存活的写回 CLAUDE.md。
- **分诊的隔离模式（quarantine）**：读不可信公开内容的 agent 没有任何高权限动作；负责行动的 agent 只看到它们的摘要。
- **根因分析**：让不同 agent 从互不重叠的证据（日志、文件、数据）各自生成假设，每个假设再面对一组验证者和反驳者，从结构上避开自我偏好。

**什么时候不用**：workflow 明显更费 token。常规编码任务先问一句"它真的需要更多算力吗"，多数传统编码任务不需要五个评审。可以用"用 10k token"这样的提示设预算上限。

**对 AI 应用工程师的启示**：三种失败模式加六种编排模式，基本就是"什么时候该上多 agent、怎么上"的答题框架。尤其要记住它给出的理由不是"多 agent 更强"，而是**独立上下文能从结构上消除自我偏好和目标漂移**。隔离模式是处理提示注入的一个实用结构，和 dots 的"后台任务只读"是同一思路。

**[Lessons from building Claude Code: How we use skills](https://claude.dev/blog/lessons-from-building-claude-code-how-we-use-skills/)** · Anthropic（claude.dev 开发者博客）· 2026-06-03

**这篇解决什么问题**：Anthropic 内部有几百个 skill 在用。这篇回答三个问题：什么样的 skill 值得做、怎么写、怎么分发。

**先纠正一个误解**：skill 不是"一个 markdown 文件"，而是一个**文件夹**，可以装脚本、资产、数据，在 Claude Code 里还能注册动态 hook。

**九类 skill**（内部盘点后的聚类；好的 skill 干净地落在一类里，想做太多的会跨几类并让 agent 困惑）：

| 类别 | 内容 | 例子 |
|---|---|---|
| 库与 API 参考 | 内部或易错的库怎么用，带代码片段和坑点 | 内部计费库的边界情况 |
| **产品验证** | 怎么测试代码真的能用，常配 playwright、tmux | 无头浏览器跑完注册流程并在每步断言状态 |
| 数据获取与分析 | 连数据和监控栈，带仪表盘 ID、常用查询 | 哪张表有权威的 user_id |
| 业务流程自动化 | 把重复流程变成一条命令 | 汇总工单和 GitHub 活动生成站会更新 |
| 代码脚手架与模板 | 按团队约定生成样板 | 新迁移文件模板和常见坑 |
| 代码质量与审查 | 强制代码规范、辅助审查 | 起一个全新视角的子 agent 批评，改到只剩吹毛求疵为止 |
| CI/CD 与部署 | 拉取、推送、部署 | 盯 PR、重试 flaky CI、解决冲突、开自动合并 |
| Runbook | 从症状出发，跨工具排查，产出结构化报告 | 按请求 ID 拉出所有相关系统的日志 |
| 基础设施运维 | 例行维护，带破坏性操作的护栏 | 找孤儿资源 → 发 Slack → 等待期 → 用户确认 → 清理 |

文中特别指出：**验证类 skill 对输出质量的可测影响最大**，值得让一个工程师花一周把它做好。技巧包括让 Claude 录下操作视频、在每一步强制程序化断言。

**写 skill 的八条建议**：

1. **不要说显而易见的事**。模型本来就会写代码、会读代码库；重复它默认会做的事只是占上下文。要写的是把它**推离默认思路**的信息。
2. **建一个 Gotchas 小节**。这是 skill 里信号最强的内容，从模型实际踩过的坑积累而来。例："`subscriptions` 表是只追加的，要的是 version 最高的那行，不是 `created_at` 最新的。"
3. **用文件系统做渐进式披露**。SKILL.md 指向别的文件（`references/api.md`、`assets/` 里的模板），告诉模型有哪些文件，它会在合适的时候去读。
4. **别把模型绑死**。skill 复用度高，指令太具体会在别的情境里出错。写目标和约束，不写每一步。
5. **想清楚初始化**。需要用户信息的 skill（比如发到哪个 Slack 频道）把配置存进 skill 目录下的 config.json，没配置就问用户。
6. **description 字段是写给模型看的触发条件，不是摘要**。会话开始时模型扫一遍所有 skill 的 description 来判断"有没有 skill 适合这个请求"。
7. **让 skill 有记忆**。在 skill 里存数据（追加日志、JSON、甚至 SQLite）。例：站会 skill 保留每次发过的内容，下次只报变化。用 `${CLAUDE_PLUGIN_DATA}` 拿稳定目录。
8. **给脚本和库**。让模型把轮次花在组合上，而不是重写样板。另外可以带**按需 hook**：只在 skill 被调用时激活，例如 `/careful` 拦住 `rm -rf`、`DROP TABLE`、force-push，`/freeze` 拦住指定目录之外的编辑。

**分发与度量**：小团队把 skill 签入仓库（`.claude/skills`）；规模大了用内部插件市场，因为每个签入的 skill 都会占一点上下文。Anthropic 没有中心团队审批：先放沙箱目录、在 Slack 里推荐，有了使用量再提 PR 进市场。用 PreToolUse hook 记录 skill 使用情况，找出受欢迎的和**触发率低于预期**的。

**对 AI 应用工程师的启示**：这篇和 9 月中补录的《Equipping agents for the real world with Agent Skills》配套，那篇讲 skill 是什么，这篇讲生产里怎么用。最值得带走的三点：**Gotchas 是 skill 的核心资产**；**description 决定触发**（本期 hillclimb 一文正好说 skill 触发率是最容易爬的指标之一）；**优先投资验证类 skill**。还有一点和自演进主线相关：文末说"多数好 skill 一开始只有几行和一个 gotcha，是人们在模型遇到新边界情况时不断往里加才变好的"。这是人工版的 skill 演化，而下面精读的论文正是在问：如果让 agent 自己这样加，会发生什么。

### 精读 · 自演进

**[Do Self-Evolving Skills Generalize to Held-Out Tasks?](https://arxiv.org/abs/2609.39148)** · Xihao Piao、Zifeng Wang、Zheng Chen（大阪大学 SANKEN，据 arXiv HTML 版作者栏）· 提交 2026-09-30

**问题**：自演进 skill 方法让 agent 在训练任务上练习，每轮根据反馈改写 skill，然后把 skill 用到同类的新任务上。**训练任务上的提升，能带到新任务上吗？** 此前各方法各报各的，模型、agent、数据划分都不同，没法比。

**实验设计**：五种自演进方法（SkillGen、Trace2Skill、SkillOpt、EvoSkill、GEPA）加一个"模型一次写成、不再改"的 One-shot skill 和一个不用 skill 的基线，在六个基准上用**同一个模型（Qwen3-Coder-480B，温度 0）、同一个 agent、同一个 train / validation / test 划分**，每个方法最多 20 轮。测试任务在所有方法选定最终 skill 之前一直锁着。

**主要发现**：

- 现有方法的 36 个最终 skill（6 种方法 × 6 个基准）里，21 个在训练任务上有提升。这 21 个当中，**5 个在测试上保住全部提升，13 个保住一部分，3 个一点没保住**（其中 2 个有害）。
- **36 个测试分里有 10 个低于不用 skill**。六个基准里有五个，至少有一种方法不如不用 skill。
- 没有哪个现有方法处处最好：SkillOpt 在 SpreadsheetBench 和 SWE-bench 上最好，SkillGen 在 SciVisAgentBench 上最好，EvoSkill 在 HealthBench 上最好；RBioBench Omics 上没有任何现有方法赢过不用 skill。
- 同一个方法在不同基准上表现差别很大：留存量从 +3.4 分（EvoSkill 在 RBioBench Clinical）到 −15.0 分（EvoSkill 在 SpreadsheetBench）。

**过拟合的 skill 里写了什么**：读最终 skill 会看到一个共同模式：**把某一个训练任务的修法写成了所有任务的规则**。有的把列名和输出文件写死，好像每个任务都有；有的把一张检查表套到所有任务上，不说适用条件；有的把"需要时创建摘要文件"改成"总是创建"。论文追踪了 SkillOpt 同一次运行里的两处编辑：都让训练分略升，第 2 轮那处（加通用检查）让测试 +10 分，第 9 轮那处（把条件规则改成全局规则）让测试 −5 分。原因在机制上：每轮都是为了通过刚失败的训练任务而改，改完的 skill 却用于所有未来任务，**每次编辑的表述都比它的证据更宽**。

**能不能靠读 skill 内容来预判？** 作者让一个 LLM judge 只读 skill，按五个维度打分（可泛化性 30%、适用条件 20%、可执行性 20%、鲁棒性 20%、清晰度 10%）：

- 对**成品 skill**：同基准内两两比较共 126 对，judge 分高的测试分也高的有 108 对（85.7%）。
- 对**单次编辑**：45 处编辑上，judge 的预测与真实测试变化的 Spearman 相关在 SpreadsheetBench 是 0.39，在 RBioBench 约为 0。前面那两处编辑，judge 都判为有害。

结论：成品 skill 的内容能说明不少问题；**单次编辑有没有用，只能跑了才知道**。

**作者的方案 GSO**：换学习目标。不学"一个用于所有任务的 skill"，而学一个**元 skill**（怎么写 skill 的指南，六部分：怎么读任务、怎么选工具和来源、怎么写步骤、怎么检查结果、怎么找出哪里错了、怎么在一次重试里修好）。每个任务由元 skill 现写一个 skill，用完即弃，所以贴合某个任务的细节没法泄漏到别的任务。元 skill 从不出现具体文件名、列名、输出路径。更新规则两条：**一次只改六部分中的一部分**；只有在验证集上修好的任务数超过弄坏的任务数的两倍才保留（更新分 = 修好数 − 2 × 弄坏数，系数 2 在任何实验之前定死）。GSO 在六个基准上测试分全部最高，比最好的现有方法高 4.3 分（HealthBench）到 22.5 分（SWE-bench）。

**需要注意的地方**：作者自己说明，GSO 在测试时每个任务多一次写 skill 的模型调用，还可以自检并重试一次，其他方法没有，所以这是"整套方法之间"的比较，说明不了具体哪一部分带来了收益；GSO 在 HealthBench 上也没保住全部提升（留存 −5.2）。全部实验只用了一个模型。

**对 AI 应用工程师的启示**：

1. **评估自演进系统必须报留出集和留存量**，训练曲线会高估。这和上期 SkillEvoReg（跑完全程比中途最好版本低 7.75 分）是同一个结论的两种测法。
2. **每次 skill 编辑都要跑过才合并**，别指望 LLM 审一眼就能判断；但可以用 judge 给成品 skill 排序，便宜且大体可靠。
3. **回归的代价要算得比修复高**。GSO 的"修好数 − 2 × 弄坏数"和本期 SAGE 的"逐题配对 + 不对称惩罚回归"是同一思想。
4. 写 skill 时警惕"条件规则被改成全局规则"。上面 Anthropic 的 skill 一文说"别把模型绑死""写目标和约束，不写每一步"，这篇给了它数据上的理由。

**[MILO: Automated Harness Discovery via Orchestrated Multi-Agent Evolution](https://arxiv.org/abs/2609.38349)** · Prithwish Jana 等 12 人（AWS AI Labs，另有 Georgia Tech、CMU、圣路易斯华盛顿大学，据 arXiv HTML 版作者栏）· 提交 2026-09-29

**问题**：harness 对 agent 表现的影响不亚于模型（文中举例：GPT-5 在 Terminal-Bench 上配 Terminus 2 是 35.2%，配 Codex 是 49.6%，token 还少 35%），但 harness 工程仍是手工活，而且**每换一个模型都要重调**。自动 harness 发现通常做成 LLM 驱动的进化搜索：mutator 提出新 harness，评测打分，结果指导下一轮。现有方法有两个问题：要么只改 prompt 或 skill（GEPA、A-Evolve），大部分搜索空间没碰；要么搜索策略固定，而 LLM mutator 天生**重利用、轻探索**，反复做同一类编辑，种群很快塌缩成少数几种设计的变体。

**做法**：MILO 让 harness 和**搜索策略本身**一起演化，分内外两层循环，三个组件：

1. **分层谱系记忆**。记忆是一片"岛屿森林"：每个岛独立演化自己的谱系树，岛之间不竞争。节点记录每个 harness 的准确率、成本、失败证据和**是否被接纳**；边记录产生它的那次编辑（源码补丁）以及带来的准确率和成本变化。**被拒绝的变异也留在树里**，作为负面证据。
2. **证据驱动的 mutator agent**。每个岛配一个 coding agent 当 mutator（实验里有 Claude Code、Codex、DeepAgents 配不同模型）。它拿到三样输入：父 harness 的源码、父 harness 的失败证据、整个岛的谱系快照（渲染成类似目录树的缩进列表，每行一个 harness 及其来路和成绩）。前两样只给磁盘路径，让 agent 按诊断需要自己打开。prompt 规定**先诊断再改**，而且重写的是**整个 harness**。
3. **元演化编排 agent**。只有它能看到所有岛。某个岛停滞时它先诊断瓶颈出在哪（mutator、谱系等四种来源之一），再干预：把一个岛的谱系**嫁接**到另一个岛、分出新物种、**给岛换一个 mutator**、修改评测任务的课程。

接纳标准是多目标 Pareto：准确率高出一个容差，或准确率在容差内而各项成本全都更低。

**结果**（所有搜索方法从同样三个专家设计的 DeepAgents 种子出发，各给 72 小时）：

| 基准（Opus 4.8） | MILO 相对最好种子的提升 | 此前最好的搜索方法 |
|---|---|---|
| Terminal-Bench 2.1 | +12.0% | +4.5%（GEPA） |
| PaperBench | +28.3% | +18.3%（Meta-Harness） |
| DeepSWE | +10.3% | 0（无提升） |

- harness 在某些任务分布上会**帮倒忙**：配 Opus 4.8 时，8 个 SoTA harness 里有 7 个在 PaperBench 上不如只有 read / write / bash 的极简 harness。
- harness 的收益**不一定跨模型迁移**：Terminal-Bench 2.1 上 8 个 harness 配 Opus 4.8 都好于极简 harness，换成 gpt-oss-120b 有 4 个不如它。

**问题**：AI 编码工具让写代码快了很多，但对整个软件开发生命周期（SDLC）影响有限，这是 Amdahl 定律效应：编码只是其中一段。这篇是微软数据系统团队的愿景加进展报告，目标是把**定目标、编码、评审、运维**四段都自动化，并让流水线产生的数据反过来改进它自己。全文只有 6 页，细节有限，价值在于生产数据。

**范围收得很窄，这是关键**：只做数据系统上的"**演化式编码任务**"（ECT），也就是**能定义一个可自动测量的目标**的编码问题（比如查询延迟）。数据系统有稳定的公共 API 和清晰的语义，优化目标历史悠久，所以能靠遥测和自动反馈把更多环节自动化。

**四个组件**：

- **World Model**：一个知识库，记录系统结构与依赖、业务上下文，以及这些概念怎么落到可观测的遥测上。对遥测和 profiling 的访问都经过它。
- **Hotspan（定目标 agent）**：给定仓库、高层目标和 World Model，它先把"让服务更快"这种模糊目标变成具体指标和约束，再从三个渠道取证列出候选优化点：遥测（最贵的区域，沿调用图传播）、代码分析（文本搜索找不到的语义和控制流 / 数据流查询）、代码评审历史（PR、issue、反模式）。它还负责**构造评测改动的基准**，并按"每 token 花费带来的指标提升"排序。
- **Darwin（演化式 agent 群）**：现有做法各有一半。agentic 编码工具会局部自我纠正，但不在更大的解空间里探索；LLM 进化搜索（如 OpenEvolve）有全局监督，但每次变异是一次性生成，没有局部纠错。Darwin 把两者合起来：**每一次"变异"是一个完整的 agent 会话**，在隔离沙箱里克隆仓库、拿到一个优化假设、改代码、跑测试和基准、看失败、调试、迭代，最后**反思并输出结构化的假设**（什么有效、下一步试什么）。几十到几百个这样的 agent 组成群，爬一个仓库级代码库上的目标。作者把这称为**持续优化（CO）**，与 CI/CD 并列，可以用闲时算力无人值守地跑。
- **AutoSRE**：把历史事故调查提炼成"事故调查图"，用于自动化检测、分诊和处置。

**两条自演进回路**：

1. **演化 World Model**。用户输入和 AI 的反思都先过一个"清算所"：按范围、敏感度、成熟度**分层并物理隔离**；个人上下文要**明确同意且被反复观察到**才能晋升到更高层；更新以类似预写日志的条目提交，经历"已提交 → 批准 / 拒绝 / 需修改 → 已处理"的生命周期，带序号，**可时间回溯和回滚**（所有物化视图都从事实源派生，回滚就是把日志重放到指定位置）。AutoSRE 的调查图用蚁群优化演化：成功的路径加强，没用的路径衰减，新的解决方式长出新节点和边。
2. **微调模型**。World Model 存的是临时的、可修订的事实和 skill；微调把稳定的能力内化进权重。Hotspan + Darwin 的每次运行都留下完整的决策轨迹，成了免费的监督信号。

作者坦白的开放问题：**World Model 的更新目前全部要人审**，安全但贵；信任怎么校准还没解决。

**证据**：

- **生产**：内部工具链叫 Autoperf，一个专门的性能团队把它用在 Dynamics、Power Platform、Agent 365 的**数十个仓库**上（每天还在接入）。团队约 43% 的时间用 Autoperf 做应用场景（其余在建基础设施和接入仓库）。这部分工作的产出是**每工程师小时 0.35 个 PR**，估计是人工开发的 4.7 倍、当前最好 agentic 编码工具的 3 倍。这些 PR 的收益（延迟、吞吐、CPU / 内存占用）**中位数 1.72 倍，90 分位 10 倍**。Autoperf 的产出进入工程评审队列，由人审。
- **开源**：对 45 个广泛部署的开源系统各给 2,500 美元推理预算，每个系统都拿到了正向改进（有的很小）；表现最好的 20 个平均性能提升 13.8%。
- **token 效率**：在 circle packing 这个经典问题上，Darwin 的成本是 MAP-Elites 的 1/22、OpenEvolve 的 1/17（摘要给的说法是 token 效率最高 22 倍）。

**对 AI 应用工程师的启示**：①这是继上期 Amazon AutoResearch 之后**第二份大厂自述的生产级自改进数据**，两份的共同点是：**只在有可自动测量目标的问题上做**，评估由 agent 改不了的遥测和基准提供。②"每次变异是一个带自我调试的 agent 会话"解释了十几到二十倍的 token 效率从哪来：一次性生成的候选大多死在编译和测试上。③World Model 的更新流程（分层隔离、同意后晋升、日志式提交、可重放回滚）是**共享记忆治理**的一份具体设计，可以直接参考。④注意它的数字是团队自估，论文省略了完整消融。

### 精读 · Harness

**[Mid-Harness: Scaling Actions Between Model and Harness for Terminal Agents](https://arxiv.org/abs/2609.39982)** · Minki Kang 等 11 人（NVIDIA，据 HF 组织字段）· 提交 2026-09-30

**问题**：终端 agent 每一步的动作是随机采样出来的。模型**能**生成一个好动作，不代表这一次采样到的就是它。而终端里一条坏命令（比如装错了包）会改变环境，妨碍后面的进展。常见的测试时加算力方式是多跑几条完整轨迹再选（Best-of-T），但那需要多次全新的环境运行，在基准之外往往做不到，因为环境状态不容易序列化。

**做法**：在模型和 harness 之间加一层，**模型和 harness 都不改**。原来的模型调用包装函数是"生成一个响应并返回"，现在改成"用同样的历史采样 N 个候选动作，交给验证器选一个，只把这一个返回给 harness 执行"，其余丢弃。只需要一个环境实例。验证器看得到任务、已观察的历史和候选动作，**看不到生成这些候选时的推理**。

比较了三种验证方式：**列表式**（一次看所有候选选一个，一次调用）、**逐点式**（每个候选单独打分）、**成对式**（两两比较）。

**发现**（TerminalBench-Lite，生成器固定为 TMAX-9B，一个在 Qwen3.5-9B 上用 RL 训练的终端模型；基线 Pass@1 是 50.00%）：

1. **候选里确实有更好的动作，但要有够强的验证器才挑得出来**。用 GPT-5.6 Sol 当验证器，N=4 时 64.63%，N=8 时 **68.03%**。
2. **验证器弱的时候，多采样没用**。同样是列表式，让 TMAX-9B 自己当验证器，N 从 4 加到 8，Pass@1 只从 49.32% 变到 51.02%。
3. **成对式是自验证里最好的**：N=8 时 54.76%（Pass@3 71.43%）。
4. **验证能力可以蒸馏**。用强验证器在 244 个难任务、732 条轨迹上的 11.7 万条成对判断，给 TMAX-9B 训一个只在验证时启用的 LoRA，N=8 的 Pass@1 从 54.76% 升到 57.14%，Pass@3 从 71.43% 升到 75.51%。生成器不变。
5. **成本**：成对式贵。N=8 时零样本成对验证的验证器总输出约 12.57 万 token，列表式只有约 600。
6. **和轨迹级方法叠加**：Best-of-3 单独是 55.10%；用 Mid-Harness 来生成这三条轨迹，零样本升到 61.22%，蒸馏版升到 66.33%，**环境运行次数不变**。和"顺序改进"（SR）叠加也有效：55.10% → 60.20%。

**对 AI 应用工程师的启示**：①**瓶颈常在"选"不在"生成"**。给便宜模型配一个强验证器来选动作（这里是 9B 生成 + 前沿模型验证，50% → 68%），是一种和"小模型执行、大模型规划"不同的混合方式，适合那些动作有副作用、环境没法回滚的场景。②想让模型自己验证自己，**两两比较比打分或一次看全部更可靠**，这和上面 dynamic workflows 一文说的"比较式判断比绝对打分可靠"是一致的。③它只动了模型调用的包装函数，现有 harness 里很容易加。④本期速览里的《Can Terminal Agents Trust Their Own Verification?》给了自验证的基线数字：错误的候选解只有 61.43% 被发现，可以对着看。

## 趋势观察

**一、"自改进"从论文概念变成了有官方流程、有生产数据的工程实践，同一周也拿到了它最系统的一份反证。**

连着四期看，这条线的问题一直在换：09-21 那周是"harness 自演进要不要加闸门"，09-25 是"闸门怎么设"，09-28 是"演化的 agent 不能兼任自己的裁判"。本期往前走了两步。

第一步是**流程标准化**。Anthropic 的 hillclimb 一文、claude.ai 提速复盘和 NVIDIA 的 NeMo Relay 教程，三篇来自不同团队，写出来的验收流程几乎一样：固定任务和确定性的判定 → 先量噪声 → 一次只改一处 → 留出集或重复运行把关 → 收益在噪声内就不采纳。论文侧的 SAGE（逐题配对检验，回归率 36.5% → 0）、GSO（修好数 − 2 × 弄坏数）、SkillSpec（每次重复评估收益都非负才提交）是同一规则的统计学版本。可以认为"**不对称地惩罚回归 + 留出集 + 一轮一改**"已经是这个领域的共识做法。

第二步是**对"泛化"的清算**。大阪大学的受控对比（21 个里只有 5 个保住全部提升）说明，过去很多自演进 skill 论文报的训练集提升要打折看。EngramBench 指出现有评测把能力抽象和答案泄漏混在一起；False Frontiers 指出出题方和解题方会在共同的错误上越走越近；周五批次的《Safety Must Survive Self-Improvement》指出环境一变，旧评分会把坏程序留下来。四篇加起来的意思是：**自演进系统的评测本身也需要被验证**，这也正是 Anthropic 那篇文章花一半篇幅讲"先把 eval 建对"的原因。

**二、harness 该多重，本期给出了看似矛盾、其实一致的证据。**

一边是 MILO 靠重写控制流超过榜首、Mid-Harness 靠加一层动作验证把 50% 提到 68%。另一边是《How Much of a Harness Does a Strong Agent Need?》显示强模型下精巧的 MLE harness 不比极简 harness 好，MILO 自己的基线里 8 个 SoTA harness 有 7 个在 PaperBench 上不如极简 harness，NVIDIA 的 A/B 显示同一批修复对 Sonnet 无效、对 Qwen 有效。《Finding the Right Fit》把它说透了：模型排名会随 harness 反转，没有通用最优。

把这些放在一起，结论是：**harness 的价值取决于它补的是不是这个模型在这类任务上真正缺的东西**。Anthropic 四篇补录文章从设计者一侧给了同样的说法：TodoWrite 在模型变强后成了束缚而被换掉；加工具的门槛很高，因为每个工具都是模型多考虑的一个选项。实际做法只有一条：**先跑极简基线，每加一层机制都按模型分别验收**。

**三、控制面同构。**

上期说"凡是 agent 能碰到的地方都不能放控制"成了 NVIDIA 的产品原则。本期 OpenAI 的 dots 安全文和 Anthropic × NVIDIA 的公告把它变成了两家前沿厂商的共同架构：执行环境与安全系统分离、凭据不进模型上下文、独立的行动前审查、按后果分级确认。OpenAI 的训练 safety case 把同样的原则用在训练侧（监控 fail-closed、轨迹不可变、grader 不看思维链）。Claude Code mods 则是反方向的一步：把 harness 的每个事件开放给用户改写，于是需要一个最先加载的安全 mod 来守住权限规则。**harness 越可编程，"谁先看到事件、谁最后说了算"就越重要。**

**四、安全事件开始直接影响发布节奏。**

OpenAI 在 DevDay 前一天宣布放弃发布 GPT-6.1 Astra（理由是没达到自己的安全标准），Altman 说 IPO 没有时间表、"现在是把安全和使命放在第一位的时候"；Gemini 4 Argon 先只给网络防御者；Anthropic 的 GLM-5.3 评估显示开源权重模型的网络能力落后前沿约四个月，安全措施花 4,400 美元就能去掉。三件事指向同一个现实：**前沿能力的发布正在被安全评估结果实际卡住，而同等能力的无护栏版本在几个月后就会出现**。对应用工程师来说，这意味着部署侧的独立防线（沙箱、出网控制、审查层）不会因为模型自带安全措施而变得多余。

**对面试的实际意义**：本期可以直接用的三套答题骨架。①"怎么做 eval 并安全地迭代 prompt / skill"：Anthropic hillclimb 一文的流程 + 大阪大学论文的数字。②"怎么设计 agent 的工具和上下文"：四篇补录（缓存决定架构、工具随模型代际做减法、渐进式披露、三种单上下文失败模式）。③"怎么给 agent 产品做安全架构"：dots 的五层 + safety case 的 fail-closed 与不可变轨迹。
