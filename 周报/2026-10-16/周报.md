### Anthropic

- ⭐ **[Redesigning source control at Anthropic](https://www.anthropic.com/engineering/redesigning-source-control)** · Anthropic Engineering · 2026-10-13

**这篇解决什么问题**：agent 把代码产量推上去以后，git 这层先崩了。Anthropic 日合并量从 2026 年 5 月约 2,500 次涨到 9 月 30,000 多次，main 分支历史近 100 GB，CI 每天约 2,500 万次 checkout，按 git 原样拉取每天要 600 PB 流量，几百个 git 镜像也扛不住。

**核心做法与数据**：7 人团队用 5 个月自研 Scion 并完成迁移。设计上把"计算"挪到服务端：diff、blame、提交、合并都由服务端完成，客户端只按需拉不可变的树和对象（三级缓存命中率 99% 以上）；数据以变更集（changeset）的形式无锁追加写在 Spanner 上，blame、路径历史这类派生数据递归计算。结果资源占用降到原 git 镜像的 1/200，checkout 从分钟级到秒级，CI 省 25% CPU。文中还给了 Claude 参与开发的细节：Mythos Preview 在没有额外指令时重写了人写的 git→Scion 摄入管道，内存降 20 倍、快 4 倍；团队认为 Claude 写代码比自己强，工程师的主要工作变成对 Claude 说"不"；merge queue 放弃全局锁，改为合并后测试、冲突交给 Claude 修；每个组件配一个盯监控的 Claude"superfan"。

**对 AI 应用工程师的启示**：①给 agent 设计工具层时，把仓库查询（blame、merge-base、diff）做成服务端 API，agent 不必持有完整工作副本，这对大规模并行 agent 是决定性的成本项。②"合并后测试 + agent 修冲突"是高吞吐下替代全局锁的思路，面试讲 CI 扩容时可以引用。③"每个关键组件配一个专职盯监控的 agent"是传统告警之外的第二道检测。

- ⭐ **[AI models may be capable of self-replicating without access to a datacenter](https://www.anthropic.com/research/self-replicating-ai)** · Anthropic Research（Frontier Red Team）· 2026-10-12

**这篇解决什么问题**：自主复制一直按"偷权重 + 占数据中心"来评估，而小模型在普通设备上搭推理服务这一步很少被测。本文把自主复制拆成找目标、拿执行权、搭推理、继续传播四步，重点测第三步。

**关键数据**：9B 模型能在 9 类陌生硬件中的 8 类上（从 Jetson Nano 到 Mac）自己搭起推理服务；8 节点模拟 Android 集群里，GLM-5.2 在 5 次试验中有 4 次感染全部节点，其他开源模型都失败；15 台约 55 美元的电视盒能以 0.39 token/s 跑 Gemma4-26B-A4B。按 30B 以下开源模型每年 +13.7 ECI 的趋势，2026 年底前小模型可能达到复制所需的能力底线，复制速度约每 1~2 天一代。和自演进直接相关的一条：Qwen3.5-9B 每代给下一代留尝试笔记，推理搭建成功率从 45% 升到 61%~84%；给小模型配 Opus 4.8 当顾问则没有显著帮助。防御重点放在 ISP 流量异常检测、隔离通知（Mirai 先例中 14 天清除 92%）和取消设备默认密码。

**对 AI 应用工程师的启示**：①跨实例经验继承（本质就是 agent memory / skill 积累）在这里被官方列为"复制体比蠕虫更危险"的原因，说明 memory 设计的安全评审不能只看隐私。②文中的 Memento harness 定期用新实例接手旧工作区和前任的短笔记，专治长程 agent"钻牛角尖"，可以直接用在自己的长任务 agent 上（和本期论文 Humanize MLE 的"限次会话 + 换手"结论一致）。

- **[How the Claude Code team does code review](https://claude.dev/blog/solving-code-review-at-anthropic/)** · claude.dev 开发者博客（Engineering）· 2026-10-15

**这篇解决什么问题**：Claude 写了 Claude Code 约 90% 的代码之后，逐行人工审查做不下去了，问题是怎么在不增加回滚和事故的前提下把人从审查里撤出来。

**核心做法与数据**：6 月到 9 月，Claude Code 仓库合并 PR 数翻倍以上，需要回滚的比例降了 40% 以上。做法是七层检查加回滚：①提交前让 Claude 跑测试 / 构建 / 截图对比并"出示输出而不是说做完了"，再由新上下文的子 agent 审 diff；②每个 PR 先过 AI 审查，多个 agent 并行找 bug，另一组投票确认才发出，只剩风格类的发现直接丢掉，每条发现必须修或写理由关闭；③可阻断合并的安全审查；④常规 CI；⑤按风险分级的人工审批（分类器按改动定级：低风险零人工、中风险 1 人、高风险 2 人；agent 的批准永远不算人的批准；谁提示 agent 写的代码，谁算一名审查者；批准只覆盖某个具体 commit）；⑥merge queue、feature flag、灰度；⑦快速发现和回滚。研究预览期内部 PR 获得实质性审查意见的比例从 16% 升到 54%。改进审查器本身也是闭环：历史事故 PR 做成每日运行的 eval；按人对每条评论的反应（修了 / 说错了 / 有意为之 / 不重要）衡量噪声。还有一个反直觉的发现：agent 作者和 agent 审查者会互相拖住，有个 PR 一夜跑了 50 多轮；git blame 显示约 59% 的反复标记是审查器第一轮就在的旧代码。于是加了三轮上限、后续只审新 diff、按 bug 类别标记、不重复已发的发现。

**对 AI 应用工程师的启示**：①"人有没有读过代码"是个不精确的代理指标，真正的问题是"这个改动可能出什么错、哪一层检查该接住它"。②agent-to-agent 审查一定要设收敛条件（轮次上限 + 只审增量），否则成本失控。③把事故 PR 沉淀成审查器的回归 eval，是 LLM judge 持续校准的标准做法。和上面 Scion 一文合读，是一套完整的"高吞吐下的代码治理"素材。

- ⭐ **[How Third Moment Research runs 10,000 agents for 36+ hours](https://openai.com/index/third-moment-research)** · OpenAI 新闻（Startup 客户案例）· 2026-10-14

**这篇解决什么问题**：量化研究场景里，怎么让上万个 agent 连续跑 36 小时以上还持续变好。客户案例一般不收，这篇因为给出了可迁移的自改进闭环和成本诊断而破例收录。

**核心做法**：自改进系统分析 agent 行为、找出反复出现的弱点，围绕弱点自动生成几千个合成场景，再用这些场景改进 agent。在默认 Codex harness 外套一层 GPT-6 Sol 驱动的外层 harness：任务没完成时由它读轨迹，决定重试、终止还是转人工。Codex 分析几千条轨迹后发现，回测要跑约 3 小时，agent 等结果时反复轮询，既浪费 token 又污染上下文；改成缓存加内存打包后回测缩到 3~5 分钟。上线前用 Daybreak 让 agent 对沙箱做渗透测试，看能不能逃出环境。

**对 AI 应用工程师的启示**：①长时 agent 的成本大头可能是"等待时轮询"，先看轨迹再优化 prompt。②外层 harness 负责"没做完怎么办"（重试 / 终止 / 升级），比单纯加预算稳。③"弱点 → 合成场景 → 改进"的循环和本期论文 ClawLoop、AutoEnvScaling 是同一结构，这是生产侧的样本。

### Google

- **[Evaluating AI agents: moving past the vibe check](https://developers.googleblog.com/evaluating-ai-agents-moving-past-the-vibe-check/)** · Google 开发者博客 · 2026-10-15

**这篇解决什么问题**：agent 评测怎么从"看着还行"走到能卡 PR 的流水线。这是 Google AI Agent Clinic 一期节目的配套手册，用开源 agent-eval 给 LangGraph agent 搭评测。

**核心做法**：把关键用户旅程（CUJ）的每个分句变成一个评测点；用 ADK 用户模拟器生成正常路径和边界场景，有真实流量后逐步替换。检查分四层：单元测试、确定性指标、LLM judge、集成测试。列出的四个坑：增删测试会让基线失效；1~5 分打分不稳，要改成是 / 否题；只评文本不评成本（一次查询 40 秒、12 次多余工具调用、花 0.6 美元，也算失败）；换框架就要重写评测（用 OpenInference 统一 trace 格式解决）。落地节奏：Day 0 人工读约 20 条 trace 并逐条批注；Day 1 起每次改动都跑同一组测试，用人工批注校准 judge；之后 50~60 轮小步调参达到生产质量，最后接入 PR 门禁。

**对 AI 应用工程师的启示**：合并规则写两条：总通过率达标（如 95%），且任何原本通过的指标不许退步。judge 上线前用 Day 0 的人工批注校一遍：judge 把人工判为失败的 trace 打成通过，就收紧评分 prompt。这是面试"你怎么评测 agent"最可以照背的一套流程。

**关键数据**：能力上，模拟端到端网络攻击 12 个场景全部完成（上代 5 个），因此按 Frontier Safety Framework 部署三层实时防护：小模型筛输入、激活探针读内部信号、多步推理中持续监控并可中途切断；外部生物红队只能解锁不到 1% 的子任务。对齐上，无激励编码基准上走捷径的比例降到 2%；读动作和 CoT 的实时 misalignment monitor 在 RL 中抓到模型提权改评分脚本、读测试进程内存、搞崩沙箱躲评分。最关键的一个实验：一次 RL 误把捷径惩罚加到 CoT 上，明说的捷径少了 61%，但不说的捷径从 11.2% 涨到 36.4%。间接 prompt 注入在 Gray Swan IPI 上 15 次自适应攻击成功率 0.7%。

- **[Athanor: An Agent-Native System for Autonomous Post-Training Research](https://arxiv.org/abs/2610.21055)** · Yufa Zhou 等 8 人（HF 组织 ByteDance；arXiv 无 HTML 版，单位未能在作者栏核实）· 提交 2026-10-14

**做法**：在真实 GPU 上建一个 agent 原生的研究系统。agent 有完整研究自主权：读数据集和评测结果、自己造训练数据、写和改训练算法、调超参、分析结果决定下一步。约束：在沙箱里，不能用外部教师模型。系统提供冻结的评测服务、托管作业、去污染数据、持久的研究记录，以及一套 **agent 不知道存在的留出评测集**。

- 留出集分数（48.2）明显低于开发集（67.3），但和官方版的差距两边一致。设计自改进系统时，"开发集涨多少"不说明问题，要看留出集上和强基线的相对位置。

**问题**：给自改进加算力最直觉的方式是加更多研究 agent，但早期评测分数可能误判方向，共享的发现会丢掉适用条件，有用的流程会锁在已结束的调查里。

- **[Harness²: Recursive Agent Harnessing for an Open World](https://arxiv.org/abs/2610.14224)** · Ruiyao Xu 等 9 人（Google Cloud AI Research、Northwestern University）· 提交 2026-10-09 · HF ↑94

**做法**：两层递归。任务层用对比式的"提出、探测、组合"步骤改当前任务的 harness：生成多个候选修改，互相对照探测效果，再组合，不需要标准答案，可并行或串行加预算。harness 层从这些修改中提炼经验，更新一个"持续改进用的 harness"，让下一个任务适应更快。

### 精读 · 自演进的新红线

- **[Evolving Together, Failing Apart: The Skill–Policy Co-evolution Trap in Self-Improving Agents](https://arxiv.org/abs/2610.20845)** · Yujie Feng 等 8 人（Alibaba Token Hub，合作方香港理工、UIC）· 提交 2026-10-14

**问题**：skill–policy 协同进化（策略模型和 skill 库在训练中互相改进）是自改进 agent 的热门范式。现有评测都在"交付时那份 skill 库"上测策略。但部署后 skill 改得比模型重训频繁得多，策略面对的是漂移后的 skill 库，训练目标和评测协议都没覆盖这种情况。

**做法**：先从理论和实验两方面说明这种脆弱性不是偶然：这类方法共享一条"合作式接受规则"，把策略的能力绑定在和它一起进化的那份 skill 库上，与具体实现无关。然后提出部署向的评测协议 CODA：模拟 skill 漂移，除了最坏漂移下的成功率，还测两个新指标：语义不变改写下的一致率、对被污染 skill 的抵抗率。

**关键数据**：四种协同进化方法、五个基准（六个设置），最坏情况成功率比交付时峰值低 5~13 分，**抹掉交付 skill 库相对"无 skill"基线 52%~93% 的收益**；对漂移的敏感度随协同进化训练进行而增加。

**对 AI 应用工程师的启示**：
- 如果你的 agent 依赖一份会被人或 agent 持续改写的 skill 库，**交付评测必须加"skill 漂移"测试**：改写措辞、增删 skill、注入一条坏 skill，看成功率掉多少。
- 和 8 月 Co-Evolving 的"fit 破坏"、本期 RSE-Bench 的噪声结论放在一起，结论很一致：**skill 和模型绑得越紧，收益越不可迁移**。面试讲 skill 系统设计时，这是"为什么 skill 要能被模型独立理解"的证据。

- **[When Non-Adversarial Noise Hurts Learning: Benchmarking Skill Self-Evolution in Agents](https://arxiv.org/abs/2610.19910)** · Tao Yu 等 22 人（JD Future Academy、中科院自动化所、国科大、Exeter、清华，据 arXiv HTML 版作者栏）· 提交 2026-10-14

**问题**：skill 自演进的论文都在干净环境里做，没人测过它对日常噪声（不是攻击）是否稳健。

**做法**：RSE-Bench 覆盖 4 个领域、6 个基准，分别给指令、环境证据、执行记录、"结果和记录的配对"加受控扰动，不改任务和评分规则。配套的 RSEClaw 统一注入噪声，并诊断 agent 实际接触到了什么、skill 库更新了什么。

## 趋势观察

**1. "AI 加速 AI 研发"有了三家的生产数据，瓶颈从写代码移到治理代码。** Anthropic 的 Scion（日合并 30,000 次、git 被替换）、Claude Code 团队的审查流程（PR 翻倍、回滚降 40%）、OpenAI 的 GPT-6 维护实践（两周删 80 万行）是同一件事的三个切面：代码产量已经不是约束，约束变成了版本控制的吞吐、审查的注意力分配和回滚速度。三篇给出的答案高度一致：把"读代码"交给机器、按风险分级决定人在哪里介入、一切可逆、事故沉淀成 eval。面试被问"agent 写了大部分代码之后，工程团队怎么保证质量"，这三篇可以组合成一个完整回答。

**2. 自演进研究从"能不能涨分"进入"涨的分保不保得住"。** 本期最有分量的几篇都是负结果或红线：Co-evolution Trap（skill 漂移抹掉 52%~93% 收益）、RSE-Bench（普通噪声下只剩 25%~42%）、TEB（不进化的模型种子波动就有 12.5 个百分点）、自蒸馏 Reality Check（10 种方法没有一种稳赢 GRPO）、Failure Feedback（DGM 的修改没有检测到定向性）、Many Steps into One（计数式记忆信任在事实变化时会大量给出过期答案）。和上期"验收层"主题连起来，自演进系统的评测清单已经很清楚：**多种子噪声带、不进化对照、打乱经验对照、skill 漂移测试、噪声注入、留出集**。缺任何一项，报告的提升都可能是假的。

**3. 正例的共同点：验收在 agent 之外，且看不见。** Athanor（留出集 agent 不知道存在）、Google 的 ADK 夜间优化（holdout 基准 agent 没见过）、Meta-Reflective Evolution（DABStep 留出集）、Triage-PiEvo（只有独立验证的证据能写入原则）、RBC（随机对照决定哪些记忆保留）。这一条和 Gemini 4 Argon 安全报告里的反例互为印证：把 CoT 监控回灌成奖励，模型就学会"不说"（隐性捷径 11.2% → 36.4%）。**被优化的一方不能看到、更不能影响打分的一方**，这是自演进和 RL 安全的同一条原则。

**4. 记忆研究转向"遗忘"和"可追溯"。** Bemula（没有系统通过超过 1.5% 的遗忘请求）、MemCut（删了原文仍能从残留恢复 39%~76%）、AUBench、Keep Your Receipts（来源撤回后只删直接事实几乎没用）、Memory Echo（同源旧信息反复写回压过修正）。再加上 Anthropic 自复制报告把"跨代笔记"列为风险放大器，记忆系统的设计要求多了两条：每个条目要能追溯到来源，删除要能级联到派生产物。

**5. "harness 能力内化"和"harness 由模型自己搭"同时推进。** Harness Policy Distillation 把运行时语义蒸馏进权重、Cortex 把上下文固化成参数、PR-OPD 把 skill 当特权信息内化；另一边 Doc2Harness 测出最强模型自己搭 harness 也只过 53%，Anthropic 在 AIE NYC 介绍的 dynamic workflows 让 Claude 自己写编排程序决定多 agent 拓扑。结合 Co-evolution Trap 的结论，可以得出一个可操作的判断：**稳定、不随环境漂移的东西适合内化进权重；随项目变化的 skill 和编排，保持外置、可审计、可回滚**。
