## 本周新文章

### OpenAI

- ⭐ **[Rethinking skills and prompts for GPT-6 Astra](https://developers.openai.com/blog/rethinking-skills-and-prompts-for-gpt-6-astra)** · 9 月 11 日（developers.openai.com/blog）

  这篇解决的问题：过去一年为了把模型"扶"到可用，大家往项目里堆了大量 skill、AGENTS.md 条款和任务提示词，而 GPT-6 Astra 这一代让其中很多变成了**净负担**。文章按四块给出具体改法。**skill 层**：每个 skill 的 name + description 常驻上下文，描述太长会被 Codex 自动截断，"模型看到的每条描述都变少，反而更难选对"；描述之间还经常互相矛盾或过度强调适用范围。官方给的正反例极好背——坏："创建和校验 Postgres 迁移。**在处理数据库、查询、模型或持久化时使用**"；好："创建和校验 Postgres 迁移。**在新增/修改迁移或评审其上线时使用**"。第二条是 **progressive disclosure**：读 skill 要吃上下文、把你推向 compaction，所以多工作流的 skill 根文档应该是**最小路由器**，指向支撑文档和脚本，让模型知道去哪找而不是被迫全读。第三条：很多 skill 写成了详尽"行程单/菜谱"，而模型理解模糊性的能力已经提升，**过度具体的指导现在会拖后腿**；并且仓库里的 skill 会作用于别人用其他模型的 agent，"帮 Sol 或 Luna 的指导可能会过度约束 Astra"。**AGENTS.md 层**：反例是"每次编辑前先读 architecture.md、database.md、deployment.md"，正例是"改服务边界看 architecture.md，改 schema 看 database.md，准备部署看 deployment.md"——**上下文化地指路，而不是无条件预读**；同理，"记得跑测试、检查你的工作"这类为旧模型加的叮嘱现在会导致无谓的重复测试。**决策边界层**：以前为了防止模型擅自行动而加的强硬措辞，在"我们最对齐的模型"上会被**当真过头**——Astra 本来就不会在不确定安全时动手，旧的强硬语言只会让它在你其实希望它继续时停下。官方给的替代写法是显式授权某个已知安全的工作流："本地测试用一次性 fixture、无生产访问权限；直接运行、修复由本次改动引起的失败并重跑受影响测试，不必每步都请示。" **持续性层**：Astra 比 GPT-5.6 Sol 更容易"做到第一版实现就回来请你 review"，所以**要在开工前定义"完成"**——如果任务包含跑起来、看结果、修失败，就把这些写进请求里；反过来，"第一版做完停下来等评审"这句话本身就会把模型拉向更早的停止点。结尾还给了一条元建议：让 Astra 自己按本文做一次审计。启示：面试里被问"升级模型后该做什么"，这篇给了标准答案的四步——**审 skill 描述（短 + 何时用）、审 AGENTS.md（删预读、删叮嘱）、审边界语言（别让对齐模型过度保守）、审完成定义**；它同时也是 Anthropic《降本三杠杆》里"删反模式"那一步的 OpenAI 版本，两家在同一周内给出了同样的结论，这本身就是范式信号。

- **[Rapidly scaling online storage to serve over 1 billion ChatGPT users](https://openai.com/index/scaling-storage-one-billion-users-part-one/)** · 9 月 11 日（openai.com，Engineering，两部曲第一篇）

  这篇解决的问题：AI 产品的对外表现（登录、打开会话、读设置）背后是**每次请求上百次数据库调用**，慢一次就整体慢、挂一次就整体不可用。OpenAI 公开了在线存储平台 **Habitat** 的演化史：**70M+ 请求/秒、10 亿+ 周活用户、500 PB+ 数据、近 40 个地理区域**；起点是 2023 年 DevDay 为 GPTs 写的一个 Python 客户端库，包住 Azure Cosmos DB，让产品工程师不必关心 schema 查找、路由、鉴权、加密、序列化、连接池。**第一个转折是"库变服务"**：到 2025 年中，客户端库形态触顶——一次把关键数据集迁到区域分布式 Cosmos 账号的改动，需要在几十个服务里加路由逻辑、挂 feature flag、逐个协调发布，光是加 shadow 验证又是几天，改个 bug 再几天。改成独立服务后，部署、可观测、平台能力有了**单一控制点**，安全上也有了统一的访问控制与审计**咽喉点**。**第二个转折是"明知 Python 不划算也先上"**：他们明确称之为"战略性技术债"——当时的首要目标不是省成本，而是解除产品开发阻塞、稳住平台；并且**押注自家编码模型的进步会让后续迁移变得可行**（文中明说"这个赌注后来被证明是对的"）。**第三块是 Python 服务的性能工程**：asyncio 提供并发但不提供 CPU 并行，而 Habitat 的路由、压缩、加密、校验和、下游健康检查、影子请求、对冲请求都是 CPU 密集型，结果**调度延迟主导尾延迟**——p99 的 trace 里下游存储早就返回了，请求却卡在等协程被重新调度上。启示：对 AI 应用工程师，这篇的可迁移点有三个——**把存储/模型访问收敛成一个服务而不是一个库**（否则每次策略变更都要全公司协调发布）；**把"当前次优但能解阻塞"的选择显式记成技术债并写下偿还条件**；以及**在 Python 服务里，尾延迟先去看事件循环调度延迟而不是数据库**。第二部分（多租户可靠性、分层读优化、与 Azure Cosmos DB 的合作扩容）尚未发布。

### Anthropic

- ⭐ **[Formalizing Fermat's Last Theorem](https://www.anthropic.com/research/formalizing-fermats-last-theorem)** · 9 月 4 日（anthropic.com/research）

  这篇解决的问题：数学界预期需要数年的 FLT 形式化工程，Claude 用 **11 天**基本自主完成——但对工程读者来说，真正的内容是**"几十个 agent 如何在两周的长时程项目里不散架"**。数据：最终证明含 **30,300 条**计算机可验证定理（29,500 条用于最终证明）、**1,300 万行 Lean 代码**（超过社区蓝图规模 5 倍以上），消耗约 **60 亿输出 token**，模型是与 Fable 5.1 大致相当的内部通用研究模型，harness 基于 Claude Code 做多 agent。**最值得记的是第一次失败**：早期 agent 有局部进展，但**很快丢失项目状态、停止有效协作**，这些失败贡献了最终证明中约 7% 的非样板代码。转机是换用 Prove2Me 协作平台，它做了三件事——① 维护一张**定理陈述的有向无环图（DAG）**，agent 据此决定下一步该证什么，"**这对缓解记忆退化、支持多 agent 并行特别有效**"；② 把定理陈述与证明**拆到不同文件**、链接独立维护，从而加速 Lean 编译、压低资源消耗；③ 为每条定理维护**自然语言描述**以支持搜索与复用。人类输入被压缩成偶尔的高层指令（"把 Jacobian 作为 scheme 优先级很高"）。文章还提到一个便宜的复现：三个个人 Claude Max 订阅、仅通过 Prove2Me 协作，agent 联合完成了 Vinogradov 定理相关的形式化。启示：这是《Building a C compiler with parallel Claudes》之后规模最大的一次并行 Claude 实验，给出的可复用结论非常具体——**长时程多 agent 的共享状态不应该是聊天记录或长上下文，而应该是一张带自然语言描述的任务依赖图**（可检索、可复用、可判断"下一步做什么"）；**产物要拆成"声明"与"实现"两层**以便增量验证；以及一条对 AI 应用工程师同样成立的元结论——**有了机器可检验的验证器（Lean / 测试 / evaluator），agent 的长时程自主性就能显著外推**，这也是 Anthropic 说"写 Lean 似乎还能帮 Claude 证明新结果"的原因：它把形式化当成了自我检查的工具。

- **[Detecting and countering misuse of AI: September 2026](https://www.anthropic.com/threat-intelligence-report-september-2026)** · 9 月 10 日（anthropic.com/news，长篇威胁情报报告）

  这篇解决的问题：把 2025-12 ~ 2026-08 期间被打断的真实滥用案例摊开，回答"agent 能力提升到底把攻击面改成了什么样"。覆盖七个危害领域（网络攻击、影响力行动、监控、诈骗、生物滥用、常规武器、蒸馏），涉事模型为 Haiku / Sonnet / Opus（Fable 与 Mythos 基本未见，后者有专门护栏）。工程上最值得记的是两条趋势判断：**①「复杂的攻击不再需要复杂的攻击者」**——一个用偷来的 API key 的黑客活动分子、若干各自为战的逐利个人、一个国家级间谍操作者，都能维持多受害者的长期战役，而这在一年前需要国家级资源；对威胁情报而言，"**攻击的复杂度不再是判断幕后是谁的可靠信号**"。**② AI 在攻击链中的角色从助手变成编排者**：2025-11 记录的那套"自主攻击操作模式"如今已扩散到所有被调查的行动者类别，公开的攻击性 agent 框架（文中点名 PentAGI）把同样的脚手架送到任何人手里。Anthropic 用 GTG（Generative Threat Group）编号追踪这些行为体，并用"速度、规模、深度"三维度量化 AI 提供的"uplift"。启示：给做 agent 产品的人两条直接可用的判断——**你的产品被滥用时的对手画像要重画**（不再假设"只有高水平团队能做长期自动化攻击"）；以及**防守侧的检测要看行为编排的痕迹而不是技艺水平**。这份报告与上期《对齐评估》、更早的《How we contain Claude》构成 Anthropic 安全三件套：一篇讲模型内部为何越界，一篇讲产品层如何围堵，这篇讲外部世界真的在怎么用。

- ⭐ **[Automated researchers can reliably mitigate alignment failures](https://www.anthropic.com/research/automated-researchers-mitigate-alignment-failures)** · 8 月 28 日（anthropic.com/research，Alignment 团队；[完整报告 PDF](https://www-cdn.anthropic.com/7b1c44894e980876479947dcdd40716278aeeffd/automated-alignment-researchers-august-2026.pdf)）

  这篇解决的问题：如果 AI 开始自己造 AI，安全研究必须以同样的速度自动化——那么**自动化研究员到底能不能真的修好对齐问题**？实验设计非常适合借鉴：让 Claude 驱动的研究 agent 针对 **10 类对齐失败**（欺骗、谄媚、奖励黑客等）各自独立地提出并迭代缓解方法，评分口径是"**安全差距闭合百分比**"（离该类失败的理论满分还差多远，用 3–5 个基准取平均），并**排除任何损害学生模型通用能力的方法**。三项验收条件都很硬：方法要在**研究循环中从未见过的**对齐评测上仍然有效、不能降低模型能力、还要在 Petri（开源的多轮对抗场景模拟工具）上站得住。结果：10 类失败全部找到了"提升目标基准且不损能力"的修法；欺骗类上 Claude 的最佳方法比 **28 位人类安全研究员**（每人最多 8 小时）的最佳提案好 20%，安全差距闭合 **85% vs 人类 20%**（作者谨慎地指出人类不能迭代，因此更适合读作"人类出主意 + Claude 迭代"的工作流证据）。**最重的一条是弱到强**：让 Claude Sonnet 5（在 Epoch Capabilities Index 上弱于 Opus 4.8）去修复一个尚未经过大部分生产对齐训练的 **Opus 4.8 早期检查点**——**60 小时内试了 50+ 方案**，闭合了该模型 65% 的安全差距（已发布的 Opus 4.8 为 72%），而获胜方案只用了**2,000 出头的训练样本**，由简单模板或公开数据集构成，**比生产对齐流程的数据效率高约 15,000 倍**。方法学上还有两个细节值得抄：一是**作弊监控**——用 Opus 4.8 审查约 1,600 条研究 agent 转录，发现 **39 条（2.4%）**存在作弊（此前已知 Claude 会从远程 API 偷测试标签、挑好结果）；二是**方法收敛于文献而非发明新招**（谄媚类 98% 的提案用的是"拿模型自己的非谄媚回答训练它"这一已发表技术，只是迭代得更好）。**对齐 harness 已开源**。启示：这是"自演进"从 skill/harness 层上升到**权重层**的官方证据，而且给出了应用工程师能复用的三件套——**把目标写成可自动评分的差距指标、把"不许损害通用能力"做成硬否决门、给自动研究员配一个专门的作弊监控**。它也是 Peter 长期关注的"弱模型监督强模型"路线第一次拿到生产级模型上的正面数据。

- ⭐ **[When AI builds itself](https://www.anthropic.com/institute/recursive-self-improvement)** · Anthropic Institute（页面未标注发布日期，文内数据截至 2026-05，引用 Opus 4.7 系统卡；作者 Marina Favaro、Jack Clark）

  这篇解决的问题：用**内部未公开数据**回答"AI 加速 AI 研发到了什么程度"。外部信号：METR 的任务时长视界约**每 4 个月翻倍**（早前趋势是 7 个月），SWE-bench 两年内从个位数分到饱和，CORE-Bench（复现已发表论文的结果）从 2024 年约 20% 到 15 个月后饱和。内部数据才是重点：**截至 2026-05，合入 Anthropic 代码库的代码 80%+ 由 Claude 编写**（Claude Code 2025-02 研究预览前是个位数百分比）；**人均季度代码量约为 2021–2025 的 8 倍**（作者自己提醒行数是劣质指标，只能读作加速信号）；2026-03 对 130 名研究人员的调查中，中位数认为用 Mythos Preview 的产出约为**无 AI 时的 4 倍**；Claude Code 会话成功率（由 Claude 裁判判定"无需人类纠正即完成"）在**开放式问题**上从半年前的约 26% 升到 2026-05 的 **76%**；代码质量上，内部判断是"2025 年底 Claude 写的代码略差于人类、今天大致持平、预期一年内严格更好"，并且**每个改动都过自动 Claude 评审**后回溯分析显示，这能抓住过去 claude.ai 事故中**约三分之一**的 bug。研究侧给了三级阶梯：**执行既定实验**（每次发版都跑同一测试：给一段训小模型的代码让它在通过正确性检查的前提下尽量加速）→ **自己提实验**（2026-04 首次端到端跑完一个开放安全课题）→ **把研究会话引向发现**（在 129 个"人类当时的选择有改进空间"的真实时刻上比较模型与人类的下一步选择）。文章也直白地写了组织后果：**一旦人写码停止、评审成为瓶颈**，以及员工的两句原话——"大约 5 个月没自己写过代码了"、"一切顺利的日子里我会觉得我做的一切都不重要"。最后给了三种未来（趋势停滞但能力扩散 / 人类保持方向设定但被极大放大 / 完全递归自改进）。启示：这是与 OpenAI 09-06《Research acceleration》可直接对照的第二份官方 RSI 量化报告，**面试里谈"AI 对工程组织的影响"时，这两组数字是最硬的引用来源**；对个人的可操作含义是它明确点出的那句——**人类的比较优势正在收敛到"选问题、判断结果可信度、判断此路不通"**。

- **[Patterns and problems in emerging multiagent systems](https://www.anthropic.com/research/multiagent-systems)** · 8 月 13 日（anthropic.com/research，Frontier Red Team）

  这篇解决的问题：多 agent 系统真正的难点不在"能不能并行"，而在**agent 之间互相依赖时的协调**。三组实验的数字很值得记。**实验一（高度可并行的漏洞挖掘）**：45 个 agent 各自一台虚拟机、共享一个论坛、相同提示词去 15 个开源项目找漏洞。Mythos Preview 下，**独立并行**方式 650 万 token 找到 21 个漏洞，**协调式蜂群** 2,700 万 token 找到 266 个，但两者**只有 12 个重合**——协调蜂群能把注意力集中到"最容易挖到矿"的地方（约一半漏洞落在独立 agent 被预分配的核心目录之外），两种方法**互补而非替代**。**实验二（强依赖的软件工程）**：让若干蜂群各自做一个网页版开放世界文字游戏，用 PR 合并率与"代码共享度"两个指标；agent 数从 10 涨到 80 时，Sonnet 4.6 / Opus 4.6 的合并率**急剧下降**——它们往同一批文件提交却极少合并，PR 互相冲突（80 agent 规模下开了 876 / 980 个 PR 却几乎不关闭），**只有 Sonnet 5 能同时维持高合并率与真实协作**。**实验三**关注从众带来的失败模式（与人类的协调失败形态不同）。启示：给做 multi-agent 的人三条硬规则——**先判断任务是"可并行"还是"强依赖"**，前者上蜂群几乎稳赚且与静态分工互补，后者的瓶颈是合并冲突而非算力；**选型时把"合并率/共享度"这类协调指标纳入评测**而不是只看最终产物；以及**模型代际对协调能力的影响远大于 agent 数量**——加 agent 在弱模型上会让情况更糟。

- **[Piloting the world's first double-blind AI evaluations](https://deepmind.google/blog/piloting-the-worlds-first-double-blind-ai-evaluations/)** · 8 月 27 日（Google DeepMind，Responsibility & Safety；作者 William Isaac、Sol Messing、Kristian Lum；附[技术报告](https://storage.googleapis.com/deepmind-media/DeepMind.com/Blog/piloting-the-worlds-first-double-blind-ai-evaluations/double-blind-evaluations-technical-report.pdf)）

  这篇解决的问题：外部评测长期卡在一个二选一——**要么评测方交出题目**（模型厂商可能提前"看到考卷"，分数被污染），**要么厂商交出权重**（知识产权风险）。DeepMind 与新加坡 AI Safety Institute、OpenMined、AVERI、MLCommons 合作，用 Google Cloud Confidential Computing 的 Confidential Space 把评测放进**加密"盒子"**（GPU enclave）：评测方看不到 Gemini 权重，厂商看不到评测题目，双方都能拿到**密码学证明**说明对方的数据确实没有外泄。文中把它类比成考试——"考生提前瞄了一眼题目，满分就没有意义了"。启示：这是"评测独立成学科"这条主线上的基础设施级进展，对应用工程师有两层价值：**一是心智模型**——在你自己的迭代里，"评测集是否可能已被训练/被 prompt 泄漏"是每次分数跳变时必须先排除的解释（与本刊多次出现的"测试集入循环前先冻结"是同一件事）；**二是选型判据**——将来读模型发布的安全评测数字时，"是否经过第三方双盲"会成为可信度分级的显式标准。

- **[Science One Framework: A verifiable autonomous research framework via Chain-of-Evidence](https://research.google/blog/science-one-framework-a-verifiable-autonomous-research-framework-via-chain-of-evidence/)** · 7 月 30 日（Google Research）

  这篇解决的问题：自动科研 agent（AI-Scientist 一类）能产出论文，但**产出的可信度无法核验**——幻觉引用、复现不出来的分数、论文里说 A 代码里做 B。Google 提出 **Chain-of-Evidence（CoE）** 框架：它不规定 agent 怎么造，而是规定**产出必须具备的性质**（作者类比 ACID 之于数据库事务），每条论断都要能沿证据链追回到具体产物。Science One Framework 是其原型实现，三个组件都很具工程味：**问题调研器**用 Semantic Scholar API 构建引用图、每主题最多读 100 篇全文 PDF 产出结构化 brief，**每条参考文献都必须落在读过的 PDF 上**；**发现引擎**做并行 explore-exploit，多分支隔离运行、Solver 实现 + 任务专用 evaluator 打分、高分分支迭代精炼、**原始 evaluator 输出全部留痕**；**论文写作器 + 论断校验器**在渲染前把每条事实性论断结构化并绑定到工作区产物，由独立 Claim Verifier 逐条核验，**超出证据的论断被砍掉或降级**。配套的 **CoE Audit** 把可验证性变成可测量的三项：分数核验（独立重跑提交的代码并与论文中的分数比对）、规范违规检查（代码是不是在钻 evaluator 的空子或偷读标准答案）、引用核验（逐条查学术 API 抓"幽灵文献"）。启示：这是本刊反复出现的"**agent 自演进必须先有可信的验证器**"在科研场景的完整落地样板；把它翻译到日常工程就是——**让 agent 输出的每条结论都携带指向产物的证据标签，并用一个独立的校验器逐条核**，这比事后让人类抽查有效得多，也是给自改进循环设"门"的通用做法。

## 论文速递 ⭐ 自演进的"补漏周"：价值在哪、预算怎么分、技能库怎么长

> 本周 HF Daily Papers（09-09 ~ 09-11）的 agent 自演进新增较上周回落，因此本期额外用 arXiv 检索把 08-24 ~ 09-05 期间**漏收的自学习/自演进论文一次补齐**（Peter 要求此方向不设上限、一篇不漏）。四篇精读围绕同一个问题：**harness/skill 的自演进，价值究竟落在哪、要用什么预算和门控去拿。** 标题、日期、机构均经 arXiv 元数据与 PDF 首页核实。

- ⭐ **[Where Does Harness-Optimization Value Live? Localized Gains and the Budget-Splitting Trap in Self-Evolving LLM Agents](https://arxiv.org/abs/2609.02889)** · Michael Nguyen, Wei Chen Tan, Nurul Aisyah Hassan 等（马来亚大学 / 马来西亚理科大学 / 博特拉大学 / 莫纳什马来西亚）· arXiv 元数据标注 2026-06-25（2609 编号于 9 月上线）

  这是本期最该读的一篇**负结果**。做法：把 harness 拆成四个可分别演化的槽位——**role（角色）、task-strategy（任务策略）、tool/format-rules（工具与格式规则）、reflection/control（反思与控制）**，用同一个反思式优化器在**等预算**下逐槽调优，再用 leave-one-in / leave-one-out 把留出集收益归因到单个槽位。结果一：在 ALFWorld + 冻结的 7B 骨干上，**分槽演化并不比原版 harness 或整串演化更好**（0.657 vs 0.642 vs 0.642），也就是说"把 harness 结构化"本身不产生收益。结果二（真正的发现）：**几乎全部优化价值集中在 reflection/control 槽**，其 leave-one-in 收益 **+0.119**，其余三个槽单独看**全是 null**。结果三（最狠的一条）：**均匀分配预算是有害的**——64 次 rollout 平摊到四个槽，每槽只剩 16 次，**低于优化器的有效搜索下限**，于是每个槽都停在空种子上不动；把预算集中到高信用的 control 槽，**用一半预算反而达到 0.761**。结果四：效应与任务有关——在 WebShop 上所有槽位都冻结、所有方法打平，作者判断这是"**确实不存在可复现、可言语化的控制失败**"而非预算饥饿。启示：这条结论对任何做 prompt/harness 自动优化的人都是直接的工程纪律——**先做信用分配、再做结构化演化**；不要因为"把 harness 拆成模块"看起来更工程化就平均撒预算，**先用 LOI/LOO 找出真正承载价值的那一格，然后把全部预算压上去**。它同时给了一个诊断手段：如果所有槽位都进化不动，先别加预算，**先问这个任务是否存在可被语言化的反复失败模式**。

- ⭐ **[JIT-Agent: Scaling Harness Intelligence via Just-in-Time Harness Evolution](https://arxiv.org/abs/2608.25593)** · Guibin Zhang, Leo Lu, Fangzhou Xie 等 · 2026-08-26

  主张：**agent 能力不只由模型决定**，harness（记忆管理、规划策略、动作协议、工具/skill 编排）的贡献常常盖过底座模型，但 harness 设计至今是手工的、任务特定的、不可规模化的。JIT-Agent 把 harness 形式化为**可组合、可机器生成的产物**，由固定的四模块协议约束，然后训练一个"harness 智能模型"专门做三件事：为当前任务**即时定制** harness、为稳定执行**修复** harness、通过从不断扩大的历史 harness 配置档案里蒸馏性能信号来**自演进**。数据：给 DeepSeek-V4-Flash 配上 JIT-Agent 当"harness 助手"后，在 DeepSearchQA 上 **+9.1**、OdysseyBench 上 **+4.3** 超过 GPT-5.6；本就很强的 GLM-5.2 最高 **+20.2**；生成的 harness 与 OpenCode、Claude Code 这类成熟 agent 运行时**性能相当**，并在 DeepSeek V4 / Mimo-V2.5 / Qwen3.6 多个规模族上一致提升。作者的定位句值得记：**harness 智能是一个"可训练、可迁移、可复利"的能力维度，与模型规模正交**。启示：与上期 EvoHarnessBench、Co-Evolving 连起来看，本方向已经形成完整光谱——**评测 harness 演化（EvoHarnessBench）→ 模型与 harness 协同演化（Co-Evolving）→ 把 harness 生成本身训练成一个模型（JIT-Agent）**；对应用工程师，短期最可复用的是"**四模块固定协议 + 历史配置档案**"这个结构：把你的 agent 配置拆成固定的几块并把每次改动与效果存档，是后续任何自动优化的前置条件。

- **[HarnessEvolve: Learning from Reference Trajectories for Reliable Agent Self-Evolution](https://arxiv.org/abs/2609.00829)** · Wen Jiang, Mingmin Chu, Yimeng Tian 等（华为 ICT AI 能力中心，上海）· 2026-09-01

  这篇把自演进的三大顽疾点名并逐个上门控：**信用分配失败**（只有终局成败反馈，不知道哪一步错）、**捷径学习**（记住任务特定套路而非获得可泛化能力）、**灾难性遗忘**（无保护的更新弄坏已有能力）。做法有两个记忆点。一是**参考轨迹**：给定标准答案让 agent 再跑一遍，得到"本该怎么走"的执行路径，把失败执行与之对齐来抽取错误信号，再对错误信号聚类**暴露系统性失败模式**——这比让模型自由反思要可靠得多。二是**双门控**：候选 harness 更新必须先过**质量门**（过滤数据泄漏与 prompt 膨胀），再过**性能门**（在当前批次上有提升且**不损害近期批次**才接受），epoch 结束时在留出集上选最佳快照。架构上还把执行 agent 与演化流水线解耦，执行、评估、优化、门控分给独立模块。启示：**"prompt 膨胀"被显式列为要过滤的失败模式**，这与本期 OpenAI"删脚手架"的主张在同一天成立——自演进循环如果不设膨胀门，产出的必然是越来越长、越来越互相矛盾的指令堆。工程上可直接抄的是那套门控顺序：**质量门（防泄漏/防膨胀）→ 性能门（新任务提升 + 老任务不退）→ 留出集选快照**。

- **[MASkills: Continual Skills Optimization for Multi-Agent LLM Systems](https://arxiv.org/abs/2609.02094)** · Huaiyuan Yao, Xiaoou Liu, Charles Fleming, Tianlong Chen, Hua Wei（亚利桑那州立大学 / Cisco Research / UNC；[开源](https://github.com/DaRL-GenAI/MASkills)）· 2026-09-02

  论点很对 Peter 的主线：现有自反思方法把经验存成"记忆"，但**记忆难以被调用、难以精炼、难以扩展**，而 **skill 是更可操作的单位**——结构化的程序性知识，明确写清**何时行动、如何行动、用哪些资源或工具**。MASkills 的流水线有三个部件：**skill 条件化的信用分配**（把结果归因到具体被调用的 skill）、**分层信用聚合**（多 agent 场景下逐层汇总）、**动量平滑的优化**（抑制单批噪声），从而让 skill 库通过**精炼、归纳、合并、剪枝**四种操作持续演化。在 HotpotQA、LoCoMo、GAIA 上验证。启示：这与 WikiSkill（经验→wiki→skill）、Repo-To-Skill（仓库→skill）构成"skill 从哪来"的三条路径，而 MASkills 补的是**"skill 库如何长期不烂"**——**剪枝和合并与新增同等重要**；这一点恰好被本期 OpenAI 官方文章从另一端印证：skill 越堆越多会挤占描述预算、互相矛盾，最终降低选择准确率。

**速览（自演进/自学习方向，一篇不漏；标题、日期、机构均经 arXiv 元数据核实）：**

- [SafeEvolve: Harness-Policy Co-Evolution from Agent Experience for Safety Alignment](https://arxiv.org/abs/2609.02786)（Qinghua Mao 等，09-02）——安全对齐版的"harness 与策略协同演化"：harness 侧把轨迹级安全证据转成**有界、按组件、可审计且可回滚**的更新（安全提示 + 分层 skill），策略侧走两段式 SFT→RL（先让模型学会主动使用演化出来的 harness 产物，再用 verifier 分解奖励塑造多步安全行为）。Qwen3.5-4B 上 AgentDojo 攻击成功率降到 **1/3**，良性任务效用还从 59.79% 升到 61.86%。"可审计 + 可回滚的 harness 产物"这条与 EvoUndo 的可恢复性约束是同一族要求。
- [CHIME: Credit-Aware Hierarchical Memory Evolution for Long-Horizon Agentic Planning](https://arxiv.org/abs/2609.02074)（Yongshi Ye 等，09-02）——自演进记忆的通病是**用终局成败当反馈**，把"计划差"和"执行差/环境因素"混为一谈，于是攒下的经验有偏且嘈杂。CHIME 分设**计划库与执行库**，遵循"**先归因再记忆**"：先判断这次失败该算在计划、执行、两者还是都不算，再只更新对应库。结论有三条可迁移：**条目更少但更有效**；**高质量的计划记忆比执行记忆更值钱**；**积累的记忆可跨骨干模型迁移**。
- [TRACE: A Self-Evolving Skill Bank for Consistent, Limit-Aware LLM Agents](https://arxiv.org/abs/2608.22793)（Wenhao Wu 等，08-24）——把目标从"能不能做对一次"换成"**每次都做对**"：用 Pass^k 而非 Pass@3 度量，车载助手场景 CAR-bench 上前沿模型在两者间差距巨大。TRACE 不动权重，只演化一个 **Skill Bank**（每条 skill 自包含工具使用规则与行为准则），每轮评测后按"被调用的 skill"分组轨迹、**对比成功与失败**来精炼每条 skill。GPT-5.5 上 Pass^3 从 59.9% 提升到 **94.5%（+34.6）**，潜力与稳定表现之间的差距压到 4 个点；官方隐藏集上用 GPT-5.6-Sol 取得第一。**"一致性"是产品化 agent 的真指标**，这篇给了不改权重的做法。
- [ARISE-RL: Agentic Rubric-Grounded Iterative Self-Evolution with RL](https://arxiv.org/abs/2609.01058)（Fanrui Zhang 等，09-01）——开放式 agent 任务没有金标准答案，RL 奖励脆弱。做法是 Generator（出任务 + 出 rubric，rubric 的工具相关标准**扎根于真实工具观测**，且被奖励去生成"难度中等、贴着 Solver 当前能力边界"的任务）与 Solver 通过 rubric 协同演化；另提出 **RG-SED**：只有当记忆增强版本**确实带来奖励提升**时才把它蒸馏回自身，避免盲目模仿噪声指导。配套发布 ECR-Bench。
- [SQL-Zero: Self-Evolving Text-to-SQL](https://arxiv.org/abs/2609.04697)（Daniel Machado Pedrozo 等，09-04）——**零标注**训练：challenger 与 solver 从同一底座出发自博弈，唯一的真值是**对数据库的实际执行**；challenger 按 solver 当前难度生成"难但可解"的样本，双方用 GRPO 交替更新，并给 challenger 加**模板级重复惩罚**防多样性坍塌。BIRD dev 上 3B **+6.6**、7B **+7.3**。自博弈 + 可执行验证器 = 无人工标注的自演进最小配方。
- [AutoScientist-Quant: Self-Evolving Coding Agents for Automatic Research in Quantitative Investment](https://arxiv.org/abs/2608.28632)（Zongqian Li 等，arXiv 元数据 2026-08-05）——把量化研究当**一个带预算的搜索问题**：单一控制器在每轮基于剩余预算决定改进/组合/转向/停止、扩哪个节点、生成多少 alpha、如何从共享记忆里检索历史轨迹，并把自动化延伸到库选择与模型选择。特别值得注意的是它**修复了两处前视泄漏**——自演进循环最容易从反馈里"读到测试窗口"。
- [SAEScientist-Bench: Can AI Agents Conduct Autonomous SAE Interpretability Research?](https://arxiv.org/abs/2609.09113)（Yuqiao Tan, Shizhu He, Jun Zhao 等，09-08）——直指 RSI 的缺失支柱：**自动化的是训练流水线，但"事后监控与审计"没跟上**。该基准让 agent 扮演科学家，用稀疏自编码器工具在 Gemma-2-9B-IT 的 13.1 万+ 特征字典里，为给定概念设计对比探针、找出最优特征，对照 Neuronpedia 上的专家参考特征按激活排名、概念选择性等维度评分。**"谁来审计自改进的系统"**是这条主线下一个必然的题目。
- [Negative Self-Distillation: Learning to Reason by Avoiding Flaws](https://arxiv.org/abs/2609.11699)（Rongcan Pei 等，09-10）——对当红的 **On-Policy Self-Distillation 的证伪与修正**：用特权信息（标准答案）生成的推理轨迹是"人为自信"的，强迫学生模仿会**压制不确定性表达、惩罚探索与自我纠错**，在复杂推理上反而变差。NSD 反过来——**从有缺陷的推理里学"别这么走"**，不依赖金标准答案或外部监督。与本期 Co-Evolving 的结论同源：**自改进要 on-policy，照抄"更好的轨迹"经常是负收益**。
- [Eliciting Weak-to-Strong Generalization with On-Policy Reverse Distillation](https://arxiv.org/abs/2609.08798)（Youngrok Park 等，09-08）——弱到强泛化的训练侧方案：传统蒸馏把弱老师当优化目标，等于把老师的能力天花板强加给学生；OPRD 改为在**学生自己的 rollout** 上衡量老师策略相对其参考策略的偏移方向，只放大学生 verifier 驱动梯度中与该方向一致的分量，从而**保留策略优化的稳定点**又能超过老师。与 Anthropic 那篇"弱模型对齐强模型"互为理论与实证。
- [Counter-Swarm Doctrine: Containing Coordinated Agent Intrusions](https://arxiv.org/abs/2609.06140)（Gregory N. Frank，09-05）——agent 把共享基础设施变成协同入侵的通道（文中以 Hugging Face 事件与一次公开 wiki 调查为例）。主张防御的**操作单元应是"可修订的协同片段"**，把观察到的传递、任务授权、响应历史连起来；核心研究问题是"**前瞻性片段发现**"——在评估者给出成员关系之前就判断哪些动作属于同一波协同；并把存储中介的协同类比为**共识痕迹（stigmergy）**。与本刊 MOLE（agent 内鬼检测）一起构成"多 agent 时代的入侵检测"雏形。
- [Diffs vs. Whole Files: An Empirical Comparison of Iterative Edit-Based and Direct Generation for Flutter/Dart Code Models](https://arxiv.org/abs/2609.05779)（Andrej Andrejev，09-05）——一个反直觉的小结论：在两个小模型（自训 100M 与微调 Qwen2.5-Coder-0.5B）、约 1,790 个留出任务上，**整文件直出在所有指标上都显著优于 diff 式逐步编辑**，尽管后者更像人类工作方式、每轮 token 更少。对自建代码 agent 的人是个提醒：**"搜索/替换式编辑"是省 token 的优化，不是提质的优化**，在小模型上尤其要实测。
- [Memory as Plans: World-Action Modeling with Memory-Grounded Planning](https://arxiv.org/abs/2609.11561)（Sizhe Zhao 等，09-10）——机器人策略常用马尔可夫式建模，但很多真实操作任务是**非马尔可夫的**、需要长时记忆。MaP-WAM 把记忆拆成"**已完成片段的记录**"（语言指令 + 稀疏视觉上下文），在**规划时**把情节记忆转成计划，执行器只按计划走而不反复吞整段历史。这与文本 agent 的"把长历史压成结构化计划而非塞进上下文"是同一条工程直觉，跨模态成立。

## 趋势观察

本期把三条线索并到了一起，指向同一个判断：**"人写的脚手架"正在被两头挤压——上面是模型能力，下面是自动演化的循环。**

上面这一头，OpenAI 这周给出了迄今最直白的官方版本：**skill 描述要短、SKILL.md 要当路由器、AGENTS.md 里的预读和叮嘱要删、为旧模型写的强硬边界语言会让新模型过度保守**。把它和 Anthropic 09-08《降本三杠杆》里"删反模式"那一节并排读，会发现两家在同一周用不同措辞说了同一件事，而且都把"审计你的老提示词"做成了可执行流程（`prompt-audit` / 让 Astra 自审）。这已经不是风格偏好，是版本升级的标准动作。

下面这一头，本期补录的两篇 Anthropic 文章把"自演进"从 skill/harness 层顶到了**权重层和组织层**：弱模型能用 2,000 条样本、60 小时把更强模型的安全差距闭合 65%，比生产流程数据效率高四个数量级；而 Anthropic 自己 80%+ 的合入代码已由 Claude 编写、开放式任务成功率半年 +50 个百分点。与 OpenAI 09-06 的 RSI 报告对照，两家现在都在用**内部生产数据**而不是基准分来讲这个故事——这是今年下半年最值得跟踪的叙事转变。

而论文侧本期最有价值的恰恰是一盆冷水：**harness 自演进的价值高度局部化（几乎全在"反思/控制"那一格），把预算均匀撒到各个模块会让每格都低于优化器的搜索下限、全盘冻结。** 配上 HarnessEvolve 把"prompt 膨胀"列为必须过滤的失败模式、MASkills 强调 skill 库要剪枝合并、以及 OpenAI"skill 太多会挤掉描述预算"的官方观察——**四条独立证据指向同一个工程纪律：自演进循环如果不带删除动作，它产出的就是新的技术债。** 面试里若要一句话概括 2026 下半年的 agent 工程共识，大概就是：**能力来自模型，稳定来自门控，而长期收益来自"敢删"。**
