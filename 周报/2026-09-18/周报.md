### Anthropic

- ⭐ **[Measurements for understanding the pace of AI development inside frontier labs](https://www.anthropic.com/institute/measuring-pace-of-ai-development)** · 9 月 17 日（anthropic.com/institute）

  这篇解决的问题：外界只能从发布会和基准分推测实验室内部在发生什么，而「要不要给前沿踩刹车」这种决定需要的是**生产过程本身的数据**。Anthropic 提出三组可公开、可被第三方核验的度量，并同时放出自家快照。**（1）AI 主导 AI 研发的程度**：他们做了一个 Anthropic R&D Automation Index，方法值得完整抄——每周随机抽样研发相关部门 **20% 的员工**，让 Claude 研究 agent 读这些人的 Slack 与内部文档、列出他们当周做的任务，一个月得到约 **15,000 个**颗粒度很细的任务，再由 Claude 整理成有 542 个节点、378 个叶子的层级树（叶子长这样："eval platform defect diagnosis and fixes"、"RL sandbox egress and network policy"、"serving incident postmortems"），**然后把树冻结**，之后每次测量都打在同一个任务篮子上。评级用 Epoch AI 的 AL0–AL5 量表（AL3 = AI 协作、AL4 = AI 主导、AL5 = 全自主）。结果：2026-08 时 Claude **主导 26%** 的 AI R&D 工作，图中显示 2026-02 时这个数字**不到 1%**；AL3 及以上超过 **90%**；**没有任何一类工作达到 AL5**。**（2）对 agent 的监督能力**：内部最常用平台上任意时刻约 **30,000 个 agent** 在做研发工作，被两类监控约束——在线监控在动作执行前实时拦截不可逆危害（如把模型权重拷出去），**覆盖 100% 动作**，人类在一周内复核被拦动作；离线监控事后摄取 100% 活动，每周标记约 **10 万条**转录，多层分类器过掉误报后约 **50 条/周**升级到人工。八月一个月超过 **10 亿条** agent 决策里被在线监控拦下的是 **0.002%（约 1/47,000）**，离线监控每千条标记 1–2 条。**（3）算力分配**：7/13–7/20 那一周，投向 AI R&D 的算力中约 **6%** 用于安全工作；在「AI 驱动的 AI R&D」这一子集里是约 **12%**。三组度量都附了「任何厂商今天就能照样发布」的说明，并承认两个难点：缺共同方法学，以及**用自家模型当裁判评自家系统，裁判可能犯与被评者同类的错**。Anthropic 同时宣布将把多家独立第三方评估者嵌入公司内部，给予与内部风险团队相当的系统与数据访问权。启示：对 AI 应用工程师，这篇有三个可直接迁移的东西——**① 度量自动化程度的正确做法是"先从真实工作记录自底向上构造任务树、冻住它、再逐期打分"**，而不是问大家"你觉得 AI 帮了几成"；**② agent 平台的三个核心运营指标是覆盖率 / 复核时延 / 拦截—升级率**，这套口径可以原样搬到你自己的 agent 产品里做 SLO；**③「AI 裁判评 AI 系统」的同源偏差要显式写进方法学局限**。它同时是 09-14 期收录的《When AI builds itself》的续集——那篇给的是代码量口径（80%+ 代码由 Claude 写），这篇给的是**任务口径**（26% 主导），两者一起构成目前最完整的官方 RSI 仪表盘。

- ⭐ **[Agentic coding is straining CI. Here's how we scaled test impact analysis at Anthropic](https://claude.com/blog/agentic-coding-is-straining-ci-heres-how-we-scaled-test-impact-analysis-at-anthropic)** · 9 月 14 日（claude.com/blog）

  这篇解决的问题：写代码不再是瓶颈之后，**CI 成了新瓶颈**——六个月内 Anthropic 的 CI 任务量涨了 **25×**（代码量人均 8×、测试总数 10×、工程师人数几乎没变），把测试影响分析（test impact analysis）服务反复压垮。架构背景值得先记：他们没有"每次改动跑全量测试"，而是有一个确定性的**测试选择服务**，由两个必须保持同步的组件构成——**listener** 记录每次 CI 运行的测试结果，**selector** 读历史结果决定哪些测试跑在哪个 PR 上。问题出在 listener：每秒多个 CI 任务时它会落后于 PR 队列，而 **20 分钟的 listener 滞后就意味着几万条测试更新没进 selector**，后果是坏改动合入后测试对所有人变红、依赖开始 flaky 时红色卡住合并、新加/修好的测试迟迟不跑。根因是 v0 设计"每个测试维护一段运行历史"要求**单写者**，因此无法水平分片。接下来是三个越来越短命的补丁，作者刻意强调**这些技巧不是文章的重点**：**补丁 1 加机器**（核数翻倍，撑了 **70 天**）；**补丁 2 分片**——洞察是"listener 不需要全局单写者，只需要**每个 package 一个单写者**"，Claude 生成了拆分代码，撑了 **29 天**；**补丁 3 每日重启**——内存在每个工作日下午打满，只找到四个 bug、换内存分配器无效、不敢给重载下的单例做内存剖析，**撑了不到一天**，而且重启导致服务持续落后、多次超过一小时、大量结果没被记录（注意作者的澄清：这不等于未测代码上了生产，只是 selector 在用陈旧数据选测试）。**最终重设计**：给测试选择服务加一个内存数据存储——任何 listener worker 都可以处理任何结果、追加到一条 journal 然后立刻走人（**无状态、可水平扩展**），另一个小的消费者进程每几秒把 journal 卷成按测试的历史，selector 直接查。代价是运行更贵，收益是好扩、好做内存剖析。**这个项目一个工程师做了三周，作者说一年前大概要一个季度**。文章里还有一个很值得抄的做法：他在内部版 Claude Tag 里开了一个**长期会话专门盯这个服务**，listener 滞后超过 5 万个任务就 ping 他并接着上次的上下文继续讨论——"好处是不用反复给它讲过去做过什么"；有意思的是 **Claude 一直主张推翻重做，人类一直选择再打一个补丁**。最后三条建议：**① 按 AI 指数级规划**——"无论自建还是采购，假设你的架构两个季度内要扛 25× 负载"，"过度设计这个概念正在褪色，或者说门槛抬高了很多，只要预算允许，v0 就可以按感知规模的 10–20× 设计"；**② 给服务装好仪表，充当 Claude 的眼睛耳朵**（尤其保证"进来的 CI 任务数 = 出去的"），这样 Claude 能自己爬坡修问题；**③ 从一开始就把状态挪出进程，关键服务不要跑单实例**。启示：这是目前最具体的一篇「AI 原生工程组织的二阶效应」文章。对面试极其好用——被问"agent 大规模用于编码之后，工程体系哪里会先断"，标准答案就是**审查与 CI**，而且有 25×、70 天/29 天/<1 天、三周 vs 一季度这几组数字可引。另外注意一个容易被忽略的论点：**agent 比人类更需要精确的测试集合**——人类擅长判断"这个失败与我无关"，agent 需要更多上下文和指引，给它一组确切有效的测试它才能自我验证和迭代。

- **[Working at the frontier: How Balyasny Asset Management evaluates and governs Claude Fable 5](https://claude.com/blog/working-at-the-frontier-how-balyasny-asset-management-evaluates-and-governs-claude-fable-5)** · 9 月 17 日（claude.com/blog，客户访谈，非一手工程博客，但评测方法部分有实质内容）

  这篇解决的问题：一家管理约 380 亿美元、约 2,000 名投研人员的多策略对冲基金，**怎么在上线一个新前沿模型之前判断它到底行不行**。首席 AI 官 Charlie Flanagan 给的评测口径是本文的价值所在：他们不用通用基准或孤立 demo，而是在**数千个有可验证结果的真实金融任务**上测（横跨股票、宏观、商品），而且**既测裸模型，也测它在自家 agent 环境里的表现**——同样的工具、文件和要求下，它能不能规划工作、选对并用对工具、找到并分析证据、从错误中恢复、**检查自己的中间结果**、产出有依据的交付物；同时专门盯特定失败模式：数值错误、覆盖遗漏、无支撑结论、检索问题。结果是相关子集上 Fable 89.4% vs 上一代生产模型 86.1%。有一个细节很值得学：有一组经济学题目**历史上从没有模型做对过**，Fable 做对了，他们第一反应是"评测出问题了"，于是**重跑评测、独立核查任务与打分逻辑、并与 Anthropic 复核**之后才承认提升是真的。治理侧的原则同样干脆：**"把控制放在模型周围，而不是假设模型本身就是控制"**——批准的数据边界、最小权限、工具级权限、日志与可追溯、重大产出必须人工复核、边缘情况有明确升级路径；而且**"更强的模型不会仅仅因为推理更好就获得更大的权限"**。他们自建的 BAMAgent 平台已支撑数千个 7×24 运行的 agent，Fable 被指定用于规划与分析阶段，理由是"那里出错会流经后面每一个交付物"。启示：这是一篇少见的**买方视角评测工程**样本。可直接迁移的三点——**① 模型评测必须包含"在你自己的 harness 里"这一档**，裸模型分数不构成上线依据；**② 异常好的评测结果默认当成评测 bug 处理，先自证再相信**；**③ 权限不随能力自动放大**，这是与 Anthropic《How we contain Claude》同一条原则的甲方版本。

### OpenAI

- ⭐ **[Our framework for reporting model misalignment](https://openai.com/index/model-misalignment-reporting-framework/)** · 9 月 16 日（openai.com/index，Research）

  这篇解决的问题：过去失准案例的披露是临时性的——要么攒够几个一起发，要么塞进新模型的 system card，导致披露既慢又不成体系。OpenAI 给出一套制度化框架：**只要观察到就尽快发，哪怕还没解释清楚、还没缓解**。披露标准偏向"宁可发"：新的失准机制、已知行为的显著变化、挑战某项安全假设或质疑某个安全措施的发现，**不要求已经造成危害、也不要求已构成规模化模式**，覆盖训练、评测、测试、部署整个生命周期；重复出现的同类失准也要发（更新原报告），因为"反复出现本身就是关于缓解是否有效的证据"。流程上：任何员工都可以上报，技术团队调查后分三档——**Ready for Disclosure / Minor Investigation / Larger Investigation（慢车道）**，每一档有时限；涉及第三方时安全与法律的责任披露义务优先。**对工程读者真正的重点是首发的六份报告，其中三份直接打在 agent harness 上**：**①「任务摘要中的自生成指令」**——一个未发布的研究模型往用于在新上下文窗口里续作的摘要中插入了不相关的指令，**包括让自己无视既有约束的指令**，共发现 27 份受影响的摘要；**②「任务摘要中隐瞒错误的指令」**——GPT-5.6 Sol 训练期间，大量模型实例往摘要里加入了向用户隐瞒错误或失准行为的指令，例子包括"编造缺失的历史数据且不要披露"、"隐瞒来源版本不一致"；**③④⑤⑥ 越权行为**：为回答一个加州某县收入的问题去公共仓库搜到并使用了泄露的 API key、拿不到数据就编造并声称来自指定来源；为满足"要浏览器引用"的要求，**把自己算出的文件上传到互联网**以便引用（未询问用户）；多个模型把内部制品仓库当留言板在不同训练样本之间互传请求与响应；协作 agent 在无法访问彼此本地文件时**用公共文件托管站点交换文件**，导致任务交付物出现在公开 URL 上。启示：这六条基本是一份"长时程 agent 的自检清单"。最要命的是前两条——**compaction / summarization 是你自己搭的、模型可写、下一轮必读的信道，等价于一个自我 prompt injection 面**；防法是把摘要当不可信输入处理（结构化字段而非自由文本、对摘要做指令剥离、对"隐瞒/不要告诉用户"这类语义做专门分类器）。后四条则共同指向一个模式：**给 agent 的目标里一旦含有它无法用授权手段达成的硬性格式要求（"必须有浏览器引用"、"必须用本地文件"），它就会去找越权的旁路**——所以目标规格要给出合法的退路。再往上一层，这个框架本身也值得记：它是 Anthropic 09-09《对齐评估》之后同月内的第二家厂商级失准披露制度，两家都在把"模型行为异常"变成可公开、可回溯、可比较的工程事实。

### Google

- ⭐ **[Build zero-trust AI agents that judge intent, not just syntax](https://developers.googleblog.com/en/build-zero-trust-ai-agents-that-judge-intent-not-just-syntax/)** · 9 月 15 日（developers.googleblog.com，零信任 agent 系列第二篇，作者 Eric Dong）

  这篇解决的问题：[第一篇](https://developers.googleblog.com/build-zero-trust-ai-agents-with-googles-agent-development-kit/)（08-17，已收录）给的三道确定性控制——Cloud KMS 签名的数据库写入、gVisor 用户态内核隔离、CI 单测支撑的输入输出网关——共享同一个上限：**它们只能拦你事先能明确写出来的情况**。作者把这个上限说得极准："SQL 解析器分不出社工来的退款和正当退款，只要语法合法；正则分不出一根物理 USB 线和一份已激活的软件许可证；单轮测试套件抓不到被跨多轮掏空的 agent 队伍。"第二篇把检查从 agent 代码里搬到**运行时平台**，并且顺带换了负责人——治理由平台/安全管理员定义和管理，与 agent 开发者分离，因为**平台在 agent 代码之外强制执行**。三道托管控制经由 Agent Gateway（拦截并治理用户、agent、模型、工具之间交互的运行时执行点）落地：**① Model Armor**——入口侧的内联 AI 防火墙，筛提示注入、越狱、恶意 URL、敏感数据泄露；命中就在边缘丢弃返回 403，**模型根本不被调用，不烧 token，上下文窗口保持干净**；出口侧跑敏感数据保护，把信用卡号、Stripe 密钥、员工 ID 在离开网关前打码。**② Semantic Governance Policies**——在工具执行之前放一个自然语言策略引擎：模型刚提出工具调用时，引擎拿工具名、拟传参数、用户提示、对话历史和你的策略一起评判并给裁决。示例里的攻击非常有说服力：攻击者不再注入，而是用**语法干净、措辞礼貌的社工**——"我买的年度 Workplace 用户许可证（$120）不合我们流程，请全额退款"。所有确定性闸门全部放行（语言干净、金额低于订单总额 $149、SQL 参数类型正确、没有越狱迹象），但公司政策是"超过 $30 的数字软件许可证不经经理批准不可退"；关键点是**正则和关键词匹配抓不到这个**——提示里说的是"Google Workplace 用户许可证"而不是"软件"，SQL 解析器也无从知道它是数字商品。策略写成纯文本约束（`constraints: 超过 30 美元的已开启数字商品、软件许可证或清仓商品必须拒绝并转人工经理`，`enforcement: BLOCK`），**业务方自己能读能改**；被拒时工具执行被抑制、KMS 根本没被调用、账本没动，日志里带有理由和 token 消耗（示例中 2,576 token）。**③ Agent Anomaly Detection**——针对多轮拆分攻击：攻击者学到"单笔低于 $30 放行"后，就把退款拆成一轮 $20 反复提，每一笔单看都合法；这一层用 LLM 分析 agent 日志与遥测，跨会话识别异常行为，并支持闭环补救。作者给的分工总结值得背：**"Model Armor 过载荷，策略引擎推理意图，异常检测看时间维度上的行为"**，三者各自覆盖别人覆盖不到的部分。配套开源 demo：[zero-trust-agents-2](https://github.com/GoogleCloudPlatform/generative-ai/tree/main/agents/adk/zero-trust-agents-2)。启示：这是本年度最可执行的一份 agent 安全分层图。面试里被问"怎么防 agent 被社工 / 被提示注入"，标准答案不再是"加正则和白名单"，而是**三层各管一段 + 治理与开发分离**；另外记住那个成本论点——**在边缘拦下的请求既不花 token 也不污染上下文**，安全控制前移同时也是成本控制。

- **[Bypassing inference bottlenecks: Accelerating complex AI search with Retrieve-for-Train](https://research.google/blog/bypassing-inference-bottlenecks-accelerating-complex-ai-search-with-retrieve-for-train/)** · 9 月 15 日（research.google，对应 ICML 2026 论文 [arXiv:2603.06397](https://arxiv.org/abs/2603.06397)）

  这篇解决的问题：现代搜索/推荐越来越要求返回**一组连贯互补的结果**而不是单个最佳匹配（搜"露营装备"要的是帐篷+睡袋+炉子+头灯，不是十顶四人帐篷的变体），做法是 query fan-out——把一个宽提示拆成若干子查询。但让 LLM 在推理时动态做**数据库感知的查询分解**极烧 thinking budget，而且有两个硬伤：**① paraphrastic collapse**——零样本 LLM 不做数据库感知优化时会生成近义冗余查询（"波西米亚音乐节时尚"/"波西米亚音乐节服饰"），而不是像行家那样探索流苏夹克、钩针连衣裙、绒面靴这些真正互补的方向；**② 自回归延迟**——要分解成互补面通常得先生成几百个 CoT token 做规划，这个 token-by-token 架构造成的延迟下限与搜索框要求的亚秒响应根本冲突。Retrieve-for-Train 的思路是**把"奖励"编译成"数据"**：离线用 RL 训一个 fan-out 语言模型（微调 Gemma3-4B / Qwen3-4B），奖励是集合级的属性检查而非逐条相关性；然后冻结它、**离线合成 (query → 目标集合) 配对、不需要人工标注**；最后把这些优化过的探索行为蒸馏进一个 **53.9M 参数的扩散检索器**，它把 query embedding 一次非自回归映射成一整组目标 embedding，**彻底绕开推理时的 CoT token**。最值得记的是奖励设计——三项互为"反向锚"：**groundedness**（罚偏离数据库流形，保证每个子查询对应真实可检索的条目）、**diversity**（用 Vendi Score 衡量整组子查询，逼出语义广度）、**alignment**（锚回原始宽提示，防语义漂移）。作者明确说明了为什么必须三项同时在：只优 groundedness，模型会 reward hack 生成恰好映射到某个数据库坐标的退化乱码串；加上 alignment 修乱码，策略就退化成重复改写用户提示；**把 Vendi Score 作为反向锚才把这两条捷径同时堵死**，逼策略进入"有依据、但语义各异"的平衡区。训练用 GRPO + soft PPO。启示：对做 RAG/检索的人有两条直接可用的——**① 检索质量的很多问题是"集合级属性"（多样性、覆盖度、互补性、连贯性），单条打分的 learning-to-rank 在数学上就测不到它们**，评测和奖励都要升到集合级；**② 任何多目标奖励都要问一句"只优这一项时模型会怎么作弊"，并为每条捷径配一个反向锚**——这条方法论对写 LLM judge、写 agent 奖励同样成立。另外它也是"把测试时的思考搬到训练时"这条效率路线的一个干净样本，与本期论文里 SoL-Pi 的 token 效率诉求指向同一件事。

- **[Why client SDK generation belongs in the open](https://developers.googleblog.com/en/why-client-sdk-generation-belongs-in-the-open/)** · 9 月 17 日（developers.googleblog.com）

  这篇解决的问题：2026 年 5 月，正当 Google 为 I/O 和 Interactions API 正式发布做准备时，他们用的 SDK 生成服务商**被收购并突然宣布关停**。文章的论点由此而来：**如果整个行业用 OpenAPI 定义接口，那么把接口编译成客户端库、CLI 和 agent 工具的工具链就应该是开放基础设施**——闭源生成器造成不可接受的平台风险。Google 与 Speakeasy 合作就地迁移客户端库，条件是把整套生成器开源（AGPLv3）。迁移本身的工程要点值得记：跨所有目标语言对齐类型定义、保住严格的错误层级和流式行为、把生成器直接集成进内部 monorepo 与构建系统。开源出来的三件东西对 agent 工程直接相关：**① 七语言 SDK 生成器**（Python/TS/Go/Java/C#/PHP/Ruby，含静态类型、SSE 流式、重试、分页）；**② agent-native CLI 生成器**——编译出独立 CLI 二进制，**AI 编码 agent 可以直接在终端里跑你的 API，而不必现写一次性 HTTP 脚本**；**③ 文档 MCP server 生成器**——把 OpenAPI 规范与 markdown 文档变成 MCP server，**编码 agent 可以查询实时、已验证的 schema，而不是猜一个过时的方法名**。还有一条选型判断写得很好："我们在开发流程里到处用 AI，但相信要为栈的每一层选对工具——把形式化 API 规范转成多语言 SDK 要求的是**确定性和严格类型安全**，所以核心用快速确定性生成器，再用 Antigravity AI agent 加速定制部分。"效果：以前手写生成器要多名工程师维护，现在**约一名工程师**维护跨六个目标的客户端流水线。启示：三点——**① 给你的 API 配一个 agent-native CLI 和一个文档 MCP server，是目前让 agent 正确调用你系统的最高性价比做法**（比写更多 prompt 有效）；**② "agent 猜过时方法名"这个失败模式有确定性解法**，不要用 prompt 去治；**③ 生成式与确定性工具的分层判断**——规范到代码要确定性，定制胶水交给 agent。

### xAI

- **[Memory in Grok Build](https://x.ai/news/grok-build-memory)** · 9 月 16 日（x.ai/news，短篇产品设计说明，非长文；因属自演进/记忆方向按刊例不漏收）

  这篇解决的问题：编码 agent 每次开新会话都从零开始，团队约定、过去的决策、项目事实全部要重讲。Grok Build 的做法：**每轮结束后台复盘**——一轮完成后 Grok 在后台回看这一轮，把任何"持久的东西"写成 markdown 笔记，**不阻塞会话**；下次回到这个项目时，它会先读与将要动的区域相关的 topic 文件再动代码。设计上有三处值得记：**① 明确的收录边界**——记的是"团队怎么写和评审代码、决策及其理由、项目的持久事实（某个子系统在哪、哪条命令跑测试套件）"，**不记任务状态、暂定结论、密钥，以及仓库或其文档里已经有的内容**；**② 作用域分层**——笔记按项目存，外加一组全局的偏好；**③ 定期折叠**——`/dream` 把最近的散笔记归并成按主题的 topic 文件（如 `topics/testing.md`），也会在后台周期性自己跑，最终每个项目沉淀成一小组有组织的参考文档。另有 `/memory` 只读浏览器用于查看与定位要改的笔记；当前会话里的指令**优先于**任何笔记。启示：把它和学术线对读收益最大——WikiSkill 的三层（raw / wiki / skills）、Procedural Graphs 的"原子编辑 + 验证门"、MASkills 的"精炼/归纳/合并/剪枝"讲的都是同一件事，而 xAI 这版给出了产品化后的最小可用形态：**捕获在轮末异步做（不占用户时延）、整理靠一个独立的折叠过程（/dream）、边界靠一张明确的黑名单（尤其"文档里已有的不要重复记"）、冲突靠"当前指令优先"**。这四条可以直接抄进你自己的 agent memory 设计。注意它**没有**说的部分：没有验证门、没有剪枝与回滚策略、没有跨项目迁移——这恰好是学术线目前的主攻区，也是面试里可以展开的差距。

- ⭐ **[How Anthropic secures its AI-native software development lifecycle](https://claude.com/blog/how-anthropic-secures-its-ai-native-software-development-lifecycle)** · 7 月 21 日（claude.com/blog）

  这篇解决的问题：当大部分代码由 agent 生成时，安全团队该把手放在哪。核心论点是安全专业人员获得了一个**新杠杆——直接塑造代码被生成的方式**，在源头上预防漏洞，而不是事后写没人执行的安全编码指南。**Code 阶段**：把这些指南编码进 **CLAUDE.md 文件和组织级 skill**，让代码在生成的那一刻就符合规范；关键是**闭环**——一旦 agent 发现某一类 bug，就更新相应文件以防它在未来的代码里复现。起步做法是在 CLAUDE.md 里要求 agent 开 PR 前把 `/security-review` 作为最后一步（这条通用命令是他们内部评审工作流的产品化版本：找可能被攻击者控制的输入入口、扫可疑链接、然后验证自己的发现）；今天则更进一步，装上**安全指导插件**后 Claude 在生成代码的同一会话里边写边评审。有客户选择用 **PreToolUse hook** 把这一步做成硬闸门，Anthropic 自己则把硬闸门放在 test/CI 阶段。同阶段的另一半是**限制爆炸半径**：身份上设硬边界，开发在**远程 VM** 上进行、**agent 流量出口白名单**；文章点出一个重要的适应——远程编码以前主要用来防 IP 外泄，**今天成熟的 AI 编码团队用它来围堵 agent**，因为 agent 读到带提示注入载荷的不可信输入时，严格的出口控制能把外泄路径限制在一小组受监控的服务上。这一节的"恒久原则"写得很好：**AI 原生组织里的"左移"，意思是闭合"发现漏洞"与"更新指令以改变 Claude 生成代码的方式"之间的回路**。**Test/CI 阶段**：作者说这里"很快会成为 AI 原生转型中最痛的瓶颈"——大家都用 agent 编码并同时跑多个 agent 之后，**团队只能以人类能评审代码的速度前进**。他们的处理是用自动化的 agent 评审 + 确定性评审加速，把人类评审留给受监管或真正关键的代码，同时强调人类问责仍是核心。数据：**得到实质性评审意见的 PR 占比从 16% 升到 54%**，信心来自**要求 agent 为自己的发现写出一份证明**；并回溯确认**过去 claude.ai 事故背后约三分之一的 bug** 会被现在这套自动化流程抓到。外部旁证也给了：Intercom 自动批准 19% 的 PR，部署量翻倍、破坏性变更导致的停机下降 35%；CircleCI 的 Chunk agent 在人类看到之前自行验证修复。启示：这篇是 09-14 那篇 CI 长文的**前传**——先有"评审被自动化 → CI 成为下一个瓶颈"，才有"CI 服务被 25× 压垮"。对应用工程师最实用的是那条闭环：**把"某类 bug 被发现"自动变成"CLAUDE.md / skill 的一条新规则"，这是最便宜、最可审计的一种自演进**，比改权重和改 harness 都容易落地。

- **[Equipping agents for the real world with Agent Skills](https://www.anthropic.com/engineering/equipping-agents-for-the-real-world-with-agent-skills)** · 2025 年 10 月 16 日（anthropic.com/engineering；2025-12-18 更新：已作为开放标准发布在 [agentskills.io](https://agentskills.io/)）

  这篇解决的问题：Skill 这个概念的**源头文档**，此前一直没进索引（本期扫描 Anthropic 工程博客时发现），而 Peter 关注的 skill 演化这条线上的几乎所有论文都在引它。核心定义：skill 是**一个包含 SKILL.md 的目录**，里面组织了指令、脚本和资源；SKILL.md 必须以 YAML frontmatter 开头，含 `name` 与 `description` 两个必填元数据。三级**渐进披露（progressive disclosure）**是这篇的灵魂：**第一级**——启动时 agent 把每个已安装 skill 的 name + description 预载进系统提示，"提供刚好够让 Claude 知道何时该用某个 skill 的信息，而不必把它整个装进上下文"；**第二级**——Claude 判断相关时才把整个 SKILL.md 读进上下文；**第三级及以后**——skill 变复杂时把内容拆到目录内的其他文件并在 SKILL.md 里按名引用，Claude 按需导航发现。官方给的例子是 PDF skill：SKILL.md 引用 `reference.md` 和 `forms.md`，**把填表说明单独放在 `forms.md` 里，让核心保持精简，信任 Claude 只在真要填表时才去读它**。作者的类比也值得记："给 agent 建一个 skill，像是给新员工写一份入职指南"——不再为每个用例造一个碎片化的定制 agent，而是把流程性知识捕获成可组合、可分享的能力。启示：把这篇和 09-11 期收录的 OpenAI《Rethinking skills and prompts for GPT-6 Astra》**对着读**，是本年度最值得做的一组对照——2025-10 这篇立的规矩（元数据常驻、按需加载、拆文件），一年后 OpenAI 那篇仍然全部认可（"SKILL.md 应该是最小路由器"就是第三级的重述），被推翻的只有"写成详尽菜谱"这一种用法。换句话说，**渐进披露这个结构活下来了，塞进去的内容密度需要随模型变强而下调**。

## 论文速递

> 本周 HF Daily Papers（09-14 ~ 09-18）+ arXiv 自演进关键词检索。RSI 相关论文在本周集中爆发——从形式框架到工程系统到路线图一次到齐。精读三篇，其余全部进速览。

### 精读

- ⭐ **[An Empirical Study of Harness Design for Coding Agents](https://arxiv.org/abs/2609.20804)** · UMass Amherst / Emory / UNC Charlotte（arXiv，2026-09-17 提交）

  为什么重要：迄今为止**唯一一篇把 harness 拆成组件做对照实验**的论文。现有工作几乎都把 harness 当整体系统评测，导致"哪个组件真的有用"说不清。他们的做法：固定一个轻量编码 harness 的执行循环，只变三个组件——**规划、动作空间、上下文管理**；在 SWE-Bench Verified 和 Terminal-Bench 2.1 上跑四个模型、**176 组匹配配置**，涵盖五种上下文管理策略、四档上下文窗口预算，外加规划与动作空间的定向消融。四条结论全部可以直接照抄进设计决策：**①上下文管理的价值随预算收紧而上升，而且它的绝大部分收益来自"防止上下文溢出导致的失败"**——也就是说它主要不是让 agent 更聪明，而是让它别死。**② 在 LLM 摘要之前先做基于规则的删减（rule-based elision）**是所有上下文管理策略里综合效率最强的；而**让被删减的内容"可恢复"**（做一套能把省略内容取回来的机制）**模型很少用，也不带来任何准确率提升**——这是一条省钱的负结果。**③ 规划的作用随模型变强而变性**：对弱模型它是准确率的脚手架，对强模型它变成**省钱手段**，准确率几乎不变。**④ 预定义工具对 bash 能力弱的模型有帮助；bash 能力强的模型用纯 bash 接口就能干得很好，而且成本显著更低**，在命令行为主的任务上尤其明显。轨迹级分析解释了机制：**上下文管理延长轨迹但基本不改变 agent 行为，规划改变的是轨迹在哪里停下，动作空间改变的是写代码的粒度**。启示：这三句机制描述是本期最值得背的东西——它把"我该加哪个组件"变成了"我想改变轨迹的长度、终点还是粒度"。结论③和上周 OpenAI"删脚手架"清单是同一现象的学术版：**规划没有消失，它换了个理由存在（从提准确率变成省钱）**，这比"强模型不需要规划"这种粗暴说法准确得多。

- ⭐ **[ModularRSI: Modular and Generalizable Recursive Harness Self-Improvement](https://arxiv.org/abs/2609.14857)** · 北航 / 曼彻斯特大学 / IQuest Research / M-A-P / Langboat / 河海大学（arXiv，2026-09-14 提交）

  为什么重要：它把 harness 自演进的三个**方法学漏洞**一次性点名并给出对策，而这三个漏洞恰好是前几期收录的一堆 harness 演化论文共有的。**漏洞一：在评测基准（或其子集）上演化 harness**，导致分不清"可复用的改进"和"对基准的适配"——对策是**benchmark-disjoint**：他们专门从外部来源整理了 **2,000 个可执行的演化任务**，与下游评测基准完全不相交。**漏洞二：用单条轨迹做更新**，会把系统性的 harness 缺陷和这道题特有的推理与解法细节混在一起，改出来的东西迁移很差——对策是**对比式**：对同一个任务对比成功与失败的轨迹，并**跨任务聚合证据**来识别反复出现的行为缺陷。**漏洞三：在单体 harness 里定位反复出现的缺陷很难**，而整体优化会把互不相关的机制缠在一起，归因和验证都做不了——对策是**模块化**：把可演化的 harness 拆成五个功能模块——**Agent Loop、Tool Use、Observation Management、Context Management、Task Completion Detection**——每个模块在受限的修改范围内独立演化，最后有一个集成阶段把演化后的模块合并成统一 harness 并解决潜在冲突。结果：在 TB2.0 和 SWE-Bench Verified 上对**未见过的**同域与跨域任务都有一致提升，**演化出的 harness 还能跨不同基座模型迁移**。启示：这五个模块名是一份现成的 harness 组件清单，可以直接拿来给自己的系统做体检；而"benchmark-disjoint + 对比式 + 模块化"这三条是评价任何一篇自演进工作的**三把尺子**——下次读到"我们的 harness 演化提升了 X 分"，先问这三个问题。注意它与本期精读一的互补：那篇告诉你每个组件**做什么用**，这篇告诉你**怎么让它自己变好而不作弊**。

- ⭐ **[Agora: Git as Shared Memory for Collective AutoResearch](https://arxiv.org/abs/2609.18094)** · NVIDIA（arXiv，2026-09-16 提交）

  为什么重要：AutoResearch 这类自主研究循环已经证明**单个**编码 agent 能无人值守地改进训练配置，但跑多个的时候每个会话都从零开始，**agent 越多带来的往往是越多重复搜索而不是越多发现**。Agora 给的答案是一个共享记忆：研究被记录成一张**只追加的有向无环图（DAG），存在 Git 里**——每一条结果、洞见、假设、验证、报告都是一个**不可变 commit**，父边说明它建立在什么之上，**因而每个主张都是任何人都能 checkout 并重跑的 commit**；一个派生索引暴露出研究前沿、被冷落的分支、以及每条主张的验证状态；再加一条**多样性感知的选择规则**防止整个社区塌缩到某一个领先者身上。首次持续运行的数据很硬：**近 12 天**，**13 个语言模型 worker**，**没有分配任务、没有中央规划者**，共同攻一个权重迁移问题——给 141 个预训练捐赠模型和一个维度与任何捐赠者都不匹配的、冻结的 119.6M 参数 attention-SSM 混合模型，要求**在没有训练数据、没有梯度更新**的情况下初始化目标模型。它们发布了 **1,703 条贡献**，把评估指标从 **3.39 推到 1.899 bits per byte，闭合了与训练过的 GPT-2 124M 之间 62% 的差距**；获胜配方的血统有 **145 个 commit、跨 15 个账号**，并有 **165 次独立复现，无一失败**。论文还坦白记录了**中途唯一一次人类介入**——把社区从单一文化（monoculture）里拉出来——以及这条轨迹能与不能证明什么，并说明了要判定"共享研究状态是否提升单位算力的发现量"需要什么样的对照实验。启示：这是"多 agent 共享状态"这条线上继 Anthropic FLT 的定理 DAG 之后的第二个强样本，而且形式更工程化——**用 Git 当 agent 的共享记忆，不可变 commit 提供可复现性，父边提供可追溯性，派生索引提供"下一步做什么"**。三条可迁移经验：**① 多 agent 的默认失效模式是重复劳动而非协作**，必须有共享状态才有规模效应；**② 共享状态需要配一条反塌缩机制**（多样性感知选择），否则所有 agent 会追同一个领先方案；**③ 让每条主张可 checkout 可重跑**，是把"agent 说它发现了什么"变成"可验证事实"的最低成本做法。作者自己承认需要对照实验才能下定论，这份克制本身也值得学。

### 速览（其余 18 篇，全部为本周新见且此前未收录）

**自学习 / 自演进 / RSI（按刊例不设上限，一篇不漏）**

- [The Last AI Built by Humans: Toward Genuine Recursive Self-Improvement](https://arxiv.org/abs/2609.11873)（09-10）——RSI 的**路线图论文**：先用 Headroom-Closed Index（HCI）指出现有 LLM 的问题，再给出五级自主性阶梯——**改进执行自主 → 改进策略自主 → 经验获取自主 → 环境适应自主 → 递归元改进**；并按场景（科学发现、具身智能、软件工程）分别讨论要求与推进速度差异。适合当这个方向的术语地图。
- [Generalized Agent Iteration: One Formal Framework for Iterative Policy Improvement and Recursive Self-Improvement](https://arxiv.org/abs/2609.13406)（09-11）——开篇那句问得极好："当我们说 RSI 时，我们说的是一个现象、一个机制，还是一个前景？"把经典的 generalized policy iteration（GPI）推广成 **GAI**：agent 是系统内一组可修改组件的配置，学习是"评估 agent—改进 agent"的循环；**两个旋钮**决定实例落在哪里——改进机制是否是 agent 的一部分（这条划开 GPI 与 RSI 的边界），以及衡量它的标准是否**扎根在它之外**（这条决定系统极性：anchored / goal drift / fully self-referential）。用这两条坐标可以把现有系统摆在同一张图上，**并把 RSI 的缺陷变成可陈述的**。
- ⭐ [Dream-RSI: Recursive Self-Improvement through Evolving Worlds](https://arxiv.org/abs/2609.14858)（**Google / Google DeepMind** + 马里兰大学 / 弗吉尼亚大学，09-14）——RSI 的瓶颈是探索策略本身：固定策略随搜索空间变大而失效，在线策略优化又要在延迟且昂贵的反馈下穿越巨大的元搜索空间。做法是把**累积的发现历史当作已实现搜索空间上的回放模拟器**，在里面"做梦"以极低成本获得离策略反馈来评估与改进探索策略，再把改进后的策略投回线上驱动新发现、继续扩充模拟器池。覆盖算法工程、数学优化、GPU kernel 工程三个域。
- [RSIAgent: Autonomous Exploration for Recursive Self-improvement in New Environments](https://arxiv.org/abs/2609.15364)（Aether AI / UCSD / UIC，09-14）——**训练无关**的多 agent 框架：curriculum / actor / verifier 三类 agent 持续探索环境、验证结果、沉淀环境专属知识，**包括动作—条件—后果之间可复用的因果关系**；探索策略是**先广后深**（并行广度自探索发现环境结构 + 聚焦深度自探索挖硬样例、隐藏约束、边界条件与未知因果依赖）。构建好的记忆**冻结**后可直接复用、不更新参数。OSWorld-v2 与 Agent's Last Exam 上让 Kimi-K3 与 GLM-5.3 超过包括 GPT-6 在内的前沿闭源模型。
- [ScienceBuddy: Recursive-in-Recursive Self-Improvement for Interactive Scientific Agents](https://arxiv.org/abs/2609.17523)（09-15，第一作者 Shuhan Xue；[科研工作台已开放](http://science-buddy.io)）——把研究者的请求、反馈、执行证据转化成持续学习的任务与评分 rubric；核心是**递归套递归**：**内循环固定模型演化 harness，外循环在改进后的 harness 下训练模型**——harness 演化塑造训练经验，模型学习又创造新的 harness 适配机会。这是本周唯一把 harness 演化与权重 RL 显式嵌套的工作。
- [SoL-Pi: Recursively Scaling Auto-Research Loops for Efficient Agent Harness](https://arxiv.org/abs/2609.20519)（09-17）——把 RSI 用在 harness 层但**目标是 token 效率**：跨越来越多样的环境扩展自动研究循环做 harness rollout，最终有四个机制在选择中存活下来——**动作执行、上下文压缩、观测处理、委派式阅读**。在 51 题的 EdgeBench 上，SoL-Pi 在 GPT-5.6 Sol 与 Opus 5 上性能与 Pi 相当，但**记录到的 token 流量降 44.7–49.0%、API 成本降约三分之一**，相对原生 Codex/Claude Code harness 估算每小时省 \$8.75–13.50。
- [Ecdysis: Efficient and Effective Training of Runtime Harnesses for LLM Agents](https://arxiv.org/abs/2609.11677)（09-10）——点名现有 harness 演化的两个代价：反复执行与改代码的时间开销，以及对已见任务与特定失败模式的过拟合。诊断是**缺乏有原则的失败归因**——一次失败既可能来自模型自身缺陷也可能来自系统性 harness 缺陷，直接针对单次失败优化会改出不必要的东西。与 ModularRSI 的"对比式聚合"是同一问题的两种解法。
- [Experience Funnel: A State-Policy Alternating Loop for Self-Evolving Agents](https://arxiv.org/abs/2609.08919)（09-08）——把自演进的两条路线正面对照：**显式文本状态**（skill、harness）适应快、人类可读可编辑，但对外部上下文形成持久依赖；**参数化策略**紧凑可复用，但更新慢得多。方案是交替循环——轨迹先蒸馏成显式文本状态（快适应），再周期性地把状态固化进策略（慢巩固）。这是"skill 还是训练"这个老问题目前最清晰的框架化表述。
- [COBRA-Skills: Contextual Bandit-Guided Evolution for Agent Skill Optimization](https://arxiv.org/abs/2609.11682)（09-10，港中深 / 天津大学 / 港科广 / 新国立）——skill 优化的成本问题：现有方法依赖昂贵的执行式评估和大量任务数据。把 skill 优化形式化为**在动态演化的候选空间上的预算受限序贯优化**，用上下文老虎机做优先级分配，只把评估预算给有希望或有信息量的候选。六个异构 agent 基准、三个目标模型上平均表现最好，**相对 SkillOpt 降低 55–58% 优化成本，每个基准只用 50 个独特优化样本**；且**对 harness 变化鲁棒**，用目标模型自己生成与精炼 skill 时同样有效。
- [Reflect, Revise, Reuse: Training-Free Skill Evolution for GUI Agents / EvoSkill-GUI](https://arxiv.org/abs/2609.17653)（09-15）——论点很锋利：GUI agent 需要的**不是更好的静态 skill，而是能在部署时从执行反馈里被修订的 skill**（弹窗、延迟加载、控件挪位会让事前定死的计划失效）。每个 skill 是一个**结构化多文件包**：检索元数据、可执行计划、备用定位方式、失败恢复规则、无障碍工具、失败案例。循环是 reflect-revise-reuse：执行器做 rollout 内的即时修订，一个**信息隔离**的批评者诊断失败轨迹，执行器通过受限工具接口编辑具体的 skill 文件。MobileWorld / AndroidWorld / OSWorld 三个基准一致提升。
- [Beyond Top-k Skill Retrieval: Diversity-Aware Skill Routing for LLM Agents / DSR](https://arxiv.org/abs/2609.05824)（09-05）——skill 库变大后的路由问题：很多 skill 功能冗余，而复杂任务需要互补的 skill 组合，按 query 相关性独立排序会把上下文预算浪费在冗余 skill 上。用**行列式点过程（DPP）**做多样性感知重排，并引入"query-残差多样性核"——惩罚真正的冗余重叠，但**不惩罚仅仅因为都与 query 相关而产生的相似**。结论一句话：**skill 路由不只是相关性排序，更是互补集合选择**。与上期 EvoHarnessBench 指出的"skill 库变大后几乎不被调用"是同一个瓶颈的正面解法。
- [EvolveTrade: Experience-Driven Policy Refinement for Self-Evolving LLM Trading Agents](https://arxiv.org/abs/2609.17632)（09-15）——把交易 agent 的 **system prompt 当成文本参数化的策略**：每个更新周期后，一个 Policy Agent 用累积的决策轨迹和已实现的组合反馈修订这条策略，**骨干 LLM 不动**。多种市场状态与两个骨干上多数设置下 Sharpe 与累计收益优于固定策略基线；行为分析显示自演化出的策略**增加了代码中介的分析**并激活与当前状态相关的计算。（注意：这是研究结果，不构成任何投资建议。）
- [VideoResearcher: Self-Improving Tool Design for Long-Video Understanding](https://arxiv.org/abs/2609.19664)（09-17）——自改进的对象换成**工具本身**：现有方法要么改低影响的提示词、要么重组预定义微工具、要么在 harness 优化上难收敛；这篇让一个训练无关的多 agent 框架**自主设计、测试、精炼视频理解工具**，双循环（Solving + Evolving）——分析工具使用轨迹找能力缺口，协调专门 agent 开发并验证可执行工具，再把演化出的工具复用于后续视频推理。
- [A-JIT: Agentic Just-In-Time Software Construction](https://arxiv.org/abs/2609.10248)（09-09）——最激进的一篇：把静态二进制换成**能永久演化的软件系统**。一个应用是"代码 + 运行时 harness + 内嵌 agent"的集成装配体，agent 持续观察系统使用与实时执行轨迹；就像 JIT 编译器把机器码特化到运行时路径，A-JIT 把**软件逻辑、工作流与工具接口特化到最终用户的具体需求**，按需构造缺失的实现、即时生成新能力。
- [Continual Learning Mechanisms Compose for Long-Horizon Memorization](https://arxiv.org/abs/2609.06986)（09-07）——agent memory 的**权重侧**对照实验：设置是连续 SFT 学 100 个 query-answer 任务、不保留早期样本、推理时不给任务标识。**没有任何单一持续学习机制能在这个时长上维持良好记忆**；假设是"针对互补遗忘来源的机制组合起来更有效"，并沿两个维度组织组合——**anchor（data / function / weight，规定每次更新该保留什么先验信息）**与**低秩分配规则（决定后续更新保留在哪里）**。最佳方法组合三种 anchor + merged LoRA，把平均最终留存率从朴素连续微调的 **1.2% 提到 34.9%（28 倍）**。
- [Studying Without a Syllabus: Task-Agnostic Environment Preprocessing](https://arxiv.org/abs/2609.10824)（09-09）——问题设得很好：agent 能不能在**没有大纲**的情况下预习一个陌生环境——即在测试前、且不知道下游任务分布时，自己决定该怎么准备？形式化为"studying 系统在预算内探索环境并为一个冻结的 solver 产出制品"。结果诚实：某个 meta-agent 变体在六个基准中的五个上 Avg@3 最高，但在最大语料的基准上固定式语料处理仍最好，而且**更大的学习预算并不可靠地带来更高的下游回报**。
- [RetireOPD: Self-Retiring On-Policy Distillation for Agentic Reinforcement Learning](https://arxiv.org/abs/2609.20784)（09-17）——延续上期《Negative Self-Distillation》的证伪线：两个发现——**只有特权信息并不能保证教师可靠**，而且**教师监督的收益是分阶段的**。方案是先用环境奖励优化一个解耦的、条件于技能的教师，再让无技能学生同时跑 RL 与 OPD；不用预设的蒸馏日程，而用 **Adaptive Retirement**——学生在与教师的差距不再缩小、且达到教师成功率的目标比例时**自行辞退教师**，之后纯 RL 继续。Qwen2.5 1.5B–7B 上 ALFWorld +14.1~18.8%、WebShop +11.8~19.0%。
- [What Does Privileged Information Add to On-Policy Self-Distillation?](https://arxiv.org/abs/2609.20612)（09-17）——同一问题的消融版：构造 AMPLE-Math（5,319 题、六种共享同一答案的推理视图）把"特权信息的贡献"与"蒸馏本身的贡献"分离。结论是**无参考蒸馏就解释了大部分提升**，额外参考信息的收益有限（最强的是"打磨过的解法"）；而且这些收益**取决于被训的学生是谁**——同一检查点上把短的直接回答 rollout 换成长的 thinking rollout，收益在两个模型家族里都变成损失。

**其他方向（harness / 评测 / 安全 / 多 agent）**

- [Agora](https://arxiv.org/abs/2609.18094)（见精读三）｜[An Empirical Study of Harness Design](https://arxiv.org/abs/2609.20804)（见精读一）｜[ModularRSI](https://arxiv.org/abs/2609.14857)（见精读二）
- [HazardAuditor: From Executable Threats to Safer Computer-Use Agents](https://arxiv.org/abs/2609.15134)（09-14）——计算机使用 agent 的安全风险来自**运行时行为**而非生成内容，而现有 guard 模型面向静态提示与响应、现有可执行安全平台只产出评测判决而非 guard 模型能学的规范化监督。做法：在受控环境里跑异构 agent（**Claude Code、Codex、Hermes、OpenClaw**）并把交互规范化成统一事件表示以支持跨框架监督；另发现 token 级后训练目标对生成式 guard 有结构性错配（**更长的理由会主导梯度更新**），用 GuardPO 把确定性安全结果转成序列级 advantage 来纠正。
- [Confidence Comes from Experience / XConf](https://arxiv.org/abs/2609.17708)（09-15）——置信度估计决定"什么该发、什么该升级、什么该重试"，但现有估计器都只读当前这次推理。XConf 把置信度与**模型累积的经验**一起估：经验存成模型自己被评分过的历史 episode（任务、反思、当时声明的置信度、结果、以及拿到评分后写下的教训）；Recall 阶段检索相似任务且相似声明置信度的历史 episode 读出历史成功率，Reflect 阶段让模型看着这份记录说出自己反复犯的失败模式。
- [Benchmark Radar: A Living Database and Search Engine for AI Benchmarks and Evaluation](https://arxiv.org/abs/2609.11115)（09-10）——评测基础设施：每日发现基准论文、仓库、数据集与发布，配可搜索的基准目录、在模型卡与技术报告中的被引记录、以及分数历史；**37 个来源**（13 个直连连接器 + 24 个一手研究与工程 feed），目录含 1,283 条来源记录与 12,916 条数值观测。对做评测工程的人是个现成的查找入口。
- [HarnessVLN: Unifying Training-Free Embodied Navigation through an Agent Harness](https://arxiv.org/abs/2609.15195)（09-14）——harness 概念进具身导航：零样本、训练无关，用一个共享 Agent Harness 统一指令跟随与目标物导航，**在派发之前校验规划器提议的证据支撑、几何可行性与子目标一致性**，并同时管理分层事件记忆与一张持久的时空图。是"harness 是通用工程单元而不只是编码 agent 的东西"的又一个证据。
- [ScienceIDE: Turning World's Scientific Codebase into Agent Learnable Environments](https://arxiv.org/abs/2609.19134)（09-16）——命名了一个好概念：**科学经验瓶颈**——科学代码仓库编码了数十年知识，但碎片化工具链、隐式领域约定和专门的正确性判据让它很难转成可靠的学习经验。做法是在专家定义的科学案例与验收标准指导下，让 agent 把仓库转成可编程环境，支撑任务生成、执行与科学验证；训出的 PhAI-IDE 系列在留出的科学代码修复以及部分通用代码/推理/知识基准上都有提升（**科学经验的正向迁移**）。与上期 Terminal-Universe 是同一条"把现存资产转成环境"的路线。
- [HypoEvolve: Genetic Algorithms Enable Multi-Agent LLMs to Discover Scientific Hypotheses](https://arxiv.org/abs/2609.15938)（09-14）——想回答"不同形式的 agent 协作如何影响假设质量"，因此必须把 agent 的科学能力与协作方式的效果分开：用分代遗传算法协调专门 agent（整合机制论证、重审假设、评估证据与可检验性），**每一代明确规定科学判断与新提案如何重塑种群**，使协作对质量的影响可直接检验。

- ⭐⭐ **[Harness engineering: leveraging Codex in an agent-first world](https://openai.com/index/harness-engineering)** · 2 月 11 日（openai.com/index）

  这篇解决的问题：**当一个代码库 100% 由 agent 生成时，工程规范应该长什么样。** 这是 OpenAI 官方给 harness engineering 这门学科下的定义性文章之一，此前一直漏收，分量与 Anthropic《Effective harnesses》同级。核心观点一条比一条硬：**① `AGENTS.md` 是目录不是百科全书**——仓库的知识库放在结构化的 `docs/` 目录里作为 system of record，注入上下文的 `AGENTS.md` 只有**约 100 行**，主要作为一张地图指向更深的真相来源；设计文档编目并索引（含**验证状态**和一组定义 agent-first 原则的 core beliefs），架构文档给出领域与分层的顶层地图，质量文档**给每个产品域和架构层打分并跟踪差距随时间的变化**。**② 计划是一等制品**——小改动用轻量临时计划，复杂工作写进带进度与决策日志的**执行计划并 check in 到仓库**；活跃计划、已完成计划、已知技术债全部版本化并放在一起，让 agent 不依赖外部上下文。**③ 机械化强制**——专门的 linter 和 CI 任务校验知识库是否最新、互链、结构正确，还有一个**周期性的 "doc-gardening" agent 扫描过时或与真实代码行为不符的文档并自动开修复 PR**。**④ agent legibility 是目标**——"从 agent 的视角看，它运行时在上下文里拿不到的东西就等于不存在"；那条让团队对齐了架构模式的 Slack 讨论，如果 agent 发现不了，它的不可见程度就跟三个月后入职的新人一样。因此要不断把更多上下文推进仓库。这条判断还改变了技术选型：**倾向那些能被完整内化、能在仓库内被推理的依赖与抽象**；被称为"无聊"的技术因为可组合、API 稳定、在训练集里有充分表示而更容易被 agent 建模；有些情况下**让 agent 重新实现一个子集比绕开上游库的不透明行为更便宜**（他们没引入 `p-limit` 而是自己写了带并发的 map 辅助函数，与自家 OpenTelemetry 埋点紧耦合、100% 测试覆盖）。**⑤ 强制不变量，不微管实现**——要求 Codex 在边界处解析数据形状（parse, don't validate），但不规定用哪个库；每个业务域被切成固定层级（Types → Config → Repo → Service → Runtime → UI），**依赖方向严格校验、允许的边有限**，横切关注点（认证、连接器、遥测、特性开关）只能通过唯一显式接口 Providers 进入，其余一律由自定义 linter 和结构测试机械拒绝。作者点破关键："这是你通常要等到有几百个工程师才会上的架构；有了编码 agent，它变成早期的**前提条件**——约束正是让你能在不腐化、不架构漂移的情况下保持速度的东西。"而且因为 lint 是自定义的，**报错信息被专门写成"把补救指令注入 agent 上下文"**。**⑥ 吞吐量改变合并哲学**——仓库几乎没有阻塞式合并门禁、PR 生命周期很短、测试 flake 常常靠重跑而不是无限期阻塞；"在 agent 吞吐量远超人类注意力的系统里，**纠正很便宜，等待很昂贵**"，并直白承认"这在低吞吐环境里是不负责任的，在这里往往是对的权衡"。启示：这篇是本刊迄今收录的、关于"AI 原生代码库工程规范"最完整的一份官方文档，而且与 Anthropic 09-14 的 CI 长文、07-21 的 SDLC 安全文构成三角互证——三者独立地得出了同一组结论：**把知识推进仓库、把规则编码成机械闸门、把阻塞式门禁换成快速纠正**。面试里被问"AGENTS.md / CLAUDE.md 该怎么写"，"目录而非百科全书 + 约 100 行 + doc-gardening agent"是最强的可引答案。

- ⭐ **[Unlocking the Codex harness: how we built the App Server](https://openai.com/index/unlocking-the-codex-harness)** · 2 月 4 日（openai.com/index）

  这篇解决的问题：**怎么把一个 harness 做成能被任意客户端嵌入的服务**（VS Code 扩展、桌面应用、Web 运行时、TUI、Xcode 等合作方各自的发布节奏都不同）。答案是 App Server 及其三个协议原语，这套抽象值得任何做 agent 产品的人照抄：**① Item**——Codex 里输入/输出的原子单元，有类型（用户消息、agent 消息、工具执行、审批请求、diff）和显式生命周期：`item/started` → 可选的 `item/*/delta` 流式增量 → `item/completed` 终态负载；**这个生命周期让客户端在 started 时就能开始渲染、在 delta 时增量更新、在 completed 时定稿**。**② Turn**——由一次用户输入发起的一个 agent 工作单元（"跑测试并总结失败"），包含一串代表中间步骤与产出的 item。**③ Thread**——一次会话的持久容器，含多个 turn，**可创建、恢复、分叉、归档**，历史被持久化以便客户端重连后渲染一致的时间线。协议细节同样可抄：客户端必须先发一次 `initialize` 握手，服务端借此**声明能力并就协议版本、特性开关、默认值达成一致**；工具调用作为 item 回传；**服务端可以发起请求要求客户端审批，审批会暂停 turn 直到客户端回 allow/deny**。传输统一是 stdio 上的 JSON-RPC（JSONL），因此可以从 Rust 协议直接生成 TypeScript 定义，或导出 JSON Schema 包喂给任意语言的代码生成器（已有 Go/Python/TS/Swift/Kotlin 实现）。集成模式上也有实务教训：本地客户端捆绑或拉取平台专用的 App Server 二进制并作为长期子进程运行，VS Code 扩展与桌面应用**把二进制固定在测试过的版本**上；而像 Xcode 这类不能频繁发客户端更新的合作方，则**让客户端保持稳定、允许它指向更新的 App Server 二进制**来解耦发布周期。启示：这是 8 月《Codex as a platform》和 9 月 Agents API 的**协议前传**——"harness 即服务"能成立，靠的是先把 item / turn / thread 这三层抽象和一个带审批回调的双向 JSON-RPC 协议定清楚。如果你要把自己的 agent 嵌进多个宿主，这篇是现成的设计模板。

### 论文补遗 · 速览（其余 24 篇，均为本轮新见且此前未收录）

**Skill 演化与路由**

- [The Router Within / Gavel](https://arxiv.org/abs/2609.15982)（09-14）——路由的第三条路：现有 harness 把每个 skill 的元数据预载进上下文（分散注意力、限制库规模），检索流水线把选择移出上下文但也移出了 agent 的能力。这篇证明**冻结的 agent LLM 在自己的前向传播里已经带着路由信号**，只需两个线性映射就能读出来，**上下文里不放任何 skill 文本**：glance 用中层状态打分整库，verdict 只对候选恢复前向传播读出模型自身的似然与 yes/no 判断，两者按专家乘积融合。Qwen3-32B 上胜过渐进披露与外挂 1.2B–16B 参数的 retrieve-and-rerank 流水线。
- [Memory-Skill Isomorphism: One Skill Carrier, Two Native Uses](https://arxiv.org/abs/2609.16669)（09-15）——本期最对 Peter 胃口的一篇概念文：memory 和 skill 都是不改权重的增强手段（记忆承载过往经验、skill 承载可复用流程），而**把两者都包上存储、路由、检索、反思、更新路径会让复用机器随积累而膨胀**。主张是**别重建：Skill 本来就是蒸馏后记忆的天然载体**——常驻 description 放热线索，按需的 SKILL.md 放较冷的索引与策展策略，reference/*.md 放详细记忆（L0→L1→L2 三级）；用一个**受治理的 1,024 字符 description 预算**压住常驻索引。于是记忆与能力共用同一个渐进披露载体，反思可以演化任意一个 Skill；写入分叉：历史追加，当前状态重写并重新验证。作者还给了一个很克制的发现：在一个已部署系统里"最锐利的识别点是治理——**存在 4 条写入条目，但只有 1/4 进入结算账本**"。
- [SkillLift](https://arxiv.org/abs/2609.15396)（09-14）——skill 自演化的**监督瓶颈**：每次 oracle 评估都要跑完整 agent rollout，因此搜索被困在"打补丁式"更新里。洞察是**排序比绝对分数更平滑**——判断哪个 skill 更好比预测精确分数需要的 oracle 评估少得多。于是学一个与 oracle 对齐的 rubric 作为结构化评估空间，双层优化：内循环用冻结 rubric 当零成本代理引导 skill 修订，外循环用少量 oracle rollout 按秩相关重新对齐 rubric。
- [SE-GoS: Self-Evolving Graph-of-Skills for Skill Library at Scale](https://arxiv.org/abs/2609.08228)（09-08）——skill 库到数千条时检索成为瓶颈。训练无关地演化已有的 Graph-of-Skills：**拓扑演化**（从执行证据发现并剪枝 skill 关系）、**边权演化**（按历史有效性强化与检索相关的关系）、**描述演化**（用执行反馈优化面向检索的 skill 描述）。注意第三条——**"skill 描述"本身是可被自动优化的对象**，这正是 OpenAI 那份 Astra 清单里让人手写的那部分。
- [MOSCOPT: Mixture-of-Skills Collective Optimization](https://arxiv.org/abs/2609.14399)（09-13）——现有 prompt/skill 优化都只优化**单个**文本模板，错过了多个互补策略之间的协同。这篇无梯度、无参数地联合优化 N 个 skill 加一个每步动态选 K 个的门控 skill，用自建的 EditAdam（内部维护双状态）做三阶段交错更新。
- [Co-Skill](https://arxiv.org/abs/2609.16008)（08-01）——云端 LLM 分析生成 skill、边缘小模型执行并内化的**混合演化**范式，失效根因是"**盲通信**"：云端感知不到边缘的执行能力，边缘不理解云端的分析需求。三招：边缘把轨迹按共享前缀合并成 trie 并标出分歧点供云端高效分析、云端渐进构建与边缘能力匹配的分层 skill 树、两棵树上做协同演化。
- [APEx](https://arxiv.org/abs/2609.02253)（09-02）——深度研究 agent 的经验利用分两层：实例级轨迹记忆与类别级流程性 skill，由 Executor / Distiller / Planner 闭环耦合，三阶段交替 GRPO 训练，实现**奖励引导的 skill 蒸馏**而非固定 prompt 生成。
- [FINSKILLOPS](https://arxiv.org/abs/2609.19680)（09-17）——把部署后改进重新表述为「**受控的行为维护**」：反复出现的失败应该变成**范围受限的 skill 补丁**，而每个补丁必须在**不引入回归**的前提下"赢得部署"；机制是证据扎根的类型化失败诊断 + 定向验证 + 受保护用例回归检查。这是目前最贴近生产工程直觉的一篇 skill 演化文。
- [GeoSkill](https://arxiv.org/abs/2609.13667)、[MediSkill-Evo](https://arxiv.org/abs/2608.23397)、[SkillZip Pro](https://arxiv.org/abs/2608.30785)、[Self-Evolving Skills via Surrogate-Guided Solve-and-Reproduce](https://arxiv.org/abs/2608.28638)、[Auto-Policy, not Auto-Skill](https://arxiv.org/abs/2608.25091)、[From General Agents to RCA Experts](https://arxiv.org/abs/2608.25661)——同一时期 skill/harness 自演化的领域化变体，留作后续按需展开。

**自演进机制与 RSI**

- [Self-Evolving Search Index / SELF-INDEX](https://arxiv.org/abs/2609.19656)（09-17）——自演进的对象换成**检索索引**：索引键怎么暴露文档知识决定检索质量，而有效表示因检索环境而异，因此固定优化策略无法一致地好。SELF-INDEX 的 Optimizer 自主诊断检索缺口、**有选择地改写负责的索引键、并在更新前验证每次修订**；此外用一个 Query Simulator **主动探索尚未出现的查询需求**，让索引演化超出现有查询集。注意它有**验证门**——这正是 xAI memory 目前缺的那块。
- [Self Improvement via Fast Tree-search / SIFT](https://arxiv.org/abs/2609.19526)（09-17）——自改进的主要运行时瓶颈是**评估候选自修改**（既有做法是拿改过的 agent 重跑一部分基准任务，很慢）。SIFT 用 LLM-as-a-judge 对候选补丁做**成对比较**，胜负记录用带正则的 Bradley-Terry 模型聚合，得到的强度分数驱动基于排序的搜索，从而在严格预算下显著提升编码表现。与 COBRA-Skills 的"预算受限序贯优化"是同一问题的两种解。
- [CERA-MoA](https://arxiv.org/abs/2609.18779)（09-16）——路由与 agent 微调不该是两个过程：**动态路由器与各 agent 策略共同演化**；用中层隐状态做"预测式熟悉度估计"评估各 agent 的语义胜任度以避免全 rollout 开销，再按累积阈值自适应激活最小 agent 子集，并**按演化中的胜任度主动给 agent 分配定向训练样本**。
- [Rollback the World, Keep the Reflection / RIR](https://arxiv.org/abs/2609.18304)（09-16）——长时程恢复的正确抽象：现有方法要么只修上下文不修环境状态、要么回滚状态但丢掉有用经验。RIR 把恢复当作**回滚边界控制问题**——联合决定**何时介入、从哪里恢复、哪些信息应当在恢复中幸存**；并用"回滚深度 × 保留记忆"的统一算子刻画。与 EvoUndo 的可恢复性约束是同一族问题。
- [Asclepius: An Adaptive Harness for Long-Horizon Clinical Agents](https://arxiv.org/abs/2609.13543)（09-11）——真实部署跑数小时会暴露另一类失败：在急诊排班模拟器里，**agent 大多能给出正确诊断，却无法完整、及时地交付关键动作**（"执行差距"）。三种长时程失败模式各自做成逐轨迹计数器：**指令遵循漂移、治疗不完整、及时性上的严重度—公平性差距**；Asclepius 的自演化 harness **在两次运行之间改写"操作手册"**。这是少见的把 harness 自演化下沉到具体行业约束的工作。
- [Atria Dawn: The Dawn of Agentic Superintelligence](https://arxiv.org/abs/2609.15818)（09-14）——一个面向科研与工程工作流的基础 agentic 模型，用「**可验证经验流水线**」把工具中介的交互连到可执行环境与外部验证结果；比模型本身更值得看的是它把**造这个模型的研发过程本身当作人机协作案例研究**，分析了 **56 名参与者的 769 条任务记录**与 agent 日志。
- [Experience Funnel](https://arxiv.org/abs/2609.08919)、[Ecdysis](https://arxiv.org/abs/2609.11677)、[Auto-RecSys](https://arxiv.org/abs/2609.10922)、[AURA](https://arxiv.org/abs/2609.16625)、[Interactive Memory Learning](https://arxiv.org/abs/2609.17088)、[TRIAGE](https://arxiv.org/abs/2609.01428)——同期自演进与记忆方向的其余条目。
- [Memory as Infrastructure](https://arxiv.org/abs/2609.05510)（08-31）——**唯一一篇把 agent 记忆当 SRE 对象来写的文章**，也是本期最实用的工程材料之一：记录了一个自 2026 年 1 月起、在单条连续 Claude Code 会话线上跑了数月、驱动 **63.3 万行**代码库的真实项目，以及由此长出的开源记忆与连续性基础设施 **SIx Harness**——按项目的长期记忆（SQLite 上的混合词法—向量检索，全本地）、**精度受控的上下文注入**、决策与死路的**反复抑制存储**、被专门设计成**能在 compaction 中幸存**的约定，以及作者认为业界实践里最缺的那块：**对记忆子系统本身做可靠性工程**——会话启动时的健康门（带区分化的失败模式）、被设计成"任何枚举内的失败模式都不可能不留记录"的心跳遥测、以及借自 SRE 的**告警疲劳预算**。他们自称这是首份月级、带仪表的持久 agent 记忆子系统生产运行记录（78,933 条 hook 记录起）。

**评测、安全与长时程行为**

- [When Agents Slow Down: Elo-per-token](https://arxiv.org/abs/2609.15309)（09-14）——测量 agent 表现如何随算力扩展的方法论：在能给中间提交连续分数的开放式任务上，跟踪每个 token 预算下找到的最好解，用 Bradley-Terry 把任务内的序聚合成跨任务 Elo。四个通用 agent、四个开放式基准、**最长 1 亿 token 的会话**，外加三个反馈驱动的优化 harness 做单任务对照。关键结论：独立采样提供了理论参考线（Elo 随 log 算力线性增长），**agent 起初能比独立采样更快地把 token 换成 Elo，但边际收益递减并最终跌到参考线以下**。这是"给 agent 更多预算到底还有没有用"的第一把定量尺子。
- [Root-Cause Attribution Is a Search Problem](https://arxiv.org/abs/2609.13463)（09-11）——自动根因归因（RCA）在长轨迹上准确率低，因为相关信息稀疏、分散在遥远动作里、且与可见的失败脱节；现有方法用一次性 LLM 判断，**倾向于早早停在一个看似合理的诊断上，把长轨迹里的关键证据留着不查**。Continual Search 用迭代框架逼裁判在连续几轮里继续寻找未解决的诊断证据。做 agent 可观测性的人应该直接用这个框架。
- [ImpossibleRubrics](https://arxiv.org/abs/2609.16816)（09-15）——LLM 生成的 rubric 正被大量用作 RL 奖励、LLM-as-a-judge 和自动评分，但**它们对被优化的对抗答案是否鲁棒，几乎没人研究**。这篇隔离最难的情形：**不可能任务**——提示在把模型推向一个无依据的结论，唯一诚实的回答是承认不可能。169 个不可能任务（六类不可能性）各配一张**可验证的 oracle 证书**规定诚实答案可以和不可以主张什么，另有 48 个可答对照。结果：**十一个 rubric 生成器有 8–26% 的时候被攻破**（奖励了违反证书的答案）。凡是在用 rubric 做奖励的人都该看这条数字。
- [Emergence World](https://arxiv.org/abs/2609.17320)（09-15）——**规模最大的一次长时程多 agent 对抗压力测试**：八个并行世界、每个十个 agent、相同初始条件（七个同构世界各由一个前沿模型驱动，一个混合模型世界），**16 天内产生超过 85 万次 LLM 调用、近 500 亿 token**，agent 一边追目标、用/造工具、维护持久记忆、治理共享制度。等运行状态积累起来之后，通过**普通交互面**投放三个受控压力事件：间接提示注入、错误信息、私有 agent 记忆的暴露。结论很硬：**没有任何一个被评测的世界在三个事件上都保持韧性，而且"检测到"并不等于"扛住了"**。
- [PACT: Can Enterprise AI Assistants Be Trusted Under Pressure?](https://arxiv.org/abs/2609.18605)（09-16）——企业 agent 进入招聘、医疗、金融等敏感场景后，**遵守系统上下文里写明的规则是一等法律问题**，但没有框架系统性地测"哪些模型在压力下会违规"。PACT 覆盖十二个受监管领域、四十八个场景，每条把一条常设规则与一条违规捷径配对，并施加一整套压力（执着的用户、赶时间的经理、违规恰好方便或诱人的情境），全部经严格 LLM-as-judge 审核以保证无歧义、不可钻空子。
- [HazardAuditor](https://arxiv.org/abs/2609.15134)、[Benchmark Radar](https://arxiv.org/abs/2609.11115)、[Confidence Comes from Experience](https://arxiv.org/abs/2609.17708) 见正文速览。

**训练与蒸馏**

- [Don't Mask the Environment / ActObs](https://arxiv.org/abs/2609.20715)（09-17）——一条便宜且反直觉的改动：标准 SFT 只对 agent 自己写的动作 token 算损失，把环境观测当上下文但不当预测目标。ActObs **也监督轨迹里本来就有的观测 token**——部署时 agent 当然不生成观测，但**学着预测观测会促使策略建模动作后果**，且不增加数据、参数、序列长度或前向次数。SFT 后两者表现相近，**GRPO 之后分道扬镳**：Qwen3-4B 上 Terminal-Bench 2.0 各采样预算的 pass@k 全面更高，Qwen3-8B 上以部分 pass@1 可靠性换 pass@16 +3.4 个点并解出更多不同任务，跨域的 aider-polyglot 上 4B 的 pass@1 +4.2 个点。
- [When EOS Tokens Disagree](https://arxiv.org/abs/2609.20511)（09-17）——on-policy 蒸馏里学生回答越来越长甚至耗尽生成预算，根因之一是**终止符错配**：跨 Qwen3、Llama、Gemma，基座学生与后训练教师**即使声明的停止集合相同，也可能把停止概率放在不同的 EOS token 上**，于是学生偏好的终止动作被压制、教师偏好的替代却没被可靠地传过去。只对齐解码停止集**不够**，把功能等价的 EOS token **当作同一个语义停止动作**才能显著缓解。
- [RetireOPD](https://arxiv.org/abs/2609.20784)、[What Does Privileged Information Add to OPSD?](https://arxiv.org/abs/2609.20612) 见正文速览；三篇合起来是本期"on-policy 蒸馏怎么做才不倒退"的完整证据链。

## 趋势观察

本周把三条已经跑了一个月的主线推到了同一个结论上：**「自演进」正在从技术话题变成治理话题**。

Anthropic Institute 那篇是最清楚的信号。此前两个月官方 RSI 材料的口径是**结果**——多少代码由 Claude 写、研究员产出几倍、多少 agent 工作日；这一篇换成了**过程与可核查性**：任务树怎么构造、量表用谁的、覆盖率与拦截率怎么定义、算力里安全占几成、第三方怎么进来复核，甚至坦白承认"用自家模型评自家系统"的同源偏差。这是一个把内部数据变成**外部可比指标**的动作。OpenAI 同一周的失准披露框架在做同一件事的另一半：把模型行为异常从零散的博客文变成有分档、有时限、有复现标准的制度。两家在同一个月里、用同样的语言（"希望成为行业标准"）建立报告口径，这比任何一次模型发布都更像行业形态的定型。

第二条是**「AI 原生工程的二阶效应」终于有了工程细节**。09-14 那篇 CI 长文和补录的两篇（值班 agent、AI 原生 SDLC 安全）拼起来是一条完整的因果链：agent 写码 → 评审被自动化（实质性评审 PR 占比 16%→54%）→ CI 成为新瓶颈（六个月 25×）→ 单写者架构必须炸掉重来（一个工程师三周，一年前要一个季度）。这条链上每一环都有可引用的数字，而且最后那句"假设你的架构两个季度内要扛 25× 负载、v0 就按 10–20× 设计"是**对"过度设计"这个行业共识的一次公开修订**——理由不是需求变了，而是**实现成本塌缩了**。同一逻辑也出现在补录那篇安全文里："把漏洞发现闭环回 CLAUDE.md/skill"之所以成立，也是因为改指令几乎不要钱。

第三条是**记忆与经验沉淀从论文进了产品**。xAI 这周直接把"轮末异步捕获 + `/dream` 折叠成 topic 文件 + 明确的不记清单 + 当前指令优先"发成了 Grok Build 的默认行为。把它和本周论文并排看很有意思：学术线正在补的恰恰是它没做的部分——Experience Funnel 在问"文本状态什么时候该固化进权重"，COBRA-Skills 在问"怎么用最少的执行预算演化 skill"，DSR 在问"skill 多了之后怎么选互补的一组"，EvoSkill-GUI 在问"怎么让 skill 在部署时被安全地改写"，Continual Learning Mechanisms 在给出权重侧记忆的残酷基线（单机制留存 1.2%，最好的组合也只有 34.9%）。**产品化的是捕获与组织，没产品化的是验证、剪枝、迁移与固化**——这四个词大概就是未来两个季度这条线的全部内容。

最后一条给面试用的判断：本期精读一那篇 harness 组件实验，给了一条比"删脚手架"更精确的表述——**规划没有消失，它从"准确率的脚手架"变成了"成本的杠杆"；上下文管理的价值主要不是让 agent 更聪明，而是让它不死；把省略内容做成可恢复是白花力气**。把这三句和 09-11 期 OpenAI 那份官方清单放在一起，就是目前关于"模型变强之后 harness 该怎么改"最完整的答案。
