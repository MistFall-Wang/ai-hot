## 今日判断

- 【必看】**代理型 agent 的瓶颈在「理解用户」这一步，不在执行**。Project Swap 里 85% 的效率损失来自偏好估计误差；用户在采集阶段多写 150 个词，排序一致率约高 4 个百分点。做代用户决策的 agent，应该优先投入偏好采集和确认环节，并且能量化 agent 对用户偏好的理解准确度。
- 【必看】**写入时总结记忆可能是错误的默认做法**。JitMem 保留原始轨迹，拿到新任务时再按任务整理，连未经训练的整理器都能追平或超过写入时蒸馏的基线。给 agent 做记忆时，应该保留原始轨迹，把「提炼」放到读取时做。
- 【警示】**把 agent 放进有利益冲突的环境，它很容易被带偏**。CAVEAT 里平台的引导机制让选对商品的比例从 78.6% 跌到 17.3%，更大的模型和更多推理也只能部分缓解。做购物、比价、代办类 agent，要在 harness 层显式锁住用户目标，并要求 agent 在做决定前补齐关键证据。
- 【值得盯】**自演进方法的标配正在变成「失败聚类 → 生成候选 → 门禁准入 → 可回滚」**。本期 TimeEvo 和 RegenHarness 与上期 AIDE²、Growing Harness 是同一个结构。TimeEvo 还给出反例：不加门禁的通用自我修订改了 147 个答案，其中 56 个被改坏，总分变化却不到 1 分。这种「静默伤害」只看平均分是发现不了的。
- 【利好】**长会话的成本在下降，但前提是缓存不被打断**。Anthropic 数据显示 Claude Code 缓存未命中的输入降了 50% 以上，并且 Opus 5.5 / Fable 5.1 中途改 effort 已经不会清缓存。长任务要开 1 小时缓存寿命，离开前先 compact。

## 今日话题

### 【必看】代用户做决定的 agent，最大的误差出在「它以为你想要什么」

Anthropic 的 Project Swap 在一个可以精确打分的换书市场里拆开了两类误差：偏好估计误差占效率损失的 85%，交易机制只占 15%，而换成更强的模型对交易结果的影响明显大于改指令（Haiku→Opus 平均提升 0.12，「冷酷」与「利他」指令只差 0.02）。CAVEAT 从另一侧补上风险：环境本身有利益时，agent 会扭曲用户的优先级、过早缩小候选集。两者合起来说明，代理型 agent 需要在偏好采集和决策依据上加工程投入，只优化谈判话术没有多大用处。

- [Project Swap: What happens when agents trade for us?](https://www.anthropic.com/research/project-swap)
- [CAVEAT: Towards Robust Computer-Use Agents in Incentive-Misaligned Environments](https://arxiv.org/abs/2609.27273)

### 【值得盯】自演进的共同结构：失败驱动、证据门禁、可回滚

TimeEvo 把 agent 的失败聚成能力缺口，针对每个缺口合成只提供证据的工具，整个工具库只有通过配对准入检验才会上线；RegenHarness 在真实机器人上让执行记录驱动对上下文规则、任务模板、路由和恢复策略的修改，改动须过固定回归检查和发布授权，并禁止修改「提交门」本身。与上期 AIDE² 的隐藏评测选优、Growing Harness 的保留集门禁一起看，「提出修改」已经不是难点，难点和价值都在准入门禁的设计上。

- [TimeEvo: Failure-Driven Self-Evolution of a Time Series Agent](https://arxiv.org/abs/2609.27277)
- [RegenHarness: A Robot Agent Harness with Evidence-Gated Recursive Self-Improvement](https://arxiv.org/abs/2609.27612)
- [Self-Organizing Agent Teams Learn to Reason Together](https://arxiv.org/abs/2609.22682)

### 【利好】agent 的上下文工程：记忆推迟到读取时整理，缓存要保护好

JitMem 说明记忆的价值要到具体任务出现时才能判断，所以应保留原始轨迹、在读取时按当前任务整理；Anthropic 的数据则说明长会话里大部分成本是重复读取的上下文，缓存命中率直接决定成本。两者都指向同一个方向：上下文越来越长之后，「什么时候整理、什么内容保持不变」比「存多少」更重要。

- [Just-in-Time Memory: Learning to Curate Task-Adaptive Memory for LLM Agents](https://arxiv.org/abs/2609.27334)
- [Coding sessions are longer and use more context. Claude Opus 5.5 is built with that in mind.](https://claude.com/blog/claude-opus-5-5-built-for-coding-sessions-that-use-more-context)

### 【值得盯】agent 接入层：MCP 从单独部署的服务器变成网关的一个功能

Google Cloud API Gateway 让已有 REST 接口通过 OpenAPI 标注直接成为 MCP 工具，与 REST 共享认证、配额和日志；GitHub Security Lab 的 fuzzing 流水线采用「agent 负责决策、MCP 工具负责执行、状态全放 SQLite」的分工；GitHub 另一篇主张让 agent 生成专用界面（canvas），不要什么都在 chat 里做。三篇合起来的方向是：agent 负责判断和编排，执行交给确定性工具和界面。

- 【必看】**[Project Swap: What happens when agents trade for us?](https://www.anthropic.com/research/project-swap)** · 出处：Anthropic（/research，Economics）· 09-24 —— Project Deal 的受控续作。旧金山、纽约、伦敦、西雅图、华盛顿、都柏林六个办公室共 201 名员工各带一本书，与 Claude 进行简短的采集对话（中位数 8 条消息、216 个词），由 Fable 5 据此为书池里每本书排序，再派 agent 上公开交易大厅换书；参与者另外亲手排 10 本书作为真值，agent 看不到。**结果**：Claude 的排序与本人一致率 61%（按热度排序 53%，协同过滤 55%）；按真值计分，市场效率 0.55，理论最优 0.89，而用 Claude 排序算出的最优解只有 0.60，即 85% 的损失来自偏好估计，15% 来自交易本身；换成集中式的 Top Trading Cycles 也只有 0.60。**重跑 205 次**：模型越强市场越有效（按 Claude 排序算，全 Haiku 0.75，全 Opus 0.88），Haiku→Opus 提升 0.12，而「冷酷」与「利他」两种指令只差 0.02；在 Opus/Haiku 混合的交易大厅里，Opus 一方始终占优。「利他」agent 接受排名更低的书的频率是「冷酷」agent 的两倍。参与者平均愿意把约三分之一的年度购书预算交给 Claude。**可借鉴**：评估代理型 agent 时，把误差拆成「理解用户」和「执行交易」两部分分别量化（用少量真值排序就能做到）；在采集阶段引导用户多写一些（300 词比 150 词一致率约高 4 个百分点），这比调谈判提示词更划算。

- **[Turn your REST APIs into MCP tools with Google Cloud API Gateway](https://developers.googleblog.com/turn-your-rest-apis-into-mcp-tools-with-google-cloud-api-gateway/)** · 出处：Google 开发者博客（Google Cloud）· 09-24 —— API Gateway 公测支持作为远程 MCP 服务器：在 OpenAPI 3.x 规范里用 `x-google-api-management.mcp` 开启，用 `x-google-mcp-tool` 定制单个工具，网关把 `tools/call` 转成对应的 REST 请求，复用已有的 JWT/API key 认证、配额和日志，同一个操作无论走 MCP 还是 REST 都计入同一份配额。**注意事项**：`tools/list` 默认不鉴权，会公开工具名和 schema，生产环境须要求 JWT（API key 不能保护这个方法）；返回空 body（如 204）的操作不会暴露；单个网关最多 1,000 个工具；MCP 与模型路由不能在同一份配置里同时启用。**可借鉴**：企业内部接 agent，优先在已有网关上加 MCP 转码层，不必单独部署 MCP 服务器，以免把鉴权和限流重写一遍；工具描述要写清「什么时候、为什么用」，不要只写返回什么；工具发现接口也要鉴权。
- **[When chat is the wrong UI](https://github.blog/ai-and-ml/github-copilot/when-chat-is-the-wrong-ui/)** · 出处：GitHub Blog（AI & ML / GitHub Copilot）· 09-24 —— 介绍 GitHub Copilot app 的 canvas：由 agent 生成、在 app 内运行的小型全栈应用，可以和 agent 双向通信，也能执行本地代码。作者的主张是：用户知道自己要做什么时，与其每次都让 agent 执行（例如让最贵的模型「stage and commit」），不如让它做一个工具，以后的操作就不再消耗 token。示例包括 Winget 包管理界面、带补全的 SQLite 查询界面，以及一个把「调研、原型、计划、实现、迭代、定稿」串起来、让人只在需要时介入的工作流 canvas（作者说这个花了大半天）。**可借鉴**：做 agent 产品时，区分哪些操作需要 agent 判断、哪些只是重复执行；后者让 agent 一次性生成确定性工具或界面，token 成本和延迟都会降下来。

## 论文（自演进优先）

- ⭐ **[TimeEvo: Failure-Driven Self-Evolution of a Time Series Agent](https://arxiv.org/abs/2609.27277)** · Jie Yang 等 11 人 · 2026-09-23 —— 先指出两种失败：一是专家整理的 21 个工具在部分任务上有害，在所有测试的基座上都拉低了异常检测准确率；二是「静默伤害」，一轮通用自我修订改了 147 个答案，其中 56 个被改坏，总分变化却不到 1 分。TimeEvo 把诊断出的失败聚类成能力缺口，为每个缺口规划测量方法并合成只提供证据的工具，候选工具库必须通过配对准入检验才会被采用。在 10 个时间序列问答任务、3 个基座上，从空工具库开始，每个任务、每个基座的准确率都有提升；在便宜模型上长出来的工具库装到更强模型上仍有增益。**可借鉴**：评估自我修订时，除了看平均分，还要统计「对变错」的数量，用配对检验做准入；自演进可以先在便宜模型上跑，再把结果迁移到强模型。
- ⭐ **[RegenHarness: A Robot Agent Harness with Evidence-Gated Recursive Self-Improvement](https://arxiv.org/abs/2609.27612)** · Kailin Wang 等 5 人 · 2026-09-23 —— 机器人 agent harness，把「模型提议」「控制器终止」「任务真正完成」严格分开：规划、监督、验证、恢复四个角色使用相互隔离的上下文；带版本的记忆区分「观察到的事实」和「已接受的进度」；任务状态的更新要经过绑定身份和版本的提交门。作者称这是首个面向具身机器人的「证据门禁递归自改进」协议：执行记录驱动对上下文规则、任务模板、路由和恢复策略的修改，由固定回归检查和发布授权决定是否接受，改动版本化并可回滚，不更新模型权重，也不允许放宽提交门。在真实四足机器人上演示了仓库导航、巡检、送信等任务。**可借鉴**：做 harness 自改进时，把「允许自动改的配置」和「不可改的安全门」明确分开写进协议，每次改动都带版本号并可回滚。
- **[Just-in-Time Memory: Learning to Curate Task-Adaptive Memory for LLM Agents](https://arxiv.org/abs/2609.27334)** · Yefan Zhou 等 5 人（HF 组织 Salesforce AI Research）· 2026-09-23 · HF ↑33 —— 多数 agent 记忆在写入时把轨迹蒸馏成反思、工作流或 skill，等于在不知道将来要查什么时就决定保留什么，信息丢失不可逆，写入决策的价值也难以归因。JitMem 保留原始轨迹，在读取时由整理器按当前任务合成紧凑的记忆内容，并直接用当前任务是否成功来训练整理器。在 ALFWorld、WebShop、τ²-bench 上比最强基线分别高 16.2、16.3、3.9 个百分点；未经训练的整理器也能追平或超过基线。**可借鉴**：记忆库里保留原始轨迹，检索后再按当前任务做一次 LLM 整理，这不需要训练就能先试用。
- **[Verifiable Hidden Dynamics Play: Generating Agentic RL Environments from Solved Mechanisms](https://arxiv.org/abs/2609.27321)** · Xinjie Shen 等 8 人（arXiv 注明 Qwen Technical Report）· 2026-09-23 · HF ↑6 —— 反转常见的环境生成顺序：先采样并求解一个数学模型，再把它的决策过程包装成有状态的工具，环境动力学和轨迹评分都来自同一个已求解模型，可以验证。以每个几美分的成本生成 3,300 个环境；训练后 Qwen3.6-35B-A3B 的平均 agent 得分从 0.204 升到 0.815，并迁移到函数调用、旅行规划和 365 天电商基准（全程没有破产，超过 Qwen3.7-Max）。
- **[CAVEAT: Towards Robust Computer-Use Agents in Incentive-Misaligned Environments](https://arxiv.org/abs/2609.27273)** · Yuxuan Li 等 4 人 · 2026-09-23 —— 9 个电商环境、8 类平台引导机制。在 5 个模型家族上，对照组 78.6% 的情况下买到对用户最优的商品，开启引导后只有 17.3%。失败点有三个：扭曲用户的优先级、过早缩小候选集、证据没补齐就下决定。针对这三点设计的 CAVEAT-Harness 让最优购买率提升 55.0%。
- **[Self-Organizing Agent Teams Learn to Reason Together](https://arxiv.org/abs/2609.22682)** · Aneesh Pappu 等 8 人 · 2026-09-19 · HF ↑4 —— 固定的 agent 团队从过往协作中学习可复用的组织策略（角色、阶段、发言、信息流），只用 15 道数学题和 25 道研究生知识题学出的策略可以原样迁移到新基准。在 5 个数理基准上平均 66.7%，最强单个成员 48.8%，算力对齐的单 agent 58.7%，完美路由 59.0%；收益大小与「团队能否辨认出正确推理」强相关（ρ=0.90）。
