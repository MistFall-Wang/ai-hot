## 今日判断

- 【必看】模型和 harness 是一起起作用的：同一个 27B 模型，只在自己的 harness 里做 RL 训一个 LoRA，SWE-bench Pro 困难子集就从 39.2% 提到 64.7%，工具调用还少了一半以上。自建 agent 的团队应该把"按自家 harness 和任务分布做轻量 RL"列入路线图，而不是只靠换模型。
- 【结论】自改进系统的上限由评测吞吐决定：CompoundingKernel 实测，扩大规模的瓶颈是可靠测量的速率，不是 agent 数量，和 11-20 期上海科技大学"评测分辨率是瓶颈"的结论一致。设计自演进循环时，先把评测做得快、准、可重复，再加并行。
- 【利好】工具调用前置检查正在变成平台标配：Google 把"LLM 评审 + 自然语言策略 + 用户原意检查"做进了 Agent Gateway，评审理由写入日志，并建议先 dry run。自己做 agent 时，可以照搬"调用前双检查 + 可审计理由"的结构。
- 【警示】蒸馏防御会改变 API 行为：OpenAI 把受保护的推理绑定到产生它的对话历史，改写了更早的消息，之后的推理就会被丢弃，旧模型族也不能读取新模型的推理。依赖重写上下文或跨模型复用推理的 agent 实现要提前检查。
- 【值得盯】评测在往"真实可执行环境 + 统计检验"走：TwinLab-Bench 用 agent 充当实验室环境执行被测 agent 设计的实验，AltRA-Test 给出"约 100 条样本就能检验 LLM 评审能否替代人工"的方法。两者都可以直接用到自家评审器的上线门槛上。

## 今日话题

### 【必看】按 harness 训适配器、按测量速率扩搜索：agent 性能的余量在"模型之外"
Hugging Face 证明，只要在目标 harness 里用经过校验的任务做 RL，就能同时提高准确率、降低开销，而且能力能部分迁移到别的 harness。Amazon 的 CompoundingKernel 则从系统层面说明，自改进搜索能走多远取决于可靠测量的速率。两者合起来看，agent 工程的重心正在从"选哪个模型"转到"任务、校验器、评测吞吐"。

### 【警示】OpenAI 收紧推理链保护：蒸馏防御既是安全措施，也改变了 API 语义
OpenAI 用内部实验说明，原始推理轨迹比推理摘要更能传授网络安全能力，因此在请求和团伙两个层面做防御，并把提取攻击日志当成回归测试。对开发者的直接影响是推理与对话前缀绑定，改写历史就会丢掉推理。

## 论文（自演进、评测优先）
