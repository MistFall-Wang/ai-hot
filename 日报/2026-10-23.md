## ⭐ 自演进重大发现

**Google Cloud 发布官方的自演进 agent 参考架构，把自我修补、自我评估、记忆沉淀和拓扑重写都放进治理关卡。** 10 月 22 日 Google 开发者博客的 Project Chrysalis 基于 Gemini 4 Argon 和 ADK：agent 在运行时生成限流补丁，补丁要依次通过 AST 沙箱检查、OPA 策略校验、Cloud KMS 签名才能挂载；随后给每个动作计算贡献分（重启数据库这类「慌乱反射」扣分，限流补丁 +0.97），把验证过的规则签名后写入向量记忆；新增「流量整形专家 agent」这种结构性改动必须经两名 SRE 批准，再在内存里改写 ADK 子 agent 图，不重启容器。在模拟的黑五缓存雪崩里，首次缓解时间从 15–45 分钟降到 1.8 秒，5xx 错误率从 72.7%–80.0% 降到 0。注意：这是参考架构加模拟演示，不是生产事故数据。

## 今日判断

- 【必看】多 agent 拆分不该照着组织架构图来。Anthropic 的建议是先用「单循环 + skills + tool search」，只有出现可测量的上下文膨胀、确实需要并行的新上下文、或者工具选择出现冲突时才拆子 agent。面试被问到多 agent 设计时，先讲什么时候不拆，再讲拆的条件，会比直接画编排图更有说服力。
- 【结论】自演进 agent 能不能上生产，关键在治理链路而不在算法。Google 的 Chrysalis 和 10 月 21 日 OpenAI 广告栈都是同一种结构：系统可以自己改，但每一种改动都有对应的关卡（沙箱、策略、签名、人工批准）。自己做自改进功能时，按「临时补丁 / 记忆规则 / 结构改动」分级，分别设审批要求。
- 【利好】Agent Skills 交给 Linux 基金会后，和 MCP 一样有了中立的标准归属。官方数据是已有 70 多个 agent 平台接入、发布了 100 万个 skill、安装量接近 2.8 亿次。现在把团队流程写成 SKILL.md 投入不会白费，跨 Claude、ChatGPT、Cursor、Copilot 都能用。
- 【值得盯】形式化证明的成本在快速下降：Opus 5.5 证明同样任务比 Opus 5 少用约 40% token，共享证明工作区还能再省 17%。安全和基础设施相关的岗位，「用 LLM 把测试变成证明」可能很快会成为面试会问到的新能力。
- 【利好】OpenAI Decisions API 每百万输入 token 0.10 美元，不收输出费，最快比走 Responses API 快 10 倍。agent 循环里的分类、路由、「继续 / 重试 / 追问」这类判断，可以从主模型调用里拆出来单独做，延迟和成本都能降。

## 官方长文（工程/研究）

- 【必看】**[Building agents: When to fold subagents into your main agent loop](https://claude.com/resources/articles/building-agents-when-to-fold-subagents-into-your-main-agent-loop)** · 出处：Anthropic，claude.com/blog（Applied AI 团队）· 2026-10-22 —— 文章认为，大企业做 agent 时常让每个团队各建一个子 agent，再由平台团队在上面加编排器，结果是 agent 架构变成了组织架构图的翻版。由此带来五个问题：上下文在 agent 之间传递时丢细节、子 agent 泛滥、各团队往系统提示里各加一句的「拼凑 prompt」、各自优化的局部评测，以及额外延迟（有客户换成单循环后运行快了约 2 倍）。建议的单循环设计是：一个模型、一个上下文窗口、harness 设轮次和成本预算以及写操作关卡；模型第一轮写计划并边做边改；流程性知识放进 skill，硬性限制和权限检查放进工具；工具按用户意图分组，超过 30–50 个工具定义后选择准确率会下降，要用 tool search 延迟加载。迁移方法：先建一个最少 10 条样例的端到端评测，然后一次只折叠一个子 agent，对比哪些任务结果翻转，每个任务至少跑两次（文中有一个回归只在两次运行中出现一次）。仍然该用子 agent 的三种情况：可测量的上下文膨胀、需要并行的一次性上下文、工具选择出现冲突。配套开源了 single-agent-loop-kit 迁移工具包。**可借鉴**：拆不拆子 agent 用评测决定：先建端到端评测集，一次只合并一个子 agent，逐任务看哪些从通过变成失败，只有合并后得分更低才保留子 agent。
- 【必看】**[LLMs are making formal software verification feasible at a much larger scale](https://www.anthropic.com/research/formal-verification)** · 出处：Anthropic Research（与 Theorem 合作）· 2026-10-22 —— 关键做法是用开发者现成的测试当规格：把 OSS-Fuzz 的 fuzz 入口编译成 RISC-V 二进制，结合 Theorem 的 RISC-V 指令和 Linux 进程形式语义，自动生成「任何 64 MB 以内输入都不崩溃（含 ASan 报错）」的规格，由 Claude 写证明、Rocq 内核检查。几周内为 123 个库的 239 个入口完成了证明，总量约 1.8 亿行 Rocq，典型证明约 60 万行，被证明的二进制中位长度约 1.8 万条指令。需要信任的只有机器语义模型、定理陈述和证明检查器本身。证明过程中 Claude 发现并修复了数百个 bug，其中不少 fuzzer 很难触发（如只在约 20 MB 特定布局输入下才出现的越界写），还重新发现了 libexpat 的一个 CVE。成本方面：Opus 5.5 在 36 个小任务上比 Opus 5 少用约 40% token；允许 agent 复制彼此的证明后再省 17%。局限：证明只覆盖单线程静态 RISC-V/musl 环境，ASan 也不能覆盖所有内存安全问题。**可借鉴**：「把已有测试自动变成规格，让 LLM 去证明，交给确定性的检查器验收」这套结构，可以搬到任何有可靠判定器的 agent 任务上；多个 agent 共享中间产物的工作区能直接省 token。
- 【注意】⭐ **[Architecting Governed, Self-Evolving AI Agents on Google Cloud](https://developers.googleblog.com/architecting-governed-self-evolving-ai-agents-on-gemini-agent-platform/)** · 出处：Google 开发者博客（Google Cloud 研究参考架构）· 2026-10-22 —— 参考架构 Project Chrysalis 运行在 Gemini 4 Argon 和 ADK 上，用模拟的黑五缓存雪崩（Redis 冷 key 被逐出、Cloud SQL 连接池耗尽）演示五种自演进能力：实时诊断；自我修补，即运行时生成令牌桶限流器，依次通过 AST 沙箱检查、OPA 策略校验（补充速率不低于 10 req/s）、Cloud KMS 与 Binary Authorization 签名后才挂进网关；自我评估，用 AgentEvolver 给每个动作打贡献分；记忆，把验证过的规则签名后写入向量检索；重构，提议新增「流量整形专家 agent」，经两名 SRE 批准后在内存里改写 ADK 子 agent 图。之后用 BigQuery 回放 400 种反事实策略（约 0.5 毫秒），再由红队 agent 在影子沙箱里压测。模拟结果：首次缓解时间从 15–45 分钟降到 1.8 秒，5xx 错误率从 72.7%–80.0% 降到 0，P99 从 519.8 ms 降到 18.2 ms。数字来自 50 请求规模的演示，不是生产数据。**可借鉴**：自改进动作按风险分三层设审批：热补丁自动过沙箱和签名，规则沉淀要先有贡献分验证，拓扑改动必须两人批准；改拓扑在内存里做，不改容器镜像。

## 论文（自演进优先）

- ⭐ **[Automating ML for Science: Can Frontier Agents Climb Scientific Hills in the Wild?](https://arxiv.org/abs/2610.28763)** · Ming Zhong 等 4 人（HF 组织 Anthropic；作者含 Nicholas Carlini）· 2026-10-20 · HF ↑13 —— Agent4Sci 覆盖 11 个领域的 20 个科学 ML 基准，测前沿 agent 能否超过已发表的最佳模型。结果是每个基准都有提升，Claude Opus 平均相对提升 10.4%，没有任何一次运行被判学术不端。但提升几乎都来自 ML 工程技巧，没有研究层面的新洞见。轨迹分析找出三个问题：对新颖性判断失准、资源用得不足、很快陷入局部的工程调参。加上研究构思、实验管理、定时检查清单三个轻量 skill 后，Claude Opus 从 10.4% 提到 20.1%，Codex 从 4.4% 提到 8.1%。**可借鉴**：长任务 agent 的典型失败（过早收敛、资源闲置）可以用「定时检查清单」类 skill 来纠正，不必改模型。
