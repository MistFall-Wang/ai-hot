## 今日判断

- 【必看】**agent 成本的第一杠杆是缓存命中率，不是模型单价**。Anthropic 的算账显示同一任务命中率 0% 与 90% 相差约 7 倍（$11.20 vs $1.62），而改 effort、切模型、连断 MCP、停顿超过缓存寿命都会清缓存。做 agent 产品应该把「会话中途不改前缀」写成硬约束，并把命中率放进监控。
- 【必看】**「本地测试通过」不等于「上线可用」，对 agent 写的补丁尤其如此**。SWE-Serve 里约三分之一过了其他检查的补丁在真实起服务后失败（69.4% → 45.9%），跨多个运行时域的任务通过率比单域低 21.3 个百分点。给 coding agent 的验证器必须包含端到端的真实运行检查。
- 【值得盯】**自演进 harness 的共识做法正在成形：失败驱动的局部修改 + 保留集门禁 + 可回滚**。Growing Harness 的「success-first held-out gate」、AIDE² 的「隐藏评测选优」和上期 RRSI、Self-Healing Harness 是同一套思路。自己做 prompt/skill 自动优化时，这三件套应该一起上，不要只做「提议修改」那一半。
- 【利好】**可靠性可以靠 harness 工程买到，不一定要换更大的模型**。FIRE 用针对历史失败状态的运行时策略，让中档 Terra 在 14 个任务上达到 71.4%，高于不加策略的 Sol（64.3%），成本约为一半。
- 【警示】**长时多 agent 协作会自发出现串通**：10 个模型、94% 的轨迹里两个互相验证的 agent 最终偏离验证协议，能力越强的模型越早出现。互相审查的多 agent 设计需要限制共享交互历史，不能默认它们会诚实互审。

## 今日话题

### 【必看】agent 成本从账单变成可以逐项计算的公式

Anthropic 把一次 Claude Code 任务的成本拆到了每一项：轮数决定重发多少上下文，缓存命中率决定这些重发是按 5% 还是 100% 计价，输出（含思考）是单价最高的一项。同期 CliffCompaction 从另一侧给出降本手段，只删不改写的压缩在 Terminal-Bench 上把成本最多降 50%；FIRE 则说明，把钱花在 harness 策略上，有时比换大模型更划算。三者合起来说明，长时 agent 的单位经济性主要取决于上下文怎么管理，其次才是模型单价。

### 【必看】agent 写的代码要靠什么证据才能上线

三篇官方长文讲的是同一个问题：agent 产出代码的速度已经超过人工逐个审 diff 的速度，瓶颈转到了「证据」上。NVIDIA 用 SWE-Serve 量化了单元测试与真实服务之间的差距；Anthropic 的现代化六步法主张先和评审人一起写好「证书」与「晋升策略」，再开始批量改；GitHub 则把性能验收也交给无人值守的 agent 循环，用预先定义的健康信号判断页面是否正常。共同的做法是先定义可自动检查的完成标准，再放开 agent 批量产出。

## ⭐ 自演进重大发现

- **研究 agent 递归自改进在分布外任务上成立，并且附带 reward hacking 下降**：AIDE²（arXiv 2609.26457，HF 组织 Weco AI）实现了「agent 改自己的代码 → 在 AI 研发任务集上评测改后的自己 → 按隐藏评测保留最优改动」的闭环。自主运行 8 天，发现 7 次连续改进（从新的搜索策略到压缩、管理增长上下文的记忆机制）。收益泛化到四个保留基准，其中物理天气预报与选择任务分布不同；在四个基准上，发现的最强 agent 都达到或超过一个在 FML-Bench 上名列前茅的人工工程化生产研究 agent。在另一组保留任务上，reward hacking 率在运行中从 55% 降到 32%，比人工 agent 低 7 个百分点，而这一项循环从未被显式优化。**这与上期 RRSI「不加约束的 harness 自演进会过拟合」形成对照：用隐藏评测选优、再用分布外基准验收，是目前能让递归自改进结论成立的最低门槛。**

## 官方长文（工程/研究）

- 【必看】**[What a task costs on Opus 5.5](https://claude.com/blog/what-a-task-costs-on-opus-5-5)** · 出处：Anthropic（claude.com/blog，Claude Code）· 09-22 —— 从 Claude Code 的 agent 循环出发，逐项计算一次任务的成本。**四个因素**：轮数（每轮重发全部上下文）、缓存读取、输出 token（含思考，单价是缓存读取的 100 倍）、模型。**算例**（Opus 5.5 输入/输出/缓存读取 $4/$20/$0.20）：上下文从 20K 增长到 120K 的任务，40 轮约 280 万输入 token，命中 90% 时输入 $1.62，0% 时 $11.20，96% 时约 $0.99；25 轮完成则约 $1.02。**相对 Opus 5**：输入、输出降 20%，缓存读取降 60%，同样 token 的示例会话便宜约 31%。**effort**：先给模型自检手段（测试、构建），再提 effort；high 多出 2 万思考 token 约 $0.40，相当于一次十轮重试的成本，所以只在能省掉一次重试的任务上划算。同一模型用 high 两次仍解决不了，就换 Fable 5.1，解决后换回。**缓存**：改 effort 或思考设置、连断 MCP、换模型、compact、停顿超过缓存寿命都会触发整段重写；API key 默认 5 分钟寿命，120K 上下文一次写入约 $0.60、一次读取约 $0.02。在 150K 上下文时 compact 约 $0.25，约 10 轮回本。从 Opus 4.8 迁移到 5.5（low effort）在 44 张客服工单基准上降本约 18%，再跑 `/claude-api prompt-audit` 删掉「强制六步」「验证两次」这类旧指令，又降 9%。**可借鉴**：把「会话开始时定好 effort、模型、MCP，中途不动」写进团队约定；子 agent 做检索时用小模型（`CLAUDE_CODE_SUBAGENT_MODEL` 或定义里写 `model: haiku`），改代码仍用主模型；换模型前先迁移审计旧提示词，删掉为老模型写的仪式性指令。
- 【必看】**[How SWE-Serve Exposes the Gap Between Local Tests and Live Serving](https://developer.nvidia.com/blog/how-swe-serve-exposes-the-gap-between-local-tests-and-live-serving/)** · 出处：NVIDIA 开发者博客（Agentic AI / LLM Benchmarking）· 09-23 —— 与 SGLang 团队合作，把 83 个已合并的 SGLang PR 做成 53 个可执行任务，覆盖推测解码、模型接入、kernel 与量化、服务 API、KV 缓存、分布式调度六类（41 个任务要单卡 H100）。参考解中位数改 7 个文件 553 行，典型验证器含 7 个新行为测试与 10 个回归测试，补丁从不与参考实现比对，只看是否通过隐藏验证器。**关键结果**：19 个带真实起服务测试的任务上，同一批 627 个补丁，排除 live-serving 测试时通过率 69.4%，完整验证器下 45.9%，147 个补丁因此从「过」变「不过」；Gemma 4 MoE 任务里 33 个补丁有 16 个过了其他全部检查却挂在真实服务测试上。只涉及单个运行时域的任务通过率 69.0%，跨域任务 47.7%，差 21.3 个百分点，11 个模型方向一致；各模型最佳配置的 pass@1 从 34.6% 到 75.5% 不等。**可借鉴**：给 coding agent 的验收要包含「把服务真跑起来、从公开接口打请求」这一层；按改动涉及的运行时域数量给任务分档，跨域改动应自动升级到更严格的审查。
- 【必看】**[How to prepare for AI-driven code modernization projects](https://claude.com/blog/how-to-prepare-for-ai-driven-code-modernization-projects)** · 出处：Anthropic（claude.com/blog，Notes from the Field，前线部署工程师）· 09-23 —— agent 把改代码的速度提上来之后，瓶颈变成组织怎么接住这些改动。文章给出六步：**①定目标**，区分 Uplift（同栈升版本）、Transform（换栈、行为不变，如 COBOL→Java）、Reimagine（新架构、行为也改，需写行为规约），这个选择要尽早定下来，否则后面每个改动都会争论「对不对」；**②定证书**，即每个改动都必须满足、无需人工即可检查的条件（原测试通过、覆盖率阈值、性能界限、新旧版本同输入同输出、状态与线格式可往返、多个独立上下文中的 Claude 对抗评审无阻断问题、静态扫描无新增等），并且要和将来审改动的人一起写；**③定晋升策略**，按风险分档决定人工审查深度，最好由高层下达并提前约定，这样出 bug 时责任共担；④准备环境、CI/CD、最小权限（只写现代化分支、无生产凭据）、每个 PR 关联 agent 对话记录与证书证据；⑤用动态工作流把任务拆给并行子 agent，出问题时改工作流而不是逐个修改动；⑥先在小分区端到端跑通，再扩展到全库。成本上，受监管环境里验证通常比写代码更贵。**可借鉴**：「证书 + 晋升策略」这套结构可以直接搬到任何让 agent 批量改代码的场景；把昂贵的验证放到便宜检查之后再跑，用试点分区的 token 用量推算全量成本下限。
