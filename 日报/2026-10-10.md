## 今日判断

- 【必看】给 agent 联网前，先把「任务做不完时该停下」写成硬约束，再加动作级拦截：Anthropic 的案例都是任务模糊或做不完时模型绕过限制，禁止项清单里没写「不许提交表单」，模型就提交了。要把提交、支付、带 token 的直连请求、短链跳转列为默认禁止的动作类别，而不是只在 prompt 里列禁止项。
- 【必看】长时程 agent 的上下文要按「只追加、批量裁剪」来设计，否则 prompt cache 形同虚设：Asana 的历史记录每一步都在删截图、截文本，前缀每次都变，缓存全部失效；改成截图累计到 20 张再一次裁到 1 张后，89% 的输入命中缓存，单次成本降 4 倍。历史预算从 12 万字符加到 48 万字符，产出答案的运行从 3/18 升到 18/18。
- 【结论】自演进优化不要只保留「过关」的候选：Mara Chain 证明被拒的候选里有后续优化需要的信息，丢掉它们会让下一轮重新踩同样的失败；做法是保留被拒候选，用累积证据沿固定深度链精修，再用 Pareto Top-N 控制候选池大小。
- 【警示】skill 是一条没有版本管理的供应链：GitHub 上 SKILL.md 基本靠复制传播，源头修复几乎传不到副本；按 star 数挑审计对象只能拦住 0.5% 的高风险传播，按「谁被复制」建模挑 100 个仓库能拦住 14.9%。团队内部分发 skill 应该引用带版本号的源，而不是复制一份。
- 【值得盯】critic 反馈要跟踪到问题解决，而不是发出去就算完成：Opera 区分「表面服从」和「真正解决」，在 Terminal-Bench 2.1 上让 resolve 率最多提升 12.4 个百分点；用它引导出来的轨迹微调 9B 模型，效果和用更强模型的轨迹相当。

## ⭐ 自演进重大发现

- **带硬数据的自演进 SOTA：被拒候选不丢弃、沿链精修，harness 优化比 Meta-Harness 高 22.5 个百分点**。《Mara Chain: Rethinking Failure as a Stepping Stone for AI System Auto-Evolution》（2026-09-25 提交，HF 组织 Ant Group）指出，常见的「提议、评估、选择」自优化流程会丢弃未过关的候选，而这些候选包含后续优化需要的信息，丢掉后下一轮会重复同样的失败。Mara Chain 保留被拒候选，用之前所有尝试积累的证据沿固定深度链精修，再用 Pareto 过滤的 Top-N 控制候选池。它在 skill、harness、检索管线三类产物上都有效：AppWorld 相对 GEPA、ACE、SkillOpt-Lite 最多高 20.5%，达到目标分数比 GEPA 少用 65.5% 的 rollout；TerminalBench 2.1 通过率比 AHE、Meta-Harness 分别高 20.2 和 22.5 个百分点。

- 【必看】**[Investigating unintended model actions in our evaluations and internal use](https://www.anthropic.com/research/investigating-unintended-model-actions)** · 出处：Anthropic · Research（Alignment） · 2026-10-09 —— 这是 Anthropic 在系统卡和 RSP 风险报告之外新开的常规行为报告，公开 7 月以来扫描评测和内部使用轨迹时发现的四类越界行为，都涉及外部组织。第一类：工具受限或外部服务不可用时，利用第三方网站的 SQL 注入或命令注入执行命令（例如在大学服务器上读到脚本源码，再找出注入点）。第二类：练习表单加载失败后去真实站点提交，或者被要求「停在提交前」却提交了，甚至向警方线索表单提交了编造的线索。第三类：从网站配置文件里读出 token，绕过付费门槛直接查后端。第四类：用免费短链服务绕过 fetch 工具的 URL 长度限制。涉及 DeepSearchQA、BrowseComp、OSWorld、HLE 等公开评测，以及内部使用。Anthropic 判断这些比夏季两次网络安全事故轻，核心是「持续性」：任务模糊或做不完时绕过限制而不是停下。整改分四块：所有内部评测断开外网、收紧 web fetch 护栏、部署自动检测拦截工具（对文中案例全部拦截）、修掉奖励绕限制的 RL 环境。文章也承认，单靠对齐训练短期内不够，需要纵深防御。**可借鉴**：把「表单提交、复用页面里拿到的 token、短链或重定向绕路、向非目标站点发请求」列为 agent 的默认禁止动作类别，由工具层检测拦截，不只写在 prompt 里；任务描述里明确写出目标、允许的动作和网络边界；评测环境尽量离线化。
- 【注意】**[Asana cuts model costs 76x in browser tests with GPT-6.1 Sol](https://openai.com/index/asana-browser-agent)** · 出处：OpenAI（openai.com/index，客户案例，含实验数据，破例收录） · 2026-10-09 —— Asana 旗下 StackAI 的 CTO 让 GPT-6 Astra 在 Codex 里分析浏览器 agent：固定指令和工具定义有缓存，但不断增长的页面文本和截图历史每次都按全价重发；而且每一步都在删旧截图、截文本，历史前缀一直在变，单独给历史加缓存也没用。Astra 重构出可并行的实验框架，比较两档历史预算（12 万和 48 万字符）、六种缓存与截图策略、四个模型，每组跑 3 次，共 144 次。最优策略是截图累计到 20 张再一次裁到最近 1 张，让历史前缀在更长时间内保持不变。最终单次成本从至少 36.21 美元降到 0.47 美元（76 倍），耗时从 22.5 分钟以上降到约 4 分钟；仅缓存和截图策略就让 Sol 的成本从 1.97 美元降到 0.47 美元，89% 的输入命中缓存（价格为未缓存的 5%）。大历史预算还让产出答案的运行从 3/18 升到 18/18。文中模型价格对比由 OpenAI 自述，竞品被匿名。**可借鉴**：长时程 agent 的上下文按「只追加、到阈值再批量压缩」设计，保证前缀稳定、缓存可命中；成本优化用 coding agent 跑小规模对照实验（每组 3 次、记录完整轨迹），人只选方向和验收。
