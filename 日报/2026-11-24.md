## 今日判断

- 【必看】评测上线前要先攻击自己的评审器：Hugging Face 的例子里，只检查最终比值的评审器会给一个跳过拟合的脚本满分。自建评测时固定跑三个对照，参考解、什么都不做的 agent、走捷径的脚本，前者全过、后两者全不过，才开始跑模型。
- 【结论】只看通过率会误判失败原因：同一组实验 24 次运行过了 11 次，13 次失败里只有 2 次是拟合错误，其余是模型第一轮就宣布完成或缺依赖包。报告分数时要同时读轨迹，并且区分 pass@k（至少成功一次）和 pass^k（每次都成功），无人值守的场景看后者。
- 【利好】"这个动作是用户要的吗"这一项检查已经有公开数字：Google 只开默认的用户原意检查、不配任何策略，929 次需要工具调用的注入攻击在 6 轮运行里一次都没成功。做 agent 防注入时，优先在工具调用执行前加一层对照用户原始请求的检查，不要去识别攻击话术。
- 【警示】动作检查挡不住"只改回复文字"的注入：Google 剩下的 0.9% 全部来自让 agent 在回复里推荐某家酒店这一类攻击，没有工具调用可拦。输出侧还需要单独的回复过滤。
- 【值得盯】代码写得快以后，瓶颈转到评审和合并：Anthropic 访谈的企业把代码评审列为新瓶颈，同一天 Anthropic 发布 Claude Ship 让 agent 接手评审、修 CI 和按策略审批。团队引入这类工具时，按官方建议先用"只观察"模式跑一段时间，再把它设成合并的必要条件。

## 今日话题

### 【必看】评测怎么做才可信：先验证评审器，再读轨迹，再报分数
Hugging Face 给出了从"要证明什么"到"公布分数"的八步流程，并用实测说明评审器漏洞、过早宣布完成、推理服务商不同都会改变分数。Google 的 AgentDojo 实验是同一套方法的应用：全量跑 6 轮取平均，结果由基准自带的 Python 检查判定，不让模型打分，并且把"任务完成且攻击失败"单独算一个指标。两篇合起来说明：一个评测数字要有重复运行、对照组和失败归因才站得住。

### 【利好】三家同一天讲 agent 安全分层：模型判断只是第一层，外面还要有固定边界
Anthropic 的指南把防护分成两层，一层靠判断（对齐训练、注入探针、auto mode 分类器），一层靠固定边界（权限规则、沙箱、出站白名单），并强调对齐训练只降低出事概率、不限制出事后果。OpenAI 的做法是把威胁模型和安全策略写成仓库里的文件，让安全评审 agent 有依据。Enterprise Frontier Safeguards 补的是跨请求的滥用监控，Shirudo 补的是漏洞修复前的运行时防护。共同点是每一层都假设上一层会失效。

## 论文（自演进、评测优先）

- **[Duopra: From Full-Duplex Conversation to Full-Duplex Agency](https://arxiv.org/abs/2611.25773)** · Chiyu Chen 等（机构未能从 abs 页或 HF 核实）· 2026-11-18 · HF ↑11 —— 全双工语音模型擅长轮流说话和处理打断，但完成任务还需要及时发起工具调用、在用户改口后修正参数。作者发现在 Full-Duplex-Bench v3 上，基线系统的大多数失败发生在工具真正执行之前。Duopra 把后端 agent 也当作一个工具，用三阶段训练（协议监督微调、奖励"及时且完整执行"的全双工强化学习、投影层修复），同一后端下 Pass@1 从 4.7% 升到 44.7%。
- **[Search From the Start: Search-Native Pretraining for Language Models](https://arxiv.org/abs/2611.26809)** · Kaustubh Ponkshe 等（HF 组织：EPFL）· 2026-11-18 · HF ↑2 —— 提出在预训练阶段就教模型使用搜索：给预训练语料大规模插入搜索查询和本地索引返回的检索结果。在 360M 到 3.3B 参数规模上，这样训练的模型在知识密集任务上更好，也更愿意采信检索到的证据；经过同样的监督微调后优势仍在，1.4B 模型打平或超过算力对齐的 3.3B 基线。
