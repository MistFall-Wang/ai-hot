## 今日判断

- 【必看】**动手优化 prompt / skill 之前先验 eval 本身**。Anthropic 给了四条检查：任务贴近生产、更强模型和更高 effort 得分更高、最强配置仍明显低于 100%、重复运行方差小；基线已到 95% 左右时，目标改成降成本或降延迟。照这四条过一遍自己的评测集，再谈改进。
- 【结论】**自演进的收益必须在留出任务上验收，训练集上的涨分不算数**。今天三篇论文给了同一方向的数字：21 个训练集上变好的 skill 只有 5 个完全保住提升；每轮只看 5 条 rollout 的 harness 演化训练 70%、留出 54%；proposer 与 solver 闭环内部奖励上升而外部正确率不升。Anthropic 的 hillclimb 流程用的也是同一条规则。
- 【利好】**「降成本且质量不降」是最稳的 hillclimb 目标**。Anthropic 的客服基准从 Opus 4.8 high（每工单 4.6 美分）一路换到 Sonnet 5 low 加 prompt 修订，留出集准确率反而从 78.6% 升到 90.5%。评测已接近饱和的系统，直接让 agent 去找省钱的配置。
- 【警示】**迁移到 Sonnet 5.5 有多处会直接返回 400**：`thinking: disabled`、强制 `tool_choice`、旧版 computer use 工具、`between_tools` 配 xhigh / max effort。读 `content[0].text` 的代码也会因为默认开启 thinking 而出错。先跑 `/claude-api migrate`，再重做 effort 扫描。
- 【值得盯】**Claude Code 的 harness 开始对用户开放改写**。mods 能改 prompt、拦截工具调用、批准权限请求，且不沙箱；同日一篇论文在 Claude Code 上复现了六类「批准的动作与执行的动作不一致」。团队环境装 mod 前先确认 `sec-default` 在加载链最前，marketplace 走管理员白名单。

- 【必看】**[Automating eval design and hillclimbing with Claude](https://claude.dev/blog/automating-eval-design-and-hillclimbing/)** · 出处：Anthropic（claude.dev 开发者博客，补录） · 2026-09-28 ⭐ —— **整体概括**：claude-api skill 新增两个子命令。`build-eval` 先访谈再建评测：样本按生产记录、bug 报告与工单、手写 5–10 条、从代码库合成的顺序取，并生成页面让人逐条确认；评分器优先用代码检查，输出开放时才用 LLM 评审（rubric 写成可核对的断言而非 1–5 分，有基线时做盲序两两比较，评审模型不能是被测模型）；跑基线时检查评分器对同一输出打两次是否一致、有无超时或截断、基线是否已到 95% 左右。好 eval 的四个特征：任务贴近生产、更强模型和更高 effort 得分更高、最强配置仍明显低于 100%、重复运行方差小；不要专挑当前模型失败的题。`hillclimb` 先确认噪声小于想要的最小提升，随机拆 train / test，每轮读 train 轨迹只提一个补丁；train 涨而 test 持平或出现回归就回滚；连续两三轮停滞时把剩余失败按原因分类。案例一：客服基准 44 张工单（30 搜索、14 留出），从 Opus 4.8 high 的 74.4%、每工单 4.6 美分，到 Sonnet 5 low 加 prompt 修订的 98.9%、约 1 美分，留出集 78.6% → 90.5%。案例二：claude-api skill 自身 66.1% → 87.9%，其中一步是发现内容都在但模型按训练记忆写旧 API，于是在 skill 顶部加「旧写法 → 新写法」对照表。**可借鉴**：失败样本的内容不要贴进 prompt，答案放在模型够不到的地方；某道题怎么改都不涨，先怀疑题目或评分器写错了。
