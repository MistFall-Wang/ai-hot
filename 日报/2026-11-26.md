## 今日判断

- 【必看】测试通过率不能当迁移完成的证据：Anthropic 的 Rust 版本 4 月通过约 98% 的测试，线上流量上只有约四分之一的输入匹配；审计移植后的测试还发现 100 多处被弱化的断言。让 agent 同时改代码和改测试时，必须有一个它改不了的外部对照，比如旧系统在真实流量上的输出。
- 【警示】验证器只能说"输出对上了"，不能说"这个修复能上线"：Anthropic 的 agent 为了让提示词匹配，提出把工具说明抄进文件这种会被丢弃的权宜方案，本地验证通过，被工程师否决。内外循环之间要留一道人工评审，人只看修复方案，不看猜测过程。
- 【结论】评审意见要变成后续 agent 都能读到的规则：Anthropic 把否决理由写进记忆、把约 60 条评审意见归纳进 CLAUDE.md、把反复出现的问题做成 lint 和合并检查，一条"照搬 Python 行为、不许猜"的规则让 agent 又找出 7 处靠猜的移植。自己的项目里同一条评审意见出现第二次，就该写成规则或检查。
- 【值得盯】公开用例上的分数会高估上线表现：OWE-Bench 里各模型在隐藏用例上平均低 18 分，而且模型自己预估时还高估 21 分。给 agent 的任务要留一批它看不到的验收用例，单独报这部分分数。
- 【利好】领域 skill 能让便宜模型追上贵模型：DeepMind 的质谱任务里，不给 skill 时三个模型准确率都低于 4%，加上 skill 后都到约 97%，轻量的 Gemini 3.8 Flash 生成的 token 还少了近四倍。把专家工作流封装成经过验证的 skill，比换更大的模型划算。

- 【必看】⭐ **[Migrating our Messages API to Rust](https://www.anthropic.com/research/migrating-api-to-rust)** · 出处：Anthropic Engineering（anthropic.com/research）· 2026-11-25 —— Anthropic 把承载全部客户和自家产品流量的 Messages API 从 Python 迁到 Rust。2024 年初到 2026 年秋流量涨了约 1,800 倍；只把输出解析改成 Rust 只省 8%–10% CPU，还让每个 token 在两种语言间穿三次，于是决定整体重写。Claude 一周写出核心路径，难点在验证：约 700 个集成测试与 Python 实现耦合，移植后有 100 多处断言被弱化；4 月测试通过约 98%，线上输入却只有约四分之一匹配。做法是影子流量：模型只跑一次，输出回放给 Rust，逐检查点比较，不读用户内容，只记差异的位置和长度差作为指纹，每 10–30 分钟按指纹分组，新种类才派一个 agent 负责。内层循环在沙箱里不调模型、一秒内比较两版提示词；外层循环在线上比较有无修复的构建；记忆循环把教训写成规则、测试、lint 和合并检查。最终每请求 CPU 降约 70%，首 token 中位时延降约 20%。**可借鉴**：做重写或迁移时，先造一个 agent 改不了的验证信号（旧系统在真实流量上的逐步输出），并让信号能定位到"哪一步、哪类 bug"；人工评审放在沙箱和线上之间，只审修复方案。
- 【注意】🧪 **[Verifiable Social Reasoning for LLM Assistants](https://research.google/blog/verifiable-social-reasoning-for-llm-assistants/)** · 出处：Google Research 博客 · 2026-11-25 —— 评测助手在"用户来咨询人际问题"时的社交推理。难点是助手只能听用户单方面转述，而"别人的动机"通常没有标准答案。框架基于 Concordia 做多 agent 模拟：给目标角色设一个隐藏动机，让它与用户角色等互动，再把用户角色抽出来向被测助手倾诉，助手要推断隐藏动机，由 LLM 评审判对错；用户角色的自信或不安等认知滤镜可调。模拟与咨询分离，同一批模拟可复用于任意模型。测了 12 个模型，开源框架和 2 万多条样本。发现：模型直接看事件时比听用户转述时准得多；用户带偏见时模型常顺着说；模型需要比实际必要更多的细节才下结论；多轮对话不一定更准，会锚定在之前的说法上。**可借鉴**：没有标准答案的能力，可以在模拟里预先埋一个可控的隐藏变量当真值；评测对话助手时把"直接看事实"和"听用户转述"两种条件分开测，差值就是被用户叙述带偏的程度。
- 【注意】**[Production monitoring with Codex](https://developers.openai.com/blog/production-monitoring-with-codex)** · 出处：OpenAI 开发者博客 · 2026-11-24 —— Codex 部署工程师写的线上故障排查接入指南，示例用 Grafana、Kubernetes 和 Codex Security。流程分四步：给 agent 只读访问 trace、运行时状态和部署历史，用服务账号控制范围，从小范围开始再按需放开；要求每个判断都带证据和引用，可以加一个专门质疑根因的评审 agent；修复方案要有边界并附回滚计划，由人批准；修复后 agent 在同一批数据源上验证恢复并协助写复盘。之后用历史事故反复演练，把需要人纠正的步骤改进指令，最后把 runbook 固化成 skill 或插件。**可借鉴**：用同一起历史事故分别跑"少给几个数据源""单 agent 对比加评审 agent"，记录定位根因的用时和被人纠正的次数，用这两个数决定配置。

- ⭐ 🧪 **[Self-Evolving Evaluation Environments for Computer-Use Agents](https://arxiv.org/abs/2611.30962)** · Wenhao Wang 等（HF 组织：Tongyi-MAI）· 2026-11-23 · HF ↑45 —— 电脑操作 agent 进步快，而基准是静态的，难度封顶、覆盖有限、总分太粗。CUA-SEE 是一个闭环评测环境，根据 agent 的运行证据同时更新任务和可执行验证器，分三个目标：基准进化按一组 agent 的表现校准难度并扩大覆盖；诊断进化针对单个 agent 出题，探它的能力边界；验证器进化把新要求转成基于系统状态的检查点，并做对抗验证。摘要未给具体分数。**可借鉴**：自建评测集时把"加题""针对某个 agent 探边界""修验证器"当成三件分开的事，验证器的每次修改都要用对抗样本复核。
- 【注意】🧪 **[OWE-Bench: A long-horizon benchmark for measuring real-world engineering](https://arxiv.org/abs/2611.30017)** · Jacob Cole 等（HF 组织：Mercor）· 2026-11-23 · HF ↑1 —— 26 个由领域专家写的长程工程任务，覆盖软件、物理工程、机器学习和科学计算，每个任务平均消耗数亿 token。按速度、成本、准确率等实际指标打分，分公开用例和隐藏用例。最好的 Claude Fable 5.2 得 54.6%，平均每任务 2.11 亿 token。给更多时间时模型会用更多计算并得分更高；GPT-6 Astra 在短时限和同等 token 下更高，Fable 5.2 在长时限下总分最高。各模型隐藏用例平均低 18 分，自己预估时还高估 21 分。**可借鉴**：评测 agent 交付物时保留一批隐藏用例，并让 agent 先预估自己的隐藏用例得分，两者的差就是它的自我校准误差。
- 🧪 **[SpecEngineeringBench: Evaluating Coding Agents as Autonomous Specification Engineers](https://arxiv.org/abs/2611.32973)** · Xingjian Wang 等（HF 组织：Tokenwave.AI）· 2026-11-24 · HF ↑10 —— 测编码 agent 能否在没有 issue 描述和入口提示的情况下，从功能需求出发自己写测试并找出缺陷。100 个实例来自 78 个开源 Python 仓库，每个实例有多个已记录缺陷。七个前沿 agent 的结果显示测试有效性与暴露缺陷脱节：通过率 91.47%、变更覆盖率 80.48%，但能让缺陷从失败变通过的只有 26.36%；定位召回从文件级 78.11% 降到函数级 51.29%。**可借鉴**：评 agent 写的测试时，不能只看能跑通和覆盖率，要用已知缺陷检查它能不能抓到。
- 🧪 **[ICLWorld: Benchmarking In-Context Learning of Agents from Digital to Physical Worlds](https://arxiv.org/abs/2611.32649)** · Qingle Liu 等（机构未能从 HF 核实）· 2026-11-24 · HF ↑18 —— 在线基准，测 agent 能否从上下文里学会新规则，覆盖电脑操作和机器人操作：30 个环境、630 段示范视频、160 个任务，规则常常反直觉，不学就做不对。最强的 Claude Opus 5.5 和 GPT-6 Astra 在电脑任务上成功 82% 和 76%，机器人任务只有 27% 和 26%；不给规则时最多 8%。GPT-6 Astra 能答对 98% 的机器人规则问题，却只完成其中 20% 的任务。**可借鉴**：评测"会不会按用户定制规则办事"时加一个不给规则的对照组，并把"说得出规则"和"照规则做完"分开计分。
- 🧪 **[Coding4Games: Can Modern Coding Agents Play Modern Video Games?](https://arxiv.org/abs/2611.31974)** · Shifang Zhao 等（HF 组织：ARC Lab, Tencent）· 2026-11-24 · HF ↑10 —— 不让模型逐帧操作游戏，而是让编码 agent 在沙箱里迭代写出一个独立程序，冻结后在不调用模型的条件下测试。15 款现代游戏，既评游戏成绩和稳定性，也评开发过程中怎么用反馈、怎么改程序。每款游戏的最好程序在 13 款上超过最强的 GUI 基线，1 款持平；人类玩家在 10 款上高于所有 agent。**可借鉴**：实时性强的任务可以让 agent 产出一段可独立运行的程序，开发和测试分离，省掉运行时的推理成本。
- 【注意】**[Lazy Agents Answer Against Their Own Beliefs: Reinforcement Learning with Verifiable Beliefs Teaches Them to Act on What They Believe](https://arxiv.org/abs/2611.32884)** · Richmond Sin Jing Xuan 等（HF 组织：Nanyang Technological University）· 2026-11-24 · HF ↑88 —— agent 在长任务里常在证据不足时就作答。只看最终答案的奖励分不清蒙对和有据可依。RLVB 利用训练时模拟器能算出每一步答案的精确后验：后验还有多个可能时奖励继续探索，证据足够时奖励作答，不用评审模型。三个视觉语言模型、三个基准（两个训练时未见）九种设置全部提升，平均 17.1%；比用 LLM 评审给过程奖励的 PPO 高 9.3%，GPU 时间少 1.6 倍。
- **[Don't Sleep, Keep Watch: Proactive Perception for Computer-Use Agents](https://arxiv.org/abs/2611.28947)** · Jiaqi Su 等（机构未能从 HF 核实）· 2026-11-21 · HF ↑84 —— 电脑操作 agent 靠截图感知，模型推理慢，动作执行时画面可能已经变了。NightWatch 不改 agent 的模型、提示词和动作空间，外挂一个 0.8B 的小模型持续监视界面状态。OSWorld 上非推理耗时降 33%、浪费的时间降 53%，成功率持平；DynaCU-Bench 上成功率从 39.5% 升到 44.2%。
- **[RECAP: Training Long-horizon LLM Agents with Context Compaction](https://arxiv.org/abs/2611.31258)** · Yulun Jiang 等（机构未能从 HF 核实）· 2026-10-19 · HF ↑1 —— 把上下文压缩和 agent 策略一起用强化学习训练，原则是摘要应保留原始历史所引发的行为。目标函数衡量压缩前后后续行为的差异，梯度分成两部分：给摘要生成的失真奖励和给后续动作的自蒸馏。在 Qwen3.5-4B 上比只用任务奖励的基线高 4.6 个百分点（BrowseComp-plus）和 4.3 个百分点（SWE-bench Verified）。
- **[ACAP: Asynchronous Coding Agents for Efficient Robot Control](https://arxiv.org/abs/2611.31205)** · Zexin He 等（HF 组织：MMLab@NTU）· 2026-11-23 · HF ↑61 —— 把一台机器人交给一组常驻编码 agent，每个负责一个控制组（如一条手臂加夹爪），异步推理和执行；上层 agent 分配任务、协调物理依赖并动态调配控制权。72 次真机运行、25 种任务与平台组合，按任务平衡的耗时比单 agent 直接控制少 28.2%。
